# Milestone-режим агента (этап 3)

Статус: **реализован за флагом `AGENT_MILESTONES`, по умолчанию выключен**. Без флага
`plan.milestones` отсутствует в каталоге инструментов, а сохранённый milestone-план не
попадает в рабочее состояние. Старые планы `plan.update` работают без изменений.

## Зачем

Большая задача на несколько запусков теряет границу: модель за один запуск начинает
следующий блок, хотя предыдущий ещё не проверен, либо после обрыва начинает с середины.
Milestone — это единица работы размером в запуск: файлы, проверки и точное определение
готовности. Один запуск завершает один milestone; следующий начинается в новом запуске.

## Формат

`plan.milestones` принимает только полный список из 3–7 этапов:

```json
{
  "milestones": [
    {
      "title": "Схема заказов",
      "scope": "Таблицы и индексы; API не входит",
      "files": ["db/schema.ts"],
      "tests": ["npm test --workspace=server"],
      "definitionOfDone": "Миграция применяется, старые тесты проходят",
      "estimatedTokens": 40000,
      "status": "in_progress"
    }
  ]
}
```

Проверки до записи плана:

- `title` уникален и не пуст;
- `files` и `tests` — непустые массивы: milestone без файлов или без проверки не принимается;
- `definitionOfDone` — конкретное условие, а не пересказ названия;
- ровно один этап может быть `in_progress`;
- если все этапы `pending`, первый автоматически становится текущим;
- если в плане уже есть `done`-этапы, следующий `pending` **не** повышается автоматически —
  это checkpoint, а не старт нового этапа.

План `PlanState` хранит `milestones` рядом с обычными `items`; `items` генерируются из
milestones, поэтому существующая панель плана, commit subject и рабочая память работают без
второй структуры. `plan.update` при активном milestone-плане отклоняется: он потерял бы
метаданные и сломал бы checkpoint.

## Checkpoint

Runtime проверяет план после `plan.milestones`:

- текущий этап отмечен `done` и остались `pending` → запуск закрыт для изменений;
- модель попыталась в одном обновлении отметить текущий `done` и следующий `in_progress` →
  это тоже checkpoint; следующий этап начнётся в новом запуске;
- все этапы `done` → работа завершена, но обычная проверка всё ещё обязательна.

После checkpoint чтение, `project.verify` и браузерная проверка разрешены, а `fs.write`,
`fs.edit`, `terminal.exec` с изменениями, установка пакетов, запись памяти и
`plan.milestones`/`plan.update` отклоняются. Модель получает системную заметку и должна
закончить ответ. Следующий запуск читает persisted-план и начинает со следующего этапа.

## Ограничения

- `estimatedTokens` — ориентир в рабочем состоянии, а не жёсткий лимит расхода: runtime не
  обрывает провайдера по этой цифре.
- Checkpoint защищает от изменений после завершения этапа, но не мешает модели ошибочно
  отметить этап `done` до проверки. Дисциплина «done только после проверки» остаётся в
  описании инструмента и системном промпте.
- Нет автоматического canary и baseline на eval; флаг не включался в production.
- Reviewer-субагент реализован отдельно: [`AI_REVIEWER.md`](AI_REVIEWER.md).
