# Статический хостинг проектов NestDev — полный поэтапный план

Статус: **план, код ещё не написан**.

Область: **один статический сайт на проект, не больше**.

Публичный адрес: `<slug>.host.nestdev.ru`.

Дата: 1 ноября 2026.

---

## 1. Коротко

Нужно сделать не «ещё один preview», а отдельный публичный хостинг:

- пользователь нажимает «Опубликовать»;
- платформа собирает статический проект в существующей песочнице;
- готовая сборка превращается в **неизменяемый релиз**;
- Caddy отдаёт файлы напрямую с диска, без Node в пути запроса;
- активный релиз переключается атомарным симлинком `current`;
- у проекта может быть **ровно один сайт** и **один активный релиз**;
- старые релизы нужны только для отката;
- сайт не зависит от рабочей папки проекта: архивация проекта не ломает сайт.

Ориентиры:

| Показатель | Значение |
|---|---:|
| Первый вертикальный срез | 3–5 рабочих дней |
| MVP без бакета | 13–19 рабочих дней |
| Календарно, один разработчик | 3–4 недели |
| Сложность | 6/10 |
| Бакет как источник правды | +3–5 дней |
| Медиа и видео | вне этого плана, отдельный проект |

Главный принцип: **сайт — это не процесс и не контейнер, а каталог с файлами и запись в базе**.

## 2. Что входит и что не входит

### 2.1. Входит

- один статический сайт на проект;
- `instant-site` — готовая статика без сборки;
- `static-build` — проект с `npm run build`, отдающий `dist`/`build`/`out`;
- публикация, статус, история релизов, откат, снятие с публикации, удаление;
- поддомен `<slug>.host.nestdev.ru`;
- HTTPS;
- лимиты на размер релиза, число файлов и количество хранимых версий;
- учёт места в квоте аккаунта;
- защита от утечки секретов и опасных файлов;
- админ-API для просмотра и снятия сайта с публикации;
- тесты, выкатка, пилот.

### 2.2. Не входит

- серверные приложения (`node-runtime`, `python-runtime`);
- несколько сайтов на один проект;
- собственные домены пользователей;
- пользовательские бакеты и S3-ключи;
- загрузка картинок/видео во время работы сайта;
- транскодирование видео;
- CDN;
- команды и роли;
- отдельная веб-админка: администрирование только через внешнее приложение и API;
- произвольные команды сборки и пользовательские `Dockerfile`.

### 2.3. Инварианты

1. **Один проект — один сайт.** Это ограничение базы, а не только интерфейса.
2. **Один сайт — один активный релиз.**
3. **Релиз неизменяем.** После публикации файлы релиза не редактируются.
4. **Caddy не ходит в Node за файлами.** Node не обслуживает запросы сайта.
5. **`SITES_DIR` не внутри `WEBNESTDEV_DATA_DIR`.** Caddy не должен видеть секреты платформы.
6. **Публичная сборка не получает секреты платформы.** Всё, что попало в бандл, считается публичным.
7. **Ошибка публикации не ломает работающий сайт.** Старый `current` остаётся на месте.
8. **Архивация проекта не влияет на сайт.** Сайт живёт в отдельном каталоге.
9. **Удаление проекта удаляет сайт.** Явно и с очисткой файлов.
10. **Пользователь не видит бакет, S3-ключи и внутренние пути.** Он видит адрес, статус и квоту.

## 3. Что уже есть в проекте

### 3.1. Определение типа проекта

`server/src/preview/project-kind.ts` уже различает:

- `instant-site` — есть готовый `index.html`, сборка не нужна;
- `static-build` — есть `scripts.build`, сборка создаёт файлы;
- `node-runtime` — нужен работающий процесс;
- `python-runtime` — нужен работающий процесс;
- `unknown` — тип не определён.

Для хостинга разрешаем только первые два. Остальные получают понятный отказ, а не попытку «как-нибудь собрать».

### 3.2. Статический preview

`server/src/preview/static-plan.ts` и `static-preview.ts` уже умеют:

- выбирать `dist`/`build`/`out` или корень;
- ставить зависимости;
- запускать `npm run build`;
- отдавать статику через Fastify;
- делать SPA-fallback;
- показывать лог сборки.

Это можно переиспользовать для сборки, но **не для публичной раздачи**. `static-preview.ts` поднимает listener внутри процесса сервера и слушает loopback; для публичного хостинга нужен Caddy.

### 3.3. Caddy и публичные адреса

`deploy/Caddyfile` уже содержит:

- домен панели;
- wildcard `*.preview.nestdev.ru`;
- on-demand TLS;
- endpoint `/api/preview/tls-ask`, который разрешает сертификат только для существующего проекта.

Для хостинга нужен отдельный wildcard `*.host.nestdev.ru` и общий TLS-ask, который проверяет и preview-, и hosting-имена.

### 3.4. Объектное хранилище

`server/src/storage/object-store.ts` уже умеет:

- `putFile`;
- `getToFile`;
- `head`;
- `remove`;
- S3-совместимую подпись;
- один приватный бакет с префиксом.

Этого достаточно для второго этапа, когда релизы начнут уезжать в бакет. В MVP бакет не обязателен.

### 3.5. Квоты и тарифы

`server/src/account/plans.ts` и `storage-quota.ts` уже считают общую квоту аккаунта: проекты, `node_modules`, архивы. Хостинг должен стать ещё одной статьёй этой же квоты, а не отдельным «невидимым» местом.

### 3.6. UI

В `WorkspaceShell` уже есть вкладки «Агент», «Задачи», «Файлы», «Git», «Терминал». В `DeploymentWizard` есть карточка внешнего облака и заглушка «NestDev Cloud — скоро».

Для хостинга лучше **отдельная вкладка «Хостинг»**, а не ещё один шаг квиза внешнего облака: это другая задача и другой пользовательский сценарий.

## 4. Целевая архитектура

### 4.1. Схема

```text
Пользователь
    │
    ▼
Панель NestDev ── POST /publish ──► API
                                    │
                                    ▼
                              Sandbox: npm install + npm run build
                                    │
                                    ▼
                              Проверка dist:
                              размер, файлы, секреты, index.html
                                    │
                                    ▼
                    SITES_DIR/<slug>/releases/<releaseId>/
                                    │
                                    ▼
                    current -> releases/<releaseId>
                                    │
                                    ▼
Пользователь ── HTTPS ──► Caddy ──► файлы с диска
```

Caddy — единственная публичная дверь сайта. API в обслуживании запросов сайта не участвует.

### 4.2. Путь запроса сайта

1. DNS `*.host.nestdev.ru` указывает на VM.
2. Caddy принимает TLS.
3. Caddy берёт первый label из `Host`: `foo.host.nestdev.ru` → `foo`.
4. Корень: `/srv/sites/foo/current`.
5. `file_server` отдаёт файл.
6. Если файла нет:
   - для пути без расширения — `index.html` (SPA-fallback);
   - для файла с расширением — честный 404.
7. Если каталога или `current` нет — 404.

Никаких запросов в API, Postgres или Node на этом пути нет.

### 4.3. Путь публикации

1. Пользователь нажимает «Опубликовать».
2. API проверяет владельца проекта и feature flag.
3. Проверяет, что у проекта нет другого сайта и другой публикации.
4. Создаёт `site_releases` со статусом `building`.
5. Запускает фоновую задачу.
6. Задача определяет тип проекта.
7. Для `static-build` ставит зависимости и всегда делает свежий `npm run build`.
8. Проверяет output-каталог.
9. Копирует файлы в `SITES_DIR/<slug>/tmp/<releaseId>`.
10. Проверяет размер, число файлов, symlink, секреты.
11. Переименовывает `tmp` в `releases/<releaseId>`.
12. Если включён бакет — загружает `tar.gz` и манифест.
13. Атомарно переключает `current` на новый релиз.
14. Обновляет `active_release_id` и `published_at`.
15. Удаляет старые релизы сверх лимита.
16. Возвращает статус; UI опрашивает его до завершения.

### 4.4. Почему не альтернативы

| Вариант | Почему нет |
|---|---|
| Node/Fastify-сервер на каждый сайт | 30–100 МБ RAM на сайт; 100 сайтов уже не помещаются |
| Контейнер на каждый сайт | ещё дороже, не нужен для статики |
| Отдавать файлы из API | API становится узким местом и падает вместе с сайтами |
| S3 website endpoint напрямую | нет нормального wildcard-TLS, дорогие GET, плохой SPA/404 |
| `s3fs`/`rclone mount` | объектное хранилище не файловая система, latency и сбои |
| Отдельный preview-домен | preview закрыт тикетом и не предназначен для публичного сайта |
| Свой домен каждому сразу | отдельный продукт: DNS, сертификаты, проверка владения |
| Бакет с первого дня | добавляет сетевые сбои и восстановление; MVP проще на диске |

## 5. Модель данных

### 5.1. `sites`

Одна строка на проект.

```sql
CREATE TABLE IF NOT EXISTS sites (
  id                   TEXT NOT NULL PRIMARY KEY,
  user_id              TEXT NOT NULL,
  project_id           TEXT NOT NULL UNIQUE,
  slug                 TEXT NOT NULL UNIQUE,
  status               TEXT NOT NULL DEFAULT 'draft',
  active_release_id    TEXT,
  publishing_release_id TEXT,
  last_error           TEXT NOT NULL DEFAULT '',
  created_at           TEXT NOT NULL,
  updated_at           TEXT NOT NULL,
  published_at         TEXT,
  unpublished_at       TEXT
);

CREATE INDEX IF NOT EXISTS idx_sites_user
  ON sites (user_id);

CREATE INDEX IF NOT EXISTS idx_sites_status
  ON sites (status);
```

`project_id UNIQUE` — это и есть ограничение «один сайт на проект». Не интерфейс, не проверка в коде, а база.

`id` — обычный UUID. `slug` — 12 строчных hex-символов из `crypto.randomBytes(6)`, генерируется один раз и не меняется при переименовании проекта. Коллизия маловероятна, но `UNIQUE` и повторная генерация всё равно нужны.

`status`:

- `draft` — сайт создан, но ещё ни разу не был опубликован;
- `live` — есть активный релиз;
- `unpublished` — сайт снят с публикации, файлы могут быть сохранены.

`publishing_release_id` — идёт публикация. Может быть заполнен при `live`: тогда старый релиз продолжает работать, а новый собирается.

`last_error` — последняя ошибка публикации, чтобы UI не терял причину; при успешной публикации очищается.

### 5.2. `site_releases`

```sql
CREATE TABLE IF NOT EXISTS site_releases (
  id            TEXT NOT NULL PRIMARY KEY,
  site_id       TEXT NOT NULL,
  user_id       TEXT NOT NULL,
  status        TEXT NOT NULL DEFAULT 'building',
  bytes         BIGINT NOT NULL DEFAULT 0,
  stored_bytes  BIGINT NOT NULL DEFAULT 0,
  files         INTEGER NOT NULL DEFAULT 0,
  sha256        TEXT NOT NULL DEFAULT '',
  storage_key   TEXT NOT NULL DEFAULT '',
  manifest_key  TEXT NOT NULL DEFAULT '',
  error         TEXT NOT NULL DEFAULT '',
  build_log     TEXT NOT NULL DEFAULT '',
  created_at    TEXT NOT NULL,
  ready_at      TEXT
);

CREATE INDEX IF NOT EXISTS idx_site_releases_site
  ON site_releases (site_id, created_at);

CREATE INDEX IF NOT EXISTS idx_site_releases_user
  ON site_releases (user_id);

CREATE UNIQUE INDEX IF NOT EXISTS idx_site_releases_building
  ON site_releases (site_id)
  WHERE status = 'building';
```

Последний индекс — страховка от двух одновременных публикаций одного сайта.

`bytes` — суммарный размер файлов релиза (то, что видит пользователь).

`stored_bytes` — размер `tar.gz` в бакете (то, что стоит платформе).

`storage_key` — ключ в S3, пустой в локальном режиме.

`build_log` — только хвост, не весь вывод.

### 5.3. Статусы релиза

```text
building ──► ready
    │
    └──────► failed
ready ─────► deleted (файлы удалены, строка может остаться для истории)
```

`active_release_id` ссылается только на `ready`-релиз этого же сайта.

### 5.4. JSON-режим

В локальной разработке и тестах, как у `project-archive-state.ts`:

```text
WEBNESTDEV_DATA_DIR/hosting/sites.json
WEBNESTDEV_DATA_DIR/hosting/releases/<siteId>.json
```

В production — PostgreSQL. Логика store одна, бэкенды разные. Если это усложняет MVP, допустим только PostgreSQL в production и JSON в тестах; важно не смешивать два источника истины в одном режиме.

### 5.5. Что не храним в базе

- содержимое файлов;
- полный build log;
- секреты;
- сертификаты;
- `current` как строку: источник истины для активного релиза — `sites.active_release_id`, а `current` — производная ссылка, которую можно восстановить.

## 6. Хранилище и раскладка файлов

### 6.1. Каталог

```text
/srv/sites/                         # SITES_DIR, отдельный bind mount
  <slug>/
    current -> releases/<releaseId>
    releases/
      <releaseId>/
        index.html
        assets/...
    tmp/
      <releaseId>/                  # staging, не отдаётся Caddy
    trash/                          # временно при удалении, если нужно
```

Почему `<slug>`:

- slug стабилен и не зависит от переименования проекта;
- Caddy получает его из `Host`;
- один каталог = один сайт;
- нет поиска по базе на каждом запросе.

### 6.2. Правила

- `SITES_DIR` — отдельный каталог, не внутри `WEBNESTDEV_DATA_DIR`.
- Caddy монтирует его **read-only**.
- Сервер монтирует его read-write.
- Владелец каталога — uid/gid сервера (1000:1000).
- Каталоги `0755`, файлы `0644`.
- `current` — относительный симлинк, чтобы он пережил смену точки монтирования.
- Временные каталоги создаются внутри `<slug>/tmp`, чтобы `rename` был атомарным в пределах одной файловой системы.
- Caddy не должен видеть `tmp`, `trash`, `.hosting` и другие служебные каталоги: они не входят в `current`.

### 6.3. Почему не named volume

Нужно, чтобы и сервер, и Caddy видели один и тот же каталог, а оператор мог проверить его с VM. Bind mount проще и прозрачнее:

```yaml
# сервер
- ${SITES_DIR:-/var/lib/webnestdev/sites}:/srv/sites

# caddy
- ${SITES_DIR:-/var/lib/webnestdev/sites}:/srv/sites:ro
```

`WEBNESTDEV_SITES_DIR=/srv/sites` внутри обоих контейнеров.

`server/entrypoint.sh` запускается root до `setpriv` и должен:

- создать `/srv/sites`, если каталога нет;
- выставить владельца uid/gid сервера (1000:1000);
- выставить `0755` на корень;
- не делать рекурсивный `chown` на каждом старте без необходимости: файлы релизов и так создаёт сервер от uid 1000.

Если каталог создан Docker'ом от root и остался root-owned, сервер не сможет писать, а сайт будет отвечать 404. Это отдельная проверка в smoke-тесте.

### 6.4. Совместимость с архивацией

Сайт не читает рабочую папку после публикации. Поэтому:

- проект уехал в бакет — сайт работает;
- проект удалён — сайт удаляется отдельной операцией;
- проект восстановлен — сайт не меняется.

В локальном MVP потеря `SITES_DIR` означает, что сайт нужно опубликовать заново из исходников; это приемлемо до этапа бакета. После этапа бакета активные релизы восстанавливаются из объектов.

Это нужно проверить тестом, а не предполагать.

## 7. Формат релиза и проверка артефакта

### 7.1. Что считается релизом

Релиз — это каталог с файлами, которые Caddy отдаёт как есть. Никаких `node_modules`, исходников и служебных файлов.

### 7.2. Проверки перед публикацией

Для `static-build`:

- `detectProject` вернул `static-build`;
- `npm run build` завершился успешно;
- output-каталог существует;
- в корне output есть `index.html`;
- output не является симлинком;
- файлы — обычные файлы, не symlink/socket/device;
- нет `..`, абсолютных путей и NUL в именах;
- нет `node_modules`, `.git`, `.env*`;
- общий размер ≤ лимита;
- число файлов ≤ лимита;
- один файл ≤ лимита;
- нет известных секретных имён;
- нет значений проектных секретов (если они вообще передавались);
- нет source map, если включён запрет.

Для `instant-site`:

- `index.html` есть;
- исходные файлы копируются по белому/чёрному списку;
- `.env`, `.git`, `node_modules`, `package.json`, lock-файлы и служебные файлы не попадают в релиз;
- остальное проверяется теми же правилами.

### 7.3. Лимиты по умолчанию

| Переменная | Значение | Смысл |
|---|---:|---|
| `HOSTING_MAX_RELEASE_BYTES` | 50 МиБ | весь релиз |
| `HOSTING_MAX_FILE_BYTES` | 25 МиБ | один файл |
| `HOSTING_MAX_FILES` | 5 000 | число файлов |
| `HOSTING_KEEP_RELEASES` | 3 | сколько готовых релизов хранить |
| `HOSTING_BUILD_TIMEOUT_MS` | 600 000 | 10 минут на сборку |
| `HOSTING_MAX_RELEASE_SECONDS` | 600 | общий предел публикации |
| `HOSTING_BUILD_CONCURRENCY` | 1 | одновременно собираем один сайт |
| `HOSTING_GLOBAL_BYTES` | 15 ГиБ | общий предел `SITES_DIR` на VM |
| `HOSTING_MIN_FREE_BYTES` | 5 ГиБ | не публиковать, если на диске меньше |

50 МиБ на релиз — сознательно консервативно для текущей VM. Видео и тяжёлые медиа в релиз не входят; для них позже будет отдельное хранилище.

### 7.4. Секреты

Публичная сборка **не должна получать приватные секреты проекта**.

Правило:

- build видит только публичные переменные с префиксами `VITE_`, `NEXT_PUBLIC_`, `REACT_APP_`, `PUBLIC_`, `ASTRO_`, `NUXT_PUBLIC_`;
- приватные ключи, токены, пароли и platform env не монтируются;
- `ensureProjectDependencies` получает режим `secrets: "public"` для хостинга;
- после сборки — дополнительный скан на известные имена и значения;
- build log обрезается и редактируется перед показом.

Если сборке нужен приватный ключ, это не статический сайт в текущем понимании. Пользователь должен вынести секрет на бэкенд, которого у нас пока нет.

### 7.5. Манифест

Для каждого релиза сохраняем:

- `releaseId`;
- размер и число файлов;
- SHA-256 архива или каталога;
- список файлов с размерами (для проверки и отладки);
- тип проекта и output-каталог;
- время сборки.

Манифест нужен для:

- проверки целостности при откате;
- очистки;
- диагностики «сайт весит 48 МБ, почему».

В локальном режиме манифест можно хранить в БД, в бакете — отдельным JSON.

### 7.6. Конфигурация

Добавить в `docker-compose.yml`, `server/src/platform/platform-env.ts` (если переменная должна переживать панель) и `deploy/scripts/make-env-vm.sh`:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `HOSTING_ENABLED` | `0` | включить маршруты и UI |
| `HOSTING_PUBLIC_DOMAIN` | `host.nestdev.ru` | домен сайтов |
| `HOSTING_TLS_MODE` | `on_demand` | `on_demand` или `wildcard` |
| `WEBNESTDEV_SITES_DIR` | `/srv/sites` | путь внутри контейнеров |
| `SITES_DIR` | `/var/lib/webnestdev/sites` | путь на VM для compose |
| `HOSTING_S3_PREFIX` | `hosting` | префикс в бакете, если включён |

`HOSTING_ENABLED=0` не должен ломать уже опубликованные сайты: Caddy продолжает отдавать файлы, отключаются только новые публикации и UI. Иначе выключение флага станет способом уронить все сайты.

## 8. Публикация: алгоритм и гонки

### 8.1. Один сайт

Создание сайта:

```text
если sites.project_id уже есть -> вернуть существующий сайт
иначе создать slug, sites(draft), release(building)
```

`project_id UNIQUE` не даст создать второй даже при двух одновременных запросах. Второй запрос получит `409` или тот же сайт — решение API.

### 8.2. Одна публикация

- `publishing_release_id` заполняется в транзакции;
- частичный уникальный индекс `site_releases(site_id) WHERE status='building'` не даёт создать второй `building`;
- в памяти — дополнительный lock на `siteId`, чтобы не запускать две задачи;
- повторный `POST /publish` при активной сборке → `409` с текущим релизом.

### 8.3. Атомарность

Порядок:

1. Сборка в `tmp/<releaseId>`.
2. Проверка `tmp`.
3. `rename(tmp, releases/<releaseId>)` — атомарно в пределах `SITES_DIR`.
4. Загрузка в бакет (если включён) — до переключения.
5. `current` → новый релиз через временный симлинк и `rename`.
6. Транзакция: `active_release_id`, `published_at`, `publishing_release_id = null`.
7. Удаление старых релизов.

Если шаг 4 или 5 упал, `current` остаётся старым, а релиз помечается `failed`; временный каталог удаляется.

Если шаг 6 упал после шага 5, сайт уже отдаёт новый релиз, а база — старый. На старте и по расписанию нужна **сверка**: прочитать `current`, сравнить с `active_release_id`, при расхождении выбрать файловую истину и обновить базу. Лучше допустить краткое расхождение, чем оставить сайт с битой ссылкой.

### 8.4. Сборка

- `static-build`: всегда свежий `npm run build`, даже если `dist` уже есть.
- `instant-site`: без сборки, но с копированием и проверкой.
- `node-runtime`/`python-runtime`/`unknown`: `422` с причиной.
- Зависимости: `ensureProjectDependencies` с публичными env.
- Сеть: установка — bridge, сборка — без сети, если текущая песочница это позволяет.
- Таймаут: 10 минут; по истечении — `failed`, процесс не оставляем.
- Параллелизм: 1 сборка на всю VM в MVP. Иначе две сборки и Caddy конкурируют за 2 vCPU.
- Очередь: если слот занят, публикация ждёт; UI показывает «в очереди», а не «ошибка».

### 8.5. Что видит пользователь во время сборки

Этапы:

```text
Проверяем проект
Ставим зависимости
Собираем
Проверяем файлы
Публикуем
Проверяем адрес
```

Статус обновляется polling'ом. Лог — хвост, не поток.

## 9. Caddy, TLS и DNS

### 9.1. Домен

Новая переменная:

```text
HOSTING_PUBLIC_DOMAIN=host.nestdev.ru
```

Адрес сайта:

```text
https://<slug>.host.nestdev.ru
```

Домен должен быть ровно из трёх меток (`host.nestdev.ru`), потому что Caddy берёт slug из `labels.3`. Если позже понадобится `host.staging.nestdev.ru`, индекс станет `labels.4`; это проверяется в этапе 0, а не угадывается на проде.

DNS:

```text
A  host.nestdev.ru      -> <IP VM>
A  *.host.nestdev.ru    -> <IP VM>
```

Wildcard DNS нужен, чтобы каждый новый сайт не требовал отдельной записи.

### 9.2. Caddy

Новый блок в `deploy/Caddyfile`:

```caddyfile
*.{$HOSTING_PUBLIC_DOMAIN:host.nestdev.ru} {
    # Режим A: сертификат на каждый поддомен. В режиме B заменяется на wildcard/DNS-01.
    tls {
        on_demand
    }

    encode zstd gzip

    # Домен host.nestdev.ru — ровно три метки, поэтому slug лежит в labels.3.
    # Если домен станет другого уровня, индекс нужно пересчитать и проверить в этапе 0.
    root * /srv/sites/{http.request.host.labels.3}/current

    # HTML не кешировать, хешированные ассеты — надолго.
    @html path / *.html
    header @html Cache-Control "no-cache"

    # Только файлы с хешем в имени: logo-abc123.png, index-abc123.js.
    # Не хешированный /assets/logo.png не должен получить годовой immutable.
    @hashed path_regexp hashed -[A-Za-z0-9_-]{6,}\.[a-z0-9]{1,8}$
    header @hashed Cache-Control "public, max-age=31536000, immutable"

    header {
        X-Content-Type-Options nosniff
        Referrer-Policy strict-origin-when-cross-origin
    }

    # Скрытые файлы и служебные каталоги наружу не отдаём.
    # RE2 не поддерживает lookahead, поэтому .well-known исключается отдельным matcher.
    @hidden {
        path_regexp dot (^|/)\.
        not path /.well-known/*
    }
    respond @hidden 404

    # SPA-fallback только для путей без расширения.
    # Файл с расширением, которого нет, должен остаться 404, а не стать index.html.
    @spa not path_regexp ext \.[a-z0-9]{1,8}$
    handle @spa {
        try_files {path} /index.html
        file_server
    }
    handle {
        file_server
    }
}
```

Это эскиз, а не финальный конфиг. Перед выкаткой:

- `caddy validate` в `vm-deploy.sh`;
- проверка `Host` с портом и без;
- проверка, что `/assets/missing.js` даёт 404, а не `index.html`;
- проверка, что `/.env` и `/.git/config` не отдаются;
- проверка, что `current`-симлинк работает;
- проверка, что каталог без `current` даёт 404;
- проверка, что `labels.3` действительно равен slug для домена из трёх меток.

### 9.3. TLS: два режима

**Режим A — on-demand на каждый поддомен.**

Плюсы:

- не нужен DNS-плагин Caddy;
- работает с текущим образом `caddy:2.8-alpine`;
- как у preview.

Минусы:

- Let's Encrypt даёт **50 сертификатов на зарегистрированный домен в неделю** ([Rate Limits](https://letsencrypt.org/docs/rate-limits/));
- при 300+ сайтах первичная выдача и продление упираются в лимит;
- каждый новый сайт — отдельный сертификат.

Подходит для пилота до ~50–100 сайтов. Сертификаты должны лежать в существующем томе `caddy-data`: без него каждая выкатка заново просила бы сертификаты и упиралась в лимит.

**Режим B — wildcard `*.host.nestdev.ru`.**

Плюсы:

- один сертификат на все сайты;
- нет лимита на число поддоменов;
- продление одно.

Минусы:

- нужен DNS-01;
- нужен DNS-API провайдера;
- текущий образ Caddy не содержит DNS-плагин;
- нужен либо кастомный образ Caddy с модулем, либо `acme.sh` + монтирование сертификата;
- кастомный образ нужно собирать в CI и пинить по digest, а не тянуть случайный `latest`.

Решение:

- **пилот** — режим A;
- **до публичного запуска с сотнями сайтов** — режим B;
- это отдельный этап, а не «потом когда-нибудь».

### 9.4. Общий TLS-ask

Сейчас Caddy спрашивает `/api/preview/tls-ask`. Для двух доменов нужен общий endpoint:

```text
GET /api/tls-ask?domain=<host>
```

Логика:

- `*.preview.<domain>` → существует проект;
- `*.host.<domain>` → существует сайт и он `live` (для `draft`/`unpublished` — 404);
- всё остальное → 404.

Старый `/api/preview/tls-ask` можно оставить как алиас на время перехода.

### 9.5. Порядок выкатки TLS

Нельзя выкатить Caddyfile с новым доменом раньше серверного endpoint: Caddy начнёт спрашивать `/api/tls-ask`, которого нет, и новые сертификаты не выдадутся.

Порядок:

1. Выкатить сервер с `/api/tls-ask` и feature flag `HOSTING_ENABLED=0`.
2. Проверить endpoint.
3. Выкатить Caddyfile/compose с hosting-блоком.
4. Включить flag для администраторов.
5. Опубликовать тестовый сайт.
6. Только потом включать всем.

`vm-deploy.sh` не должен удалять или пересоздавать `SITES_DIR`: выкатка обновляет код и compose, но не данные сайтов. Каталог — такой же том состояния, как `DATA_DIR`, и проверка «сайты после выкатки на месте» входит в smoke.

Откат образа на версию без `/api/tls-ask` означает, что уже выданные сертификаты продолжат работать, а новые сайты не получат TLS. Поэтому при откате сервера нужно откатывать и Caddyfile (или оставлять старый endpoint-заглушку).

## 10. API

Все пользовательские маршруты — с сессией и `requireProjectUser`.

Все административные — с Bearer-токеном админки, без cookie.

### 10.1. Пользовательские

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/api/projects/:id/hosting` | сайт, релизы, лимиты, можно ли публиковать |
| `POST` | `/api/projects/:id/hosting/publish` | `202`, `releaseId`, статус |
| `GET` | `/api/projects/:id/hosting/releases` | история релизов |
| `POST` | `/api/projects/:id/hosting/releases/:releaseId/activate` | откат/переключение |
| `POST` | `/api/projects/:id/hosting/unpublish` | снять с публикации, релизы сохранить |
| `DELETE` | `/api/projects/:id/hosting` | удалить сайт и файлы |
| `GET` | `/api/projects/:id/hosting/logs` | хвост последней сборки |

`GET /hosting` при отсутствии сайта отвечает `200` с `site: null`, а не `404`: для UI это нормальное состояние «ещё не публиковали». `404` — только если проекта нет или он чужой.

`GET /hosting` должен отдавать:

```json
{
  "enabled": true,
  "site": {
    "id": "...",
    "slug": "...",
    "url": "https://....host.nestdev.ru",
    "status": "live",
    "activeReleaseId": "...",
    "publishingReleaseId": null,
    "publishedAt": "...",
    "lastError": "",
    "bytes": 1234567,
    "files": 42
  },
  "releases": [],
  "limits": {
    "maxReleaseBytes": 52428800,
    "maxFiles": 5000,
    "keepReleases": 3,
    "usedBytes": 1234567,
    "accountLimitBytes": 10737418240
  },
  "project": {
    "kind": "static-build",
    "reason": "...",
    "canPublish": true,
    "blockedReason": ""
  }
}
```

`canPublish=false` с причиной:

- `HOSTING_ENABLED=0`;
- тип проекта не поддерживается;
- нет `index.html`;
- идёт публикация;
- квота;
- глобальный диск;
- сайт удаляется.

Ошибки:

- `401` — нет входа;
- `404` — проекта/сайта нет или чужой;
- `409` — уже публикуется;
- `413` — релиз больше лимита;
- `422` — тип не поддержан, сборка не создала output;
- `429`/`507` — квота/диск;
- `503` — хостинг выключен.

### 10.2. Публичный TLS

| Метод | Путь | Доступ |
|---|---|---|
| `GET` | `/api/tls-ask?domain=...` | без сессии; вызывается Caddy, публично отдаёт только 200/404 |

Ответ — только `200`/`404`, без деталей проекта.

### 10.3. Админские

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/admin/hosting/sites` | список сайтов, фильтры, размеры |
| `GET` | `/api/admin/hosting/sites/:id` | карточка сайта и релизов |
| `POST` | `/api/admin/hosting/sites/:id/unpublish` | снять с публикации с причиной |
| `POST` | `/api/admin/hosting/sites/:id/restore` | вернуть в строй, если снимали |
| `GET` | `/api/admin/hosting/summary` | всего сайтов, байт, ошибок |

Audit-события:

```text
hosting.site.published
hosting.site.unpublished
hosting.site.deleted
hosting.site.admin_unpublished
```

### 10.4. Фоновая задача

`POST /publish` не должен держать HTTP-запрос 10 минут. Он:

1. создаёт `building`-релиз;
2. запускает `void publishRelease(...)` с обработкой ошибок;
3. сразу отвечает `202`.

UI опрашивает `GET /hosting` каждые 1.5–2 секунды, пока `publishingReleaseId` не станет `null`.

При рестарте сервера:

- все `building` старше 30 минут → `failed` с причиной «сервер перезапустился»;
- временные каталоги → удалить;
- `current` и БД → сверить.

## 12. Квоты и лимиты

### 12.1. Куда относить место

Хостинг входит в **общую квоту хранилища аккаунта**, как написано в `docs/PLANS_AND_LIMITS.md`.

Почему:

- это тот же диск VM;
- пользователь уже понимает «10 ГБ хранилища»;
- отдельная квота потребует ещё одного счётчика и объяснения.

В `StorageOverview` добавляется:

```text
projectsBytes
hostingBytes
usedBytes = projectsBytes + hostingBytes
```

`hostingBytes` = сумма `site_releases.bytes` только по `ready`-релизам, файлы которых ещё лежат на диске. Неудачные релизы файлов не оставляют и в квоту не входят.

### 12.2. Когда блокировать

- перед созданием релиза, если `usedBytes + ожидаемый размер > limit` — но ожидаемый размер неизвестен до сборки;
- после сборки, перед публикацией — точная проверка;
- если превышено — релиз `failed`, старый сайт не трогаем.

Глобальный диск:

- `statfs(SITES_DIR)`;
- если свободно меньше `HOSTING_MIN_FREE_BYTES` — `507`;
- если `SITES_DIR` больше `HOSTING_GLOBAL_BYTES` — `507` и алерт.

### 12.3. Удаление

- старый готовый релиз сверх 3 — удалять после успешной публикации;
- неудачный релиз — удалять файлы сразу, метаданные хранить 7 дней;
- удаление сайта — удалить `SITES_DIR/<slug>` и объекты бакета;
- удаление проекта — вызвать удаление сайта; если не удалось, записать orphan и повторить фоновой уборкой.

### 12.4. Что не делать

- не удалять старый релиз до успешного переключения;
- не удалять активный релиз;
- не считать размер по `du` на каждый запрос — хранить в БД;
- не позволять `HOSTING_KEEP_RELEASES=0` (не будет отката);
- не делать «бесконечное хранение» на текущей VM.

### 12.5. Ёмкость текущей VM

Текущая VM по документации проекта: 2 vCPU, 4 ГБ RAM, диск 50 ГБ, свободно около 39 ГБ. На ней уже живут API, Postgres, Docker-образы, песочницы и preview.

Под хостинг разумно зарезервировать **10–15 ГБ**, а не все 39 ГБ.

| Сценарий | На сайт (3 релиза) | Комфортно на текущей VM |
|---|---:|---:|
| Лёгкие лендинги, 2–5 МБ на релиз | 6–15 МБ | 500–1000 |
| Обычные Vite/React, 10–20 МБ | 30–60 МБ | 300–500 |
| Тяжёлые сборки, 50 МБ | 150 МБ | 60–100 |

По RAM хостинг почти ничего не добавляет: Caddy — один процесс на 50–100 МБ, отдельного процесса на сайт нет. По CPU обслуживание статики дешёвое; узкими местами становятся исходящий трафик, TLS-сертификаты и одновременные сборки, а не число сайтов само по себе.

Поэтому в MVP:

- 1 сборка одновременно;
- 50 МБ на релиз;
- 3 релиза;
- 10–15 ГБ общего лимита;
- TLS на каждый поддомен только до пилота, дальше wildcard.

## 13. Безопасность

### 13.1. Изоляция от панели

- `host.nestdev.ru` — отдельный origin;
- cookie сессии панели host-only для `nestdev.ru` и на поддомен не уходит;
- Caddy не ставит cookie;
- сайт не получает доступ к API панели с credentials;
- CORS платформы не расширяется на hosting-домен;
- в сайт не внедряются скрипты платформы (в отличие от preview-моста).

### 13.2. Файлы

- только обычные файлы;
- запрет symlink;
- запрет `..` и абсолютных путей;
- запрет dotfiles;
- запрет `node_modules`, `.git`, `.env*`;
- проверка размера и числа файлов;
- `index.html` обязателен;
- Caddy `file_server` без browse;
- Caddy read-only.

### 13.3. Секреты

- платформенные env не монтируются;
- приватные секреты проекта не монтируются в публичную сборку;
- публичные env — только по префиксам;
- скан вывода на известные имена и значения;
- build log редактируется;
- в API не отдавать пути и содержимое.

### 13.4. Sandbox

- сборка идёт тем же `runInSandbox`, что preview;
- CPU/память/PID лимиты;
- сеть только для установки зависимостей;
- пользовательский `Dockerfile` не исполняется;
- таймаут;
- один сборщик на VM.

### 13.5. Abuse

Публичный хостинг привлекает фишинг и malware. Для коммерческого запуска нужно:

- правило в оферте: запрещённый контент;
- админский unpublish;
- audit;
- контакт для жалоб;
- быстрый способ снять сайт без удаления данных;
- лимит публикаций в час;
- блокировка аккаунта.

Без этого хостинг нельзя открывать всем.

### 13.6. Path traversal и гонки

- slug — только `^[a-z0-9][a-z0-9-]{0,62}$`;
- releaseId — только `^[a-z0-9-]{8,64}$`;
- все пути строятся через `path.join` и проверяются `assertInside`/`path.relative`;
- `current` читается и проверяется, что target внутри `<slug>/releases`;
- Caddy не должен строить root из произвольного `Host`: root допустим только для имени, которое прошло проверку на одну DNS-метку (matcher `host`/`expression` выбрать и проверить в этапе 0); отдельно проверить `Host: ../../etc/passwd...`;
- удаление и публикация одного сайта сериализуются;
- удаление проекта во время публикации: публикация проверяет, что проект ещё есть, перед переключением.

## 14. Отказы и восстановление

| Отказ | Что с сайтом | Что с публикацией | Что делать |
|---|---|---|---|
| Сборка упала | старый работает | `failed`, `current` не менялся | показать лог, повторить |
| Кончилось место | старый работает | `507`, `current` не менялся | очистка/квота |
| Бакет недоступен | локальный работает | публикация/откат не идут | повторить, алерт |
| Caddy упал | все сайты недоступны | не важно | рестарт Caddy, внешний монитор |
| Postgres упал | Caddy продолжает отдавать | статус/публикация недоступны | восстановить БД |
| `current` пропал | 404 | — | сверка, восстановить ссылку из БД |
| БД говорит один релиз, диск другой | Caddy отдаёт диск | — | сверка при старте, файловая истина |
| TLS не выдался | HTTPS не работает | — | проверить DNS/ask, Caddy повторит |
| Выкатка откатилась | старый образ | старые маршруты | Caddyfile совместим, сайты живы |
| Пользователь удалил проект | сайт удаляется | — | подтверждение, очистка |

Главное правило: **публикация никогда не удаляет и не перезаписывает активный релиз до успешной проверки нового**.

## 15. Админка и наблюдаемость

### 15.1. Health

В внутренний `/api/health` добавить:

```text
hosting: {
  enabled,
  sites,
  live,
  releases,
  bytes,
  diskFreeBytes,
  lastPublishAt,
  failures24h
}
```

Публичный ответ через Caddy не должен раскрывать количество сайтов и пути. Оставить только `ok`/`service`/`build`.

### 15.2. Логи

Одна строка на публикацию:

```text
[hosting] publish site=<slug> release=<id> kind=static-build bytes=... files=... ms=... result=ok|failed
```

Без секретов и без полного лога.

### 15.3. Алерты

- `SITES_DIR` > 75% от `HOSTING_GLOBAL_BYTES`;
- свободно на диске < `HOSTING_MIN_FREE_BYTES`;
- 5+ неудачных публикаций за 15 минут;
- `/api/tls-ask` отвечает 5xx;
- Caddy недоступен (внешний монитор).

### 15.4. Admin API

Список сайтов, размеры, статусы, последняя ошибка; снятие с публикации с причиной; audit. Отдельной веб-админки нет — только внешнее приложение и API.

## 16. Бакет: следующий этап

### 16.1. Зачем

- диск VM перестаёт быть единственным местом хранения;
- релизы переживают потерю диска;
- можно хранить больше истории;
- дешевле гигабайт;
- позже — CDN и медиа.

### 16.2. Как

Абстракция:

```ts
interface ReleaseStore {
  put(site, release, dir): Promise<{ key: string; storedBytes: number }>;
  get(site, release, dest): Promise<void>;
  remove(site, release): Promise<void>;
}
```

Две реализации:

- `LocalReleaseStore` — текущий диск;
- `S3ReleaseStore` — `tar.gz` в бакете.

Ключи:

```text
hosting/<userId>/<siteId>/releases/<releaseId>.tar.gz
hosting/<userId>/<siteId>/releases/<releaseId>.json
```

На первом шаге можно переиспользовать существующие `PLATFORM_S3_*` и префикс `HOSTING_S3_PREFIX=hosting`, не заводя второй бакет. Отдельный бакет понадобится, только если у хостинга будут свои lifecycle-правила, квоты или доступы. `object-store.ts` уже умеет `putFile`/`getToFile`/`head`/`remove`; для очистки хватит известных ключей из БД.

Правила:

- после включения бакет — источник правды для готовых релизов, локальный `current` — горячий кэш;
- бакет приватный;
- только серверные ключи;
- один `tar.gz` на релиз, не тысячи объектов;
- загрузка до переключения `current`;
- локальный `current` остаётся горячим кэшем;
- при откате, если локального релиза нет, скачать из бакета и проверить tar перед распаковкой (пути, symlink, размер);
- при потере диска — восстановить активные релизы фоновой задачей;
- старые объекты удалять вместе с релизами;
- lifecycle для брошенных `tmp`/незавершённых загрузок.

### 16.3. Что не делать

- не отдавать сайт напрямую из S3 без CDN;
- не давать пользователю S3-ключи;
- не создавать бакет на пользователя;
- не делать `s3fs`-монтирование;
- не загружать каждый файл отдельным объектом.

### 16.4. Когда

После стабильного MVP и пилота. Ориентир: +3–5 дней. Если бакет нужен сразу, это меняет порядок этапов, но не архитектуру.

## 17. Этапы

### Этап 0. Решения и замеры — 0,5–1 день

- проверить, что Caddy отдаёт файл по `labels.3` для `host.nestdev.ru`;
- проверить размеры 10 реальных сборок;
- выбрать TLS-режим для пилота;
- проверить DNS-провайдера и возможность wildcard;
- зафиксировать лимиты 50 МБ / 5 000 файлов / 3 релиза.

**Готово, когда:** есть замеры и подтверждённый способ TLS.

### Этап 1. Модель и хранилище — 1,5–2 дня

- таблицы `sites`, `site_releases`;
- JSON fallback;
- `SITES_DIR`, конфиг, проверка пути;
- генерация slug;
- store-функции;
- unit-тесты.

**Готово, когда:** можно создать один сайт на проект, получить его по projectId, второй создать нельзя.

### Этап 2. Публикация — 2–3 дня

- определение типа;
- сборка через существующий sandbox;
- копирование и проверка артефакта;
- staging/rename/current;
- лог и ошибки;
- тесты с fixture-проектами.

**Готово, когда:** Vite-проект и готовая статика публикуются, а неудачная сборка не меняет активный релиз.

### Этап 3. Caddy и edge — 2–3 дня

- блок `*.host`;
- общий `/api/tls-ask`;
- compose mounts;
- entrypoint и права;
- DNS;
- `caddy validate`;
- smoke на тестовом домене.

**Готово, когда:** `https://<slug>.host...` открывается, TLS валиден, неизвестный поддомен — 404.

### Этап 4. API — 1,5–2 дня

- статус, публикация, история, откат, unpublish, delete;
- auth/ownership;
- лимиты и коды ошибок;
- фоновая задача и сверка;
- route-тесты.

**Готово, когда:** весь сценарий проходится curl'ом без UI.

### Этап 5. UI — 2–3 дня

- вкладка «Хостинг»;
- API-клиент;
- все состояния;
- стили;
- мобильная версия;
- ссылка из `DeploymentWizard` для статических проектов.

**Готово, когда:** пользователь публикует, откатывает и снимает сайт без терминала.

### Этап 6. Защита и лимиты — 1,5–2 дня

- квоты;
- скан секретов;
- запрет dotfiles/symlink;
- очистка;
- health;
- admin unpublish;
- audit.

**Готово, когда:** сайт с 51 МБ, symlink или `.env` внутри не публикуется.

### Этап 7. Тесты, выкатка, пилот — 2–3 дня

- полный typecheck;
- серверные тесты;
- deploy;
- пилот на 5–10 проектах;
- проверка архивации/удаления;
- документация;
- rollback-план.

Тест-матрица:

- unit: slug, пути, лимиты, статусы, манифест;
- unit: скан секретов и запрещённых файлов;
- route: чужой проект, второй сайт, повторная публикация, откат, unpublish;
- artifact: symlink, 51 МБ, 5 001 файл, `.env` в `public`, отсутствующий `index.html`;
- integration: Vite-fixture и instant-site в temp `SITES_DIR`;
- deploy: `caddy validate`, проверка `labels.3`, HTTPS, 404 на неизвестный поддомен;
- smoke: архивация проекта не ломает сайт, удаление проекта удаляет сайт.

**Готово, когда:** пилот живёт сутки без ошибок, диск не растёт бесконтрольно, старый релиз откатывается.

### Этап 8. Бакет — 3–5 дней

- `S3ReleaseStore`;
- загрузка/восстановление;
- ключи;
- очистка;
- тест «удалили локальный релиз — восстановили из бакета».

### Этап 9. Масштаб — отдельно

- wildcard TLS;
- CDN;
- медиа;
- custom domains;
- вторая VM.

## 19. Риски

| Риск | Вероятность | Влияние | Мера |
|---|---|---|---|
| TLS-лимит на поддомены | высокая при 100+ | сайт без HTTPS | wildcard до масштаба |
| Диск VM закончился | средняя | публикация/проекты | квоты, глобальный cap, алерт |
| Секрет попал в бандл | средняя | утечка | только public env, скан |
| Пользователь залил 500 МБ | высокая | диск | лимит 50 МБ, 5 000 файлов |
| Caddy-конфиг сломан | средняя | все сайты | validate, staged deploy |
| Публикация сломала живой сайт | низкая | простой | immutable + current |
| Проект архивирован, сайт пропал | низкая | простой | отдельный SITES_DIR, тест |
| Abuse/фишинг | средняя | репутация/блокировки | admin unpublish, оферта |
| Две публикации одновременно | средняя | гонка | partial unique index + lock |
| Бакет недоступен | средняя | нет публикации | локальный кэш, retry |
| Старый образ не знает endpoint | средняя | TLS не выдаётся | порядок выкатки |
| Сборка ест CPU | средняя | API тормозит | concurrency=1, timeout |

## 20. Критерии готовности

Функционально:

- [ ] у проекта ровно один сайт, второй создать нельзя;
- [ ] `instant-site` публикуется;
- [ ] `static-build` публикуется;
- [ ] `node-runtime`/`python-runtime` получают понятный отказ;
- [ ] адрес `https://<slug>.host...` открывается;
- [ ] TLS валиден;
- [ ] неизвестный поддомен — 404;
- [ ] отсутствующий ассет — 404, а не `index.html`;
- [ ] SPA-маршрут отдаёт `index.html`;
- [ ] HTML не кешируется, хешированные ассеты кешируются;
- [ ] `.env`, `.git`, dotfiles не отдаются;
- [ ] откат на предыдущий релиз работает;
- [ ] снятие с публикации даёт 404;
- [ ] удаление сайта удаляет файлы;
- [ ] архивация проекта не ломает сайт;
- [ ] удаление проекта удаляет сайт;
- [ ] квота аккаунта учитывает сайт;
- [ ] лимиты 50 МБ / 5 000 файлов соблюдаются;
- [ ] админ может снять сайт с публикации через API;
- [ ] audit пишется;
- [ ] health показывает состояние;
- [ ] диск не растёт после 10 публикаций;
- [ ] старый `current` не удаляется при ошибке.

Проверки:

- [ ] `npx tsc -b --noEmit`;
- [ ] `npx tsc -p server/tsconfig.json --noEmit`;
- [ ] серверные тесты;
- [ ] `caddy validate`;
- [ ] deploy на staging/VM;
- [ ] smoke на живом домене;
- [ ] пилот 5–10 сайтов.

## 21. Что решить до этапа 1

| Вопрос | Предлагаемое решение | Почему |
|---|---|---|
| Формат адреса | 12-символьный стабильный slug | не зависит от переименования |
| TLS пилота | on-demand | не требует DNS-плагина |
| TLS масштаба | wildcard через DNS-01 | лимит 50/неделю |
| Квота | общая квота аккаунта | один диск, понятно пользователю |
| Хранение | 3 релиза | откат без бесконечного диска |

| Бакет | после MVP | меньше сбоев в первой версии |
| Архив проекта | сайт остаётся | сайт не зависит от workspace |
| Удаление проекта | сайт удаляется | нет сирот |
| Даунгрейд | сайт жив, новые публикации по квоте | не ломать существующее |
| Блокировка аккаунта | снять сайты с публикации | безопасность |

## 23. Итог

Это **средняя по сложности** задача: Caddy отдаёт файлы почти бесплатно, но вокруг него нужно сделать релизы, откат, лимиты, TLS, безопасность и UI.

Правильный порядок:

1. один сайт на проект;
2. локальный диск и неизменяемые релизы;
3. Caddy и поддомен;
4. лимиты и защита;
5. пилот;
6. бакет;
7. wildcard TLS;
8. медиа и CDN — только после этого.

Главное — не начинать с медиа, CDN и кастомных доменов. Статический хостинг сам по себе уже даёт продукт, а его ограничения (50 МБ, один сайт, три релиза) защищают текущую VM и делают запуск предсказуемым.
