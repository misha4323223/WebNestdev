## 1. Задача

Снизить нагрузку на ВМ от вызовов функций в двух режимах:

1. **production-хостинг** — `*.host`, где сейчас каждый запрос `/api/*` может запускать
   одноразовый Docker-контейнер;
2. **preview** — предпросмотр проекта, где функции должны проверяться до публикации, но не
   должны запускать контейнер на каждый запрос страницы.

Дополнительное условие: у владельцев сайтов будут админки, где меняются цена, фото, описание
и текст страниц. Решение не должно превращать правку в полную пересборку сайта.

|---|---|
| Caddy отправляет весь `/api/*` на отдельную дверь функций | `deploy/Caddyfile`, `server/src/hosting/caddy-config.ts` |
| Дверь находит сайт по Host и активному релизу | `server/src/functions/host-server.ts` |

ответа». Это основная нагрузка, которую можно убрать без переноса в чужое облако.

### 2.4. Админки и контент

| Факт | Где |
|---|---|
| `/api/admin/*` — админка платформы, не админка сайта пользователя | `server/src/routes/admin-*.ts` |
| Отдельного CMS/контентного runtime для сайтов пользователей нет | `server/src` |
| `sites` и `site_releases` есть; таблиц контента страниц/товаров нет | `server/src/storage/pg.ts` |
| Публикация сбрасывает CDN-кеш всего ресурса `/*` | `server/src/hosting/cdn-purge.ts` |
| HTML отдаётся с `no-cache`; хешированные ассеты — `immutable` | `deploy/Caddyfile` |
| `routes/cache-headers.ts` запрещает кешировать документы панели и API панели | `server/src/routes/cache-headers.ts` |

**Вывод:** если у пользователей будут админки, нужно различать два пути:

- **минимальный:** read-only функции получают явный opt-in кеш; админка пишет в базу, TTL
  делает изменение видимым через несколько секунд;
- **полный:** контент сайта хранится в таблицах платформы, публичный рендер читает его из
  базы, админка меняет запись и инвалидирует кеш без пересборки.

Этот план сначала делает минимальный путь, потому что он не требует переписывать проекты
пользователей и сразу снимает основную нагрузку. Полный контентный runtime остаётся отдельным
этапом с продуктовым решением.

## 3. Главный вывод

Нельзя исполнить произвольный код, не потратив чей-то CPU и RAM. Можно:

1. **не исполнять** read-only функцию на каждый запрос — отдать кеш;
2. **не запускать контейнер** на каждый запрос — держать тёплый исполнитель;
3. **не пересобирать** сайт из-за фото/видео — они уже в S3;
4. **не кешировать** то, что зависит от пользователя: корзину, заказ, авторизацию, оплату.

Поэтому целевая модель:

```text
GET /api/products, /api/product, /api/promo
    → кеш ответа функции (TTL + точечная инвалидация)
    → при промахе один вызов, остальные ждут тот же результат

POST /api/orders, /api/login, /api/cart
    → всегда функция, без общего кеша
    → заказ перепроверяет цену и наличие

preview
    → один исполнитель на проект / сессию, фикстуры и явный вызов функции
    → не контейнер на каждый переход

media
    → S3/CDN, без проксирования через ВМ
```

## 4. Границы

В этот план **не входит**:

- перенос функций в Yandex Cloud или другой внешний FaaS;
- замена Docker на другой изолятор;
- полная статическая генерация всех страниц;
- автоматический CMS-конструктор для любых проектов без отдельного решения;
- пересборка сайта после каждой правки цены;
- кеширование авторизованных и платёжных запросов;
- изменение существующих проектов пользователей без явного контракта в манифесте.

## 5. Целевая архитектура

### 5.1. Production

```text
Caddy
  ├── статика релиза → файлы
  └── /api/* → functions host
        ├── есть безопасный кеш → ответ без контейнера
        ├── нет кеша → limiter → docker run → ответ
        └── запись в кеш, если функция это разрешила
```

Кеш включается **только явно** в `nestdev.functions.json`. По умолчанию функция не
кешируется. Это защищает заказы, авторизацию и любые побочные эффекты.

### 5.2. Preview

```text
preview
  ├── статика → файлы
  └── /api/* → один preview-executor на проект
        ├── запросы из страницы не запускают новый контейнер
        ├── результат можно сохранить как фикстуру
        └── явная кнопка «выполнить заново» для проверки API
```

### 5.3. Админка

```text
админка → запись в БД → версия контента / TTL
                           ↓
публичный GET → кеш → функция только при промахе
```

Если нужна мгновенная смена цены без TTL, добавляется точечная инвалидация по сайту и пути.
Полный контентный runtime — этап 5, только после решения о модели данных.

### Этап 2. Безопасный кеш ответов функций

Статус: **выкачен 17.11.2026, 20:49 UTC; `FUNCTIONS_CACHE_ENABLED=1` на node-1. Живых
вызовов после рестарта не было, hit/miss ещё не проверены на реальном трафике.**

Цель: read-only GET не запускает контейнер, если ответ уже есть.

Контракт манифеста — только явный opt-in:

```json
{
  "name": "products",
  "path": "/api/products",
  "methods": ["GET"],
  "handler": "api/products.ts#handler",
  "cache": { "ttlSeconds": 60 }
}
```

Правила:

- кеш разрешён только для `GET`/`HEAD`;
- запрос с `Authorization` или `Cookie` по умолчанию не кешируется;
- ключ: `siteId + releaseId + functionName + method + path + query + Accept + Accept-Language`;
- ошибки, `Set-Cookie`, `Cache-Control: no-store/private`, `Vary: *` и ответы с jobs не кешируются;
- размер кеша ограничен по байтам и числу записей;
- single-flight: параллельные одинаковые запросы ждут один вызов;
- при публикации/откате кеш сайта сбрасывается;
- TTL — страховка, а не единственный механизм инвалидации.

Факты реализации:

- `server/src/functions/manifest.ts` — `cache.ttlSeconds` (1–86 400) только для явного opt-in;
- `server/src/functions/build.ts` — политика сохраняется в `manifest.json` релиза;
- `server/src/functions/response-cache.ts` — LRU, TTL, лимит 512 записей / 16 МиБ по умолчанию,
  single-flight и `clearSite`;
- `server/src/functions/host-server.ts` — `x-function-cache: HIT` на попадании, запись только
  после успешного ответа;
- `server/src/hosting/publisher.ts` — сброс кеша сайта после публикации и отката;
- `docker-compose.yml` — `FUNCTIONS_CACHE_ENABLED`, `FUNCTIONS_CACHE_MAX_ENTRIES`,
  `FUNCTIONS_CACHE_MAX_BYTES` для отката без пересборки образа.

Критерий:

- 100 одновременных GET одного публичного endpoint дают 1 выполнение при пустом кеше;
- повторный GET в пределах TTL не запускает контейнер;
- запрос с cookie/Authorization не попадает в общий кеш;
- публикация сбрасывает кеш сайта;
- заказы и другие POST не кешируются.

Ограничение этапа: `staleWhileRevalidate` ещё не реализован. Сейчас истёкший TTL — это
промах и повторный вызов; фоновое обновление будет только если оно действительно нужно.

### Этап 3. Точечная инвалидация и две ноды

Статус: **выкачен 17.11.2026, 20:49 UTC; на обеих нодах
`function cache invalidation listening on webnestdev_function_cache` и health
`cacheInvalidation=pg_notify`. Сценарий публикации на двух нодах ещё не прогонялся.**

Цель: админка меняет цену, кеш на обеих нодах перестаёт отдавать старое.

Выбран вариант 3 — `pg_notify`. PostgreSQL уже есть в production, поэтому не нужен Redis и
не появляется второй источник правды. Версия контента в БД отвергнута: она добавляла бы
чтение версии на каждый публичный запрос, то есть возвращала бы часть нагрузки, которую
убирает кеш.

Как работает:

- `invalidateFunctionCache(siteId)` сразу очищает локальный кеш сайта, затем отправляет
  `pg_notify` в канал `webnestdev_function_cache` (префикс — `PG_TABLE_PREFIX`);
- каждая нода после инициализации хранилища открывает отдельное `LISTEN`-соединение и при
  уведомлении очищает только этот сайт; при обрыве соединение переподключается;
- публикация и откат вызывают инвалидацию после фиксации релиза в БД;
- уведомление не является очередью: если нода была отключена, TTL остаётся страховкой;
- ошибка `pg_notify` не отменяет публикацию и не оставляет релиз в `failed`;
- в JSON-режиме и при `FUNCTIONS_CACHE_ENABLED=0` остаётся только локальный сброс;
- `/api/health` показывает `activity.functions.cacheInvalidation: "pg_notify" | "local"`.

Файлы:

- `server/src/functions/cache-invalidation.ts` — локальный сброс, `pg_notify`, слушатель;
- `server/src/storage/pg-notifications.ts` — `LISTEN` с переподключением и проверкой имени
  канала;
- `server/src/hosting/publisher.ts` — инвалидация после публикации и отката;
- `server/src/index.ts` — запуск и остановка слушателя вместе с хранилищем;
- `server/src/routes/health.ts` — режим инвалидации в health;
- `server/src/functions/cache-invalidation.test.ts` — локальный сброс, ошибка уведомления,
  безопасное имя канала.

Ограничение этапа: инвалидация сейчас по сайту, а не по отдельному пути; внутреннего
маршрута для правки контента ещё нет, потому что контентного runtime нет. Точечный CDN
purge относится к этапу 7 и не входит в этот этап.

Критерий: после изменения цены обе ноды перестают отдавать старый ответ в заданном окне;
ошибка purge не ломает запись и не оставляет сайт в `failed`. Код и unit-тесты готовы;
критерий на двух нодах будет закрыт после выкатки.

Как работает:

```text
static preview
  ├── файлы → listener в процессе API
  └── /api/* → один контейнер functions-preview
                 └── runtime.mjs → собранные handlers
```

- `functions-preview.ts` собирает функции в скрытый `.webnestdev/functions-preview/<session>`
  проекта, кладёт туда `runtime.mjs` и запускает один контейнер через тот же runner, что
  hybrid backend;
- `runtime.mjs` читает `manifest.json`, держит модули в памяти и обрабатывает запросы
  последовательно, поэтому страница с несколькими запросами к API не создаёт контейнер на
  каждый запрос;
- статический listener — тот же hybrid-listener: файлы отдаются из процесса API, только
  `/api` идёт в контейнер;
- executor включается правом `serverlessFunctions`, а не `containerPreview`: на «Плюсе»
  функции публикуются, поэтому их можно проверить в preview; на «Старте» `/api` — 404;
- `FUNCTIONS_PREVIEW_MAX_CONTAINERS` (по умолчанию 4) ограничивает число таких контейнеров
  на процесс; это локальный, а не кластерный лимит;
- watcher следит за `.ts/.tsx/.js/.jsx/.mjs/.cjs/.json` в проекте, игнорирует `node_modules`,
  `.webnestdev`, `dist` и другие выходные каталоги; после паузы 400 мс пересобирает функции
  в новую версию и отправляет runtime команду перечитать модули;
- контейнер при этом не перезапускается, старые модули живут в памяти до успешного reload;
  неудачная сборка оставляет работать предыдущую версию и пишет причину в лог;
- если runtime всё-таки упал, supervisor внутри контейнера поднимает его заново; после
  трёх падений за минуту контейнер завершается, чтобы не крутить бесконечный цикл.

Файлы:

- `server/src/functions/preview-runtime.mjs` — HTTP-runtime внутри контейнера;

### Этап 7. CDN и точечный purge

Статус: **выкачено 17.11.2026, 20:49 UTC; точечный purge работает, полная изоляция сайтов
упирается в общий CDN-ресурс.**

Цель: не сбрасывать кеш всех сайтов из-за одной правки.

- [~] Purge по hostname/site: MWS API принимает только пути внутри CDN-ресурса, без
  hostname. Ресурс общий, поэтому полная изоляция сайта этим API недостижима.
- [x] Purge только изменившихся путей: новые/изменённые HTML и обычные ассеты, без
  immutable-хешей.
- [x] Не считать ошибку purge ошибкой публикации или отката.
- [x] HTML остаётся `no-cache`, хешированные ассеты — `immutable` (Caddy уже настроен).

Что сделано:

- список путей строится по манифесту релиза, а не по всему `/*`;
- файлы с хешем в имени не чистятся вообще: у нового содержимого новый URL;
- при публикации сравниваются sha256 нового и предыдущего релиза, поэтому чистятся только
  реально изменившиеся пути;
- откат тоже очищает CDN по манифесту восстанавливаемого релиза;
- битый манифест или больше 100 путей — осторожный откат к `/*`;
- ошибка CDN не меняет статус релиза.

Остаётся структурное ограничение: один общий CDN-ресурс `hosting` не позволяет очистить
кеш только одного сайта. Одинаковый путь вроде `/` или `/index.html` у другого сайта тоже
станет MISS. Для полной изоляции нужен отдельный CDN-ресурс на сайт или cache key по Host,
это уже инфраструктурное решение, а не правка публикатора.

Файлы:

- `server/src/hosting/cdn-purge.ts`;
- `server/src/hosting/publisher.ts`;
- `server/src/hosting/caddy-config.ts`, `deploy/Caddyfile`;
- тесты.

Критерий: правка одного сайта не вызывает массовый `MISS` на остальных; после публикации
новый HTML и ассеты видны без ручной очистки. Сейчас выполнено частично: массовый purge
всего ресурса убран, но общие пути `/` и `/index.html` всё ещё общие для всех сайтов.

## 7. Инварианты

1. **Заказ не доверяет кешу.** Цена, наличие и сумма перечитываются в `orders`.
2. **Авторизация не кешируется.** Запросы с cookie/Authorization не попадают в общий кеш.
3. **Ошибка не кешируется.** 5xx и `no-store` не сохраняются.
4. **Публикация не ломает старый сайт.** Кеш сбрасывается после успешной фиксации релиза.
5. **Медиа не идёт через ВМ.** Только S3/CDN URL.
6. **Preview не становится production.** Отдельный executor, отдельные лимиты.
7. **Кеш можно выключить.** Один env-флаг возвращает текущее поведение без отката образа.
