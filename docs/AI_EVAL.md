# AI eval: методика и baseline

Дата: **15.11.2026**  
Статус: **каркас реализован; baseline ещё не снят**  
Связанный план: [`AI_AGENT_CAPABILITY_PLAN.md`](AI_AGENT_CAPABILITY_PLAN.md), этап 0.

## 1. Зачем нужен eval

Без воспроизводимого замера любое «улучшение агента» — вкусовщина. Eval отвечает на четыре
вопроса на одном и том же наборе задач:

1. Стало ли больше успешных задач, а не только красивее ответы?
2. Не выросли ли регрессии и вмешательства человека?
3. Во сколько обошлись токены, шаги и время?
4. Не сломался ли маленький сценарий (лендинг), пока улучшали большой?

Eval — не бенчмарк модели вообще. Он измеряет **продукт целиком**: модель, harness, контекст,
инструменты, проверку, флаги и окружение. Поэтому отчёт всегда привязан к commit, модели и
набору включённых флагов.

## 2. Что уже лежит в коде

| Модуль | Назначение |
|---|---|
| `server/src/agent/eval/types.ts` | Типы задачи, наблюдения, лимитов и отчёта |
| `server/src/agent/eval/tasks.ts` | Каталог из 36 задач и валидатор каталога |
| `server/src/agent/eval/runner.ts` | Таймауты, бюджеты, метрики, JSON/Markdown-отчёт |
| `server/src/scripts/agent-eval.ts` | CLI: список задач, проверка каталога, прогон через адаптер |
| `server/src/agent/features.ts` | Шесть фича-флагов, выключенных по умолчанию |

Runner не знает, как устроен проект и как запускается агент. Он владеет только тем, что должно
быть одинаковым между этапами: лимитами, таймаутами, пропуском задач и агрегацией метрик.
Подготовка workspace и запуск агента — ответственность адаптера.

## 3. Каталог задач

36 задач, по размерам из плана:

| Размер | Задач | Что проверяет |
|---|---:|---|
| `landing` | 8 | вёрстка, адаптивность, форма, SEO, тема, ассеты |
| `mvp` | 8 | auth, CRUD, API, миграции, поиск, загрузка, письма, состояния |
| `large` | 8 | рефакторинг, кросс-файловый баг, сквозная функция, миграция, API v2, performance, тесты, authz |
| `monorepo` | 6 | общий тип, новый пакет, порядок сборки, граница пакетов, проверки, обновление зависимости |
| `real` | 6 | задачи на репозитории NestDev: домены, preview, инструмент агента, БД, SEO, storage |

Задача содержит пользовательский prompt без подсказок по реализации, команды проверки, размер,
ожидаемые файлы (мягкая подсказка для отчёта) и лимит времени. `repo: "eval://..."` — это
идентификатор, который разрешает адаптер: локальная фикстура, checkout open-source проекта или
рабочая копия NestDev.

Задачи не удаляются после падения. Если задача стала нестабильной, это фиксируется в отчёте и
разбирается отдельно; «убрать мешающую задачу» — не способ поднять success rate.

## 4. Как считается результат

Адаптер возвращает `EvalObservation`:

```ts
type EvalObservation = {
  ok: boolean;
  testsPassed?: boolean;
  regressions?: number;
  filesChanged?: string[];
  interventions?: number;
  steps?: number;
  tokens?: { input: number; output: number; cached?: number };
  costUsd?: number;
  contextTrims?: number;
  cacheHitRate?: number;
  error?: string;
};
```

`ok` — единственный источник pass/fail. Runner не пытается угадать результат по выводу команды:
это делает адаптер, который знает, что именно проверялось. `testsPassed` и остальные поля нужны
для диагностики и метрик, а не для повторного решения.

Runner считает:

- **success rate** — успешные / выполненные (пропущенные не занижают и не завышают);
- **время** — сумма, среднее, p50 и p95;
- **токены** — вход, выход, кэш и сумма;
- **стоимость** — сумма `costUsd`;
- **шаги** — сумма и среднее;
- **тесты** — сколько наблюдений с отчётом о тестах были зелёными;
- **файлы** — сколько путей изменили задачи;
- **регрессии**, **вмешательства человека**, **сжатия контекста**;
- **cache hit rate** — среднее по задачам, где адаптер его измерил;
- **разбивку по размерам** — чтобы улучшение large не прятало падение landing.

## 5. Лимиты и kill switch

| Лимит | По умолчанию | Смысл |
|---|---:|---|
| `maxTasks` | 40 | не запускать больше задач за прогон |
| `maxDurationMs` | 1 час | остановить suite по общему времени |
| `maxCostUsd` | $10 | остановить suite по cumulative cost |
| `maxTotalTokens` | 5 000 000 | остановить suite по токенам |
| `taskTimeoutMs` | 10 минут | максимум на одну задачу; больше 10 минут запрещено |

Остановка не выдаёт пропущенные задачи за успешные: они попадают в отчёт как `skipped`, а
`stoppedReason` называет причину (`max-tasks`, `duration`, `cost`, `tokens`, `aborted`).
Внешний `AbortSignal` — операторский kill switch: после него новые задачи не стартуют.

## 6. Запуск

Проверить каталог (не запускает модель, безопасно в CI):

```bash
npm run agent:eval --workspace=server
```

Показать задачи:

```bash
npm run agent:eval --workspace=server -- --list
```

Прогнать через адаптер:

```bash
npm run agent:eval --workspace=server -- \
  --adapter ./eval-adapter.mjs \
  --size large \
  --out /tmp/nestdev-eval
```

Адаптер — ES-модуль, который экспортирует `adapter` (или `default`) с сигнатурой
`(task, { signal, timeoutMs }) => Promise<EvalObservation>`. Он сам готовит workspace, запускает
агента и проверяет результат. В отчёт не должны попадать ключи, `.env`, полные транскрипты и
содержимое секретных файлов.

Отчёт пишется в `eval-report.json` и `eval-report.md` (или в путь `--out`). Код возврата `1`,
если есть хотя бы одна упавшая задача; пропущенные задачи сами по себе код возврата не меняют.

## 7. Baseline: правила съёма

Baseline ещё не снят: для него нужен адаптер к реальному агенту и подготовленные репозитории
(см. открытые вопросы в плане). Нельзя подменять baseline прогоном на fake-адаптере — такой
отчёт выглядит зелёным и ничего не говорит о продукте.

Когда адаптер появится, baseline снимается так:

1. Один и тот же commit, одна и та же модель, один и тот же набор флагов (на старте — все
   выключены), один и тот же набор репозиториев.
2. Три прогона каждой задачи; в отчёт идёт медиана, а разброс (min/max) сохраняется.
3. Сначала все 36 задач, затем отдельные срезы `landing`, `mvp`, `large`, `monorepo`, `real`.
4. Упавшая задача остаётся в наборе; причина разбирается, а не скрывается.
5. Отчёт прикладывается к PR/релизу вместе с commit SHA и датой.

Шаблон вывода:

```text
commit: <sha>
model: <точное имя>
flags: AGENT_* = 0
date: <ISO>
runs: 3, median
landing:  __/8
mvp:      __/8
large:    __/8
monorepo: __/6
real:     __/6
success:  __%
p50/p95:  __ / __
cost:     $__
```

## 8. Живой адаптер: `--live`

Дата: **27.11.2026, 23:40 UTC**.

`--live` — не заглушка и не отдельный «тестовый агент». Каждая задача поднимает временный проект,
наполняет его каталог фикстурой `eval://…`, запускает настоящий `AgentRuntime` (тот же промт, тот же
каталог инструментов, та же авто-проверка) на модели платформы из админки и затем проверяет
результат командами самой задачи (`verify`) плюс скрытым чекером. Проект, его предпросмотр и
каталог удаляются после задачи.

```bash
# на сервере, из каталога данных (там же, где работает API: /app)
node server/dist-eval/scripts/agent-eval.js --live --size landing --out /tmp/eval
```

Флаги: `--task <id>` (можно несколько), `--size`, `--user <id|email>` (по умолчанию первый аккаунт),
`--plan free|pro|team` (по умолчанию `pro`), `--command-timeout-ms`, `--keep-projects`,
`--timeout-ms`, `--duration-ms`.

Требования к процессу, который запускает `--live`:

- рабочая директория — та же, что у API (иначе панельные ключи ищутся не в том `WEBNESTDEV_DATA_DIR`
  и запрос уходит на устаревший env-ключ);
- `initializeStorage()` и `loadPlatformEnv()` выполняются самим CLI;
- импортирован `tools/register.ts` — без регистрации инструментов модель получает запрос без `tools`
  и просто рассказывает, что собирается сделать;
- в каталоге сборки лежат `functions/*.mjs` (`preview-runtime.mjs`, `preview-supervisor.mjs`,
  `worker.mjs`): штатный Dockerfile копирует их рядом с `dist`, и без них авто-предпросмотр падает
  с `ENOENT`.

`ok` задачи = запуск не упал + все команды `verify` вернули 0 + скрытый чекер (если он есть) прошёл.
Отдельной строкой отчёта идёт политика `mustCall`/`mustNotCall` по фактическим вызовам; `mustCall`
проверяется по всему прогону, а не по первому шагу.

Фикстуры и их покрытие каталога лежат в `server/src/agent/eval/live/fixtures/`; задачи без
фикстуры `--live` не запускает и печатает их список — они не считаются ни успешными, ни
пропущенными по ошибке. Скрытые чекеры (`live/checks.ts`) пишутся в проект только после работы
агента: модель не может их прочитать и подстроиться.

## 9. Гейт этапа 0

Этап 0 считается закрытым только когда:

- [x] каталог 30–40 задач и валидатор;
- [x] runner, таймауты, бюджеты, JSON/Markdown-отчёт;
- [x] фича-флаги выключены по умолчанию;
- [x] CLI и точечные тесты runner/флагов;
- [ ] baseline по всем размерам на реальном агенте;
- [ ] прогон в CI (хотя бы catalog-check + runner-тесты, затем ночной eval).

Пока два последних пункта открыты, этап 0 — **каркас**, а не закрытый этап. Следующий шаг —
адаптер к реальному агенту и фикстуры/репозитории для baseline; только после него можно
сравнивать этап 1 с честным «до».
