# Клиентские базы данных: поэтапный план

Дата: 18.11.2026, 12:39 UTC (2026-11-18T12:39:42Z). Обновлено: 18.11.2026, 16:25 UTC.
Статус: код выкачен на production 18.11.2026, 16:18 UTC; кластер и провижининг проверены
живым smoke-тестом. Фича включается только при заданных `CLIENT_DB_ADMIN_URL` и
`CLIENT_DB_PUBLIC_HOST`; в текущем `.env` их нет, поэтому маршрут отвечает 503.

Документ описывает, как выдать клиентам платформы свою базу данных так, чтобы это работало на
3000+ проектов и не стоило лишних денег. Числа себестоимости — оценки по тарифам MWS на 18.11.2026;
точные суммы подтверждаются в консоли при создании ресурсов.

## 1. Решение

**Одна база PostgreSQL, схема на аккаунт.** Не база на аккаунт и не кластер на аккаунт.

- На аккаунт создаётся схема `tenant_<accountId>` и роль `tenant_<accountId>` с
  `search_path = tenant_<id>, public`.
- Клиент получает обычный `DATABASE_URL` вида `postgres://tenant_<id>:…@db.nestdev.ru:6432/app`.
  Код проекта ничего не знает про схемы: `search_path` приходит из роли.
- Создавать объекты в `public` клиентской роли запрещено: расширения ставит платформа
  (`pgcrypto`, `uuid-ossp`, `citext`, `pg_trgm`), они общие для всех схем одной базы.
- Квоты тарифа считаются по данным схемы, а не по размеру инстанса.

Почему не база на аккаунт:

- у MWS Managed PostgreSQL жёсткий лимит **100 баз на кластер** и **3000 пользователей на кластер**;
  на 3000 аккаунтов это 30 кластеров при квоте проекта в 3 кластера и 64 vCPU;
- модель «схема на аккаунт» одинаково работает на своём PostgreSQL и на managed, поэтому переезд
  позже не превращается в переделку;
- на 3000 схем каталог базы растёт на десятки мегабайт, а не на 21 ГБ копий `template1`;
- один `pg_dump -n tenant_<id>` вместо дампа целой базы на каждого клиента.

## 2.1. Целевые машины production и текущий стенд

Это описание плановой конфигурации, а не значения в конфигурации приложения: числа ниже ничего
не включают и не проверяют в коде.

| | Сейчас (стенд для разработки) | Production (план) |
|---|---|---|
| `node-1` | 2 vCPU / 4 ГБ | **4 vCPU / 8 ГБ**, primary |
| `node-2` | 2 vCPU / 4 ГБ | **2 vCPU / 16 ГБ**, standby и preview |
| Диск на ноду | 19 ГБ том | **50 ГБ** |
| Gluster | replica 2 | replica 2 → полезно **50 ГБ**, а не 100 |
| Клиентский PostgreSQL | не развёрнут | отдельный инстанс на локальном диске, не на Gluster |

Текущие маленькие машины — для разработки и проверок. Production по плану — машины выше; это
ориентир для расчётов ёмкости, а не жёстко заданная конфигурация.

Бюджет `node-1` (8 ГБ): ОС и Docker 0,8–1,0; API 0,5–0,7; Caddy, HAProxy, egress, runner,
`db_proxy` 0,3; платформенный PostgreSQL 0,8; клиентский PostgreSQL с `shared_buffers` 1 ГБ
1,4–1,6; два preview 0,8–1,4; Gluster 0,3. Итого 5,0–6,1 ГБ — запас 2–3 ГБ на page cache.

`node-2` (16 ГБ) по памяти свободна, ограничение — 2 ядра: не держать на ней больше одного
контейнерного preview; после failover API на ней будет вдвое медленнее, это принятое
ограничение старта.

Диск 50 ГБ на ноду: ОС и образы 8–12 ГБ, данные PostgreSQL 3–5 ГБ, остальное (~30 ГБ) — проекты
и хостинг. Ориентир: 200–400 проектов и 100–300 клиентских баз без расширения. Пороги: диск
> 70 % (≈35 ГБ), клиентских баз > 300, свободная RAM < 500 МБ, CPU `node-1` > 70 % за 15 минут.

## 3. Архитектура

```text
serverless-функция (контейнер проекта)
        │ TLS, DATABASE_URL
        ▼
PgBouncer (transaction pooling, auth_query)  :6432
        │
        ▼
PostgreSQL primary  ──streaming──▶  standby
        │                              │
        └──── WAL / PITR в S3 ─────────┘
```

| Компонент | Ответственность | Где живёт |
|---|---|---|
| `provisioning.ts` | создать схему, роль, вернуть URL; идемпотентно | API |
| `schema-size.ts` | размер схемы и решение о квоте | API, раз в сутки |
| backup job | `pg_dump -n` с реплики, ретенция, восстановление | API/воркер |
| PgBouncer | пул соединений, TLS, лимит на пользователя | рядом с базой |
| PostgreSQL | данные, роли, права | пилот — `node-1`; далее выделенная пара ВМ |
| `db_proxy.py` | стабильная цель HAProxy при переезде | `deploy/ha/` |

**Решение 18.11.2026:** клиентская база разворачивается на общих дисках `node-1` и `node-2`
(50 ГБ на ноду), второй кластер PostgreSQL с потоковой репликацией и автоматическим promotion.

### Этап 0. Проверки и закрытие сети (1–2 дня, 0 ₽)

Цель: убедиться, что функция вообще может дойти до базы, и не открыть при этом внутреннюю сеть.

Работы:

1. Из контейнера в `bridge` проверить доступ к `10.0.0.x:6432` и к внутренним API платформы.
   Ожидание: доступ есть — это и есть дыра, которую надо закрыть.
2. Ввести сеть `webnestdev-functions` и правила `DOCKER-USER`: разрешены только PgBouncer на
   `:6432` и egress-прокси на `:3128`, остальное `REJECT`.
3. Расширить egress-правила: исключение для адреса PgBouncer и порта 6432 (сейчас прокси
   пропускает только 80/443).
4. Замерить: свободная память узла после 2 preview, время `pg_dump` тестовой схемы.

Приёмка: из функции открывается соединение с PgBouncer; `example.com` и внутренние API
недоступны; существующие функции не сломались.

Риск: смена сети функций — изменение поведения для всех проектов. Откат: вернуть `bridge` и снять
правила одной командой (`egress-firewall.sh clear`).

### Этап 1. Пилотный инстанс (2–3 дня, 0 ₽)

Цель: рабочая база без новых расходов, на которой проверяется вся модель.

Работы:

- отдельный инстанс PostgreSQL на `node-1` (свой том, свой пароль, порт 5433) — **не** база
  `webnestdev` и не общий кластер платформы;
- PgBouncer перед ним: `pool_mode=transaction`, `auth_query`, `max_user_connections=2`,
  `server_idle_timeout=30`, `default_pool_size=25`;
- standby на `node-2` по той же схеме, что у платформенной базы;
- `statement_timeout` и `idle_in_transaction_session_timeout` на роли клиента;
- 1–3 тестовых аккаунта, ручная выдача схемы.

Приёмка: проект читает и пишет данные из функции по `process.env.DATABASE_URL`; роль не видит
чужую схему; перезапуск standby не рвёт данные.

Риск: память `node-1` делится с preview и API. Пилот ограничен 200–300 тенантами, дальше — этап 5.

### Этап 2. Провижининг и выдача URL (3–5 дней, 0 ₽)

Цель: клиент получает базу кнопкой, без ручных действий.

Работы:

- `server/src/database/provisioning.ts`: `CREATE SCHEMA`, `CREATE ROLE`, `GRANT`, отзыв
  `CREATE ON SCHEMA public`, установка `search_path` на роль; повторный вызов возвращает то же;
- запись URL в зашифрованное хранилище проекта — существующим механизмом (`database.env` уже
  умеет `DATABASE_URL`, менять рантайм не нужно);
- маршрут `POST /api/projects/:id/database` и кнопка «Подключить базу NestDev» в
  `src/features/database/DatabaseConnect.tsx`;
- удаление: отзыв роли сразу, `DROP SCHEMA` через 7 дней;
- тесты рядом с модулями: провижининг, идемпотентность, изоляция схем.

Приёмка: новый проект получает базу за один запрос; функция сразу видит `DATABASE_URL`; повторное
нажатие не создаёт вторую схему.

### Этап 3. Квоты и защита от шумных соседей (3–4 дня, 0 ₽)

Цель: лимит тарифа нельзя превысить и он не роняет соседей.

Работы:

- `schema-size.ts`: сумма `pg_total_relation_size` по `pg_class` схемы; раз в сутки; на 90 % —
  предупреждение в интерфейсе, на 100 % — `ALTER ROLE … SET default_transaction_read_only=on`;
- лимиты на роль: `statement_timeout` (например 10 с), `idle_in_transaction_session_timeout`,
  `temp_file_limit`, `work_mem`;
- PgBouncer: `max_user_connections`, `max_db_connections`, очередь ожидания;
- запрет `CREATE EXTENSION`, `pg_read_file`, суперпользователя;
- `search_path`-изоляция проверяется тестом: роль `tenant_a` не читает `tenant_b`.

Приёмка: тенант, заливший квоту, получает понятный отказ и режим read-only; соседние тенанты
не деградируют; 3000 ролей проходят прогон через PgBouncer без исчерпания `max_connections`.

### Этап 4. Бэкапы, восстановление, удаление (3–4 дня, ~50–300 ₽/мес S3)

Работы:

- ночной `pg_dump -Fc -n tenant_<id>` **с реплики**, 4 параллельных потока, ретенция 7 дней
  (30 — по запросу);
- проверка восстановления раз в неделю на одном случайном тенанте в отдельную схему;
- сценарий «клиент удалил аккаунт»: дамп сохраняется 7 дней, затем удаляется вместе со схемой;
- метрики: длительность дампа, размер, ошибки.

Приёмка: восстановление одного тенанта не требует остановки базы; дамп 1000 схем укладывается
в ночное окно; удаление аккаунта не оставляет данных.

### Этап 5. Выделенная пара ВМ и переезд (3–5 дней, ≈17 800 ₽/мес)

Цель: клиентские данные перестают делить узлы с preview.

Работы:

- две ВМ gen-4-16 (primary/standby) в той же приватной сети, свой диск;
- перенос: `pg_dump`/`pg_restore` по схемам, сверка количества строк, переключение цели в
  `db_proxy.py`; `DATABASE_URL` клиентов не меняется, потому что endpoint стабильный;
- мониторинг: соединения, диск, топ тенантов по размеру, медленные запросы, отставание реплики.

Приёмка: переезд на копии при нулевом даунтайме записи (переключение в окно < 1 мин); после
переезда старый инстанс выключен, данные сверены.

### Этап 6. 3000+ и эксплуатация (постоянно, ≈40–55 000 ₽/мес)

Работы:

- шардирование по хэшу аккаунта: второй шард при >1500 тенантов или >70 % диска;
- PgBouncer на каждый шард, endpoint выбирается при провижининге и хранится в проекте;
- PITR на уровне кластера + дампы на тенанта; учебное восстановление раз в квартал;
- алерты: соединения >70 %, диск >70 %, ошибки дампов, рост медленных запросов.

Приёмка: потеря одной ноды не теряет данные; клиентские URL не меняются при добавлении шарда.

## 5. Тарифы и экономика

| Модель | Себестоимость на 3000 | Комментарий |
|---|---|---|
| Кластер на аккаунт (managed) | ≈3 900 000 ₽/мес | не рассматривать |
| Второй PostgreSQL на существующих нодах, общий диск | **0 ₽/мес** | до 200–300 клиентских баз |
| Второй PostgreSQL на отдельном диске 50 ГБ | **≈930 ₽/мес** (диск 446 + 2000 IOPS 488) | если нужна изоляция данных по диску |
| Своя пара ВМ gen-2-8, 100 ГБ | ≈11 300 ₽/мес → **≈4 ₽ на аккаунт** | первый шаг после узлов |
| Своя пара ВМ gen-4-16, 100 ГБ | ≈17 800 ₽/мес → **≈6 ₽ на аккаунт** | рекомендуемый вариант с запасом |
| Managed HA, схема на аккаунт | ≈31 000 ₽/мес → ≈10 ₽ на аккаунт | если не хотим администрировать PostgreSQL |

Предлагаемые квоты: «Плюс» — 128 МБ, «Премиум» — 512 МБ на аккаунт. При 3000 аккаунтов и полном
заполнении это 384 ГБ — верхняя граница; планировать диск на 500 ГБ, а не на 150 ГБ.

Базу можно включить в тариф без роста цены: 6–10 ₽ на аккаунт — это доли процента от 990 ₽.
Отдельная платная опция «выделенный кластер» имеет смысл только по цене от 9 000 ₽/мес.

## 6. Чего не делать

- Не создавать managed-кластер на клиента — убыточно в 4 раза уже на «Премиуме».
- Не использовать базу `webnestdev` для клиентских данных: там сессии, платежи и служебные таблицы.
- Не давать клиенту суперпользователя, `CREATE EXTENSION` и доступ к `public`.
- Не делать `pg_dump` всей базы на каждого клиента и не запускать дампы на primary в пик.
- Не включать базу всем проектам при создании: 70 % проектов её не откроют, а схемы займут место.
- Не переносить клиентские данные на `node-2` как на единственный узел.

## 7. Риски

| Риск | Проявление | Снижение |
|---|---|---|
| Исчерпание соединений | 500 при массовом всплеске вызовов | PgBouncer, `max_user_connections`, очередь, алерт |
| Шумный сосед | один тенант грузит CPU/IOPS | `statement_timeout`, `temp_file_limit`, лимиты роли, топ-тенанты в мониторинге |
| Ошибка в `search_path` | тенант видит чужую схему | `ALTER ROLE … SET search_path`, отзыв прав, тест изоляции |
| Дампы не успевают | окно бэкапа > ночи | дамп с реплики, параллельность, инкрементальный сценарий для крупных |
| Переезд ломает URL | клиенты теряют базу | стабильный endpoint `db_proxy`, переключение цели без смены строки |
| Лимит 100 баз у managed | нельзя перейти на managed «как есть» | модель «схема на аккаунт» выбрана заранее |

## 8. Чек-лист перед выкаткой

- [ ] соединение из контейнера функции до PgBouncer проверено на живой системе;
- [ ] внутренние адреса платформы из контейнера функции недоступны;
- [ ] роль не читает чужую схему (тест);
- [ ] квота переводит в read-only и возвращает понятный текст;
- [ ] дамп и восстановление одного тенанта проверены;
- [ ] `pg_dump` 1000 схем укладывается в ночное окно;
- [ ] PgBouncer держит 3000 пользователей без роста `max_connections` выше предела;
- [ ] удаление аккаунта удаляет схему, роль и дампы;
- [ ] выкатка не меняет `DATABASE_URL` существующих внешних баз.

проверены на живом кластере в 16:24 UTC: созданы временная схема и роль, PgBouncer принял
подключение по паролю, `search_path` указывает на схему тенанта, запись в `public` и чтение
чужой схемы запрещены; тестовые объекты удалены. В контейнер сервера настройки теперь
передаются через override обеих нод, но без `CLIENT_DB_ADMIN_URL` фича остаётся выключенной.

| Что | Где |
|---|---|
| Лимиты базы в тарифах: 0 / 128 МБ / 512 МБ | `server/src/account/plans.ts` (`databaseBytes`, `databaseLimitFor`) |
| Конфиг фичи, выключен без адресов | `server/src/database/client-db/config.ts` |
| Имена схем, DDL, учётная таблица, SQL размера | `server/src/database/client-db/sql.ts` |
| Создание схемы и роли, размер, read-only | `server/src/database/client-db/provision.ts` |
| Выдача URL в секреты проекта, статус, отключение, job квот | `server/src/database/client-db/service.ts` |
| Маршруты `GET/POST/DELETE /api/projects/:id/client-database` | `server/src/routes/database.ts` |
| Скрипт ежедневной проверки квот | `server/src/scripts/client-db-quota.ts` |
| Кластер, репликация, PgBouncer, failover, бэкап | `deploy/ha/client-db/` |
| Агент знает квоту базы своего тарифа | `server/src/agent/plan-brief.ts` |
| Инструмент агента `database.client`: `status` / `provision` / `disable` | `server/src/tools/client-database-tools.ts` |

Как включается: в окружении сервера задаются `CLIENT_DB_ADMIN_URL`, `CLIENT_DB_PUBLIC_HOST`,
опционально `CLIENT_DB_PORT` (по умолчанию 6432), `CLIENT_DB_NAME` (по умолчанию `app`),
`CLIENT_DB_SSL=0` для локальной проверки без TLS. Без двух первых переменных маршрут отвечает
503 `CLIENT_DATABASE_NOT_CONFIGURED`, а тарифная карточка и агент продолжают работать как раньше.

Проверки этой части: 34 точечных теста (`client-db/*.test.ts`, `client-database-tools.test.ts`
и `plan-brief.test.ts`),
7 тестов политики failover (`deploy/ha/client-db/test_failover.py`), `bash -n` скриптов,
`python3 -m py_compile`, `tsc -p server/tsconfig.json --noEmit` — без ошибок.

Живой прогон 18.11.2026 (15:15–15:25 UTC): кластер поднят на обеих нодах, потоковая
репликация и PgBouncer работают; остановка primary → promotion standby за ~30 с, запись
через PgBouncer прошла; rejoin вернувшейся ноды — standby с теми же данными; обратный
переход primary на `node-1` — за ~50 с. Найдено и исправлено: `pg_hba` без адреса соседа,
`auth_file` PgBouncer, слот на новом primary, кавычки в `ALTER ROLE`, а главное — promotion
по ошибке авторизации (теперь `unknown` не продвигает, только сетевая недоступность).

Сознательно не сделано: включение фичи в production `.env`, egress из контейнера функций,
загрузка дампов в S3 (сейчас только локальный каталог и хук), PITR для клиентских схем и
автоматический rejoin вернувшейся ноды. Следующий шаг — задать `CLIENT_DB_ADMIN_URL`
(через PgBouncer, ведущий на текущий primary) и проверить маршрут на тестовом аккаунте.
