Дата: **15.11.2026**  
Статус: **этапы 0–3 в работе: карта, тесты, память и milestone-режим за флагами; baseline/canary открыты**  
Основание: разбор текущего агентского контура и публичных данных по AI-агентам на ноябрь 2026.  
Связанные документы: [`AI_EVAL.md`](AI_EVAL.md), [`AI_REPO_MAP.md`](AI_REPO_MAP.md), [`PLATFORM_AI.md`](PLATFORM_AI.md),
[`PRODUCTION_STATE.md`](PRODUCTION_STATE.md), [`SEO_PLATFORM_PLAN.md`](SEO_PLATFORM_PLAN.md).

## 0. Как читать этот документ

Это не описание уже сделанного, а **поэтапный план производства**. Каждый этап имеет:

- цель и границы;
- конкретные артефакты и модули;
- критерии приёмки, которые можно проверить;
- production-гейт: без него этап не выкатывается;
- оценку и зависимости.

Правило: **нельзя начинать следующий этап, пока предыдущий не прошёл свой гейт**. Исключение —
этап 0 (измерение), он идёт параллельно с проектированием.

## 1. Честное определение цели

«8–9/10 для огромного проекта» в этом документе означает:

> **8–9/10 = ИИ + harness + тесты + человек-архитектор на границах.**  
> Агент сам находит нужный код, делает изменение, запускает релевантные проверки,
> объясняет риски и оставляет ревьюируемый diff. Человек утверждает архитектуру,
> необратимые миграции и продуктовые компромиссы.

Это не «модель полностью автономно ведёт монорепо». По публичным данным 2026 года
полностью автономный агент на 1M+ строк с кросс-модульными изменениями не даёт 8–9.
Реалистичная цель:

| Возможность | Сейчас | Цель | Режим |
|---|---:|---:|---|
| Лендинг/сайт с нуля | 9 | 9 | автономно |
| MVP с БД, auth, платежами | 6 | 9 | автономно с ревью |
| Большой проект, локальная задача | 5 | 8–9 | автономно с тестами |
| Сквозные изменения в большом проекте | 2 | 8 | с человеком-архитектором |
| Монорепо 1M+ строк | 1 | 8 | с человеком; автономно 6–7 |

Если нужен «полностью автономный 9/10 на монорепо» — это исследовательская задача
не на 6 месяцев; текущие публичные бенчмарки этого не подтверждают.

### Что уже является сильной стороной

- Планировщик физически не может менять проект.
- Секреты не попадают в контекст.
- Набор инструментов ограничен на запуск — экономия промпта.
- Проверка встроена в цикл: typecheck → build → Preview → HTTP/SSR → браузер.
- Есть рабочая память, дайджест и checkpoint.
- Есть production-обвязка: sandbox, Preview, деплой, домены, БД, секреты.

### Что ограничивает большие проекты

- Карта репозитория и граф импортов есть только за флагом `AGENT_REPO_MAP`; baseline/canary и 100k LOC ещё не пройдены.
- Нет полноценного тестового контура и анализа затронутых тестов.
- Один агент-писатель; разведчик только читает.
- 40 шагов и 250k контекста — не «поставил задачу на сутки».
- Память живёт в заметках, а не в архитектуре.
- Проверка smoke-level, а не матрица продукта.
- Нет monorepo/toolchain поддержки.
- Нет eval на больших репозиториях — улучшения нельзя измерять.

## 3. Целевые KPI

Baseline фиксируется на этапе 0. Цели:

| Метрика | Цель |
|---|---:|
| Успех на задачах 100k LOC (тесты + acceptance) | ≥80% |
| Успех на scoped-задачах 1M LOC с ревью | ≥70% |
| Регрессии на принятых изменениях | <2% |
| Вмешательства человека на задачу | ≤0,5 |
| Стоимость успешной задачи | −30% к baseline |
| Время задачи 3–10 файлов | ≤30 минут |
| Reviewer catch rate на внедрённых дефектах | ≥50% |
| Покрытие индекса исходников | ≥95% |
| Тесты для изменённых модулей | ≥80% |
| Критичные инциденты после canary | 0; rollback <5 минут |

## 4. Принципы

1. **Сначала измерение, потом улучшение.** Без eval любая оптимизация — вкусовщина.
2. **Не гнаться за 1M контекста.** 1M окно не равно 1M понимания; нужны карта, поиск,
   декомпозиция.
3. **Тесты — главный предохранитель.** Сборка и Preview доказывают запуск, но не отсутствие
   регрессий.
4. **Каждый этап — фича-флаг, fallback и откат.**
5. **Не ломать маленькие сайты.** Текущие 9/10 для лендингов — конкурентное преимущество.
6. **Человек остаётся на архитектуре и рискованных решениях.**
7. **Размер файлов.** Новые модули — небольшие, с одной ответственностью; не добавлять
   крупные блоки в `agent-runtime.ts` и другие большие файлы.

## 5. Этапы

### Этап 0. База, eval и предохранители — 1–2 недели

**Цель:** измерить текущее состояние и получить безопасную выкатку.

**Артефакты:**

- `docs/AI_EVAL.md` — методика и набор задач.
- `server/src/agent/eval/` — runner, отчёты, метрики (не в пользовательском пути).
- 30–40 задач:
  - 8 — лендинг/сайт (0,2–2k строк);
  - 8 — MVP (10–30k);
  - 8 — большое приложение (100–200k);
  - 6 — монорепо/несколько сервисов (300k–1M);
  - 5–10 — задачи на реальном репозитории NestDev (с разрешением).
- Метрики: успех, тесты, регрессии, файлы, токены, стоимость, время, вмешательства,
  обрезка контекста, cache hit.
- Фича-флаги: `AGENT_REPO_MAP`, `AGENT_TEST_RUNNER`, `AGENT_ARCH_MEMORY`,
  `AGENT_MILESTONES`, `AGENT_REVIEWER`, `AGENT_MULTI_WRITER`, `AGENT_MODEL_ROUTER`.
- Kill switch и лимиты стоимости.

**Приёмка:**

- [ ] Baseline-отчёт по всем размерам (нужен адаптер и репозитории).
- [ ] Eval запускается одной командой и в CI: команда и catalog-check есть, CI-прогона пока нет.
- [x] Флаги выключены по умолчанию; поведение не меняется.
- [x] Есть откат: выключить флаг → старый путь.
- [x] Нет замера дольше 10 минут без явного разрешения (runner отклоняет больший лимит).

**Оценка:** 1 инженер, 1–2 недели.

### Этап 1. Карта репозитория и поиск — 4–6 недель

**Цель:** агент видит структуру большого проекта, а не 500 случайных записей.

**Новые модули** (несколько небольших файлов, не один общий):

- `server/src/agent/repo-index/scan.ts` — обход с игнором `node_modules`, `dist`, `.git`,
  секретов, symlink, лимитами и fingerprint — **реализовано**.
- `parse-ts.ts` — TypeScript Compiler API (уже есть `typescript`). — **изменено:** `parse.ts`
  на консервативных regex: в production-образе `typescript` не установлен (`npm ci --omit=dev`),
  а тащить компилятор в рантайм нельзя. Точная карта символов остаётся у `fs.outline`.
- `parse-python.ts` — Python AST/tree-sitter; fallback на `python -m ast`. — **пока regex**
  для relative-импортов и top-level символов.
- `graph.ts` — импорты, экспорты, символы, маршруты, тесты, скрипты пакетов. — **частично:**
  импорты, экспорты, workspace-пакеты, entrypoints и тесты в `build.ts`/`query.ts`.
- `store.ts` — `.webnestdev/index/repo.json` или SQLite; атомарная запись, версия схемы,
  lock, rebuild при повреждении. — **файловый кэш** `.webnestdev/repo-index.json`, атомарная
  запись, fingerprint; SQLite/lock — следующий шаг.
- `rank.ts` — ранжирование: совпадение с задачей + импорты + тесты + недавность + entrypoint. —
  **реализовано** в `query.ts` без недавности.

**Инструменты:**

- `repo.map` — карта модулей/пакетов/точек входа, бюджет 15–20k символов.
- `repo.find` — поиск по символу, маршруту, тесту, пакету.
- [x] `fs.grep` получает `scope` (пакет/модуль), чтобы не искать по всему монорепо.
- [x] `context-builder.ts` добавляет сжатую карту; сырое дерево остаётся fallback.
- [x] `context-retrieval.ts` использует индекс, fallback — старый путь.

**Приёмка:**

- [x] 100k LOC: индекс <60 секунд, инкремент <5 секунд. — синтетический прогон 1 002 файла /
  100 000 строк: cold 475 мс, cache 438 мс, incremental 470 мс (`agent:index-bench`). Реальный
  репозиторий ещё проверить на canary.
- [ ] Нужный файл в top-10 в ≥80% eval-задач. — нужен baseline.
- [x] `repo.map` ≤20k символов, контекст не раздут: ответ ограничен `context-budget` (7k) и
  содержит только метаданные.
- [x] Секреты и symlink не попадают в индекс.
- [ ] 20+ тестов: парсеры, граф, повреждённый индекс, параллельная запись. — сейчас 20
  точечных тестов (scan/parse/build/query/repo-tools); параллельной записи и SQLite нет.
- [x] Флаг `AGENT_REPO_MAP`; canary на внутренних проектах — **не включён**, поэтому canary
  ещё не проводился.
- [x] Fallback: индекс недоступен → старое лексическое поведение.

**Оценка:** 2 инженера, 4–6 недель.

### Этап 2. Тесты, affected tests и матрица проверок — 3–4 недели

**Цель:** агент проверяет поведение, а не только сборку.

**Статус:** каркас начат; `test-impact` и `project.test` есть за флагом `AGENT_TEST_RUNNER`,
тесты встроены в автоматическую проверку после сборки. Детали — [`AI_TEST_RUNNER.md`](AI_TEST_RUNNER.md).

**Артефакты:**

- [x] `server/src/tools/test-tools.ts`:
  - `project.test`: определяет пакетный менеджер и тестовый скрипт (`npm test`, pnpm, yarn,
    bun, pytest); не ставит пакеты; таймаут 5 минут; хвост вывода; парсинг упавших тестов;
    `not_configured`, если тестов нет. Авто-вызов подключён после сборки.
  - [x] `onlyAffected`: безопасное дописывание путей для Vitest/Jest/node --test/pytest;
    неизвестный скрипт, watch-режим и пути вне cwd дают полный набор.
- [x] `server/src/agent/test-impact.ts` — affected tests по графу импортов.
- [x] `verification-policy.ts` / `agent-runtime.ts`:
  - typecheck → build → tests → Preview → HTTP/assets → browser runtime → browser scenario;
  - fail fast, 3 попытки, затем остановка с понятной причиной;
  - checkpoint только после успешных проверок;
  - для крупных изменений — полный набор тестов на финализации. — тесты после сборки
    включаются флагом `AGENT_TEST_RUNNER`; проект без тестов даёт `not_configured`, а не
    ложное падение.
- Изоляция: sandbox, без секретов, маскирование `.env`.

**Приёмка:**

- [ ] Регрессии на eval снижены ≥50%.
- [ ] ≥70% задач запускают релевантные тесты.
- [ ] Нет тестов дольше лимита без разрешения.
- [ ] Рост токенов ≤20%.
- [ ] Тесты на таймауты, flaky, отсутствие тестов, падение тестов.
- [ ] Флаг `AGENT_TEST_RUNNER`; canary.

**Оценка:** 2 инженера, 3–4 недели.

reviewer с чистым контекстом и diff. Детали — [`AI_ARCH_MEMORY.md`](AI_ARCH_MEMORY.md),

**Память проекта:**

- [x] `ARCHITECTURE.md` — модули, границы, потоки данных, инварианты.
- [x] `DECISIONS.md` — решения и причины.
- [x] `CONTRACTS.md` — контракты API/БД/событий.

**Milestone-режим:**

- [x] `server/src/agent/orchestrator/milestones.ts` — 3–7 milestone’ов.
- [x] Каждый: scope, файлы, тесты, definition of done, оценка токенов.

- [x] Возобновление из persisted-плана после обрыва, перезагрузки и нового запуска.
- [ ] Явный бюджет на milestone: `estimatedTokens` показывается, но не обрывает расход.

**Reviewer-субагент:**

- [x] `server/src/agent/reviewer.ts` — read-only, чистый контекст, видит diff, тесты, инварианты.
- [x] Проверяет регрессии, контракты, секреты, опасные операции, отсутствие тестов.
- [x] Возвращает `pass/fail` + замечания; обязателен выше порога (>5 файлов или >200 строк).
- [ ] Отдельная модель/маршрут для ревью и замер ≥50% внедрённых дефектов.

**Приёмка:**

- [ ] 3–5 последовательных milestone’ов на eval без потери контекста.
- [ ] Resume после kill/перезапуска.
- [ ] Reviewer ловит ≥50% внедрённых дефектов.
- [ ] Память не расходится с кодом >10% на выборке.
- [ ] Флаги `AGENT_ARCH_MEMORY`, `AGENT_MILESTONES`, `AGENT_REVIEWER`; canary на платных тарифах.

**Оценка:** 2 инженера, 4–5 недель.

### Этап 4. Multi-agent и роутинг моделей — 6–8 недель

**Цель:** параллелить большие задачи и снизить стоимость.

**Роли:**

- Explorer — scout, расширенный картой и историей.
- Implementer — пишет изменения, свой контекст и бюджет.
- Tester — запускает проверки, анализирует падения.
- Reviewer — read-only, проверяет diff и инварианты.

**Изоляция:**

- Каждый implementer — отдельный worktree или copy-on-write sandbox.
- Merge только через патч + тесты; конфликты — явная ошибка.
- Максимум 2–3 писателя; общие файлы сериализуются.
- `server/src/agent/orchestrator/subagents.ts`, `merge.ts`.

**Оркестратор:**

- Декомпозиция по модулям/пакетам.
- Граф зависимостей задач; независимые — параллельно, затем интеграция.
- Финальный integration run: typecheck, build, tests, Preview, browser.

**Роутинг моделей:**

- Эвристика: план/архитектура/ревью → Max; механические правки → Mini.
- Автоэскалация после 2 неудачных проверок.
- Жёсткий бюджет на запуск и задачу; stop при превышении.

**Приёмка:**

- [ ] Multi-module eval: throughput ≥2× без роста регрессий.
- [ ] Конфликты merge <10%; каждый виден и разрешается явно.
- [ ] Стоимость успешной задачи −20% или лучше.
- [ ] Kill switch и лимиты на параллелизм.
- [ ] Аудит: кто что писал и какие инструменты вызывал.

**Оценка:** 2–3 инженера, 6–8 недель.

### Этап 5. Монорепо, toolchain и CI — 6–8 недель

**Цель:** довести 1M+ LOC и multi-service до 8/10 с человеком.

**Артефакты:**

- Monorepo detection: workspaces, Nx/Turborepo, pnpm/yarn workspaces; per-package карта.
- Package graph: зависимости, владельцы, тесты, сборки; `repo.map` на уровне пакетов.
- Custom runtime images для native-зависимостей; админское approval, не произвольный Docker.
- Service compose для локального запуска нескольких сервисов; Preview на сервис.
- CI-интеграция (read-only first): статусы GitHub Actions, падения тестов, логи.
- PR-создание — только явное действие пользователя (текущее правило push сохраняется).
- Производительность: шардирование индекса, инкрементальные обновления, кэш, лимиты.

**Приёмка:**

- [ ] Eval на 300k–1M LOC: scoped-задачи ≥70% с ревью.
- [ ] Индекс 1M LOC <2 минут, инкремент <15 секунд.
- [ ] Нет чтения всего репозитория в контекст.
- [ ] Стоимость и latency в SLO.
- [ ] Design partners, canary, rollback.

**Оценка:** 2–3 инженера, 6–8 недель.

### Этап 6. Hardening и непрерывный eval — постоянно

- Ночной прогон eval на 3 размерах репозиториев.
- Регрессионные gate: успех упал >5% или стоимость выросла >20% — не выкатывать.
- Observability: success rate, tokens, cost, test pass, context trims, cache hit,
  reviewer findings, human interventions.
- Chaos: битый индекс, таймаут тестов, 429 провайдера, обрыв, перезапуск, потеря lock.
- Prompt injection: файлы/README/тесты — данные, не команды; тесты на это.
- Security: секреты, path guard, межпроектная изоляция индекса и памяти.
- Runbook: зацикливание, скачок стоимости, ложное ревью.

Суммарно: **6–9 месяцев** до целевого состояния; первые 3 этапа дают основную часть роста.

## 7. Что не делаем

- Не увеличиваем контекст до 1M «потому что модель умеет».
- Не делаем embeddings основным поиском: сначала grep + граф, dense — только при precision
  выше порога.
- Не запускаем несколько писателей без изоляции и merge-протокола.
- Не считаем зелёную сборку доказательством корректности.
- Не включаем автономность без eval и kill switch.
- Не ломаем маленькие сайты и текущий production-flow.
- Не смешиваем этапы с текущими preview-правками: отдельные ветки, флаги, коммиты.

## 8. Риски и меры

| Риск | Мера |
|---|---|
| Индекс устарел/повреждён | hash + mtime + git SHA, атомарная запись, rebuild, fallback |
| Тесты flaky | retry 1 раз, quarantine, не блокировать на известном flaky, отчёт |
| Multi-agent конфликты | worktree, маленькие diff, сериализация общих файлов, integration run |
| Скачок стоимости | бюджет на задачу, router, cache, лимиты, kill switch |
| Prompt injection из репозитория | файлы — данные, не команды; тесты |
| Утечка между проектами | индекс и память только внутри проекта, path guard |
| Модель/провайдер изменился | provider abstraction, eval, canary, fallback |
| Медленный rollout | флаги, внутренние проекты → design partners → платные тарифы |

## 9. Production-гейт каждого этапа

Этап выкатывается только если выполнены все четыре:

1. **Код:** `tsc`, точечные тесты, интеграционные тесты, `npm run build` — без ошибок.
2. **Eval:** успех не упал, стоимость не выросла выше лимита, регрессии в норме.
3. **Безопасность:** секреты, path guard, межпроектная изоляция, prompt injection.
4. **Эксплуатация:** флаг, fallback, метрики, алерты, rollback, runbook.

Rollout: внутренние проекты → 5% → 25% → все платные → бесплатные (с урезанным лимитом).

## 10. Что останется за человеком

- Архитектурные границы и выбор технологий.
- Опасные миграции данных и необратимые операции.
- Продуктовые компромиссы и приоритеты.
- Финальное ревью критичных изменений.
- Юридические и security-решения.

Это не недоработка. Это то, что делает 8–9 production-оценкой, а не демо.

## 11. Открытые вопросы перед реализацией

1. **Eval-репозитории:** какие реальные проекты можно использовать (свои, клиентские,
   open-source) и на каких условиях.
2. **Индекс:** файл в проекте на Gluster или PostgreSQL; нужен ли отдельный сервис
   индексации для больших монорепо.
3. **Worktree:** `git worktree` или отдельные копии sandbox; как это переживает
   переключение узлов.
4. **Custom images:** кто и как approving образы для native-зависимостей.
5. **CI:** read-only интеграция с GitHub Actions на первом этапе; PR-создание — отдельное
   продуктовое решение.
6. **Модели:** какие Max/Mini используются для плана/ревью и правок; нужен ли
   автоматический router или ручной выбор на старте.
7. **План-лимиты:** как новые проверки и индексация влияют на кредиты и тарифы.
