## 0. Как читать этот план

1. Этапы идут **строго от лёгкого к тяжёлому**. Внутри этапа пункты тоже упорядочены.
2. Правило перехода: этап считается закрытым только после выкатки в прод, замера и записи
   результата. Не начинаем следующий, пока предыдущий не закрыт — иначе ошибки складываются.
   Исключение — отсутствие оборудования: можно готовить независимые от него части следующего
   этапа, но статус предыдущего не закрывается.
3. У каждого пункта есть критерий готовности. «Работает у меня» критерием не считается.
4. Каждый этап заканчивается обновлением документации и планом отката.
5. Оценка «сколько выдержит» берётся не из головы, а из `docs/SCALING_PLAN.md` §4 и замеров на
   реальных проектах.

### ✅ 2.1. gVisor (`runsc`) для контейнеров команд и превью (закрыт 30.10.2026)

**Зачем.** Сегодня контейнеры делят ядро с хостом. Брокер убрал «RCE в API = root на хосте», но
побег через уязвимость ядра остаётся. gVisor даёт контейнеру собственное песочное ядро в
пользовательском пространстве: до настоящего ядра доходят только проверенные вызовы.

**Почему не microVM сейчас.** Firecracker/Kata требует `/dev/kvm` (вложенная виртуализация), а
у Yandex Cloud её нет — это уже записано в `docs/PRODUCTION_DEPLOYMENT.md`; у MWS нужно
уточнять. Плюс нужен оркестратор, снапшоты и своя сеть. Это отдельный проект на месяцы, он
оправдан на 1000+ и bare-metal. gVisor даёт большую часть выгоды за малую часть работы.

**Что сделать:**

- поставить `runsc` на ВМ и зарегистрировать как Docker runtime; установка выполняется
  деплоем, терминал на ВМ не нужен;
- добавить выбор рантайма в `dockerRunArgs` (`SANDBOX_RUNTIME=docker|runsc`) и в контейнер
  предпросмотра;
- разрешить `Runtime: runsc` в политике брокера (`deploy/docker-broker/policy.mjs`), иначе
  `create` будет отклонён;
- прогнать матрицу: `node`, `npm install`, `git`, `npm run build`, `docker exec`, поиск порта по
  `/proc/net/tcp`, WebSocket/HMR, `--read-only` и `/tmp`;
- замерить время сборки и памяти до/после; записать цифры;
- включать постепенно: сначала один тип контейнеров, потом все; флаг для мгновенного возврата.

**Файлы:** `server/src/sandbox/docker/args.ts`, `server/src/preview/preview-runner.ts`,
`deploy/docker-broker/policy.mjs`, `docker-compose.yml`, тесты.

**Сделано (30.10.2026, выкатка `9341f03`):**

- `SANDBOX_RUNTIME=docker|runsc`, по умолчанию `docker`; неизвестное значение останавливает
  сервер на старте, а не превращается в случайный runtime;
- runtime передаётся во все контейнеры: команды, долгие задания, превью и оба self-check;
- брокер разрешает только `BROKER_RUNTIME` (по умолчанию `docker`), поэтому клиент не может
  подставить произвольный runtime; при `runsc` пустой `Runtime` тоже отклоняется, иначе Docker
  молча взял бы runc; тесты на оба случая есть;
- `deploy/scripts/install-runsc.sh` ставит закреплённый `release-20261026.0`: проверяет SHA256,
  при отсутствии `bzip2` устанавливает его через пакетный менеджер, распаковывает `runsc` и
  sidecar-бинари вместе в `/usr/local/bin`, вызывает `runsc install`, перезагружает Docker,
  а если reload не подхватил runtime — перезапускает его; версия переопределяется `RUNSC_VERSION`;
- `vm-deploy.sh` при `SANDBOX_RUNTIME=runsc` и отсутствии runtime сам присылает установщик
  и запускает его через `sudo -n`; если reload не подхватил runtime, Docker перезапускается,
  после чего выкатка продолжается. Ошибка установки останавливает выкатку до подмены версии;
  `RUNSC_INSTALL=0` отключает автоматику для заранее подготовленного хоста;
- `docker-compose.yml` пробрасывает `SANDBOX_RUNTIME`; `vm-deploy.sh` печатает
  `SANDBOX-RUNTIME=...` и проверяет, что Docker знает runtime (`SANDBOX_RUNTIME_CHECK=0` —
  пропустить); workflow (включая ручной выбор `sandbox_runtime=runsc`) и `make-env-vm.sh`

**Доведено 30.10.2026 (`2fa1cea`, `62363b4`):**

### ✅ 2.2. Сервер не root + rootless Docker на узлах (закрыт 30.10.2026)

**Зачем.** Это незакрытый этап 4 из `docs/DOCKER_BROKER.md`: API всё ещё работает root в

**Что сделать:**

- entrypoint сбрасывает права на непривилегированного пользователя;

- проверить запись файлов проекта, `git`, монтирование секретов и работу превью от нового uid;

**Сделано (30.10.2026, выкатка `9341f03`):**

- `server/entrypoint.sh` стартует root только для подготовки: chown data, разовый chown дерева

### ✅ 3.1. Реестр узлов и размещение проекта

- таблица `nodes` (`id`, адрес, ёмкость, занято, `last_seen`, статус);
- поле `node` у проекта: пока проект активен, он «прилип» к узлу;
- планировщик выбирает узел по свободной памяти и числу контейнеров, а не по round-robin;
- команда «вывести узел из обслуживания» (drain): новые проекты не ставятся, текущие
  доживают/архивируются.

**Сделано (30.10.2026):** таблица `nodes` создаётся вместе со схемой; `projects.node`
заполняется при создании и сохраняется для старых строк (blank → локальный узел). Локальный
узел регистрируется сам и обновляет память/число контейнеров раз в 30 секунд. Размещение
сравнивает свободную память после резерва проекта, затем число контейнеров и проектов;
`draining`, `offline` и устаревший heartbeat исключаются без локального фолбэка. На каждой
машине задаётся уникальный `WEBNESTDEV_NODE_ID` (compose прокидывает его в сервер). Админ-API
`GET /api/admin/nodes` и `POST /api/admin/nodes/:id/status` показывает размещение и включает
drain; узел проекта виден в `/api/admin/infra`, `/api/admin/sandboxes` и карточке проекта.
Файлы: `server/src/nodes/*`, `server/src/routes/admin-nodes.ts`, `server/src/project-store.ts`,
`server/src/storage/pg.ts`. Тесты: `nodes/placement.test.ts`, `nodes/node-store.test.ts`,
`admin-nodes.test.ts`, `project-store.node.test.ts`.

**Не закрыто:** фактическое открытие проекта на другом узле и отказ реальной машины — для
этого нужна вторая машина и общий POSIX-каталог. Код маршрутизации и runner готовы (см. 3.2–3.3);
без общего `SANDBOX_DIR` API осознанно отказывает, а не пишет проект на свой локальный диск.

**Готово, когда:** проект после архивации может открыться на другом узле; drain не теряет
данные; в админке видно, что и где запущено.

### ✅ 3.2. Runner-сервис: исполнение отдельно от API

Рекомендуемый минимальный вариант — не тащить весь API на каждый узел, а вынести узкую
поверхность исполнения:

- тот же образ, роль `runner`: принимает команды «создать/выполнить/логи/удалить/подключить
  сеть» и работу с файлами проекта;
- API больше не вызывает `docker` локально, а ходит на runner по приватной сети (mTLS или
  общий секрет); интерфейс `SandboxHost` с двумя реализациями — локальной и удалённой;
- на runner нет ключей платформы, платёжных секретов и доступа к Postgres;
- превью-контейнеры живут на том же узле, что и проект.

**Почему так, а не «сервер на каждой машине»:** полная копия API на каждом узле размножает
доступ к секретам и базам. Узкая поверхность исполнения меньше и её проще проверять.

**Подготовка (30.10.2026):** введён `SandboxHost` (`server/src/sandbox/host.ts`) с локальной
реализацией (`local-host.ts`) и реестром хостов по id узла. Через него уже идут команды
агента, долгие задания, preview и проверки песочницы.

**Сделано (31.10.2026):**

- `server/src/runner/main.ts` — отдельный процесс на приватной сети; на нём нет Postgres,
  платёжных ключей и `.env` платформы. `RUNNER_TOKEN` (32+ символа) — bearer-аутентификация,
  тело запроса ограничено, `GET /health` отдаёт только `{ok,nodeId}`;
- `server/src/runner/policy.ts` — allowlist Docker: только hardened `docker run` (read-only,
  uid 1000, cap-drop ALL, no-new-privileges, CPU/memory/PID limits, монтирование только своего
  проекта), плюс `rm/logs/inspect/exec/network` для контейнеров с метками платформы. Runner
  не может `exec` в Postgres/API даже при утёкшем токене. Отдельно закрыты `--read-only=false`
  и `--init=false`, а сеть `docker run/network connect` ограничена `none`, `bridge` и сетью
  предпросмотра — сеть базы/API недоступна;
- `server/src/sandbox/remote-host.ts` — `RemoteSandboxHost` с таймаутами, проверкой id узла и
  понятными `RUNNER_*` ошибками; `resolveSandboxHost` берёт адрес из реестра, лениво
  регистрирует host и при устаревшем heartbeat один раз переспрашивает runner;
- `runInSandbox`, долгие задания и preview используют `config.node`, а не глобальный Docker
  API-машины. Долгие задания хранят host в своей записи; preview хранит `node` в состоянии;
- `WEBNESTDEV_REMOTE_NODES` или `POST /api/admin/nodes` регистрируют узел; API опрашивает
  `/v1/status` и обновляет память/контейнеры/last_seen. `offline` убирает кэш host и даёт 503,
  `draining` запрещает только новое размещение;
- общий hot workspace обязателен: `WEBNESTDEV_SHARED_SANDBOX=1` на API и runner, один
  абсолютный `SANDBOX_DIR` на POSIX-хранилище. Без него `getSandbox` отказывает, а не создаёт
  пустой локальный каталог;
- `server/entrypoint.sh` — режим `WEBNESTDEV_RUNNER=1` отключает подготовку платформенных
  данных и рекурсивный `chown` общего workspace; `sandboxStatus()` ограничен 5 секундами,
  чтобы зависший Docker не держал health-check;
- тесты: `runner/policy.test.ts`, `runner/server.test.ts`, `runner/preview-relay.test.ts`,
  `sandbox/remote-host-routing.test.ts`; протокол проверен end-to-end с фейковым runner.

**Проверено 31.10.2026:** `tsc -p server/tsconfig.json --noEmit` и `tsc -b --noEmit` — чисто;
все 215 test-файлов сервера прошли, `npm run test:broker` — 29/29.

**Не закрыто:** реальный runner на второй машине, NFS/shared workspace, mTLS вместо
bearer-секрета, проверка изоляции ключей на живой машине и отказ живой машины. Bearer-токен —
единственная аутентификация runner: он должен стоять только в приватной сети/VPN, а не в
интернете. Без второй машины это не приёмка, а только локальный harness.

**Что не путать:** код runner готов, но `docker-compose.yml` не запускает runner и не включает
удалённые узлы. Пока пусты `WEBNESTDEV_RUNNER_TOKEN` и `WEBNESTDEV_REMOTE_NODES`, API работает
только на локальном Docker.

**Готово, когда:** команда агента и превью работают на удалённом узле так же, как локально;
падение runner не роняет API; на узле нет ключей платформы.

### ✅ 3.3. Маршрутизация и sticky-сессии

- API проксирует запросы проекта на его узел (файлы, терминал, превью, WebSocket);
- при недоступности узла — понятная ошибка (`NODE_UNAVAILABLE`/503), а не «белый экран»;
  opt-in auto-move переносит закрепление на другой узел, но не восстанавливает проект из S3;
- метрики на узел: память, число контейнеров, очередь, p95 старта превью.

**Сделано (31.10.2026):**

- команды/задания/preview идут на узел проекта; локального фолбэка нет (`NODE_UNAVAILABLE`);
- для preview на runner поднимается приватный TCP relay: API получает его адрес через
  `/v1/preview/relay`, поэтому работают и HTTP, и HMR WebSocket, а не только медленный
  `docker exec`. Relay закрывается вместе с контейнером; `docker exec` остаётся аварийной
  дверью, если relay недоступен;
- preview-сеть, `docker exec`, логи и удаление контейнера выбираются по `node`; `PreviewState`
  хранит `node` и `containerPort`, публичный прокси и Chromium идут по relay;
- API опрашивает runner'ы и пишет метрики в реестр; `GET /api/admin/nodes` показывает ёмкость,
  свежесть, проекты, число живых preview и p95 старта preview за последние 30 минут
  (`previewStarts.count/p95Ms/failures`). Метрика in-memory и не переживает рестарт API;
- при `WEBNESTDEV_AUTO_MOVE_PROJECTS=1` проект с потерянного узла переносится только при общем
  workspace и без активного preview/задания. Это перенос закрепления (`projects.node`), а не
  восстановление из S3: проект должен уже лежать на общем диске;
- runner убирает свои осиротевшие preview/job контейнеры на старте; API делает то же для
  удалённых узлов, если `PREVIEW_REAP_ON_START` не отключён.

**Не до конца / не закрыто:**

- 30 одновременных preview на двух узлах, реальная потеря узла, перезапуск API при живом
  runner и сетевые задержки relay не проверены — нужна вторая машина и общий POSIX-каталог;
- очередь по каждому узлу отдельно не считается: `previewStarts` даёт p95 старта, но не
  `queued/active` на узле;
- автоматического восстановления проекта из S3 при переносе нет; auto-move меняет только
  закрепление узла и требует общего workspace;
- p95 считается по последним 30 минутам в памяти API, а не хранится как история.

**Готово, когда:** 30 одновременных превью на двух узлах без свопа и отказов по памяти;
перезапуск API не рвёт уже открытые превью (или честно показывает переподключение).

#### Включение runner: сейчас и после второй машины

**Сейчас, на одной ВМ:** ничего нового добавлять не нужно. Удалённый режим выключен, пока пусты
`WEBNESTDEV_RUNNER_TOKEN` и `WEBNESTDEV_REMOTE_NODES`:

```env
WEBNESTDEV_RUNNER_TOKEN=
WEBNESTDEV_REMOTE_NODES=
WEBNESTDEV_SHARED_SANDBOX=0
WEBNESTDEV_AUTO_MOVE_PROJECTS=0
WEBNESTDEV_REBALANCE_PROJECTS=0
```

`WEBNESTDEV_RUNNER=1` на API **не ставить**: это режим только для отдельного runner-процесса,
иначе entrypoint пропустит подготовку данных и секретов API.

**Когда появится вторая машина:** сначала один общий токен (`openssl rand -hex 32`), затем
одинаковый NFS-каталог на обеих машинах под одним абсолютным путём. На API:

```env
WEBNESTDEV_RUNNER_TOKEN=<тот же токен>
WEBNESTDEV_SHARED_SANDBOX=1
WEBNESTDEV_REMOTE_NODES='[{"id":"node-2","address":"10.0.0.12:8790"}]'
```

`WEBNESTDEV_NODE_ID` на API не меняйте, если он уже задан; `node-2` должен быть только у runner
и совпадать с `id` в `WEBNESTDEV_REMOTE_NODES`. Вместо переменной узел можно зарегистрировать
через `POST /api/admin/nodes` с тем же `id` и адресом.

На второй машине (runner):

```env
WEBNESTDEV_RUNNER=1
WEBNESTDEV_NODE_ID=node-2

RUNNER_TOKEN=<тот же токен>
RUNNER_BIND=0.0.0.0
RUNNER_PORT=8790
RUNNER_PREVIEW_BIND=0.0.0.0
RUNNER_PREVIEW_HOST=10.0.0.12

WEBNESTDEV_SHARED_SANDBOX=1
WEBNESTDEV_SANDBOX_DIR=/srv/webnestdev/sandboxes
WEBNESTDEV_SANDBOX_HOST_DIR=/srv/webnestdev/sandboxes
```

Пути `WEBNESTDEV_SANDBOX_DIR`/`WEBNESTDEV_SANDBOX_HOST_DIR` на runner должны совпадать с
`SANDBOX_DIR` API и быть одним NFS-каталогом. `RUNNER_PREVIEW_HOST` — приватный адрес второй
машины, доступный с API; `8790` и relay-порты нельзя открывать в интернет. На runner не
монтируются `.env`, база, платёжные ключи и данные API; ему нужен только Docker socket.

Если на API явно задан `PREVIEW_NETWORK`, задайте то же значение на runner (runner выбирает
сеть по нему; имя должно существовать в Docker второй машины). Если не задан, runner берёт
сеть, в имени которой есть `preview`. `SANDBOX_IMAGE`/`SANDBOX_RUNTIME` на runner должны
совпадать с API; при значениях по умолчанию их можно не задавать.

**После приёмки, не раньше:** `WEBNESTDEV_AUTO_MOVE_PROJECTS=1` на API. Он переносит только
закрепление проекта на другой узел при общем workspace и без активного preview/job;
восстановления из S3 и проверки реальной потери узла этим не закрываются.

**Порядок приёмки:** с API проверить `GET http://10.0.0.12:8790/health` → узел появился в
`GET /api/admin/nodes` → одноразовый проект на удалённом узле → preview и HMR → 30 preview на
двух узлах → остановить runner и увидеть `NODE_UNAVAILABLE`/503. На боевых проектах это не
тестировать; для приёмки нужен staging или отдельная тестовая пара машин.

**Появилось вместе с приёмкой (07.11.2026, выкачено сборкой `42220d7`):**

- возврат проекта на освободившийся узел сам по себе не выполняется: авто-перенос работает
  только «от потерянного узла». Вернуть проект без автоматики можно новым админ-маршрутом.

прод вернулся к одноузловому режиму. **С 10.11.2026:** `node-1` — primary, `node-2` — streaming standby, общий Gluster и NLB на два
бэкенда (см. [`PRODUCTION_STATE.md`](PRODUCTION_STATE.md) §12); вечером того же дня `node-2`

она используется как streaming standby** (с вечером 10.11.2026 — с выключениями на ~2 недели);
`node2-runner` и NFS больше не используются.
Если снова понадобится runner, его запуск совместим с Postgres, но на 4 ГБ это тесно — лучше не
совмещать production-базу и runner на одной машине.

4.3 закрыт на двух реальных ВМ 10.11.2026; 4.4 требует отдельного от API инстанса Postgres —
сейчас primary делит ВМ с API.

### ✅ 4.1. Лимиты и счётчики — в общее хранилище (закрыт 10.11.2026)

**Что оказалось на самом деле.** В памяти жили две разные вещи, и переносить в базу нужно было
только одну:

- **счётчики частоты** (`auth/auth-rate-limit.ts`): попытки входа, регистрации, SMS-кодов,
  подтверждения почты, входа админки и TOTP. Это и есть «лимиты, которые обнуляет рестарт и не
  делят реплики»; теперь они в PostgreSQL;
- **семафоры ресурсов** (`concurrency.ts`, `run-limiter`, `sandbox-limiter`, `preview-limiter`,
  лимитеры браузера/vision/сети). Они защищают память конкретной машины и обязаны оставаться
  локальными: общий счётчик в базе разрешил бы второй ВМ запускать контейнеры, которых у неё нет
  по памяти. Здесь меняется только будущий этап 3 (узел считает свои).

**Сделано:** таблица `rate_limits` (`key`, `count`, `reset_at`) и `storage/rate-limit-store.ts`
с атомарным `INSERT … ON CONFLICT DO UPDATE` (окно 15 минут, как раньше; одинаковые лимиты и
одинаковые ответы `429` + `Retry-After`). Недоступное хранилище трактуется как «пропустить» с
записью в лог: база не должна запирать вход всем сразу. В JSON-режиме — файл `rate-limits.json`
(локальная работа и тесты). Просроченные окна удаляются сами.

**Готово, когда:** две реплики API видят один общий лимит; рестарт не обнуляет счётчики входа;
тесты на гонку (два одновременных запроса не проходят сверх лимита).

**Проверено:** 8 тестов (`storage/rate-limit-store.test.ts` — лимит, окно, **20 одновременных
попыток при лимите 5 дают ровно 5 разрешений**, сброс; `auth/auth-rate-limit.test.ts` — обе двери,
счётчик виден в хранилище, а не только в памяти) плюс затронутые наборы и весь сервер — 1473 теста.

**Приёмка на двух репликах (10.11.2026).** Проверено на живой паре: каждая нода — своя реплика
API (`127.0.0.1:8787`), база одна (`node-1:5433`).

- 5 попыток входа админа с одним адресом на `node-1` + 5 на `node-2` дали ровно **10** разрешённых
  (по лимиту `adminLogin` по аккаунту); 11-я с `node-1` — `429` с `Retry-After: 898`, 12-я с
  `node-2` — тоже `429`. То есть реплики видят один счётчик, а не каждая свой;
- после `docker restart` API на `node-2` счётчик остался `13` и ответ остался `429`: рестарт окна
  не обнуляет;
- тестовые ключи `subject:adminLogin:accept41*` удалены из `webnestdev_rate_limits`, чужие окна не
  тронуты; прод после рестарта — `/api/ready` 200 локально и снаружи.

Телефонные коды к этому не относятся: `phone-store` в PostgreSQL **не переносим**, вход по номеру
и SMS отменены навсегда (10.11.2026, см. `AGENTS.md`).

### ✅ 4.2. Очередь заданий и воркер (закрыт 08.11.2026)

- таблица `jobs` (`kind`, `subject`, `state`, `attempts`, `run_after`, аренда `locked_until`) с
  `FOR UPDATE SKIP LOCKED` и частичным уникальным индексом на активное задание;
- воркер — `server/src/jobs/worker.ts`, внутри API по умолчанию и отдельным процессом
  `node server/dist/scripts/job-worker.js` (`JOBS_INLINE_WORKER=0` выключает встроенный);
- ретраи с backoff (30 с → 10 мин, три попытки), дедупликация по паре `(kind, subject)`,
  видимость в админке — `GET /api/admin/jobs` с `state`/`kind`/`projectId`/`limit` и счётчиками;
- API не ждёт `tar`/загрузку: `POST /api/admin/projects/:id/archive` отвечает `202` с `jobId`;
  восстановление пишет строку очереди как страховку от рестарта (сама распаковка идёт в процессе,
  как и раньше, — панель теряет свой 409-прогресс только если процесс умер).

**Готово, когда:** 100 проектов на выгрузку обрабатываются без блокировки API; рестарт воркера
не теряет задания; зависшее задание возвращается в очередь по таймауту.

**Сделано:** `server/src/jobs/store.ts` (два режима — PostgreSQL и JSON для локальной работы),
`server/src/jobs/worker.ts`, `server/src/scripts/job-worker.ts`, таблица `jobs` в `pg.ts`,
ручка `GET /api/admin/jobs`. Проверено 12 тестами очереди и воркера (дедупликация, захват без
дублей, возврат по истёкшей аренде, исчерпание попыток, backoff, прогресс, задание без
обработчика) плюс весь набор сервера.

**Приёмка на рестарте (08.11.2026):** тест `jobs/worker.test.ts` «падение воркера не теряет
задание» захватывает задание воркером, останавливает его внутри обработчика (так выглядит
рестарт процесса), ждёт истечения аренды и показывает, что второй воркер забирает то же задание
и доводит его до `done`; попытка при этом засчитывается (2), а прогресс не теряется. Критерий
«рестарт воркера не теряет задания; зависшее задание возвращается по таймауту» закрыт.

**Живая приёмка на проде (08.11.2026):** тестовый проект `test-proj` (тестовый аккаунт,
209 749 598 байт) поставлен в очередь; API перезапущен, когда задание было `running`. После
рестарта задание осталось в базе с `attempts=1`; аренда сдвинута вручную, второй воркер взял его
с `attempts=2` и довёл до `done`, прогресс сохранился (209 749 598/209 749 598). `/api/ready`
после рестарта — 200. Тестовые файлы, записи очереди и объект в бакете удалены, проект и аккаунт
остались на месте.

**Уборка хвостов (08.11.2026):** при старте API, до `listen` и до воркера, `storage/temp-cleanup.ts`
удаляет только `archive-*.tar.gz` в своём каталоге временных файлов и `.restore-<node>-*`
рядом с песочницами.
Рабочие папки проектов, S3 и отметки архива не трогаются; ошибка уборки не мешает старту. При
встроенном воркере (обычная выкатка) удаляются все совпадения, включая хвост только что убитого
процесса; при `JOBS_INLINE_WORKER=0` — только старше часа, чтобы не задеть идущую распаковку
отдельного воркера. Проверено тестами `storage/temp-cleanup.test.ts` (4 теста).

**Ограничение для 4.3 (закрыто в C1.0):** стартовая уборка удаляет временные файлы, которые
принадлежат этому процессу. Пока API один, это было безопасно. Если несколько реплик делят один
каталог песочниц и `tmp`, старт одной реплики мог удалить свежую `.restore-*`/`archive-*` другой.
Теперь временные каталоги разведены по репликам (`tmp/<node-id>` и `.restore-<node-id>-*`, см.
`server/src/storage/temp-paths.ts`), а уборка чистит только свой namespace. Часовой порог
по-прежнему нужен для вынесенного воркера (`JOBS_INLINE_WORKER=0`).

**Вне критерия 4.2:** планировщик холодного яруса всё ещё вызывает `archiveProject` напрямую (он
работает вне HTTP и сам ограничивает параллелизм); перевод его на ту же очередь — отдельный шаг
вместе с пересчётом цели по диску, не блокирует 4.3.

### ✅ 4.4. Postgres вне Docker: system PostgreSQL, streaming standby и PITR (закрыт 10.11.2026)

Managed-инстанс с автоматическими бэкапами и PITR либо отдельная ВМ. Критерий — восстановление
на момент времени проверено, а не «галочка в панели».

**Состояние на 10.11.2026.** PostgreSQL больше не в Docker: primary — system-сервис, вторая
нода — streaming standby (плановый switchover через `data/ha-switchover.json`, затем rejoin
`standby.sh`; лаг 0, RPO 0). Слоты `node1`/`node2` создаются самим `standby.sh`;
promotion при потере primary и rejoin проверены destructive-прогонами. Приложение переезд не
заметило: оба API ходят в локальный HAProxy `:5432`, цель меняет `db_proxy.py`, `DATABASE_URL`
не менялся. PITR закрыт (base backup 88 МБ, drill на момент времени, таймеры работают только на
primary).

**Текущее размещение.** С вечера 10.11.2026 primary возвращён на `node-1`, `node-2` — streaming
standby: пользователь выключает `node-2` примерно на две недели. Это осознанный временный режим;
разделение API и базы по разным ВМ и TLS — предпродовые шаги, их порядок записан в
[`PRODUCTION_LAUNCH.md`](PRODUCTION_LAUNCH.md) и в этом плане не ведётся.

**Заготовка на второй ВМ (08.11.2026).** Вторая ВМ `node-2` (Ubuntu 24.04, 2 vCPU / 4 ГБ, диск
20 ГБ) подготовлена как отдельный Postgres:

- установлен PostgreSQL **17.11** — та же мажорная версия, что на проде; Ubuntu-версия 16 не
  подошла бы для переноса дампа;
- `listen_addresses = 'localhost,10.0.0.5'`; в `pg_hba.conf` доступ к базе `webnestdev` разрешён
  только с основной ВМ `10.0.0.4/32`, наружу порт не публикуется;
- роль и база `webnestdev` созданы; пароль сгенерирован на ВМ и лежит только в
  `/root/webnestdev-pg.env` (права `600`), в репозиторий и чат не попадает;
- с прода снят дамп 3.7 МБ и восстановлен на второй ВМ: 55 таблиц, 16 проектов, 17 пользователей,
  9 заданий, 15 архивов, 51 сессия — совпадает с продом; подключение с основной ВМ проверено;
- `postgresql` включён в автозапуск (`systemctl is-enabled postgresql`); после `sudo reboot`
  проверено, что сервер поднимается сам (`pg_isready`, 55 таблиц) и доступ с основной ВМ
  сохраняется;
- временные дампы (транспортные файлы для переноса) удалены с обеих ВМ; сама восстановленная
  база остаётся на диске `node-2`. На 08.11.2026 после проверки `node-2` была выключена
  (`power=OFF`); с 10.11.2026 она используется как streaming standby, а вечером того же дня
выключается на ~2 недели. Прод продолжает
  отвечать 200 на `/` и `/api/ready`; тогда это была ещё **не** production-база, прод работал
  с Postgres на основной ВМ.

**Что изменилось 10.11.2026.** `DATABASE_URL` больше не смотрит на конкретную ВМ: оба API ходят
в локальный HAProxy `:5432`, цель переключает `db_proxy.py`. Поэтому primary можно переносить
между узлами без изменения конфигурации приложения, а потеря узла переживается promotion'ом
(пока вторая нода включена).

**PITR закрыт 10.11.2026.** Включён `archive_mode=on`, WAL-сегменты уходят в
`/var/lib/postgresql/wal-archive`, раз в неделю снимается физический `pg_basebackup`, чистка

**Вывоз WAL в S3 — готов к включению.** `deploy/scripts/pg-pitr-s3.sh` каждые 5 минут
выгружает новые сегменты и base backup (`pitr/wal/…`, `pitr/basebackup/<ts>.tar.gz`, индекс и

## Этап 5. Сеть и антиабьюз (3–4 недели)

### ✅ 5.1. Egress-фильтр для кода проекта (включён в проде 10.11.2026)

**Зачем.** Сейчас у превью и песочниц есть свободный интернет: майнинг, спам, атаки и обход
квот с нашего IP. gVisor это не закрывает — это другой слой.

**Включено в проде 10.11.2026.** В `deploy/node1` и `deploy/node2` override'ах теперь
`EGRESS_MODE: allowlist` и `EGRESS_ENFORCE: "1"`; на обеих нодах стоят юниты
`webnestdev-egress.service` (в `node-2` — впервые), правила `DOCKER-USER` применены и переживают
перезагрузку. Прокси на каждой ноде в режиме `allowlist`, 33 встроенных домена.

Проверка на живой системе (тот же `MODE=egress`, что в выкатке): прокси жив, сервер ходит наружу
сам (npm registry 200), через прокси registry 200, `example.com` → 403, контейнер проекта ставит
пакеты через прокси 200, прямой сокет из контейнера не открывается. Дополнительно вручную:
`github.com` через прокси — 200, `example.com` — 403.

Если понадобится ослабить фильтр: сначала `EGRESS_MODE: private-only` (публичное разрешено,
обход прокси всё ещё закрыт), затем `EGRESS_ENFORCE: "0"` — полный откат. Оба изменения требуют
пересоздания контейнера сервера на ноде.

**Важно для `node-2`:** у неё нет `.env`, compose читает `runtime.env` и `node2.env`. Поэтому
при ручном `MODE=egress` на этой ноде нужен `COMPOSE_ENV_FILES=runtime.env,node2.env`, иначе
`compose_env_value` не читает режим и `docker compose exec` в проверке возвращает пустоту.

**Что сделать:**

- egress-прокси на каждом узле с allowlist (npm registry, GitHub, нужные CDN) и запретом
  приватных адресов и metadata-сервиса;
- маршрут контейнеров превью и команд через прокси, DNS — только через него;
- журнал отказов (домен, проект, счётчик), без содержимого трафика;
- лимит трафика на аккаунт и на узел.

**Что сделано:**

- **Прокси с allowlist** — `server/src/egress/` (`allowlist.ts` — правила, `proxy.ts` — пересылка,
  `proxy-main.ts` — процесс, `attribution.ts` — проект по адресу). HTTPS не расшифровывается:
  `CONNECT` остаётся туннелем, поэтому в журнал попадают домен, порт, причина и проект, а не
  содержимое. Решение принимается по имени домена и уже разрешённому адресу, и прокси соединяется
  именно с проверенным адресом — DNS-rebinding не расходится с проверкой.
- **Правила по умолчанию:** реестры пакетов (npm, yarn, pypi, rubygems), git-хостинги (GitHub,
  GitLab, Bitbucket, GitVerse), типовые CDN, шрифты. Расширение без пересборки — `EGRESS_ALLOWLIST`
  в `.env`; встроенный минимум при этом сохраняется (замена означала бы, что одна опечатка в `.env`
  отключает установку пакетов во всех проектах и это не видно по коду).
- **Внутреннее закрыто всегда:** loopback, RFC1918, CGNAT, link-local, ULA и metadata-сервис
  (`169.254.169.254`, `169.254.170.2`, `100.100.100.200`, `metadata.google.internal`) — и в режиме
  `allowlist`, и в `private-only`. Разрешённый домен заказчика с A-записью внутрь нашей сети — отказ.
- **Режимы:** `allowlist` (по умолчанию), `private-only` (всё публичное — аварийный выключатель,
  когда allowlist ломает нужный проект), `off` (поведение до 5.1). Опечатка в `EGRESS_MODE` —
  ошибка запуска, а не молчаливый `off`.
- **Маршрут контейнеров:** `HTTP_PROXY`/`HTTPS_PROXY`/`npm_config_*` добавляются ко всем контейнерам
  команд и заданий (`sandbox/docker/args.ts`) и к предпросмотру (`preview/preview-runner.ts`).
  Переменные задаёт сервер, а не `.env` проекта: приложение не должно переопределять путь наружу.
  Прокси — третий процесс контейнера под супервизором (как дверь в 6.1); без супервизора
  (разработка) он поднимается в процессе API, чтобы адрес не вёл в пустоту.
- **Запрет обхода:** `deploy/scripts/egress-firewall.sh` + юнит `webnestdev-egress.service`. В
  `DOCKER-USER` для подсети `webnestdev-preview`: выход разрешён контейнерам сервера и брокера и
  трафик внутри подсети (API, дверь, прокси :3128), остальное — `REJECT`. Юнит возвращает правила
  после перезагрузки ВМ, когда выкатки не было. Выкатка применяет правила, проверяет фильтр на

- **Журнал:** строка `[egress] отказ: {"host":…,"port":…,"reason":…,"source":…,"projectId":…}`

### ✅ 5.2. Квоты и антиабьюз (реализовано 07.11.2026)

- CPU-минуты, трафик, диск и число контейнеров — на аккаунт и на тариф;
- лимиты по IP на edge (регистрация, вход, создание проектов);
- признаки майнинга/скама: длительная загрузка CPU, много исходящих соединений, шаблонные
  регистрации; реакция — ограничение, а не молчаливое убийство;
- блокировка демо-режима в production флагом (P2 #17 из `docs/SECURITY.md`).

**Что сделано:**

- **Минуты контейнеров на аккаунт** — `server/src/account/resource-quota.ts`. Считаются секунды
  жизни контейнеров песочницы (команды агента, установки, сборки) за UTC-сутки, лимит по тарифу:
  Старт 120 мин, Плюс 600, Премиум 1800 (`resourceLimits.sandboxMinutesPerDay` в каталоге).
  Счётчик — та же таблица `usage_counters`, вид `sandboxSeconds`, прибавление одним
  `ON CONFLICT DO UPDATE`; миграция не нужна. Исчерпанный лимит — 429 `SANDBOX_QUOTA_EXCEEDED`
  с числом минут, временем сброса и ссылкой на поддержку.
- **Один контейнер на аккаунт** — `sandbox/sandbox-limiter.ts`: у аккаунта своя очередь, и она
  всегда одного размера (1) на всех тарифах: агент запускается один, вторая параллельная сборка
  ничего не ускоряет, а место хоста занимает. `SANDBOX_MAX_PER_USER` переопределяет число, `0`
  снимает ограничение на аккаунт. Лишняя команда ждёт своего места и не занимает место хоста,
  поэтому чужой пользователь проходит без задержки. Проверка бюджета стоит до очереди.
- **Аккаунты по IP** — `auth/signup-ip.ts`: три аккаунта с одного адреса **навсегда**, счётчик
  в таблице `signup_ips` (общий на реплики). Считаются и почта, и телефон; суточное окно здесь
  не годится — оно обходится регистрацией по одному аккаунту в день. Четвёртый получает 403
  `SIGNUP_IP_LIMIT` с путём в поддержку, отказ пишется в журнал `security.signup.blocked`.
  `SIGNUP_IP_LIMIT` меняет предел, `0` выключает.
- **Создание проектов по IP** — `routes/projects.ts`: 10 новых проектов за 24 часа с одного адреса
  (счётчик в PostgreSQL, общий на реплики), 429 `PROJECT_CREATE_RATE_LIMITED`. Лимиты входа и
  регистрации по адресу и аккаунту были закрыты ещё в 1.1.
- **Детектор майнинга** — `security/abuse-watch.ts`: раз в минуту снимает `docker ps` / `stats`
  через брокер, проект определяет по метке или `WEBNESTDEV_PROJECT_ID`. Контейнер проекта выше
  90% CPU десять минут подряд (настраивается `ABUSE_CPU_PERCENT`, `ABUSE_SUSTAINED_MS`) — аккаунт
  блокируется с причиной и записью `security.abuse.blocked` в журнале, контейнеры нарушителя
  останавливаются. Просадка CPU сбрасывает отсчёт; наблюдение выключается `ABUSE_WATCH=0`.
- **Демо-режим в production** — P2 #17: демо-аккаунт не создаётся с паролем по умолчанию
  (`demo1234`), демо-номер не включается с номером по умолчанию; нужны свои значения.
- **В интерфейсе** — панель агента знает код `SANDBOX_QUOTA_EXCEEDED`: отдельное сообщение и
  окно «Время песочницы исчерпано» с временем сброса и путём в поддержку.
- **Тесты:** `auth/signup-ip.test.ts` (8), `routes/auth-register-ip.test.ts` (3),
  `routes/phone-auth-ip.test.ts` (2), `account/resource-quota.test.ts` (8),
  `sandbox/sandbox-account-limit.test.ts` (4),
  `security/abuse-watch.test.ts` (13), `routes/project-ip-limit.test.ts` (2),
  `auth/demo-guard.test.ts` (3), брокер — stats/stop в `policy.test.mjs`. Полный прогон — 1591/1591.

**Остатки (сознательно за рамками):**

- **Трафик на аккаунт** — прокси 5.1 считает байты глобально (`bytesUp`/`bytesDown`), но не
  разрезает их по проекту в базу. Лимит трафика требует счётчика на проект в прокси и его записи в
  `usage_counters`; сейчас трафик ограничен только allowlist и счётчиком отказов.
- **Лимиты по IP на edge** — считаются в API, а не в Caddy: до приложения запрос доходит, и
  `trustProxy` обязан быть настроен корректно (иначе все клиенты будут одним адресом).
- **Шаблонные регистрации** — отдельного детектора нет: остаются лимиты по адресу и аккаунту.
- **Remote-узлы** — наблюдение и квоты описаны для локального узла; runner получает их при
  приёмке этапа 3.

**Готово, когда:** один аккаунт не может занять узел; превышение квоты объяснено в интерфейсе;
есть журнал ограничений и апелляция через поддержку. **По этим трём критериям закрыто:** очередь
на аккаунт, окно с объяснением и кодом, запись в `security_audit` + причина при входе + «напишите
в поддержку». Трафик как квота остаётся в остатках.

### ✅ 5.3. Остатки по безопасности из аудита (закрыт 08.11.2026)

Не всё требует роста, но дешевле закрыть сейчас: ключ API поддержки (P1 #10 — в итоге удалён),
смена/сброс пароля (#6), подтверждение email (#13). Это небольшие ручки, но при 3к аккаунтов они
становятся обязательными.

**Что сделано.**

- **Восстановление пароля по почте.** `POST /api/auth/password-reset/request` принимает адрес и
  всегда отвечает `{sent:true}` — и для существующего, и для неизвестного; `retryAfter` не
  возвращается, чтобы пауза не выдавала наличие аккаунта. Письмо уходит тем же SMTP/Postbox
  (`auth/password-reset-mail.ts`), ссылка ведёт на `/?reset_password=<токен>` и живёт час.
  В таблице `password_resets` лежит только SHA-256 токена, один актуальный на аккаунт; переход
  гасит токен до записи пароля, поэтому две одновременные вкладки не меняют его дважды.
- **Подтверждение сброса.** `POST /api/auth/password-reset/confirm` проверяет токен, пишет новый
  scrypt-хеш, отзывает все сессии и выдаёт новую. Переход по ссылке доказывает владение адресом,
  поэтому заодно ставится `email_verified` — иначе человек сменил бы пароль и всё равно не вошёл.
- **Смена пароля.** `POST /api/auth/password/change` требует текущий пароль (одна украденная
  cookie не должна закреплять новый), отзывает остальные сессии и оставляет текущий браузер
  в аккаунте.
- **Служебные адреса.** У входа по SMS, Яндекс ID и VK ID пароль случайный, а адрес —
  `…@phone.webnestdev.local` / `…@yandex-id.webnestdev.local` / `…@vk-id.webnestdev.local`.
  Письмо туда не отправляется, а форма смены пароля в настройках скрыта: `hasPassword` приходит
  в `/api/auth/me` и `/api/account/settings`.
- **Ключ поддержки удалён.** Отдельного `SUPPORT_API_KEY` больше нет: обращения читаются только
  по админ-сессии (пароль + TOTP, срок, бездействие, отзыв) — той же, что у остальной админки.
  Статический общий ключ не давал ничего сверх неё, а утечка открывала все обращения до ручной
  смены. Если появится неинтерактивный клиент, ему нужны именные токены (хеш, срок, отзыв).
- **Аудит.** Новые события: `user.password.reset.requested`, `user.password.reset`,
  `user.password.changed`.
- **UI.** На экране входа — «Забыли пароль?» и форма нового пароля по ссылке; в настройках →
  «Безопасность» — смена пароля (только для аккаунтов с настоящим паролем).
- **Тесты.** `routes/auth-password-reset.test.ts` — 7 проверок (одинаковый ответ, одноразовость,
  истечение, отзыв сессий, подтверждение неподтверждённого аккаунта, `PASSWORD_NOT_SET`, сбой
  почты); `routes/support.test.ts` — лимит ключа и запись в журнал без значения ключа.

**Остаток.** Регистрация по-прежнему отвечает `EMAIL_TAKEN` на занятую почту — это вторая
половина P1 #13 и отдельное решение: ответ «такой адрес уже есть» нужен форме, но он же
позволяет перебирать адреса.

## Этап 6. Край и предпросмотры (2–3 недели)

### ✅ 6.1. Дверь превью — отдельный сервис (закрыт 06.11.2026)

Сейчас публичная дверь живёт внутри процесса API и имеет потолок 256 соединений и 64 WebSocket
на весь сервер. Вынести её в отдельный процесс/контейнер (тот же код), масштабировать
независимо, а Caddy направить на него. Лимиты — на узел, а не на весь API.

**Что сделано:**

- `server/src/preview/door-main.ts` — та же дверь (`createPreviewHostServer`), но отдельным
  процессом: свои лимиты, свой health на `127.0.0.1:8789` (`/__health`: лимиты, занятые
  соединения и WebSocket, uptime) и корректная остановка по `SIGTERM`.
- **Состояние — у API.** Карта живых предпросмотров (`preview/preview-store.ts`) принадлежит
  процессу API, и в другом процессе её нет. Поэтому добавлен внутренний канал
  `POST /api/internal/preview/lookup` и `/event` (`routes/preview-door.ts`): существование
  проекта, статус и адрес предпросмотра, а также отметки «адрес перестал отвечать» и «пошли
  внутрь контейнера». Байты приложения через API не идут — дверь проксирует их сама.
- **Защита канала — токен, а не адрес.** `/api/*` виден снаружи через Caddy, поэтому «внутренний
  адрес» ничего не ограничивает. Токен выводится HMAC-ом из `WEBNESTDEV_ENCRYPTION_KEY`
  (`preview/door-token.ts`): новой переменной в `.env` на ВМ не появляется, а утёкший заголовок
  не даёт ключ расшифровки секретов. Сравнение — постоянного времени.
- **Кеш в двери — одна секунда** на положительный ответ (`PREVIEW_DOOR_CACHE_MS`): экран
  приложения — это десятки запросов, и каждый не должен стоить запроса к API. Отрицательные
  ответы не кешируются: проект могли открыть только что.
- **API больше не поднимает дверь** при `PREVIEW_DOOR_SEPARATE=1` и пишет в лог, что она вынесена;
  `/api/health` → `activity.previews.door` показывает режим, лимиты и живое состояние.
- **Супервизор** `server/preview-door-run.sh` (CMD образа): API — главный процесс (его код
  завершает контейнер), дверь перезапускается отдельно с паузой, штатный выход (код 0 — домена
  нет) цикл заканчивает. Падение двери панель не трогает; `PREVIEW_DOOR_SEPARATE≠1` или старый
  образ — поведение прежнее, один процесс.
- **Тесты:** `server/src/preview/door-token.test.ts`, `door-client.test.ts`,
  `routes/preview-door.test.ts` — 19 проверок: детерминированность токена и его отличие от ключа,
  отказ без токена/ключа (401/503), кеш и его истечение, некеширование отрицательного ответа,
  ошибка вместо «предпросмотра нет» при недоступном API, разбор кривой формы ответа, валидация
  событий. Полный прогон сервера — 1492/1492.

**Почему процесс, а не отдельный контейнер.** Второй контейнер — это вторая точка, которую
выкатка обязана уметь откатывать: Caddy смотрел бы на новый адрес, а предыдущий образ двери не
содержит вовсе, и автоматический откат после неудачной проверки здоровья оставил бы предпросмотры
без апстрима. В схеме «второй процесс в том же контейнере» апстрим не меняется
(`webnestdev-server:8788`), а старый образ просто не запускает дверь отдельно. Настоящая изоляция
ресурсов и независимое масштабирование двери — вместе с отдельным узлом (этап 3), куда
`door-main.ts` переезжает как есть.

**Готово, когда:** 60 одновременных превью не увеличивают RSS API; падение двери не роняет
панель; лимиты видны в health.

### ✅ 6.2. Wildcard-сертификат для `*.preview` (закрыт 05.11.2026, принят в бою 06.11.2026)

**Зачем.** Caddy выдаёт сертификат на каждый новый поддомен по запросу (on-demand + `ask`,
см. `deploy/Caddyfile`). Это работает, но каждый проект — отдельная выдача: лимит Let's Encrypt
50 сертификатов на домен в неделю, плюс задержка на первом заходе в проект. Один
`*.preview.<домен>` закрывает все имена сразу.

**Почему `acme.sh`, а не Caddy.** Wildcard нельзя получить по HTTP-01 — нужен DNS-01, то есть
API регистратора. Caddy умеет DNS-01 только через плагин, а плагинов в официальном образе нет:
вариант «собрать образ с xcaddy» добавил бы свою сборочную цепочку и свой график обновлений
ради одной функции. `acme.sh` — один скрипт, у него уже есть `dns_regru` (переменные
`REGRU_API_Username` / `REGRU_API_Password`), и он умеет сам ставить обновлённые файлы и звать
команду перезагрузки. Caddy при этом остаётся на статическом сертификате.

**Что сделано:**

- `deploy/scripts/wildcard-cert.sh` — выпуск, установка, продление и переключение схемы:
  `--issue` (идемпотентно: пока сертификату больше `RENEW_BEFORE_DAYS` = 30 дней, выдачи нет),
  `--status`, `--check` (код 0/1 для мониторинга), `--disable` (вернуть on-demand), `--force`.
  Сертификат EC-256, ключ `600`, каталог `700`, провайдер задаётся `ACME_DNS_PROVIDER`
  (по умолчанию `dns_regru`), установку самого `acme.sh` скрипт делает только при
  `ACME_SH_INSTALL=1` — молчаливого похода в сеть на проде нет.
- **Продление** — cron, который ставит `acme.sh` при установке; `--install-cert` записывает
  `reloadcmd` с абсолютными путями (`docker compose … caddy reload`), потому что из cron нет
  переменных окружения выкатки. Сниппет при продлении не меняется — те же два пути.
- **Свой ежедневный запуск.** На этой ВМ штатный установщик `acme.sh` не ставит cron, поэтому
  продление не должно зависеть от него и от пушей: у workflow `deploy` есть расписание
  (`30 3 * * *` UTC) с `MODE=cert` — он возит сниппет и скрипт, выпускает/продлевает при
  необходимости, перечитывает Caddy и выходит, не трогая ни образ, ни сервис. Тот же режим
  запускается руками: `Actions → deploy → Run workflow → mode: cert`.
- **Выбор схемы в конфиге.** У Caddyfile нет условий, поэтому `deploy/Caddyfile` подключает
  `import /etc/caddy/preview-tls.caddy`, а этот файл целиком переписывает скрипт: либо
  `tls { on_demand }`, либо `tls /certs/preview/fullchain.pem /certs/preview/key.pem`.
  Репозиторный `deploy/preview-tls.caddy` — on-demand, то есть поведение по умолчанию не
  меняется, пока wildcard не выпущен.
- **Доставка.** `docker-compose.yml` монтирует сниппет и `${CERTS_HOST_DIR:-./certs}` (каталог
  рядом с compose, чтобы обойтись без root) как `/certs:ro`; `deploy/scripts/vm-deploy.sh` возит
  сниппет рядом с Caddyfile (`PREVIEW_TLS_B64`
  из workflow, `PREVIEW_TLS_SRC` при локальном запуске), но **не перезаписывает** файл, который
  уже ссылается на `/certs/` — иначе каждая выкатка откатывала бы выпущенный wildcard. Проверка
  `caddy validate` монтирует и сниппет, и каталог сертификатов: без второго монтирования
  правильный конфиг с wildcard был бы отвергнут как «файл не читается». Если сниппета на ВМ нет
  вовсе, выкатка пишет on-demand — `import` не должен ссылаться на отсутствующий путь.
- **Обратный ход.** `--disable` возвращает on-demand и перечитывает Caddy, файлы сертификата при
  этом остаются: вернуться можно тем же `--issue` без новой выдачи. On-demand остаётся и рабочим
  запасным вариантом, если DNS API недоступен, — просто с прежним расходом лимита.
- **Тест:** `bash deploy/scripts/wildcard-cert.test.sh` — 17 проверок без сети, Let's Encrypt и
  Docker (заглушки `acme.sh` и `docker`): идемпотентность, перевыпуск истекающего, пауза после
  неудачной попытки, смена сниппета в обе стороны, права ключа, `reloadcmd`, отказ без домена.
  Оба варианта сниппета проверены `caddy validate` на caddy 2.8.4 (on-demand и статические
  файлы). Режим `MODE=cert` проверен локальным запуском `vm-deploy.sh` на пустом `APP_DIR`:
  сниппет ставится, выпуск без учётных данных пропускается с понятной строкой, `exit 0`.

**Включение — без терминала.** У ВМ **нет интерактивного терминала** (ни SSH, ни `scp`), поэтому
выпуск сделан шагом выкатки: два секрета репозитория (`REGRU_API_USERNAME`, `REGRU_API_PASSWORD`)
+ обычный деплой; `vm-deploy.sh` сам возит скрипт на ВМ и запускает его только при заданных
секретах, а при ошибке выпуска не валит выкатку (превью остаются на on-demand). Продление —
cron, который ставит себе `acme.sh`, и собственный ежедневный запуск `MODE=cert` на случай, когда
этот cron не установился (так и вышло на этой ВМ). Пока секреты не добавлены, wildcard не включён: превью работают
как раньше, лимит расходуется. Ограничение записано в `docs/PRODUCTION_DEPLOYMENT.md` (блок
«There is no interactive terminal on the VM») и относится к любому будущему пункту плана: если
действие требует оболочки на ВМ, его нужно автоматизировать в выкатке, а не писать инструкцию
«зайди и запусти».

**Готово, когда:** новый проект открывается без выдачи отдельного сертификата; продление
автоматическое; лимит Let's Encrypt не расходуется.

**Приёмка на проде (06.11.2026).** Сертификат выпущен Let's Encrypt в 10:25 UTC, копия лежит в
`$APP_DIR/certs/preview`; проверка рукопожатием на произвольном имени превью отдаёт
`CN = *.preview.nestdev.ru`, `notAfter = 04.02.2027` — то есть Caddy уже работает по статическому
сертификату, а не выдаёт отдельный на каждое имя. В логе выкатки: `[cert] wildcard подключён …
(89 дн.)`, `[cert] Caddy перечитал конфигурацию`, `[deploy] wildcard в порядке`. Продление —
ежедневный запуск по расписанию `30 3 * * *` UTC: GitHub задержал первый запуск до 11:23, режим
`MODE=cert` проверил готовый сертификат и вышел, не трогая образ и сервис.

**Выяснилось при приёмке и исправлено:**

- Запись TXT через API reg.ru доходит до зоны (остаточная запись отвечает с TTL 21600), но не за
  две минуты: две попытки с паузой 120 с упали на проверке Let's Encrypt. `ACME_DNS_SLEEP`
  поднят до 600 с — пауза удлиняет только ту выкатку, которая действительно выпускает
  сертификат (раз в ~60 дней), а сорванная выдача стоит трёх часов кэша отрицательного ответа
  DNS (SOA-минимум зоны 10800 с) и одной из пяти неудач в час.
- Выкатка обрывалась на перечитывании Caddy (`ssh … bash -s` + `docker compose exec`, который
  вычитывал скрипт из stdin): с 04.11 не выполнялись ни проверка здоровья с автооткатом, ни
  verify-шаги, ни уборка образов. Скрипт теперь кладётся в файл и запускается с stdin в EOF,
  `exec` перенаправляет stdin; код возврата SSH снова отражает исход выкатки. Обратная сторона
  этого дефекта видна в цифрах: 16 образов по 1,45 ГБ накопились на диске, Docker занимал
  20,5 ГБ вместо 6,2 ГБ и вернулся к норме на первой же выкатке после починки.

**Что это не решает.** Статические сайты (`*.host.<домен>`) по-прежнему на on-demand: там тот
же лимит, но сайтов на порядок меньше. Если понадобится — тот же скрипт с
`WILDCARD_DOMAIN=host.<домен>` и отдельным сниппетом в блоке `*.{$HOSTING_PUBLIC_DOMAIN}`.

### 6.3. CDN для статических сайтов хостинга (пилот 11.11.2026)

Изначально пункт формулировался про статические превью. На практике превью приватные и
меняются каждую минуту — кешировать их бессмысленно; CDN подключается только к опубликованным
сайтам хостинга (`<slug>.host.nestdev.ru`). Превью остаются на нодах как есть.

**Сделано 11.11.2026:**

- NLB проверен на живом сайте: 40 запросов через `my-furniture.host.nestdev.ru` дали
  49,7% / 50,3% по отданным байтам между `node-1` и `node-2` — балансировка есть, обе ноды
  отдают сайт из общего Gluster.
- Создан CDN-ресурс `hosting-pilot` в `project-pimashin2015` с origin
  `https://my-furniture.host.nestdev.ru` и Host-заголовком того же домена; FQDN
  `top873590456.mwscdn.ru`, статус `Active`.
- Кеш: CSS `MISS → HIT`; HTML всегда `MISS` из-за `Cache-Control: no-cache` от Caddy — так и
  должно быть, чтобы публикация была видна сразу.
- Purge через `cacheTasks` дошёл до `OK`, после него CSS снова `MISS`, затем `HIT`.
- Тариф: 0,8418 ₽/ГБ с НДС, без платы за запросы; тестовый период до 14 дней.

**Критерий готовности:** статический сайт хостинга отдаётся через край, публикация сбрасывает
кеш, origin не получает повторные запросы. Пилот это подтвердил.

**Подготовлено 11.11.2026 для всех сайтов сразу:**

- managed-сертификат `host-wildcard` на `*.host.nestdev.ru` — **`valid=true`**;
- общий CDN-ресурс `hosting` (`top3561259317.mwscdn.ru`), wildcard-CNAME, origin NLB с
  пересылкой Host и SNI — **включён**, `OK`;
- проверка через `--resolve` до DNS: `my-furniture` и `my-sayt` отдают 200 через CDN,
  содержимое совпадает с origin, кеш по Host раздельный, CSS `MISS → HIT`.

**Сделано 11.11.2026:** в REG.RU `*.host` переключён на CNAME `top3561259317.mwscdn.ru.`;
сертификат `valid`, ресурс `hosting` активен; `my-furniture` и `my-sayt` проверены через CDN
(200, содержимое совпадает с origin, кеш `HIT`); пилот `hosting-pilot` удалён. Все сайты, старые
и новые, попадают в CDN автоматически — отдельный ресурс на сайт не создаётся.

**Авто-purge:** реализован в `server/src/hosting/cdn-purge.ts` и вызывается после успешной
публикации; ошибка purge не ломает сайт. Включается `HOSTING_CDN_PURGE=1` и параметрами
ресурса в compose. Тесты 7/7, typecheck прошёл, реальная задача purge дошла до `OK`.

**Осталось:** выкатить образ с авто-purge и проверить, что реально новый сайт после публикации
открывается через CDN и обновлённые ассеты не залипают (ожидается без дополнительных действий).

**Чего CDN не делает:** не разгружает динамические превью, не отменяет ноды, не заменяет HA
PostgreSQL. С тремя нодами origin для CDN должен быть стабильным адресом (NLB/роутер), а не
конкретной машиной — сайты в общем Gluster это уже позволяют.

## Чего не делать

- Не покупать одну огромную ВМ вместо нескольких средних: это откладывает архитектурную
  проблему, а не решает её.
- Не строить Kubernetes и microVM раньше ~500–1000 активных.
- Не хранить маркеры архивов только на хосте при нескольких репликах.
- Не делать восстановление синхронным для проектов больше 100 МБ.
- Не оставлять Postgres без бэкапов и проверки восстановления.
- Не собирать Docker-образ на каждый проект.
- Не возвращать серверу прямой `docker.sock`.
- Не включать gVisor сразу на всё: сначала матрица совместимости и замер.
