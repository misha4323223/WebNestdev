## 0. Как читать этот план

1. Этапы идут **строго от лёгкого к тяжёлому**. Внутри этапа пункты тоже упорядочены.
2. Правило перехода: этап считается закрытым только после выкатки в прод, замера и записи
   результата. Не начинаем следующий, пока предыдущий не закрыт — иначе ошибки складываются.
3. У каждого пункта есть критерий готовности. «Работает у меня» критерием не считается.
4. Каждый этап заканчивается обновлением документации и планом отката.
5. Оценка «сколько выдержит» берётся не из головы, а из `docs/SCALING_PLAN.md` §4 и замеров на
   реальных проектах.

### 1.3. Архивация по давлению на диск

**Зачем.** Сейчас архивация только по таймеру (6 часов). Диск может кончиться раньше, а полный

## Этап 2. Дешёвая изоляция: gVisor и сервер не root (1–2 недели)

Это не «microVM», а следующий по важности слой. Работает на текущей ВМ и почти не меняет
архитектуру.

### 2.1. gVisor (`runsc`) для контейнеров команд и превью

**Зачем.** Сегодня контейнеры делят ядро с хостом. Брокер убрал «RCE в API = root на хосте», но
побег через уязвимость ядра остаётся. gVisor даёт контейнеру собственное песочное ядро в
пользовательском пространстве: до настоящего ядра доходят только проверенные вызовы.

**Почему не microVM сейчас.** Firecracker/Kata требует `/dev/kvm` (вложенная виртуализация), а
у Yandex Cloud её нет — это уже записано в `docs/PRODUCTION_DEPLOYMENT.md`; у MWS нужно
уточнять. Плюс нужен оркестратор, снапшоты и своя сеть. Это отдельный проект на месяцы, он
оправдан на 1000+ и bare-metal. gVisor даёт большую часть выгоды за малую часть работы.

**Что сделать:**

- поставить `runsc` на ВМ и зарегистрировать как Docker runtime;
- добавить выбор рантайма в `dockerRunArgs` (`SANDBOX_RUNTIME=docker|runsc`) и в контейнер
  предпросмотра;
- разрешить `Runtime: runsc` в политике брокера (`deploy/docker-broker/policy.mjs`), иначе
  `create` будет отклонён;
- прогнать матрицу: `node`, `npm install`, `git`, `npm run build`, `docker exec`, поиск порта по
  `/proc/net/tcp`, WebSocket/HMR, `--read-only` и `/tmp`;
- замерить время сборки и памяти до/после; записать цифры;
- включать постепенно: сначала один тип контейнеров, потом все; флаг для мгновенного возврата.

**Файлы:** `server/src/sandbox/docker/args.ts`, `server/src/preview/preview-runner.ts`,
`deploy/docker-broker/policy.mjs`, `docker-compose.yml`, тесты.

**Готово, когда:** обычный проект собирается и открывается под `runsc`; `exec` и определение
порта работают; есть замер замедления; выключатель возвращает обычный Docker одной переменной.

### 2.2. Сервер не root + rootless Docker на узлах

**Зачем.** Это незакрытый этап 4 из `docs/DOCKER_BROKER.md`: API всё ещё работает root в
контейнере, а брокер видит демон хоста целиком.

**Что сделать:**

- entrypoint сбрасывает права на непривилегированного пользователя;
- общая группа на сокет брокера (`BROKER_SOCKET_MODE`), права на каталог песочниц;

**Готово, когда:** `/api/health` зелёный, песочницы и предпросмотр работают, процесс сервера
запущен не от uid 0, прямой доступ к сокету демона отсутствует.

## Этап 3. Второй узел исполнения (3–4 недели)

Самый тяжёлый архитектурный шаг, но именно он превращает «одну большую ВМ» в «добавляем машины».

### 3.1. Реестр узлов и размещение проекта

- таблица `nodes` (`id`, адрес, ёмкость, занято, `last_seen`, статус);
- поле `node` у проекта: пока проект активен, он «прилип» к узлу;
- планировщик выбирает узел по свободной памяти и числу контейнеров, а не по round-robin;
- команда «вывести узел из обслуживания» (drain): новые проекты не ставятся, текущие
  доживают/архивируются.

**Готово, когда:** проект после архивации может открыться на другом узле; drain не теряет
данные; в админке видно, что и где запущено.

### 3.2. Runner-сервис: исполнение отдельно от API

Рекомендуемый минимальный вариант — не тащить весь API на каждый узел, а вынести узкую
поверхность исполнения:

- тот же образ, роль `runner`: принимает команды «создать/выполнить/логи/удалить/подключить
  сеть» и работу с файлами проекта;
- API больше не вызывает `docker` локально, а ходит на runner по приватной сети (mTLS или
  общий секрет); интерфейс `SandboxHost` с двумя реализациями — локальной и удалённой;
- на runner нет ключей платформы, платёжных секретов и доступа к Postgres;
- превью-контейнеры живут на том же узле, что и проект.

**Почему так, а не «сервер на каждой машине»:** полная копия API на каждом узле размножает
доступ к секретам и базам. Узкая поверхность исполнения меньше и её проще проверять.

**Готово, когда:** команда агента и превью работают на удалённом узле так же, как локально;
падение runner не роняет API; на узле нет ключей платформы.

### 3.3. Маршрутизация и sticky-сессии

- API проксирует запросы проекта на его узел (файлы, терминал, превью, WebSocket);
- при недоступности узла — понятная ошибка и автоматический перенос после восстановления из S3,
  а не «белый экран»;
- метрики на узел: память, число контейнеров, очередь, p95 старта превью.

**Готово, когда:** 30 одновременных превью на двух узлах без свопа и отказов по памяти;
перезапуск API не рвёт уже открытые превью (или честно показывает переподключение).

### 4.1. Лимиты и счётчики — в общее хранилище

Сейчас лимиты входа, запусков агента, песочниц и превью живут в памяти процесса: рестарт их
сбрасывает, реплики не делят. Перенести счётчики в Postgres (атомарный upsert) или Redis,
сохранив текущее поведение очередей и ошибок.

**Готово, когда:** две реплики API видят один общий лимит; рестарт не обнуляет счётчики входа;
тесты на гонку (два одновременных запроса не проходят сверх лимита).

### 4.2. Очередь заданий и воркер

- таблица `jobs` (`kind`, `payload`, `state`, `attempts`, `run_after`) с `FOR UPDATE SKIP
  LOCKED`;
- воркер архивации/восстановления — отдельный процесс;
- ретраи с backoff, дедупликация, видимость в админке;
- API не ждёт `tar`/загрузку в ответе пользователю.

**Готово, когда:** 100 проектов на выгрузку обрабатываются без блокировки API; рестарт воркера
не теряет задания; зависшее задание возвращается в очередь по таймауту.

### 4.3. Несколько реплик API

- сессии уже в Postgres; проверить, что нет состояния в памяти, кроме лимитов;
- WebSocket: sticky-маршрутизация по cookie или вынос состояния запусков в общее хранилище;
- health/ready каждой реплики, аккуратное выкатывание (сначала одна, потом вторая).

**Готово, когда:** перезапуск одной реплики не рвёт активные задачи; балансировщик не отправляет
`/ws` на случайную реплику.

### 4.4. Postgres отдельно от API

Managed-инстанс с автоматическими бэкапами и PITR либо отдельная ВМ. Критерий — восстановление
на момент времени проверено, а не «галочка в панели».

## Этап 5. Сеть и антиабьюз (3–4 недели)

### 5.1. Egress-фильтр для кода проекта

**Зачем.** Сейчас у превью и песочниц есть свободный интернет: майнинг, спам, атаки и обход
квот с нашего IP. gVisor это не закрывает — это другой слой.

**Что сделать:**

- egress-прокси на каждом узле с allowlist (npm registry, GitHub, нужные CDN) и запретом
  приватных адресов и metadata-сервиса;
- маршрут контейнеров превью и команд через прокси, DNS — только через него;
- журнал отказов (домен, проект, счётчик), без содержимого трафика;
- лимит трафика на аккаунт и на узел.

**Готово, когда:** `npm install` и типовой проект работают; произвольный домен из allowlist не
пускается; в журнале видно, кто и куда стучался; превышение квоты даёт понятную ошибку.

### 5.2. Квоты и антиабьюз

- CPU-минуты, трафик, диск и число контейнеров — на аккаунт и на тариф;
- лимиты по IP на edge (регистрация, вход, создание проектов);
- признаки майнинга/скама: длительная загрузка CPU, много исходящих соединений, шаблонные
  регистрации; реакция — ограничение, а не молчаливое убийство;
- блокировка демо-режима в production флагом (P2 #17 из `docs/SECURITY.md`).

**Готово, когда:** один аккаунт не может занять узел; превышение квоты объяснено в интерфейсе;
есть журнал ограничений и апелляция через поддержку.

### 5.3. Остатки по безопасности из аудита

Не всё требует роста, но дешевле закрыть сейчас: ключ API поддержки с ограничением и аудитом
(P1 #10), смена/сброс пароля (#6), подтверждение email (#13). Это небольшие ручки, но при 3к
аккаунтов они становятся обязательными.

## Этап 6. Край и предпросмотры (2–3 недели)

### 6.1. Дверь превью — отдельный сервис

Сейчас публичная дверь живёт внутри процесса API и имеет потолок 256 соединений и 64 WebSocket
на весь сервер. Вынести её в отдельный процесс/контейнер (тот же код), масштабировать
независимо, а Caddy направить на него. Лимиты — на узел, а не на весь API.

**Готово, когда:** 60 одновременных превью не увеличивают RSS API; падение двери не роняет
панель; лимиты видны в health.

### 6.2. Wildcard-сертификат для `*.preview`

Сейчас Caddy выдаёт сертификат на каждый новый поддомен по запросу. Let's Encrypt даёт 50
сертификатов на домен в неделю — на росте это стена. Нужен один wildcard-сертификат и
обновление по DNS-01 (у reg.ru может не быть модуля Caddy — тогда `acme.sh` с DNS API и
монтирование сертификата, либо смена DNS-провайдера).

**Готово, когда:** новый проект открывается без выдачи отдельного сертификата; продление
автоматическое; лимит Let's Encrypt не расходуется.

### 6.3. CDN для статических превью

Статический предпросмотр сейчас отдаёт сам сервер. Выгружать сборку в S3/CDN и отдавать через
край — это снимает и трафик, и файловые дескрипторы. Критерий: статический предпросмотр не
нагружает API-процесс.

## Этап 7. Нагрузка, автоматика, microVM (постоянно)

- **7.1. Нагрузочный прогон** на целевые 300 одновременных сессий и 60 превью; замерить p95
  старта превью, восстановления, запуска агента; записать в документ.
- **7.2. Пул узлов и автоскейл** (Nomad/Kubernetes или простой менеджер узлов) — только когда
  ручное добавление машины станет узким местом.
- **7.3. Учения по инцидентам**: потеря узла, потеря Postgres, переполнение диска, отказ
  провайдера модели. Раз в квартал.
- **7.4. Решение по microVM** (Firecracker/Kata) — отдельный spike на 3–5 дней, только если
  появится bare-metal или провайдер с `/dev/kvm`, и если gVisor уже не покрывает риск. До этого
  не начинать.

## Чего не делать

- Не покупать одну огромную ВМ вместо нескольких средних: это откладывает архитектурную
  проблему, а не решает её.
- Не строить Kubernetes и microVM раньше ~500–1000 активных.
- Не хранить маркеры архивов только на хосте при нескольких репликах.
- Не делать восстановление синхронным для проектов больше 100 МБ.
- Не оставлять Postgres без бэкапов и проверки восстановления.
- Не собирать Docker-образ на каждый проект.
- Не возвращать серверу прямой `docker.sock`.
- Не включать gVisor сразу на всё: сначала матрица совместимости и замер.
