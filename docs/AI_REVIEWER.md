# Reviewer-субагент

Статус: **реализован за флагом `AGENT_REVIEWER`, по умолчанию выключен**. Без флага основной
запуск не меняется: ревьюер не вызывается и не тратит токены.

## Когда запускается

Reviewer работает в режиме Developer после успешной проверки сборки, тестов, preview, SSR и
браузера, но **до** записи точки в историю проекта. Порог — больше 5 изменённых файлов или
больше 200 добавленных/удалённых строк. Меньшие изменения проверяются обычным контуром и не
платят за отдельный контекст.

## Чистый контекст

Ревьюер не видит переписку, размышления и выводы инструментов основного агента. Он получает
только:

- исходную задачу;
- план и milestone’ы, если они опубликованы;
- реальный unified diff рабочего дерева по изменённым файлам;
- уже пройденные проверки;
- детерминированные замечания, найденные до вызова модели.

Инструменты ревьюеру не выдаются: `toolNames: []`. Он не может читать другие файлы, менять
проект или запускать команды.

## Детерминированная часть

До модели проверяются факты, которые не должны зависеть от её уверенности:

- новые секреты в добавленных строках (удаление старого секрета ошибкой не считается);
- `it.only` / `describe.only` / `fit` / `fdescribe` в diff;
- `it.skip` / `xit` и другие пропуски тестов — предупреждение;
- `DROP TABLE`, `TRUNCATE TABLE`, `DELETE FROM` без `WHERE` — ошибка;
- `eval` / `new Function` — предупреждение;
- изменения вне `files` ни одного этапа плана;
- большой diff без тестов в списке проверок.

Статическая ошибка не отменяется ответом модели `pass` и не зависит от доступности модели:
она возвращает `fail` до вызова провайдера, поэтому битый ответ ревьюера не может её пропустить.

## Ответ модели

Модель возвращает строгий JSON:

```json
{
  "verdict": "pass",
  "summary": "кратко",
  "findings": [
    { "severity": "error", "title": "Потеряна обработка ошибки", "detail": "fetch может упасть", "file": "src/orders.ts", "line": 12 }
  ]
}
```

`error` блокирует завершение, `warning`/`info` остаются замечаниями. Ответ без валидного JSON и
`verdict` считается инфраструктурным отказом: запуск не получает ложный `pass`, но и не теряет
уже проверенную работу — отказ логируется, а ревью помечается как недоступное. Статические
ошибки к этому моменту уже проверены и не пропускаются.

## Цикл исправления

Если ревью не прошло, основной агент получает системное сообщение с findings, исправляет причину
и снова проходит обычную проверку. После неё ревьюер запускается повторно. После двух неудачных
ревью запуск завершается ошибкой, а не выдаёт непроверенную точку за готовую.

## Ограничения

- Ревьюер использует ту же модель и маршрут, что основной запуск; отдельная модель для ревью
  пока не настроена.
- Инфраструктурный отказ ревьюера не блокирует завершение, но и не считается `pass`.
- Нет canary, baseline и замера «сколько внедрённых дефектов ловит ревьюер».
- Для локальной проверки `.env.local` переключён на Polza.ai с тестовым ключом и моделью
  `deepseek/deepseek-v4.1-flash-1017`; у ключа фиксированная сумма, поэтому нагрузочные
  запросы не запускались. Это локальная конфигурация, а не production-секрет.
- Reviewer не заменяет тесты: статическая часть видит только формы, а модель — только diff.
- В модель уходят первые 30 изменённых файлов и не больше 60 000 символов diff; остальное
  считается по порогу, но не просматривается. Это ограничение стоимости, а не полное покрытие.
- Без git-репозитория ревью пропускается: нет базы, относительно которой строить diff.
- Изменения, сделанные командой в терминале, видны только если путь попал в `changedFiles`
  основного запуска; произвольные файлы, изменённые shell-командой, reviewer может не увидеть.
- Флаг `AGENT_REVIEWER` не включался в production.
