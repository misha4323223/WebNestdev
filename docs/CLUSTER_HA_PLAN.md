# Кластер: active-active API и Postgres primary/standby

Статус: **двусторонний failover реализован и проверен на живой паре**, 08.11.2026. Проверены оба направления: `node-1 → node-2` и `node-2 → node-1`, включая PostgreSQL promotion, fencing через MWS, GlusterFS-хранилище, API/Caddy и DNS. 10.11.2026 дополнительно проверены плановый switchover в обе стороны, оба rejoin и холодный старт `node-2` с актуальным HA-кодом; повторный destructive выполнен с временным `quorum-type=none` и выявил блокеры storage-quorum/automount, поэтому чистым прохождением не считается. Автоматического failback базы нет: вернувшийся узел пересоздаётся как standby отдельным rejoin. **Принятое production-решение: `node-2` постоянно включена, обе ВМ работают active-active для API/runner/preview; PostgreSQL остаётся один primary, второй — standby.** `node-2` — вторая production-нода; сейчас она выключена **только из-за стоимости** до запуска production-HA. ### 0.1a. Как должны работать обе ВМ одновременно

Это не два независимых приложения с двумя базами. Логическая база **одна**: на каждой
ВМ может быть свой PostgreSQL-процесс, но писать имеет право только текущий primary.
Оба API должны смотреть в **один и тот же primary**, а не каждый в свою локальную копию.

Целевое поведение, которое нужно получить:

- `node-1` и `node-2` обе запускают API, Caddy, runner и принимают проекты, sandbox и
  preview. Пользователь не выбирает, на какую ВМ ему попасть.
- PostgreSQL primary — ровно один. Второй узел — streaming standby; его API читает и
  пишет через primary endpoint, а не в локальный read-only кластер.
- Вернувшаяся после сбоя ВМ **не становится primary автоматически**, но сразу поднимает
  API/runner и снова принимает проекты. Её PostgreSQL остаётся standby, пока не будет
  явного планового переключения.
- Публичный вход — **один постоянный адрес**, который не меняется при переключении. Для
  этого нужен NLB (или другой постоянный VIP); адрес конкретной ВМ не должен быть
  точкой входа.
- **Новый внешний адрес для NLB не нужен.** У нас уже есть статический адрес MWS
  `ea-webnestdev` = `178.236.27.102`, на который смотрит REG.RU. NLB должен использовать
  именно его как external listener, а не создавать второй IP. Тогда DNS остаётся
  `178.236.27.102` и при аварии не меняется. Адрес перестаёт быть «адресом первой ВМ» и
  становится адресом кластера: перед подключением к NLB его нужно отсоединить от NAT
  `node-1`, а SSH/исходящий доступ первой ВМ организовать отдельно (правило NLB или
  management-адрес).
- Пока третьей witness-ВМ нет, внешним арбитром служит MWS power fencing: promotion
  базы разрешён только после подтверждённого `power=OFF` второго узла. Если MWS
  недоступен, автоматический promotion запрещён. Это временная замена кворуму, а не
  вечный обходной путь.
- Для GlusterFS на двух узлах без arbiter запись должна быть запрещена, пока живы оба
  узла, но они не видят друг друга. После подтверждённого fencing и выключения второго
  узла оставшийся узел может временно работать один; при возврате второго и завершении
  heal кворум восстанавливается. Это реализовано в `deploy/ha/storage_quorum.py`.

Что уже сделано для этой схемы:

- `deploy/ha/db_proxy.py` направляет локальный HAProxy каждого API в **текущий primary**:
  локальный PostgreSQL, если узел primary, или HAProxy peer, если его база standby.
  Поэтому второй API не ходит в свою read-only копию и может принимать проекты.
- `deploy/ha/storage_quorum.py` держит `cluster.quorum-type=auto`, пока оба узла живы,
  и переводит тома в `none` только после того, как MWS подтвердил `power=OFF` peer.
  Если peer включён, но не отвечает, запись замораживается, а не разрешается двум узлам.
- `node-2` входит в production-контур постоянно включённой; выключение после теста —
  свойство текущего стенда, а не проекта.

Ingress уже готов: NLB `webnestdev-nlb-main` на постоянном адресе, оба target проверены.
Осталось для production: witness/quorum, исправление storage-quorum и automount, **чистый**
повторный destructive failover drill на текущем `deploy/ha` (10.11 прогон прошёл только с
временным `quorum-type=none`), проверка quorum-переходов под нагрузкой и постоянное
включение `node-2`.

### 0.3. Что осталось и чего не хватает

- **Автоматического failback нет:** вернувшийся узел нужно явно пересоздать как standby
  (`deploy/ha/standby.sh`), после чего он снова готов принять роль.
- **`node-2` — production-нода, но сейчас выключена из-за стоимости.** На ней проверены
  и оставлены установленными HAProxy, API/Caddy/runner, standby PostgreSQL и актуальный
  HA-контроллер. После production-решения она работает постоянно; до этого включается
  для работ, которым нужны две ВМ.
- **Ручной старт PostgreSQL защищён systemd-guard:** при data directory от primary guard
  проверяет роль peer; если peer тоже primary или его роль не подтверждена при `power=ON`,
  старт блокируется. Ошибка 09.11 больше не проходит через обычный `systemctl start`.
- **Ingress готов к production:** NLB `webnestdev-nlb-main` создан на существующем
  `ea-webnestdev` = `178.236.27.102`; правила `tcp:80`/`tcp:443`, бэкенды
  `10.0.0.4` и `10.0.0.5`, health check TCP 443. Во время проверки оба target были `OK`;
  после выключения `node-2` её target снова `FAILED`, рабочий — только `node-1`. DNS не менялся.
  Старый NLB на `62.113.70.155` удалён, адрес освобождён; management-адрес `node-1` —
  `2.59.83.250` (`ea-webnestdev-admin`). В `webnestdev-failover.service` включён
  `DNS_ENABLED=0`: контроллер больше не трогает REG.RU при promotion.
- **Кворум:** третьей witness-ВМ нет. Временная замена — MWS fencing плюс
  `storage_quorum.py`: при разделении сети запись в GlusterFS замораживается, а
  promotion базы разрешается только после `power=OFF` peer. Это не вечный кворум, но
  не даёт двум узлам одновременно писать. После появления третьей ВМ её arbiter должен
  заменить ручное переключение.
- **GlusterFS replica 2 без arbiter:** риск split-brain при сетевом разделении; для
  production нужен arbiter/третья ВМ или managed shared filesystem.
- Старый контейнер `src-postgres-1` остановлен, его том `src_postgres-data` сохранён; том не
  удалять до отдельной проверки. PITR и managed PostgreSQL не настроены.

`node-2` выключена 10.11.2026 после HA-проверки: MWS подтвердил `power=OFF`, SSH к
`10.0.0.5` больше не отвечает, standby data directory сохранён. Контейнеры остановились
вместе с ВМ; в реестре узлов heartbeat устарел, и placement её не выбирает. В БД за ней
остаются проекты и сайты; файлы и данные не удалялись. При следующем включении PostgreSQL
поднимается как standby, start-guard не даст ей стать вторым primary.

На `node-1` включены `WEBNESTDEV_SHARED_SANDBOX=1` и `WEBNESTDEV_AUTO_MOVE_PROJECTS=1`,
поэтому проект с pin на выключенной `node-2` при первом открытии переносит **только
закрепление** на `node-1`; файлы уже лежат на общем GlusterFS. Перенос ленивый, по одному проекту,
и выполняется только при отсутствии активного preview/задания: после выключения один проект
уже переехал, остальные 15 остаются с pin `node-2` до первого открытия. Если у проекта есть
живой preview/job на `node-2`, автоперенос намеренно отказывает, а не бросает контейнер. Для
постоянного вывода ВМ из эксплуатации всё равно нужен явный drain и перенос оставшихся pin на
`node-1`. Не оставлять `node-2` включённой «на всякий случай».

## 1. Цель

После аварии первой ВМ вторая должна:

1. остаться доступной по обычному адресу панели;
2. иметь актуальную базу и принимать записи;
3. открывать те же проекты, превью и терминалы, что и до аварии;
4. не создавать второго primary и не терять данные из-за split-brain.

Когда первая ВМ возвращается, она **не** забирает роль обратно автоматически. Она приходит как
standby для базы и как рабочий узел для проектов, превью и терминалов. Возврат роли — только
плановый failover или явное решение оператора.

Третья ВМ пока не куплена. Она закладывается в схему как **witness/quorum и рабочая ёмкость**,
а не как обязательный второй экземпляр базы. До её появления автоматический failover базы
ограничен и требует внешнего fencing; это осознанное ограничение, а не недоделка.

## 2. Целевая схема

```
                         DNS / MWS Network Load Balancer
                         (один публичный адрес, TCP 80/443)
                                      |
                 +--------------------+--------------------+
                 |                                         |
        +--------v--------+                       +--------v--------+
        | node-1          |                       | node-2          |
        | API + Caddy     |                       | API + Caddy     |
        | runner          |                       | runner          |
        | PostgreSQL      |<---- streaming ------>| PostgreSQL      |
        | primary/standby |      replication      | standby/primary |
        +--------+--------+                       +--------+--------+
                 |                                         |
                 +------------ shared POSIX storage --------+
                         (оба узла видят один SANDBOX_DIR,
                          DATA_DIR и SITES_DIR)

        +-------------------+
        | node-3 (позже)    |
        | witness/quorum    |
        | worker/runner     |
        +-------------------+
```

Роли намеренно разделены:

| Роль | Где живёт | Почему |
| --- | --- | --- |
| API | node-1 и node-2, active-active | панель, API, WebSocket агента, админка |
| Runner / worker | на каждом узле, где есть Docker | команды, сборки, превью, терминалы |
| PostgreSQL primary | один из node-1/node-2 | только один writer |
| PostgreSQL standby | другой из node-1/node-2 | горячий резерв, репликация |
| Shared storage | независимый от API-узлов POSIX-слой | проекты должны пережить падение API-ВМ |
| Ingress | NLB или DNS failover | один адрес, health checks |
| Witness/quorum | node-3, когда появится | исключает двух primary при разделении сети |

API-узел и runner — не одно и то же. API можно поднять без Docker, но тогда он не сможет
исполнять проекты, закреплённые за этим узлом. В целевой схеме на каждом API-узле есть и
runner, иначе запрос, попавший на «чужой» API, не сможет выполнить команду на узле проекта.
Сейчас `docker-compose.yml` не содержит сервиса runner: на второй ВМ его нужно добавить
отдельным сервисом/файлом, иначе `WEBNESTDEV_REMOTE_NODES` будет указывать в пустоту.

## 3. Инварианты, которые нельзя нарушать

1. **Один primary базы.** Никакой автоматики, которая повышает standby, не выключив старый
   primary или не подтвердив, что он не работает. Сначала fencing, потом promotion.
2. **Один владелец проекта.** У проекта ровно один `projects.node`. Перенос — только смена
   владельца, а не два одновременных исполнителя.
3. **Общий workspace.** API, runner и контейнеры проекта видят один и тот же абсолютный путь с
   одними и теми же файлами. Два локальных диска вместо общего — это потеря проекта, а не HA.
4. **Нет автоматического failback.** Вернувшийся узел не становится primary сам. Иначе два
   узла будут спорить за роль после каждого мигания сети.
5. **Состояние, пережившее реплику, — в PostgreSQL или в общем хранилище.** В памяти процесса
   могут оставаться только кэши и то, что можно потерять без порчи данных.
6. **Никаких двух писателей в одну папку.** Пока нет общего storage и fencing, второй узел не
   получает проект «на запись».
7. **Секреты не размножаются без нужды.** Runner не получает `.env`, базу и платёжные ключи.
   API-реплики получают только то, что им действительно нужно.

| Состояние | Файл | Что произойдёт при двух API |
| --- | --- | --- |
| Живые preview | `preview/preview-store.ts` (`Map`) | API на другой ВМ не знает о preview и не может его проксировать |
| Долгие команды `terminal.start` | `sandbox/jobs.ts` (`Map`) | запрос на другую реплику не найдёт задание |
| Один запуск агента на аккаунт | `agent/run-limiter.ts` (`Map`) | два API разрешат по запуску одному аккаунту |
| Активные запуски проекта | `agent/active-runs.ts` (`Map`) | архиватор на другой реплике не увидит активность |
| Лимит preview на аккаунт/хост | `preview/preview-limiter.ts` | лимит считается отдельно на каждой реплике |
| OAuth/репозиторные состояния | `github/github-oauth-state.ts`, `repos/routes.ts` | callback может попасть на реплику, которая не начинала вход |
| Телефонные коды | — | не актуально: вход по номеру и SMS отменены навсегда, общий store не нужен |
| Алерты, реконсиляция, архиватор | `health/alerts.ts`, `hosting/reconcile.ts`, `storage/archive-scheduler.ts` | несколько реплик делают одну работу или шлют дубли |

Часть этого можно закрыть sticky-маршрутизацией, но sticky не спасает при падении узла:
пользователь переподключится, а состояние всё равно потеряно. Для preview/jobs/лимитов нужен
общий реестр в PostgreSQL; для запусков агента — как минимум корректная потеря и понятное
переподключение, в идеале — аренда запуска в базе.

### 5.2. Временные файлы реплик пересекаются

`storage/temp-cleanup.ts` при старте удаляет `archive-*.tar.gz` из `DATA_DIR/tmp` и
`.restore-*` рядом с песочницами. Пока API один, это безопасно. Две реплики на общем диске
могли удалить свежие файлы друг друга. В C1.0 введены отдельные `tmp/<node-id>` и
`.restore-<node-id>-*` (`storage/temp-paths.ts`); уборка одной реплики больше не трогает
файлы другой. Старые файлы без узла в имени остаются: удалять их «на всякий случай» значило бы
вернуть ту же гонку.

### 5.3. `DATA_DIR` и `SITES_DIR` локальны

`webnestdev-data` — именованный том конкретной ВМ. В нём лежат платформенные ключи, настройки
почты, `project-archives`, `runtime-secrets` и другие небольшие, но важные файлы. Если запрос
попадёт на вторую API-реплику с пустым томом, она не увидит ключи платформы и часть настроек.

`HOSTING_SITES_DIR` тоже локальный. Для общей выдачи статических сайтов нужен
`HOSTING_SHARED_STORAGE=1` и общий `SITES_DIR` на всех API/Caddy.

### 5.4. Storage — точка отказа

На рабочей паре поднят **GlusterFS replica 2**: тома `sandboxes`, `sites` и `data` имеют
по brick на каждой ВМ и смонтированы в одинаковые пути. NFS-сервер `node-1` выключен,
NFS-клиент `node-2` убран. Это уже не единая точка отказа на `node-1`: при выключении
одной ВМ вторая продолжает отдавать данные, что и проверено в обоих направлениях.

Остаточный риск — split-brain у replica 2 без arbiter. Для production нужен третий
witness/arbiter или managed shared filesystem; текущая схема — рабочий двухузловой
вариант, а не доказательство кворума.

### 5.5. Ingress и TLS

Caddy работает на обеих ВМ; сертификаты и `caddy-data` — локальные тома, каждый узел
обслуживает TLS сам. Публичный адрес `178.236.27.102` принадлежит NLB
`webnestdev-nlb-main`, бэкенды — Caddy на `10.0.0.4` и `10.0.0.5`, health check TCP 443.
NLB автоматически исключает unhealthy-бэкенд, DNS при переключении не меняется.

Публичный адрес предпросмотра `*.preview` должен попадать на узел, который знает о preview;
для этого дверь-не-владелец проксирует запрос на приватную дверь владельца (см.
[PRODUCTION_STATE.md](PRODUCTION_STATE.md) §10). Осталось проверить TLS/WebSocket через NLB
под нагрузкой и trusted proxies на обоих узлах.

### 5.6. База и её failover

**Фактически на 10.11.2026:** PostgreSQL — системный кластер `17/main` на `node-1`, порт
`5433`, primary (`pg_is_in_recovery() = f`). API ходит через HAProxy на
`host.docker.internal:5432`, HAProxy направляет в `127.0.0.1:5433`. `node-2` после rejoin —
streaming standby от `node-1` (`pg_stat_replication`: `17/main|streaming|async`, нулевой лаг);
она выключена (`power=OFF`) до production-запуска. При включении поднимается standby,
start-guard не даст ей стать вторым primary. Старый контейнер `src-postgres-1` остановлен;
его том `src_postgres-data` не используется и не удалён.

PostgreSQL на первой ВМ:

- `wal_level=replica`, `max_wal_senders=10`, `hot_standby=on`;
- `archive_mode=off`, `synchronous_commit=on`;
- порт наружу не опубликован, HBA разрешает подключения с приватной сети.

В main `docker-compose.yml` сервис `postgres` остаётся для локальной/одной ВМ. На node1/node2
override-файлы запускают API с `--no-deps`, поэтому локальный `postgres` не поднимается, а
`DATABASE_URL` указывает на `host.docker.internal:5432` (HAProxy). Для внешней базы (managed или
`node-2`) нужен явный `DATABASE_URL` и профиль без локального Postgres; это отдельный пункт C2,
а не деталь выкатки.

Для HA нужно:

- настроить streaming replication и слот (слот `node1`/`node2` уже создавался в тесте:
  он будет копить WAL);
- выбрать synchronous или asynchronous commit (см. 7.1);
- добавить стабильный endpoint базы (`DATABASE_URL` не должен указывать на конкретную ВМ,
  которая может уехать);
- добавить TLS между API и PostgreSQL;
- реализовать fencing и promotion, иначе автоматический failover запрещён.

### 5.7. Инициализация схемы и фоновые задачи

`initializeStorage()` создаёт и мигрирует таблицы из каждого процесса. Две реплики,
стартующие одновременно, выполняли DDL параллельно. В C1.0 добавлен blocking advisory-лок
`webnestdev:storage-init` на выделенном соединении: DDL делает один процесс, остальные ждут.
`CREATE TABLE IF NOT EXISTS` и `ADD COLUMN IF NOT EXISTS` обычно переживали гонку, но это не
гарантия для будущих миграций и constraint-ов. Лок проверен typecheck-ом; отдельный прогон
двух процессов против PostgreSQL — в следующем шаге C1.

Фоновые задачи, которые надо либо взять под advisory-лок, либо оставить только на лидере:

- архивация проектов (`storage/archive-scheduler.ts`);
- реконсиляция статических сайтов (`hosting/reconcile.ts`);
- аварийные письма (`health/alerts.ts`);
- billing sweep и mail queue (проверить идемпотентность на двух репликах);
- `storage-scheduler` уже использует advisory-лок;
- `jobs` уже использует `SKIP LOCKED`, его можно запускать на нескольких воркерах.

### 5.8. Ёмкость второй ВМ

Замер 08.11.2026: `node-2` — 2 vCPU, 3,8 ГБ RAM, диск 19 ГБ (занято 7,1 ГБ, свободно 12 ГБ),
PostgreSQL 23 МБ, Docker-образы 4,2 ГБ. Прод — те же 2 vCPU и 3,8 ГБ RAM, но диск 48 ГБ
(занято 14 ГБ); его нагрузка в простое — load average 0,01, CPU 98 % idle, контейнеры
API + broker + Caddy + PostgreSQL занимают около 315 МБ RAM. Образ сервера — 1,45 ГБ,
sandbox-образ — 1,67 ГБ.

**Вывод:** для текущей нагрузки 2 vCPU / 4 ГБ достаточно и второй API-реплике: она не обязана
быть мощнее первой, пока первая справляется. 20 ГБ также хватает на лабораторный тест:
образы и данные небольшие. Предупреждение «мало» относится не к обычной работе, а к запасу на
будущее: несколько одновременных preview/сборок (по 1 ГБ каждая), 30 preview из тест-матрицы,
копия `DATA_DIR`/`SITES_DIR`/`SANDBOX_DIR` и бэкапы. Для production-HA это нужно либо
масштабировать, либо разделить роли (БД/standby на `node-2`, API на другой машине). Для C1
текущей конфигурации достаточно; после переключения нужно смотреть на фактическую память и
диск, а не увеличивать заранее.

## 6. Модель отказов

| Отказ | Что должно произойти | Чего делать нельзя |
| --- | --- | --- |
| Упал процесс API на node-1 | NLB/health убирает node-1; запросы идут на node-2; WebSocket и терминалы переподключаются | Считать, что незавершённый запуск агента продолжится сам |
| Упала вся node-1 | node-2 остаётся API; БД повышается после fencing; проекты открываются с общего storage | Поднимать второй primary без подтверждения, что node-1 выключена |
| Упал primary PostgreSQL | standby получает WAL, затем promotion; API переподключается к новому endpoint | Позволять старому primary принимать записи после возврата |
| Разделилась сеть | Ни один узел не повышается без внешнего подтверждения/fencing; панель может быть недоступна, но данные целы | «Автоматически лечить» разделение повышением обоих |
| Упал storage | Проекты недоступны; API и БД могут работать, но это деградация | Писать проекты в локальный диск «на время» |
| Вернулась node-1 | Стартует как standby, API/worker; проекты могут снова размещаться на ней | Автоматически делать её primary |
| Упал node-3 (witness) | Кворум может потеряться; автоматический failover базы приостанавливается | Повышать standby без кворума |

Отдельно: **терминалы и WebSocket рвутся** при падении узла. Это нормально, если панель
показывает переподключение, а не «белый экран». Превью на упавшем узле останавливаются; проект
поднимается на выжившем узле из общего storage или из S3-архива.

## 7. Решения, которые нужно зафиксировать до кодирования

### 7.1. База: managed PostgreSQL или self-hosted пара

**Вариант A — MWS Managed PostgreSQL (рекомендуется для прода).** Провайдер даёт
primary/standby, автоматический failover, постоянный primary endpoint, бэкапы и PITR.
Приложение не делает promotion и не может создать split-brain; `DATABASE_URL` указывает на
стабильный endpoint. Это снимает самую рискованную часть с двух узлов и позволяет третью ВМ
использовать как worker/witness, а не как обязательный второй сервер базы.

Минусы: зависимость от провайдера и стоимость; заготовка PostgreSQL на `node-2` становится
стендом для миграции, а не production-базой.

**Вариант B — self-hosted PostgreSQL primary/standby.** Больше контроля и нет отдельного
платежа, но нужны:

- streaming replication, слот, мониторинг лага;
- стабильный endpoint (HAProxy/VIP или DNS);
- fencing через MWS API (выключить старую ВМ) перед promotion;
- контроллер, который не повышает standby без кворума/подтверждения;
- регулярные учения с реальным выключением ВМ.

На двух узлах кворума нет. Автоматический failover в варианте B допустим только с внешним
fencing (MWS API) и запретом promotion при недоступности API провайдера. С третьим узлом
появляется witness/quorum, и зависимость от provider API можно уменьшить.

**Решение по умолчанию для этого плана:** сначала довести API/storage до active-active,
затем выбрать A или B на этапе C2. Если A доступен по цене и сети — выбрать A. Если остаёмся
на B, то до включения автоматики проверить fencing на реальном выключении `node-1`.

### 7.2. Storage: что считать общим

Кандидаты:

1. **NFS на независимом storage-хосте.** Просто, но появляется ещё одна точка отказа. Годится
   для лабораторного теста на двух ВМ, не для прода без резервирования.
2. **DRBD + NFS на паре узлов.** Блочная репликация, NFS-сервер переезжает вместе с ролью.
   Хорошо ложится на две ВМ и даёт POSIX-семантику. Требует kernel-модуля, аккуратного
   split-brain и fencing. Основной кандидат для двух узлов.
3. **GlusterFS replica 2 + arbiter на третьем узле.** Userspace, проще с kernel-модулями,
   но на двух узлах без arbiter есть риск split-brain; третий узел решает.
4. **Managed file share / network volume**, если провайдер даёт POSIX-семантику и доступ с
   двух ВМ одновременно.
5. **S3 + локальный кэш.** Не даёт live POSIX без переписывания приложения; можно как холодный
   ярус и восстановление, но не как основной workspace.

**Рекомендация:** лабораторно проверить DRBD+NFS и GlusterFS на `node-2` (spike C1.5), выбрать
один слой и только потом переносить production `DATA_DIR`, `SITES_DIR`, `SANDBOX_DIR`.
До этого не обещать HA storage.

### 7.3. Ingress и сертификаты

- MWS Network Load Balancer, внешний, TCP 80/443, health check на Caddy/`/api/ready`.
- Caddy на каждом API-узле; NLB не терминирует TLS, сертификаты живут на узлах.
- `WEBNESTDEV_TRUSTED_PROXIES` должен включать адрес, с которого NLB приходит к Caddy;
  иначе клиентский IP станет адресом балансировщика и лимиты входа начнут считать всех одним
  клиентом. Это проверяется вместе с NLB, а не после аварии.
- Wildcard-сертификат `*.preview` и `*.host` должен быть на всех узлах. Либо общий
  `CERTS_HOST_DIR`, либо выпуск на каждом узле, либо TLS-терминация на NLB (если появится).
- Публичный preview должен попадать на узел, который владеет preview. Для этого нужен общий
  реестр preview с `node`/`host`/`port`/relay, а не локальный `Map`.

### 7.4. Fencing

Fencing — обязательное условие автоматического promotion. В MWS есть API управления питанием
ВМ. Схема:

1. standby замечает, что primary не отвечает дольше порога;
2. standby проверяет через MWS API, что primary действительно не работает, и выключает её;
3. только после подтверждения `power=OFF` повышает локальный PostgreSQL;
4. старый primary при включении стартует как standby (или не стартует PostgreSQL, пока не
   получит роль);
5. если MWS API недоступен, автоматический promotion запрещён — остаётся ручной.

Это требует сервисного аккаунта MWS с минимальными правами (питание конкретной ВМ), ключ
лежит только на узлах кластера и не попадает в репозиторий. На двух узлах это единственный
способ не получить два primary; на трёх узлах арбитр становится основным, а provider API —
резервным.

### 7.5. Третья ВМ

До покупки третьей ВМ:

- не включать автоматический failover базы без внешнего fencing;
- не делать третью роль обязательной для работы;
- заложить в конфигурацию `node-3` как `witness`/`worker`, но не хранить на ней единственную
  копию данных.

После покупки:

- witness/quorum (etcd/Patroni или собственный арбитр) на node-3;
- worker/runner на node-3;
- при желании — третий кандидат в storage (arbiter, не единственная копия);
- учения: потеря node-1, потеря node-2, потеря node-3, разделение сети.

## 8. Этапы

### C0. Фиксация исходного состояния (0.5–1 день)

- Записать в документ текущие адреса, роли, версии PostgreSQL, размеры дисков, точки входа.
- Проверить, что свежий бэкап и restore drill проходят.
- Зафиксировать `WEBNESTDEV_NODE_ID` для каждой ВМ, одинаковый `SANDBOX_DIR` и токен runner.
- Проверить время (NTP) на всех узлах: без него timeout-ы и TLS ведут себя непредсказуемо.
- Зафиксировать firewall: API ↔ runner 8790, API ↔ PostgreSQL 5432, NFS/DRBD, NLB → Caddy.
- Определить, где будет публичный ingress и кто владеет сертификатами.

**Готово, когда:** есть таблица узлов, ролей и адресов; бэкап проверен; понятно, какие порты
открыты.

### C1. Active-active API на двух ВМ (3–5 дней)

Цель — падение API-процесса или API-ВМ не роняет панель, а запросы обслуживает вторая
реплика. База пока остаётся на первой ВМ; это ещё не полный failover, а проверка stateless-слоя.

Задачи:

1. **✅ Разделить временные файлы реплик.** `DATA_DIR/tmp/<node-id>` и
   `.restore-<node-id>-*`; стартовая уборка чистит только своё.
2. **✅ Advisory-лок на инициализацию схемы.** Один процесс делает DDL, остальные ждут.
3. **✅ Общий реестр preview.** Таблица `previews` (project, owner, node, mode, container,
   host, port, container_port, last_used, TTL) в PostgreSQL; `preview-store` пишет туда и
   поднимает состояние из базы при промахе локального кэша. Static-preview намеренно остаётся
   локальным: его слушатель живёт в процессе одной реплики. `previewStatus`, `previewLogs`,
   `stopPreview`, heartbeat и проверки архивации/переноса уже спрашивают общий реестр.
   Стартовая уборка (`reapOrphanPreviews`/`reapRemotePreviews`) больше не убивает контейнеры,
   на которые есть непросроченная строка реестра; в JSON-режиме поведение прежнее, а
   `PREVIEW_REAP_ON_START=0` остаётся аварийным выключателем.
4. **✅ Общие аренды запусков.** Таблица `run_leases` с TTL и heartbeat; локальный лимитер
   остаётся быстрым предохранителем процесса и работает, если PostgreSQL недоступен. В строке
   аренды хранится `project_id`: `isRunActiveAnywhere` не даёт архивации, переносу, idle-уборке
   preview и удалению проекта на второй реплике тронуть файлы во время запуска на первой.
5. **✅ Общие лимиты preview на аккаунт.** Менеджер считает container-preview по общему
   реестру, а перед стартом занимает короткую бронь в `preview_reservations` (TTL 15 минут).
   Бронь, живые preview и проверка лимита читаются в одной транзакции под коротким
   advisory-локом; снимается после записи строки в общий реестр. Поэтому одновременный старт
   с двух реплик больше не может превысить ни лимит аккаунта, ни `PREVIEW_MAX_CONTAINERS`.
   Если PostgreSQL недоступен, остаётся прежняя локальная проверка — это осознанное
   ослабление на время сбоя, а не постоянный режим.
6. **✅ OAuth/репозиторные состояния.** GitHub, GitLab и Yandex используют общую таблицу
   `oauth_states`; PKCE-verifier GitVerse теперь едет в той же строке, а не в памяти процесса,
   поэтому callback на второй реплике не теряет вход. Телефонные коды не входят в scope:
   вход по номеру и SMS отменены навсегда, общий store для них не нужен.
7. **`DATA_DIR` и `SITES_DIR`.** Для теста — общий GlusterFS с `node-2`; для прода — выбранный
   storage. `HOSTING_SHARED_STORAGE=1` на всех репликах.
8. **Runner на каждом узле.** API-реплика должна уметь выполнить проект, закреплённый за её
   узлом, и проксировать чужой проект на runner владельца. Без этого «вторая ВМ приняла API»
   не означает «вторая ВМ приняла проект». Сам runner в коде есть (`npm run runner:start`);
   на node-2 его нужно поднять отдельным сервисом с общим `SANDBOX_DIR`.
9. **✅ Health/ready с учётом роли.** Добавлен `/api/node/ready`: он проверяет Docker и
   монтирование песочницы на этом узле и подходит для health-check runner/NLB. `/api/ready`
   намеренно не ослаблен — он остаётся общей готовностью API (хранилище + песочница), потому
   что на него смотрит выкатка.
10. **NLB/DNS.** Один адрес на два Caddy; health check; проверить WebSocket и большие ответы.

**Приёмка на двух ВМ:**

- остановить `webnestdev-server` на node-1 → панель и `/api/ready` отвечают через node-2;
- вход, список проектов, открытие проекта, файлы, запуск агента и preview работают на node-2;
- терминал переподключается, а не показывает вечную загрузку;
- вернуть node-1 → обе реплики снова в NLB, без потери проекта;
- база при этом ещё на node-1 и не переезжает: это тест API-слоя, не тест БД.

### C2. PostgreSQL replication и failover (3–5 дней)

- Выбрать A (managed) или B (self-hosted) из 7.1.
- Для B: backup → basebackup на node-2 → streaming replication → слот → мониторинг лага.
- `synchronous_commit`: на двух узлах не включать жёсткий synchronous commit, иначе при
  выключенной второй ВМ primary перестанет принимать записи. Начать с asynchronous, измерить
  лаг; sync — только когда standby постоянно включён и есть кворум/третий узел.
- Стабильный endpoint: HAProxy/VIP/DNS или managed endpoint. `DATABASE_URL` меняется только
  на endpoint, не на конкретную ВМ.
- Убрать обязательный локальный сервис `postgres` из compose (профиль/отдельный файл): иначе
  контейнер API продолжит стартовать с `postgres:5432`, даже если в `.env` уже другой адрес.
- TLS между API и PostgreSQL; HBA только с приватных адресов.
- Fencing-контроллер (7.4): проверка питания через MWS API, выключение старого primary,
  promotion, запись события в аудит.
- Возврат node-1: запуск как standby, `pg_rewind`/reclone при необходимости; **без failback**.

**Приёмка:**

- жёстко выключить node-1 (power off) → node-2 становится primary, API пишет, проект
  открывается;
- включить node-1 → она становится standby, не принимает записи, догоняет WAL;
- при разделении сети (iptables drop между узлами) автоматический promotion не происходит;
- проверить RPO/RTO на реальных данных, записать цифры;
- старый primary после возврата не имеет двух primary и не теряет транзакции незаметно.

### C3. Storage HA и полный переход на node-2 (3–5 дней)

- ✅ Spike выполнен: выбран GlusterFS replica 2; DRBD не понадобился.
- Перенести `SANDBOX_DIR`, `DATA_DIR`, `SITES_DIR` на общий POSIX-слой.
- Проверить права uid 1000, NFS `all_squash`/UID mapping, блокировки, `rename` и `fsync`.
- Настроить автоматическое перемонтирование и health-проверку storage.
- Проверить, что API на node-2 читает и пишет проекты, созданные на node-1.
- Проверить восстановление проекта из S3, если storage потерян.

**Приёмка:**

- выключить node-1 целиком → node-2 открывает существующий проект, запускает preview,
  терминал и агент;
- вернуть node-1 → она видит те же файлы как клиент storage, не создаёт вторую копию;
- отключить storage на 30 секунд → API отдаёт понятную ошибку, а не пишет в локальный диск;
- проверить, что `DATA_DIR` с платформенными ключами доступен обеим репликам.

### C4. Ingress, TLS и preview (2–4 дня)

- NLB с health check на оба Caddy; один публичный адрес.
- Сертификаты на всех узлах; wildcard не выпускается заново на каждом.
- Preview: общий реестр + маршрутизация на узел-владелец; проверить HTTP и HMR WebSocket.
- WebSocket агента: sticky по cookie или корректное переподключение; проверить, что второй
  запрос не стартует второй запуск.
- Терминалы: переподключение и понятная ошибка при падении узла.

**Приёмка:**

- остановить Caddy на node-1 → HTTPS продолжает работать через node-2;
- preview, открытый до остановки node-1, после перезапуска поднимается на node-2;
- HMR WebSocket работает через NLB;
- вход и cookie `__Host-` не ломаются при смене узла.

### C5. Третья ВМ и кворум (когда появится)

## 11. Риски и открытые решения

| Риск/решение | Почему важно | Статус |
| --- | --- | --- |
| Нет третьей ВМ | нет кворума, автоматический failover на двух узлах рискован | открыто |
| Storage без кворума | GlusterFS replica 2 работает, но без arbiter есть риск split-brain | открыто |
| `node-2` 20 ГБ | не хватит на API+runner+БД+storage | нужно увеличить или разделить роли |
| `node-2` выключена до production | без включённого standby двусторонний контур не активен | standby после rejoin 10.11 готов; включить при запуске HA |
| Managed vs self-hosted DB | влияет на стоимость, RTO и сложность | решить в C2 |
| Ingress | без NLB/DNS второй API не получит трафик | NLB готов; проверить TLS/WebSocket под нагрузкой |
| Секреты в `DATA_DIR` | общий диск увеличивает blast radius | минимизировать, права 700/600 |
| Две реплики и фоновые задачи | дубли архивов, писем, реконсиляции | лок/лидер в C1–C2 |

**Важное следствие:** двусторонний failover уже проверен, но до production-запуска `node-2`
выключается из-за стоимости. Для постоянного production-HA её нужно включить и держать
включённой; standby после rejoin 10.11 готов, но после каждого switchover всё равно нужен
rejoin. Иначе это режим «ручной cutover со свежим дампом», а не HA.

### 11.1. Правило работы с `node-2`

`node-2` — вторая production-нода, а не тестовая машина. Сейчас она выключается только
из-за стоимости до production-запуска:

- для работы, которой нужны две машины, `node-2` включается **без отдельного вопроса**;
- после **всех** работ она выключается — при успехе, ошибке, таймауте и прерванной проверке;
- работа не считается законченной, пока MWS не покажет `power=OFF`;
- оставлять её включённой «чтобы не включать снова» нельзя до production-решения;
- production `DATABASE_URL` и storage не могут зависеть от ВМ, которую выключают;
- после запуска production-HA `node-2` работает круглосуточно постоянно.

Перед тестом: включить, дождаться SSH и сервисов, убедиться, что прод не смотрит на `node-2`.
После теста: вернуть прод в исходное состояние, выключить ВМ и проверить `power=OFF`.

## 12. Что делаем первым

Первый слой не требует выключения `node-1` и не переводит прод на `node-2`:

1. **✅ Изоляция временных файлов реплик.** `DATA_DIR/tmp/<node-id>` и
   `.restore-<node-id>-*`; уборка при старте чистит только свой namespace. Это устраняет
   документированное ограничение из `SCALING_3000_PLAN.md` (4.2) и делает безопасным запуск
   второй API-реплики на общем диске. Новый модуль — `server/src/storage/temp-paths.ts`.
2. **✅ Advisory-лок инициализации схемы.** Один инициализатор, остальные ждут; без этого
   несколько реплик не должны стартовать одновременно. Лок вынесен в отдельный модуль
   `server/src/storage/init-lock.ts`, снимается в `finally`, падение процесса освобождает его
   вместе с соединением.
3. **✅ Общий реестр preview.** `server/src/preview/preview-registry.ts` хранит container-preview
   в `previews` (`server/src/storage/preview-table.ts`) и поднимает его при промахе локального
   кэша. `preview-store.ts` пишет в базу через очередь на проект, `preview-manager.ts`
   гидрирует состояние в статусе, логах и остановке; health, egress, архивация и перенос
   проекта тоже видят preview с другой реплики. TTL — `PREVIEW_REGISTRY_TTL_MS`, по умолчанию
   15 минут; heartbeat продлевает его не чаще раза в 15 секунд.
4. **✅ Общие аренды запусков.** `server/src/agent/run-lease.ts` и таблица `run_leases`
   (`server/src/storage/run-lease-table.ts`) дают один запуск агента на аккаунт между
   репликами. Аренда живёт `RUN_LEASE_TTL_MS` (120 с) и продлевается раз в треть TTL; локальный
   лимитер остаётся предохранителем процесса. В аренде хранится проект, поэтому
   `server/src/agent/run-activity.ts` отвечает «проект занят» и для запуска на другой ВМ;
   этим пользуются архивация, перенос, idle-уборка preview и удаление проекта. Если PostgreSQL
   недоступен, запуск не блокируется навсегда — остаётся локальное правило, это осознанное
   ослабление на время сбоя.
5. **✅ Общие лимиты preview.** Менеджер считает container-preview по общему реестру, а
   `server/src/preview/preview-reservation.ts` и таблица `preview_reservations`
   (`server/src/storage/preview-reservation-table.ts`) закрывают окно между проверкой и
   стартом. Бронь короткая, но переживает падение процесса благодаря TTL; лимит аккаунта и
   потолок хоста проверяются атомарно. В JSON-режиме и при недоступной базе остаётся
   локальная проверка.
6. **✅ OAuth-состояния между репликами.** `oauth_states` хранит state, владельца и
   PKCE-verifier; обычные подключения и GitVerse-вход переживают callback на другой реплике.
7. **✅ Разделение готовности.** `/api/node/ready` проверяет Docker и монтирование песочницы,
   `/api/ready` остаётся общей готовностью API для выкатки и монитора.

**Приёмка C1 на живой паре:** общий `DATA_DIR`/`SITES_DIR`/`SANDBOX_DIR` через GlusterFS,
API/Caddy/broker на `node-2`, двусторонний PostgreSQL failover и DNS failover проверены
08.11.2026; плановый switchover, оба rejoin, холодный старт и cross-replica preview —
10.11.2026. Остались production-усиления: witness/quorum, исправление автоматического
storage-quorum и automount, **чистый** destructive failover drill на текущем `deploy/ha`
по [PRODUCTION_LAUNCH.md](PRODUCTION_LAUNCH.md) и постоянное включение `node-2`. Static-preview
теперь пишется в общий реестр с `owner_address`; подробности —
[PRODUCTION_STATE.md](PRODUCTION_STATE.md) §10. Телефонный вход и SMS отменены навсегда
(10.11.2026), поэтому `phone-store` и общий store для кодов в оставшийся scope не входят.

**Проверено локально (08.11.2026, после правок):** полный набор сервера — **1656/1656**;
