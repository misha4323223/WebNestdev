# Тарифы и собственный serverless-runtime

Статус: **основной путь реализован и проверен локально**. Обновлено: 17.11.2026, 13:08 UTC.

Документ фиксирует разницу между тем, что уже есть в коде, и целевой моделью:

| Тариф | Что продаём |
|---|---|
| Старт (`free`) | Только статические сайты. Без терминала, без контейнерного preview, без функций. |
| Плюс (`pro`) | Статические сайты и serverless-функции на своём хосте. Без терминала и без контейнерного preview. |
| Премиум (`team`) | Статические сайты, serverless-функции, интерактивный терминал и контейнерный preview. |

Важно: serverless-функции **не требуют постоянного контейнера за сайтом**. Код функции собирается
один раз, хранится как артефакт и исполняется в общем пуле короткоживущих изолированных
исполнителей только на время запроса. Терминал и контейнер — инструменты разработки Премиума, а не
обязательная часть хостинга функций.

## 1. Что уже есть

### Тарифы

- `server/src/account/plans.ts` — каталог `free/pro/team`, названия уже «Старт», «Плюс», «Премиум».
- `accountPlanFor` (`server/src/billing/store.ts`) — единственный источник действующего тарифа.
- Лимиты проектов, кредитов, хранилища, поиска, интеграций и минут песочницы уже проверяются на
  сервере.
- Витрина и оплата читают каталог из `publicPlans()` (`server/src/billing/robokassa.ts`).

### Хостинг

- `server/src/hosting/*` — статический хостинг: сайт, релизы, S3-архив, rollback, Caddy, TLS,
  пользовательские домены.
- `HostingProjectKind = "instant-site" | "static-build"`.
- Публикация отклоняет всё, что не статика (`PROJECT_NOT_STATIC`), поэтому функции сейчас
  захостить нельзя даже на Премиуме.

### Preview и терминал

- `server/src/preview-manager.ts` умеет три режима: `static`, `container`, `hybrid`.
- Статический preview не занимает контейнер; контейнерный и hybrid занимают.
- `server/src/routes/preview.ts` запускает preview без проверки тарифа.
- `server/src/routes/workspace.ts` (`POST /api/projects/:id/terminal`) запускает команды без
  проверки тарифа.
- Панель терминала (`src/features/terminal/TerminalPanel.tsx`) видна всем.
- Агентские `terminal.exec`, `terminal.start`, `npm.install`, `pip.install` — это внутренние
  инструменты сборки, а не пользовательский терминал. Их нельзя отключать на Плюсе: без них агент
  не сможет собрать и проверить статический сайт или функцию.

### Фундамент для функций

- `server/src/deployment/profile.ts` уже распознаёт `static-functions` и `functions`, каталоги
  `functions/`, `api/`, `server/`, `backend/`, `netlify/functions/`, `vercel/api/`,
  `serverless.yml`, `vercel.json`, `netlify.toml`, пакеты Yandex/Google/Azure/Netlify/AWS.
- Этого профиля достаточно, чтобы понять **что** за проект, но не чтобы его исполнять.
- Docker runner, Docker-брокер, sandbox-контейнеры, S3, PostgreSQL, секреты, job queue и
  owner-routing уже есть. Их можно переиспользовать для сборки и пула функций.

## 2. Что реализовано (17.11.2026, 13:08 UTC)

1. `account/entitlements.ts` — единая матрица возможностей, `PLAN_FEATURE_REQUIRED` (403).
2. Тариф проверяется на сервере: терминал панели, контейнерный/hybrid preview, публикация функций.
3. `functions/manifest.ts` — строгий `nestdev.functions.json`; неизвестные поля, дубли, пути вне
   `/api`, выход из проекта и лишние методы отклоняются.
4. `functions/build.ts` — esbuild-бандл каждой функции в `.functions/<name>/index.mjs` и
   `.functions/manifest.json`; нативные аддоны, секреты в бандле и превышение размера отклоняются.
5. `functions/invoke.ts` + `functions/worker.mjs` — один контейнер на запрос: read-only артефакт,
   `--cap-drop ALL`, `no-new-privileges`, non-root, лимиты CPU/RAM/PID, `bridge`, Node permission
   model, таймаут и удаление контейнера.
6. `functions/host-server.ts` — отдельный слушатель `:8792`, Host → сайт → активный релиз →
   функция. Нет функции — JSON 404, а не `index.html`.
7. Caddy (`deploy/Caddyfile` и custom-domain генератор) отправляет `/api/*` на `:8792` до
   статического fallback.
8. Функции лежат внутри релиза и попадают в тот же S3-архив; rollback возвращает статику и API
   одной версией.
9. Агент на «Старте»/«Плюсе» не собирает серверный проект: `terminal.exec`/`terminal.start`
   отказывают до запуска, если профиль проекта — постоянный сервер. Тесты, линтеры и статические
   сборки остаются доступны.

Ещё не сделано: тёплый пул (сейчас cold start на каждый запрос), Python-runtime, потоковые
ответы, точные метрики p50/p95 и лимит числа вызовов по тарифу. Это следующие этапы, а не
скрытая часть текущего.

## 3. Целевая архитектура

### 3.1. Единая модель возможностей

`server/src/account/entitlements.ts`:

```ts
type PlanFeature =
  | "staticHosting"
  | "serverlessFunctions"
  | "interactiveTerminal"
  | "containerPreview";
```

| Возможность | Старт | Плюс | Премиум |
|---|---:|---:|---:|
| `staticHosting` | да | да | да |
| `serverlessFunctions` | нет | да | да |
| `interactiveTerminal` | нет | нет | да |
| `containerPreview` | нет | нет | да |

Правила:

- Ограничение проверяется на сервере в момент действия, а не только прячется в UI.
- Ответ отказа: HTTP 403, `code: "PLAN_FEATURE_REQUIRED"`, `feature`, `requiredPlan`.
- Агентские инструменты сборки и установки зависимостей не считаются интерактивным терминалом.
- Статический preview разрешён всем; контейнерный и hybrid — только Премиуму.
- Уже созданные проекты и сайты не удаляются при понижении тарифа. Отключается только действие.

### 3.2. Манифест функций

Явный контракт важнее угадывания. Поддерживаются два источника:

1. `nestdev.functions.json` в корне проекта — основной формат.
2. Автоопределение по каталогам (`functions/`, `api/`, `serverless.yml`) только для предложения
   миграции, не для публикации.

Пример:

```json
{
  "version": 1,
  "runtime": "node",
  "functions": [
    {
      "name": "orders",
      "path": "/api/orders",
      "methods": ["GET", "POST"],
      "handler": "functions/orders.ts#handler",
      "timeoutMs": 10000,
      "memoryMb": 256
    }
  ]
}
```

Требования:

- `path` начинается с `/api/`, без `..`, без query и fragment.
- `handler` — путь внутри проекта, файл и экспорт.
- Один путь не может принадлежать двум функциям.
- Method по умолчанию `["GET"]`, допустимы `GET/POST/PUT/PATCH/DELETE/OPTIONS`.
- Неизвестные поля отклоняются с понятной ошибкой.

### 3.3. Сборка

Сборка выполняется один раз при публикации, в отдельном job, без интерактивного терминала:

1. Прочитать и проверить манифест.
2. Установить зависимости проекта (`npm ci` / `npm install` по lock-файлу).
3. Собрать каждую функцию в отдельный bundle (Node — esbuild/tsc, Python — wheel/venv-архив).
4. Записать `manifest.json` с версией, хешем и списком файлов.
5. Загрузить артефакт в S3; в БД хранить ключ, хеш и размер, а не код.
6. Активировать релиз атомарно вместе со статикой.

Правила:

- Сборка не имеет доступа к production-секретам.
- Секреты монтируются только при исполнении, не попадают в артефакт и логи.
- Ограничения: размер bundle, время сборки, число функций на проект.

Фактическая реализация: зависимости проекта уже стоят в песочнице (иначе функция не соберётся);
`esbuild` собирает `path#export` в один ESM-файл. Один собранный файл — до 10 МиБ, общий размер
релиза ограничен `HOSTING_MAX_RELEASE_BYTES`. Внешние нативные `.node`-аддоны не поддерживаются:
их нужно заменить JS-реализацией или вынести в отдельный сервис.

### 3.4. Исполнение

```text
Клиент → Caddy/NLB → API-роутер сайта → пул исполнителей → функция → ответ
```

- Роутер знает по хосту и пути, какой релиз и какая функция должны ответить.
- Исполнитель — короткоживущий изолированный процесс/контейнер из общего пула.
- На запрос передаются method, path, query, headers, body, project id, function name.
- Внутрь передаются только разрешённые env/секреты проекта.
- Ответ ограничен по размеру; потоковый ответ — отдельный этап.
- Таймаут убивает исполнитель, а не оставляет процесс.
- Один исполнитель обслуживает один запрос; никакого общего состояния между проектами.
- Тёплый пул уменьшает cold start, но не создаёт «контейнер сайта»: после простоя исполнители
  масштабируются до нуля.

Изоляция:

- без Docker-сокета и без доступа к хосту;
- без чтения чужих workspace;
- только проектный артефакт, смонтированный read-only;
- `cap-drop ALL`, `no-new-privileges`, non-root, лимиты CPU/RAM/PID;
- egress только через политику: БД и разрешённые API, без доступа к внутренней сети платформы;
- секреты не видны в `ps`, логах и ответах.

### 3.5. Маршрутизация и домены

- Статика сайта отдаётся как сейчас.
- `/api/*` уходит в functions-роутер только если в релизе есть функции.
- Если функции нет — честный 404, а не HTML сайта.
- Пользовательский домен и `*.nestdev.ru` работают одинаково.
- Ошибка функции не роняет статику и другие сайты.
- Rollback возвращает и статику, и функции одной версией.

### 3.6. Лимиты и наблюдаемость

На функцию:

- время выполнения;
- память;
- размер запроса и ответа;
- конкурентность на проект и глобально;
- число вызовов в месяц по тарифу;
- размер артефакта и число функций.

Собираем:

- число вызовов, ошибок, таймаутов;
- p50/p95 длительности;
- cold start;
- потребление памяти;
- логи с корреляцией `requestId`, но без секретов.

## 4. Поэтапный план

### Этап 1. Entitlements и запреты (в работе)

- Добавить `entitlementsFor(plan)` и тесты.
- Вернуть возможности в `/api/account/entitlements` и `/api/billing`.
- Закрыть `POST /api/projects/:id/terminal` для Старта и Плюса.
- Закрыть контейнерный и hybrid preview для Старта и Плюса; статический preview оставить.
- Скрыть вкладку терминала в панели, если возможности нет.
- Обновить карточки тарифов.
- Не трогать агентские инструменты сборки.

Критерий: прямой API-запрос терминала на Плюсе получает 403; статический preview работает на всех;
контейнерный preview на Плюсе отклоняется до запуска контейнера; тесты и typecheck зелёные.

### Этап 2. Контракт и сборка функций

- `server/src/functions/manifest.ts`: схема, валидация, безопасные пути.
- `server/src/functions/discover.ts`: предложение манифеста по структуре проекта.
- `server/src/functions/build.ts`: сборка bundle и артефакта.
- Таблица `project_functions` и `function_releases`.
- Проверка `serverlessFunctions` при публикации.
- Тесты: невалидные пути, дубли маршрутов, отсутствующий handler, сборка Node-функции.

Критерий: проект с `nestdev.functions.json` собирается в артефакт, но ещё не принимает трафик.

### Этап 3. Runtime MVP

- Пул исполнителей и протокол запроса/ответа.
- Локальный вызов функции для preview и тестов.
- Таймауты, лимиты, завершение процессов.
- Логи вызова.
- Feature flag `FUNCTIONS_RUNTIME_ENABLED`.

Критерий: тестовый сайт на Плюсе отвечает через `/api/health`; Старт получает 403; таймаут
возвращает 504 и не оставляет процессов.

### Этап 4. Публичный хостинг функций

- Роутер по хосту и пути.
- Совместный релиз статики и функций.
- Rollback.
- Пользовательские домены.
- Egress-политика и секреты только на исполнении.

Критерий: опубликованный сайт на Плюсе работает после перезапуска API и ноды; откат возвращает
предыдущую версию целиком.

### Этап 5. Квоты, биллинг и панель

- Месячные вызовы и конкурентность по тарифу.
- Страница функций: список, маршруты, логи, последние ошибки.
- Метрики и алерты.
- Обновление оферты и лимитов.

Критерий: лимит вызовов объясняется в UI и проверяется сервером; в логах нет секретов.

## 5. Что не входит в первый runtime

- Произвольные Dockerfile и пользовательские образы.
- Долгоживущие WebSocket-функции.
- Очереди и cron как отдельный продукт.
- GPU.
- Многорегиональность.
- Биллинг за каждый миллисекундный вызов.

## 6. Риски

| Риск | Мера |
|---|---|
| Побег из песочницы | отдельный исполнитель, read-only артефакт, без сокета, egress-политика |
| Cold start | тёплый пул с малым TTL, честные таймауты, метрика |
| Утечка секретов | секреты только в env исполнителя, маскирование логов |
| Один проект съедает хост | конкурентность и CPU/RAM на проект и глобально |
| Сломанный релиз | атомарная активация и общий rollback |
| Смешение статики и API | явный `/api/*`-роутер и 404 вместо fallback на index.html |
| Обход тарифа | проверка на сервере, а не только скрытие кнопки |

## 7. Проверки

- Точечные тесты сервера: `npm test --workspace=server -- --test-name-pattern=...`.
- Полный серверный набор перед выкаткой.
- `npx tsc -p server/tsconfig.json --noEmit`.
- `npx tsc -b --noEmit`.
- Для runtime: тест с реальным контейнером, таймаутом и параллельными вызовами.
- Для хостинга: публикация, запрос к статике, запрос к функции, rollback, перезапуск API.
