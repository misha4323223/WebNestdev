# Docker-брокер: узкий сокет вместо `docker.sock`

Статус: **этапы 1–4 включены и проверены на проде (30.10.2026)**: сервер говорит с Docker только
через брокер, прямой `/var/run/docker.sock` ему не смонтирован; процесс сервера работает не от
root, сокет брокера доступен ему по общей группе. Откат на предыдущий образ и полный порядок — в §6.
Закрывает P1 #5 из [SECURITY.md](SECURITY.md): раньше сервер в контейнере работал root и держал
`/var/run/docker.sock`, поэтому любая RCE в API равнялась root на хосте.

## 1. Что это меняет и чего не меняет

Сегодня сервер запускает `docker ...` напрямую и получает полный Engine API: можно смонтировать `/`,
прочитать `.env` на хосте, том `postgres-data`, SSH-ключи и закрепиться в системе.

После включения брокера сервер говорит с Docker через `/run/webnestdev-docker/docker.sock`, а
брокер — единственный, кто видит настоящий сокет. Он пропускает ровно те операции, которые нужны
платформе, и проверяет каждый `containers/create`:

- монтировать можно только путь внутри каталога песочниц (плюс `.secret-runtime` только как `ro`);
  путь проверяется дважды — по префиксу и по `realpath`, потому что каталог песочниц смонтирован
  в брокер только на чтение. Иначе ссылка `link -> /` внутри проекта обходила бы проверку;
- обязательны `ReadonlyRootfs`, `CapDrop: ["ALL"]`, `no-new-privileges`, uid 1000, лимиты памяти,
  CPU и pids;
- сеть — только `none`, `bridge` или сеть предпросмотра; `host`, `container:<id>` и сеть базы
  отклоняются. `NetworkingConfig` разрешён только для той же сети, что `HostConfig.NetworkMode`, и
  только с пустыми настройками endpoint: Docker CLI присылает его при каждом `--network`, а aliases,
  links и IPAM позволяли бы выдать контейнер за другой сервис;
- запрещены `Privileged`, `CapAdd`, `Devices`, `PidMode`/`IpcMode`/`UsernsMode`, публикация портов,
  `RestartPolicy` кроме `no`, удалённые драйверы логов (иначе вывод контейнера можно увести на чужой
  syslog), `Sysctls`, `ExtraHosts`, `Dns`, `VolumesFrom`, `CgroupParent`, `SecurityOpt` кроме
  `no-new-privileges:true`, `Tmpfs` вне `/tmp`;
- операции над существующими контейнерами (`start`, `attach`, `exec`, `exec/{id}/json`, `logs`,
  `inspect`, `rm`) разрешены только для своих: контейнер должен иметь метку `webnestdev.*` или имя
  `wnd-*`. Иначе через `logs` или `inspect` было бы видно чужие контейнеры, включая `postgres`;
  `exec/{id}/json` (код выхода) — только для сессии, созданной через брокер;
- `network connect` — только для сети предпросмотра и только для своего контейнера. Иначе
  пользовательский контейнер можно было бы подключить к сети базы;
- всё остальное (`images/create`, `build`, `volumes`, `secrets`, `configs`, `swarm`, `plugins`,
  `containers/{id}/archive`, …) отклоняется: набор эндпоинтов закрыт по умолчанию.

**Чего это не закрывает.** API по-прежнему читает файлы всех проектов и расшифровывает секреты —
компрометация API остаётся тяжёлой. Контейнеры по умолчанию делят ядро с хостом: побег через
уязвимость ядра закрывается только осознанным включением gVisor (`SANDBOX_RUNTIME=runsc`, этап 2
в SCALING_3000_PLAN.md), а не брокером. Брокер сам привилегирован, поэтому он маленький и с
тестами на отказ.

## 2. Разбор поверхности: что сервер вызывает у Docker

Собрано по коду (`spawn("docker")`, `dockerExec`, `runDocker`). Брокер обязан пропускать всё это
без изменения поведения:

| Место | Вызовы | Что проверяет брокер |
|---|---|---|
| `sandbox/docker/args.ts` + `sandbox/jobs.ts` + `docker-sandbox.ts` | `run`, `rm -f`, `logs`, `inspect`, `version` | `create` по политике; остальное — свой контейнер |
| `preview/preview-runner.ts` | `run -d`, `inspect`, `logs`, `rm -f` | то же; метка `webnestdev.preview` делает контейнер своим |
| `preview/app-http.ts`, `app-port.ts`, `app-relay.ts`, `exec-proxy.ts`, `docker-exec.ts` | `exec` (в том числе `-d`) | контейнер свой; hijack проксируется байт-в-байт |
| `preview/preview-network.ts` | `network ls`, `network inspect`, `network connect`, `inspect` | сеть только `*preview`; контейнер свой |
| `routes/admin-infra.ts`, `routes/admin-prune.ts` | `ps --filter label`, `system df`, `image ls`, `builder prune`, `image prune` | только чтение и уборка кеша |
| `scripts/preview-selfcheck.ts` | `version`, `run -d`, `exec`, `rm -f` | как выше |

Четыре места, которые нельзя было сделать «по общим правилам»:

1. **Монтирование секретов предпросмотра** — это не каталог проекта, а
   `sandbox/.secret-runtime/<id>/*` как `:ro` (`secrets/preview-secrets.ts`). Белый список монтирований
   включает этот путь отдельно.
2. **`inspect` своего контейнера.** `serverNetworks()` определяет сети сервера по своему hostname.
   Брокер не может отличить «свой сервер» от «postgres», поэтому появился отдельный эндпоинт
   `GET /_webnestdev/self`: брокер сам смотрит свой hostname (он стоит в тех же сетях) и отдаёт
   список сетей. Сервер использует его, когда брокер активен. `inspect` произвольного контейнера
   закрыт.
3. **Hijack.** `docker exec` и `docker run` без `-d` открывают upgraded-соединение. Брокер
   проксирует его как поток байт после проверки, что контейнер свой, а `exec` создан через брокер.
   Тело upgrade-запроса (`exec/start` шлёт `{"Detach":false,"Tty":false}`) демон читает **до**
   ответа: в `postContainerExecStart` сначала `ReadJSON`, потом `HijackConnection` и `101`. Поэтому
   брокер собирает тело целиком (до `Content-Length`) и только затем соединяется с демоном: если
   отдать сокет сразу, байты тела, пришедшие между событием `upgrade` и подключением, теряются в
   потоке без слушателя, демон ждёт тело, клиент ждёт `101` — взаимоблокировка до таймаута, а в
   журнале демона остаётся `499` (отмена запроса клиентом). Молчание дольше
   `BROKER_HIJACK_TIMEOUT_MS` (15 с) даёт `504` с названием запроса и строку «hijack» в журнале.
   `docker exec` читает код выхода отдельным `GET /exec/{id}/json`; без него команда внутри
   контейнера выполнялась, а платформа видела отказ — на этом держатся готовность приложения,
   поиск порта по `/proc/net/tcp` и дверь предпросмотра через `docker exec`.
4. **Заголовки потокового ответа сбрасываются сразу.** `docker run` синхронно ждёт заголовки
   `POST /containers/{id}/wait`, и только потом посылает `start`, — так клиент гарантирует, что не
   пропустит выход короткоживущего контейнера. Демон отвечает `200` сразу и держит тело до остановки
   контейнера. Прокси, который пишет заголовки, но не сбрасывает их (Node отправляет их только с
   первым куском тела или в конце), получал взаимоблокировку: CLI ждёт заголовки, контейнер не
   стартует, тело не приходит. Поэтому после `writeHead` вызывается `flushHeaders()`. Симптом в
   журнале сервера — «Превышено время ожидания операции Docker», а в журнале брокера — запросы
   `create` и `wait` без единого `/start`.

## 3. Как это включено

- Брокер — тот же образ, что сервер, с другой командой:
  `node deploy/docker-broker/index.mjs`. Отдельного образа и отдельной выкатки в GHCR нет: версия
  брокера всегда совпадает с версией сервера, откат образа возвращает обе части.
- `docker-compose.yml`: сервис `docker-broker` держит `/var/run/docker.sock` и пишет свой сокет в
  том `docker-broker`; сервер монтирует только этот том и получает
  `DOCKER_HOST=unix:///run/webnestdev-docker/docker.sock`. Настоящий сокет серверу не смонтирован,
  поэтому `docker run -v /var/run/docker.sock ...` из API невозможен не политикой, а отсутствием
  файла. На хосте сокет остаётся — иначе не работал бы сам брокер.
- Сервер при старте проверяет сокет брокера (`GET /_ping`) и ждёт его до
  `WEBNESTDEV_DOCKER_BROKER_WAIT_MS` (по умолчанию 10 с), чтобы одновременный старт compose не
  ронял платформу. Если брокер так и не ответил, сервер убирает `DOCKER_HOST` и пишет
  предупреждение: API и панель работают, песочницы и предпросмотр — нет, потому что прямого
  сокета в контейнере больше нет.
- `WEBNESTDEV_DOCKER_BROKER=0` выключает брокер принудительно, не меняя compose. Это переключатель
  для разработки, где смонтирован прямой сокет; на текущем production-образе он оставит сервер
  без Docker, а не вернёт прежнее поведение.
- Инвариант: брокер стоит в тех же сетях, что сервер (`webnestdev`, `webnestdev-preview`), иначе
  `/_webnestdev/self` вернёт не тот набор сетей и предпросмотр потеряет адрес.
- Сокет создаётся с правами `0660`; брокер остаётся root (только он видит настоящий
  `docker.sock`), а сервер после entrypoint работает от uid 1000. Compose запускает брокер с
  `user: "0:1000"`, поэтому сокет создаётся сразу с группой сервера; `chown` остаётся запасным
  путём для другого `BROKER_SOCKET_GID` и без `CAP_CHOWN` не сработает. `BROKER_SOCKET_MODE`
  по-прежнему `0660`.
- Runtime контейнеров задаёт `SANDBOX_RUNTIME` (`docker` или `runsc`), но клиент не может прислать
  произвольный `HostConfig.Runtime`: брокер сверяет его с `BROKER_RUNTIME` (по умолчанию `docker`)
  и отклоняет остальное. При включённом `runsc` пустой `Runtime` тоже отклоняется: Docker взял бы
  рантайм по умолчанию (runc), и gVisor обходился бы одним отсутствующим флагом. Обе переменные
  должны совпадать; при включении gVisor это `SANDBOX_RUNTIME=runsc` и `BROKER_RUNTIME=runsc`
  (workflow/compose передают одно значение).
- У каждого запроса к демону есть предел ожидания заголовков ответа — `BROKER_UPSTREAM_TIMEOUT_MS`
  (по умолчанию 10 с). Молчащий демон получает `504` с текстом «демон не ответил на `<метод> <путь>`
  за N с», и это же уходит в журнал брокера. Без предела зависший `create`/`start` выглядел в
  журнале сервера как «Превышено время ожидания операции Docker» без указания, что именно не
  ответило; теперь причина в логе на шаг раньше. Для потоковых ответов (`logs`, hijack) предел
  действует только на соединение и на заголовки: тишина внутри потока — нормальная работа
  приложения, а не зависший демон. Подкоманда, на которой истёк предел сервера, теперь тоже
  называется в ошибке (`run`, `inspect`, `exec`), так что причину видно и без журнала брокера.

## 4. Этапы и критерии

| Этап | Что | Критерий |
|---|---|---|
| 1 | Брокер, политика, тесты, compose с обоими сокетами, сервер с фолбэком | тесты брокера и сервера зелёные; выкатка поднимает `docker-broker` |
| 2 | Обкатка: выкатка и сутки обычной работы | `DOCKER-CHECK=ok` в логе выкатки; предпросмотр, `npm install`, долгие задания, админская уборка работают |
| 3 | Снять `/var/run/docker.sock` у сервера в compose | ✅ сделано: `DOCKER-CHECK=ok` и `PREVIEW-NETWORK=ok` в логе выкатки, сервер в логе старта сообщает «работаю через Docker-брокер» |
| 4 | Сервер не root (entrypoint сбрасывает права) + группа на сокет брокера | ✅ выкачено и проверено 30.10.2026: `SERVER-USER=ok uid=1000`, `/api/health` зелёный, песочницы и предпросмотр работают |

Этап 3 сделан отдельным коммитом: пока брокер обкатывался, прямой сокет был нужен для мгновенного
отката. После этапа 2.2 возврат одной строки монтирования уже не работает: сервер под uid 1000
не имеет доступа к `root:docker 0660`. Штатный откат — предыдущий образ, полный порядок в §6.

## 5. Проверка на ВМ после выкатки

```bash
cd ~/webnestdev/src
docker compose ps docker-broker webnestdev-server
docker compose logs --tail=50 docker-broker
# куда реально ходит процесс сервера — единственный надёжный признак:
docker compose logs webnestdev-server | grep '\[docker\]'
# видит ли брокер запросы платформы:
docker compose logs --tail=200 docker-broker | grep '\[broker\]'
# процесс сервера не root: uid/gid из PID 1, а не из exec-сессии
docker compose exec -T webnestdev-server sh -c 'awk "/^Uid:/{print \$2, \$3}" /proc/1/status'
# и то же в /api/health (внутренний запрос с хоста):
curl -fsS http://127.0.0.1:8787/api/health | grep -o '"process":{[^}]*}'
# путь Docker из контейнера сервера (через сокет брокера):
docker compose exec -T webnestdev-server sh -c 'echo $DOCKER_HOST; docker version --format "{{.Server.Version}}"'
# полная проверка пути предпросмотра (через брокер):
docker compose exec -T webnestdev-server node server/dist/scripts/preview-selfcheck.js
```

Ожидаемо: `DOCKER-CHECK=ok` в логе выкатки, строка
`[docker] работаю через Docker-брокер: /run/webnestdev-docker/docker.sock` в логе старта,
запросы в логе брокера и `PREVIEW-NETWORK=ok`. `echo $DOCKER_HOST` в `compose exec` показывает
переменную из конфигурации контейнера, а не выбранный процессом адрес: после неудачного старта
сервер убирает её только у себя в памяти. Поэтому признак «сервер ходит через брокер» — строка
в логе и трафик брокера, а не эта переменная.

## 6. План Б: как вернуть всё назад

Порядок — от самого быстрого к полному. Важно: после этапа 2.2 сервер работает от uid 1000, а
прямой `/var/run/docker.sock` принадлежит `root:docker` с mode `0660`. Поэтому одного возврата
строки монтирования уже недостаточно — uid 1000 получит `EACCES`. Прямой сокет работает только
со старым образом (или с явно возвращённым root, чего делать не нужно).

1. **Брокер упал, сервер жив.** `docker compose restart docker-broker`; сервер переподключится
   сам — `DOCKER_HOST` указывает на сокет, а не на процесс. Если сокет не появился, смотрите
   `docker compose logs docker-broker`: чаще всего это занятый файл сокета или ошибка прав.
2. **Сервер не доходит до брокера.** Проверьте, что `BROKER_SOCKET_GID` (в compose он берётся из
   `WEBNESTDEV_GID`) совпадает с gid процесса сервера и что том `docker-broker` смонтирован в
   оба контейнера. Проверка:
   ```bash
   docker compose exec -T --user 1000:1000 webnestdev-server docker version
   ```
   Если ошибка сохраняется, пересоздайте брокер и сервер; это не требует менять образ.
3. **Вернуть прошлый образ сервера.** Это штатный откат этапа 2.2. `deploy.yml` умеет
   откатываться на предыдущий образ; старый сервер работает root, поэтому может использовать и
   сокет брокера, и прямой сокет. Брокер при этом можно оставить. Если пересоздаёте и брокер
   (`--force-recreate`), в старом образе кода брокера нет: добавьте `WEBNESTDEV_DOCKER_BROKER=0`
   **и** верните монтирование прямого сокета — иначе Docker у сервера не будет вовсе.
   `WEBNESTDEV_DOCKER_BROKER=0` на текущем (не-root) образе не поможет: прямого сокета ему всё
   равно недостаточно.
4. **Полный откат.** `git revert` коммитов брокера и этапа 2.2, затем обычная выкатка: compose
   вернётся без сервиса `docker-broker` и с прямым сокетом, сервер — на root. Никаких ручных
   действий на ВМ не требуется.

Если брокер упал в работе: `docker compose restart docker-broker`. Сервер переподключится сам —
`DOCKER_HOST` указывает на сокет, а не на процесс. Если не поднимается — уровень 2.

## 7. Остаточные риски

- Прямого сокета у сервера больше нет, но брокер видит демон хоста целиком: RCE в API больше не
  даёт хост напрямую, а компрометация брокера — даёт. Поэтому брокер остаётся маленьким, с
  закрытым по умолчанию набором запросов и тестами на отказ.
- Контейнеры по умолчанию делят ядро с хостом: побег через уязвимость ядра обходит и брокер.
  gVisor для контейнеров команд и превью включён на проде флагом `SANDBOX_RUNTIME=runsc`
  (30.10.2026); установка автоматизирована в деплое, но матрица HMR/WebSocket и замеры ещё не
  закрыты (`docs/SCALING_3000_PLAN.md`, этап 2.1).
- Брокер не различает проекты: смонтировать каталог другого проекта он разрешит. Разграничение
  владения — задача API (и она есть в маршрутах); брокер защищает хост, а не арендаторов друг от
  друга.
- `exec` внутри контейнера по-прежнему работает от root (как и раньше): это root внутри песочницы,
  не на хосте.
