# API администратора платформы

Текущее состояние работ, доступы и следующая задача: [ADMIN_HANDOFF.md](ADMIN_HANDOFF.md).

Вход в админку — отдельная дверь, не связанная ни с пользователями панели, ни с их сессиями.
Админ-приложение обращается к API с `Authorization: Bearer <токен>`; cookie не используются вообще,
поэтому браузер не может приложить вход к чужому запросу, а CORS открывается только для адресов из
`WEBNESTDEV_ADMIN_ORIGINS`.

Код: `server/src/routes/admin.ts`, `server/src/admin/*`. Тесты: `server/src/admin/totp.test.ts`,
`server/src/routes/admin.test.ts`.

## 1. Создание администратора

Самостоятельной регистрации нет: аккаунт создаётся на сервере, то есть с теми же правами, что нужно
для развёртывания.

```bash
# разработка
cd server
npm run admin:create -- --email admin@example.com

# production (в образе только собранный dist)
docker compose exec webnestdev-server node server/dist/scripts/admin-cli.js create --email admin@example.com
```

Команда печатает пароль **один раз** — его надо сохранить в менеджере паролей. Дальше:

| Команда | Что делает |
|---|---|
| `create --email <адрес>` | создаёт администратора, печатает пароль |
| `password --email <адрес>` | новый пароль, TOTP сохраняется, все входы отзываются |
| `reset-2fa --email <адрес>` | сбрасывает TOTP и recovery-коды, отзывает все входы |
| `list` | список администраторов и состояние второго фактора |

`reset-2fa` — единственный способ вернуть доступ при потерянном телефоне и кодах. Через API сброс
недоступен: иначе украденный пароль сам снимал бы с себя второй фактор.

### 1.1. Если терминала на ВМ нет

Пароль нельзя придумать в панели: аккаунта ещё нет. Поэтому первого администратора можно объявить
в окружении развёртывания — выкатка доставляет переменные в `.env` на ВМ, а сервер создаёт запись
при старте.

1. В GitHub: **Settings → Secrets and variables → Actions → Secrets** добавьте два секрета:
   `ADMIN_BOOTSTRAP_EMAIL` (ваш адрес) и `ADMIN_BOOTSTRAP_PASSWORD` (не короче 12 символов;
   лучше 16+ букв и цифр без кавычек, `#` и `$` — значение идёт через `.env` и docker compose,
   где такие символы могут сломать разбор строки).
2. Запустите выкатку: **Actions → deploy → Run workflow**.
3. В логе старта появится `admin account created from environment`; сам пароль в лог не пишется.
4. Войдите в админ-приложении этими адресом и паролем: первый вход попросит подключить TOTP и
   выдаст коды восстановления.
5. После входа замените значение `ADMIN_BOOTSTRAP_PASSWORD` на длинную случайную строку и выкатите
   снова. Удалить секрет недостаточно: пустые значения выкатка пропускает, и прежняя строка
   осталась бы в `.env`. Пока администратор существует, значение всё равно не действует — замена
   нужна на случай, если запись когда-нибудь удалят.

Пароль короче 12 символов отклоняется — в логе будет `admin bootstrap skipped` с причиной, а
существующая запись не меняется ни при какой повторной выкатке: ни пароль, ни TOTP не сбрасываются.

Этим же способом можно завести ещё одного администратора: поменяйте `ADMIN_BOOTSTRAP_EMAIL` на
другой адрес — сервер создаст новую запись, прежние останутся. Сброс пароля и фактора по-прежнему
делается CLI (`password`, `reset-2fa`). Если у ВМ есть веб-консоль (VNC) в карточке инстанса в MTS
Cloud Platform, оттуда доступен обычный терминал и те же команды.

## 2. Вход

Пароль сам по себе сессию не выдаёт. Он возвращает короткий пропуск (`challenge`) и стадию:

- `enroll` — второй фактор ещё не подключён, его нужно настроить;
- `verify` — нужен код из аутентификатора или код восстановления.

### 2.1. Пароль

```bash
curl -s https://panel.example.com/api/admin/login \
  -H 'content-type: application/json' \
  -d '{"email":"admin@example.com","password":"…"}'
```

```json
{ "stage": "enroll", "challenge": "…", "email": "admin@example.com", "totpEnabled": false }
```

Неверный пароль и неизвестный адрес отвечают одинаково: `401 {"error":"Неверный email или пароль"}`.
Пропуск живёт 10 минут (`ADMIN_CHALLENGE_TTL_MS`), ошибок в коде — не больше пяти.

### 2.2. Первое подключение фактора

```bash
curl -s https://panel.example.com/api/admin/2fa/setup \
  -H 'content-type: application/json' \
  -d '{"challenge":"…"}'
```

```json
{
  "challenge": "…",
  "secret": "JBSWY3DPEHPK3PXP…",
  "otpauth": "otpauth://totp/NestDev:admin%40example.com?secret=…&issuer=NestDev&algorithm=SHA1&digits=6&period=30",
  "issuer": "NestDev",
  "account": "admin@example.com",
  "digits": 6,
  "period": 30
}
```

Секрет показывается один раз. В аутентификатор его вводят вручную (группами по четыре символа) или
открывают ссылку `otpauth`/рисуют из неё QR-код — API QR не отдаёт, чтобы не тянуть зависимость.

Подтверждение кодом завершает и подключение, и вход:

```bash
curl -s https://panel.example.com/api/admin/2fa/enable \
  -H 'content-type: application/json' \
  -d '{"challenge":"…","code":"123456"}'
```

```json
{
  "token": "…",
  "expiresAt": "2026-10-25T23:00:00.000Z",
  "admin": { "id": "…", "email": "admin@example.com", "totpEnabled": true, "createdAt": "…" },
  "recoveryCodes": ["ABCDE-23456", "…"],
  "recoveryCodesLeft": 10
}
```

`recoveryCodes` — единственный раз, когда коды видны в открытом виде. В базе лежат только их
sha256-хеши.

### 2.3. Обычный вход

```bash
# 1) пароль
curl -s https://panel.example.com/api/admin/login -H 'content-type: application/json' \
  -d '{"email":"admin@example.com","password":"…"}'
# → {"stage":"verify","challenge":"…"}

# 2) код из аутентификатора (или один из recovery-кодов)
curl -s https://panel.example.com/api/admin/2fa/verify -H 'content-type: application/json' \
  -d '{"challenge":"…","code":"123456"}'
# → {"token":"…","expiresAt":"…","admin":{…},"usedRecoveryCode":false}
```

Каждый принятый код TOTP запоминается по номеру шага (`lastTotpStep`): повторно предъявить его в
том же окне нельзя. Код восстановления удаляется после первого использования; `recoveryCodesLeft`
в ответе говорит, сколько осталось.

## 3. Маршруты

| Метод и путь | Авторизация | Назначение |
|---|---|---|
| `POST /api/admin/login` | — | пароль → `challenge` + стадия |
| `POST /api/admin/2fa/setup` | `challenge` | новый TOTP-секрет и `otpauth`-ссылка |
| `POST /api/admin/2fa/enable` | `challenge` | подтвердить фактор, получить токен и recovery-коды |
| `POST /api/admin/2fa/verify` | `challenge` | код TOTP или recovery → токен |
| `POST /api/admin/2fa/recovery` | `Bearer` | перевыпустить набор recovery-кодов (нужен действующий код) |
| `GET /api/admin/me` | `Bearer` | кто вошёл и до какого времени |
| `POST /api/admin/logout` | `Bearer` | закрыть текущий вход |
| `POST /api/admin/logout-all` | `Bearer` | закрыть все входы администратора |
| `GET /api/admin/stats/overview` | `Bearer` | обзор: люди, проекты, токены, запуски, модели |
| `GET /api/admin/stats/series` | `Bearer` | ряд по дням (пустые дни — нулями) |
| `GET /api/admin/stats/models` | `Bearer` | расход по моделям и доля каждой |
| `GET /api/admin/users` | `Bearer` | пользователи: поиск, сортировка, страница |
| `GET /api/admin/users/:id` | `Bearer` | карточка: проекты, модели, ряд за 30 дней |
| `GET /api/admin/projects` | `Bearer` | проекты: поиск, владелец, расход |

Ответы не кэшируются (`cache-control: no-store`). Ошибки: `401` — нет или истёк вход / не подошёл
код, `403` — источник не разрешён, `429` — лимит попыток (заголовок `Retry-After`), `400` —
некорректное тело.

## 4. Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `WEBNESTDEV_ADMIN_ORIGINS` | пусто | источники админ-приложения через запятую — они попадают в CORS |
| `ADMIN_TOTP_ISSUER` | `NestDev` | имя платформы в аутентификаторе |
| `ADMIN_SESSION_TTL_MS` | 8 часов | абсолютный срок админ-сессии |
| `ADMIN_SESSION_IDLE_TTL_MS` | 30 минут | бездействие, после которого вход закрывается |
| `ADMIN_CHALLENGE_TTL_MS` | 10 минут | сколько живёт пропуск между паролем и кодом |

Сессия админ-приложения короче пользовательской намеренно: админка даёт доступ ко всей платформе,
и брошенная вкладка не должна оставаться входом на весь день. Токен хранится только как sha256 —
копия хранилища не даёт войти.

## 5. Границы

- Админ-аккаунт не является пользователем панели: у него нет проектов, песочниц и подписок.
- `WEBNESTDEV_ADMIN_EMAILS` из `server/src/platform/admin.ts` по-прежнему решает, кто из
  **пользователей** может открывать панель ключей платформы. Это отдельный механизм; новый вход
  его не заменяет и не расширяет.
- Cookie в админ-API не принимаются: браузерное приложение не может «случайно» отправить туда
  пользовательскую сессию и не может получить CSRF-запрос от чужой страницы.

## 6. Клиенты: Expo (Android) и Electron

API рассчитан именно на нативные клиенты: вход даёт токен в теле ответа, cookie нет вообще, а
`Authorization: Bearer` одинаково работает и в React Native, и в Electron. CORS для этого не нужен —
он применяется браузером к `fetch` со страницы, а не к нативному HTTP-клиенту.

### 6.1. Expo / Android

- `fetch` из React Native не отправляет `Origin`, поэтому ни CORS, ни Origin-guard не мешают. Нужен
  только HTTPS: Android по умолчанию запрещает cleartext-трафик, а `Expo Go` с `http://` на телефоне
  упрётся в сетевую политику.
- Токен храните в `expo-secure-store` (входит в Expo Go), а не в `AsyncStorage`: он даёт доступ ко
  всей платформе, и это единственное место, где его не прочитают другие приложения.
- `otpauth` из `2fa/setup` покажите QR-кодом — набирать 32 символа вручную на телефоне неудобно:
  `react-native-qrcode-svg` рисует его из готовой ссылки и работает в Expo Go. Рядом оставьте
  «ввести вручную» — на случай, если камера занята или приложение уже открыто на этом же телефоне.
- Десять `recoveryCodes` из `2fa/enable` покажите один раз списком с копированием и предупредите,
  что второй раз их не покажут. Отправлять их в заметки по умолчанию — плохая идея: обычно это и
  есть место, где их ищет злоумышленник.
- Перед запросом на экране восстановления после сворачивания проверяйте `GET /api/admin/me`: сессия
  закрывается после 30 минут бездействия, и лучше показать вход, чем ловить 401 посреди действия.
- Клавиатуру на коде TOTP ставьте цифровую (`keyboardType="number-pad"`), а автозаполнение
  выключайте (`autoComplete="off"`, `textContentType="oneTimeCode"` — для кода из SMS/аутентификатора).

### 6.2. Electron

- HTTP-запросы делайте **в main-процессе** (`net.fetch` или обычный `fetch` Node 20+), а рендерер
  общайтесь с ним через `contextBridge`/IPC. Тогда CORS не участвует вовсе, и токен не попадает в
  память страницы — а значит, не достаётся ни XSS, ни расширениям Chromium, ни devtools.
- Токен храните через `safeStorage.encryptString` (Keychain/DPAPI/libsecret) на диске и держите
  расшифрованную копию только в main-процессе; `localStorage` для него не годится.
- Если рендерер всё же ходит в API сам (браузерная `fetch`), его источник обязан быть в
  `WEBNESTDEV_ADMIN_ORIGINS`: например `app://admin` для страницы, отданной по зарегистрированной
  `standard`-схеме. Страница `file://` даёт `Origin: null` — он намеренно не разрешён, поэтому такой
  вариант работать не будет; это же правило закрывает путь «страница на чужом сайте дернула API».
- При блокировке экрана и при выходе из приложения вызывайте `POST /api/admin/logout`, чистите
  `safeStorage` и экран входа; не оставляйте токен жить в фоне.
- Автообновление подписи не нужно: сервер проверяет только `Authorization`. Сертификат должен быть
  публичным (Caddy/Let's Encrypt) — самоподписанный не пройдёт ни на Android, ни в Electron без
  отключения проверки TLS, что для админки недопустимо.

### 6.3. Общее для обоих клиентов

| Ситуация | Что делать |
|---|---|
| `401` на `2fa/verify` с `attemptsLeft` | показать остаток попыток; при `0` — вернуться к паролю |
| `401` на запросе с токеном | сессия истекла или отозвана: очистить токен и показать вход |
| `429` | показать `Retry-After` в секундах, не повторять запрос в цикле |
| `500` при live-настройке | скорее всего `WEBNESTDEV_ENCRYPTION_KEY` не тот: TOTP-секрет не расшифровывается, нужен `admin:reset-2fa` |
| телефон потерян | `reset-2fa` на сервере, затем вход с новым подключением фактора |

Значения по умолчанию (8 часов всего, 30 минут бездействия) выбраны для админки на общем
компьютере. Для личного телефона их разумно увеличить через `ADMIN_SESSION_TTL_MS` и
`ADMIN_SESSION_IDLE_TTL_MS`, но не до бесконечности: токен живёт столько же, сколько доступ к
платформе.

## 7. Статистика

Код: `server/src/routes/admin-analytics.ts`. Тесты: `server/src/routes/admin-analytics.test.ts`
(границы периода и заполнение пустых дней).

Все шесть маршрутов — только чтение, с тем же `Authorization: Bearer`, что и остальная админка, и
с `cache-control: no-store`. Данные берутся из существующих таблиц; источник расхода —
`model_usage`: в ней лежат модель, токены, проект и пользователь, поэтому «сколько потратил клиент»
и «какая модель» не расходятся между собой. Новых таблиц нет, добавлены только индексы
`model_usage (usage_date)` и `model_usage (project_id, usage_date)` — иначе обзор и список проектов
перебирали бы таблицу целиком.

| Маршрут | Параметры | Что отдаёт |
|---|---|---|
| `GET /api/admin/stats/overview` | `days` = 1…90 (7) | всего/новые пользователи и проекты, активные за период, токены (`prompt`, `completion`, `previousTotal`), запуски, среднее на запуск, число моделей |
| `GET /api/admin/stats/series` | `days` = 1…90 (7) | ровно `days` точек, последняя — сегодня; пустые дни с нулями |
| `GET /api/admin/stats/models` | `days` = 1…90 (7) | `runs`, `promptTokens`, `completionTokens`, `totalTokens`, `users`, `share` (0…1), по убыванию расхода |
| `GET /api/admin/users` | `query`, `sort` (tokens/projects/created), `limit` 1…200, `offset`, `days` 0…365 (0 = всё время) | `total` — сколько подходит под фильтр, и страница пользователей с расходом, проектами, диалогами, `lastActiveAt` |
| `GET /api/admin/users/:id` | — | карточка: проекты (до 100), `topModels` (share внутри расхода человека), ряд за 30 дней; `404`, если пользователя нет |
| `GET /api/admin/projects` | `query` по названию/id/почте владельца, `limit`, `offset`, `days` | проекты с расходом, числом диалогов и временем последнего запуска |

`previousTotal` равен `null`, когда в предыдущем окне такой же длины расхода не было: это не ноль,
а отсутствие базы для сравнения. Числа приходят обычными `number` — `BIGINT` и `numeric` из
Postgres приводятся на сервере, потому что node-postgres отдаёт их строками. Даты — ISO-строки.

Статистика читает SQL, поэтому нужен `WEBNESTDEV_STORAGE=postgres` (production); на JSON-хранилище
в разработке эти маршруты отвечают `500`. Проверка после выкатки:

```bash
TOKEN=…  # токен из /api/admin/2fa/verify
curl -s -H "Authorization: Bearer $TOKEN" 'https://panel.example.com/api/admin/stats/overview?days=7'
curl -s -H "Authorization: Bearer $TOKEN" 'https://panel.example.com/api/admin/users?limit=5'
```
