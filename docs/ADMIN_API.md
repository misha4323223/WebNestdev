# API администратора платформы

Текущее состояние работ, доступы и следующая задача: [ADMIN_HANDOFF.md](ADMIN_HANDOFF.md).

Вход в админку — отдельная дверь, не связанная ни с пользователями панели, ни с их сессиями.
Админ-приложение обращается к API с `Authorization: Bearer <токен>`; cookie не используются вообще,
поэтому браузер не может приложить вход к чужому запросу, а CORS открывается только для адресов из
`WEBNESTDEV_ADMIN_ORIGINS`.

Код: `server/src/routes/admin.ts`, `server/src/admin/*`. Тесты: `server/src/admin/totp.test.ts`,
`server/src/routes/admin.test.ts`.

## 1. Создание администратора

Самостоятельной регистрации нет: аккаунт создаётся на сервере, то есть с теми же правами, что нужно
для развёртывания.

```bash
# разработка
cd server
npm run admin:create -- --email admin@example.com

# production (в образе только собранный dist)
docker compose exec webnestdev-server node server/dist/scripts/admin-cli.js create --email admin@example.com
```

Команда печатает пароль **один раз** — его надо сохранить в менеджере паролей. Дальше:

| Команда | Что делает |
|---|---|
| `create --email <адрес>` | создаёт администратора, печатает пароль |
| `password --email <адрес>` | новый пароль, TOTP сохраняется, все входы отзываются |
| `reset-2fa --email <адрес>` | сбрасывает TOTP и recovery-коды, отзывает все входы |
| `list` | список администраторов и состояние второго фактора |

`reset-2fa` — единственный способ вернуть доступ при потерянном телефоне и кодах. Через API сброс
недоступен: иначе украденный пароль сам снимал бы с себя второй фактор.

### 1.1. Если терминала на ВМ нет

Пароль нельзя придумать в панели: аккаунта ещё нет. Поэтому первого администратора можно объявить
в окружении развёртывания — выкатка доставляет переменные в `.env` на ВМ, а сервер создаёт запись
при старте.

1. В GitHub: **Settings → Secrets and variables → Actions → Secrets** добавьте два секрета:
   `ADMIN_BOOTSTRAP_EMAIL` (ваш адрес) и `ADMIN_BOOTSTRAP_PASSWORD` (не короче 12 символов;
   лучше 16+ букв и цифр без кавычек, `#` и `$` — значение идёт через `.env` и docker compose,
   где такие символы могут сломать разбор строки).
2. Запустите выкатку: **Actions → deploy → Run workflow**.
3. В логе старта появится `admin account created from environment`; сам пароль в лог не пишется.
4. Войдите в админ-приложении этими адресом и паролем: первый вход попросит подключить TOTP и
   выдаст коды восстановления.
5. После входа замените значение `ADMIN_BOOTSTRAP_PASSWORD` на длинную случайную строку и выкатите
   снова. Удалить секрет недостаточно: пустые значения выкатка пропускает, и прежняя строка
   осталась бы в `.env`. Пока администратор существует, значение всё равно не действует — замена
   нужна на случай, если запись когда-нибудь удалят.

Пароль короче 12 символов отклоняется — в логе будет `admin bootstrap skipped` с причиной, а
существующая запись не меняется ни при какой повторной выкатке: ни пароль, ни TOTP не сбрасываются.

Этим же способом можно завести ещё одного администратора: поменяйте `ADMIN_BOOTSTRAP_EMAIL` на
другой адрес — сервер создаст новую запись, прежние останутся. Сброс пароля и фактора по-прежнему
делается CLI (`password`, `reset-2fa`). Если у ВМ есть веб-консоль (VNC) в карточке инстанса в MTS
Cloud Platform, оттуда доступен обычный терминал и те же команды.

## 2. Вход

Пароль сам по себе сессию не выдаёт. Он возвращает короткий пропуск (`challenge`) и стадию:

- `enroll` — второй фактор ещё не подключён, его нужно настроить;
- `verify` — нужен код из аутентификатора или код восстановления.

### 2.1. Пароль

```bash
curl -s https://panel.example.com/api/admin/login \
  -H 'content-type: application/json' \
  -d '{"email":"admin@example.com","password":"…"}'
```

```json
{ "stage": "enroll", "challenge": "…", "email": "admin@example.com", "totpEnabled": false }
```

Неверный пароль и неизвестный адрес отвечают одинаково: `401 {"error":"Неверный email или пароль"}`.
Пропуск живёт 10 минут (`ADMIN_CHALLENGE_TTL_MS`), ошибок в коде — не больше пяти.

### 2.2. Первое подключение фактора

```bash
curl -s https://panel.example.com/api/admin/2fa/setup \
  -H 'content-type: application/json' \
  -d '{"challenge":"…"}'
```

```json
{
  "challenge": "…",
  "secret": "JBSWY3DPEHPK3PXP…",
  "otpauth": "otpauth://totp/NestDev:admin%40example.com?secret=…&issuer=NestDev&algorithm=SHA1&digits=6&period=30",
  "issuer": "NestDev",
  "account": "admin@example.com",
  "digits": 6,
  "period": 30
}
```

Секрет показывается один раз. В аутентификатор его вводят вручную (группами по четыре символа) или
открывают ссылку `otpauth`/рисуют из неё QR-код — API QR не отдаёт, чтобы не тянуть зависимость.

Подтверждение кодом завершает и подключение, и вход:

```bash
curl -s https://panel.example.com/api/admin/2fa/enable \
  -H 'content-type: application/json' \
  -d '{"challenge":"…","code":"123456"}'
```

```json
{
  "token": "…",
  "expiresAt": "2026-10-25T23:00:00.000Z",
  "admin": { "id": "…", "email": "admin@example.com", "totpEnabled": true, "createdAt": "…" },
  "recoveryCodes": ["ABCDE-23456", "…"],
  "recoveryCodesLeft": 10
}
```

`recoveryCodes` — единственный раз, когда коды видны в открытом виде. В базе лежат только их
sha256-хеши.

### 2.3. Обычный вход

```bash
# 1) пароль
curl -s https://panel.example.com/api/admin/login -H 'content-type: application/json' \
  -d '{"email":"admin@example.com","password":"…"}'
# → {"stage":"verify","challenge":"…"}

# 2) код из аутентификатора (или один из recovery-кодов)
curl -s https://panel.example.com/api/admin/2fa/verify -H 'content-type: application/json' \
  -d '{"challenge":"…","code":"123456"}'
# → {"token":"…","expiresAt":"…","admin":{…},"usedRecoveryCode":false}
```

Каждый принятый код TOTP запоминается по номеру шага (`lastTotpStep`): повторно предъявить его в
том же окне нельзя. Код восстановления удаляется после первого использования; `recoveryCodesLeft`
в ответе говорит, сколько осталось.

## 3. Маршруты

| Метод и путь | Авторизация | Назначение |
|---|---|---|
| `POST /api/admin/login` | — | пароль → `challenge` + стадия |
| `POST /api/admin/2fa/setup` | `challenge` | новый TOTP-секрет и `otpauth`-ссылка |
| `POST /api/admin/2fa/enable` | `challenge` | подтвердить фактор, получить токен и recovery-коды |
| `POST /api/admin/2fa/verify` | `challenge` | код TOTP или recovery → токен |
| `POST /api/admin/2fa/recovery` | `Bearer` | перевыпустить набор recovery-кодов (нужен действующий код) |
| `GET /api/admin/me` | `Bearer` | кто вошёл и до какого времени |
| `POST /api/admin/logout` | `Bearer` | закрыть текущий вход |
| `POST /api/admin/logout-all` | `Bearer` | закрыть все входы администратора |
| `GET /api/admin/stats/overview` | `Bearer` | обзор: люди, проекты, токены, запуски, модели |

| `GET /api/admin/stats/models` | `Bearer` | расход по моделям и доля каждой |

| `GET /api/admin/stats/economics` | `Bearer` | выручка против расхода, маржа, цена подписки |
| `GET /api/admin/users` | `Bearer` | пользователи: поиск, сортировка, страница |
| `GET /api/admin/users/:id` | `Bearer` | карточка: проекты, модели, ряд за 30 дней |

| `POST /api/admin/infra/prune` | `Bearer` | безопасная очистка Docker: тело `{confirm: true}`, не чаще раза в 30 секунд (раздел 7.6) |
| `GET /api/admin/users/:id/restriction` | `Bearer` | заблокирован ли аккаунт и кем (раздел 7.7) |
| `POST /api/admin/users/:id/sessions/revoke` | `Bearer` | завершить все сеансы аккаунта (раздел 7.7) |
| `POST /api/admin/users/:id/block` | `Bearer` | заблокировать вход и отозвать сеансы (раздел 7.7) |
| `POST /api/admin/users/:id/unblock` | `Bearer` | снять блокировку (раздел 7.7) |
| `POST /api/admin/users/:id/plan` | `Bearer` | выдать тариф без оплаты или снять его (раздел 7.7) |
| `POST /api/admin/users/:id/tokens` | `Bearer` | надбавка к месячному пулу токенов (раздел 7.7) |
| `GET /api/admin/billing?days=&limit=` | `Bearer` | платежи, подписки, истекающие и калибровка пула (раздел 7.8) |
| `GET /api/admin/plans` | `Bearer` | тарифы: название, описание, базовая цена и скидка (раздел 7.10) |
| `POST /api/admin/plans` | `Bearer` | изменить витрину и скидку; ответ уже содержит итоговую цену (раздел 7.10) |
| `GET /api/admin/projects/:id` | `Bearer` | карточка проекта: репозиторий, превью, переменные, выкатка (раздел 7.9) |
| `GET /api/admin/support/stats` | `Bearer` | где болит: очередь, важность, давность (раздел 8.5) |

Ответы не кэшируются (`cache-control: no-store`). Ошибки: `401` — нет или истёк вход / не подошёл
код, `403` — источник не разрешён, `429` — лимит попыток (заголовок `Retry-After`), `400` —
некорректное тело.

## 4. Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `WEBNESTDEV_ADMIN_ORIGINS` | пусто | источники админ-приложения через запятую — они попадают в CORS |
| `ADMIN_TOTP_ISSUER` | `NestDev` | имя платформы в аутентификаторе |
| `ADMIN_SESSION_TTL_MS` | 8 часов | абсолютный срок админ-сессии |
| `ADMIN_SESSION_IDLE_TTL_MS` | 30 минут | бездействие, после которого вход закрывается |
| `ADMIN_CHALLENGE_TTL_MS` | 10 минут | сколько живёт пропуск между паролем и кодом |
| `ADMIN_INFRA_CACHE_MS` | 20 000 | кэш снимка инфраструктуры; зажимается в 15–30 секунд |
| `ADMIN_INFRA_BUCKET_MAX_PAGES` | 10 | сколько страниц ListObjectsV2 считать до `truncated: true` |

Сессия админ-приложения короче пользовательской намеренно: админка даёт доступ ко всей платформе,
и брошенная вкладка не должна оставаться входом на весь день. Токен хранится только как sha256 —
копия хранилища не даёт войти.

## 5. Границы

- Админ-аккаунт не является пользователем панели: у него нет проектов, песочниц и подписок.
- `WEBNESTDEV_ADMIN_EMAILS` из `server/src/platform/admin.ts` по-прежнему решает, кто из
  **пользователей** может открывать панель ключей платформы. Это отдельный механизм; новый вход
  его не заменяет и не расширяет.
- Cookie в админ-API не принимаются: браузерное приложение не может «случайно» отправить туда
  пользовательскую сессию и не может получить CSRF-запрос от чужой страницы.

## 6. Клиенты: Expo (Android) и Electron

API рассчитан именно на нативные клиенты: вход даёт токен в теле ответа, cookie нет вообще, а
`Authorization: Bearer` одинаково работает и в React Native, и в Electron. CORS для этого не нужен —
он применяется браузером к `fetch` со страницы, а не к нативному HTTP-клиенту.

### 6.1. Expo / Android

- `fetch` из React Native не отправляет `Origin`, поэтому ни CORS, ни Origin-guard не мешают. Нужен
  только HTTPS: Android по умолчанию запрещает cleartext-трафик, а `Expo Go` с `http://` на телефоне
  упрётся в сетевую политику.
- Токен храните в `expo-secure-store` (входит в Expo Go), а не в `AsyncStorage`: он даёт доступ ко
  всей платформе, и это единственное место, где его не прочитают другие приложения.
- `otpauth` из `2fa/setup` покажите QR-кодом — набирать 32 символа вручную на телефоне неудобно:
  `react-native-qrcode-svg` рисует его из готовой ссылки и работает в Expo Go. Рядом оставьте
  «ввести вручную» — на случай, если камера занята или приложение уже открыто на этом же телефоне.
- Десять `recoveryCodes` из `2fa/enable` покажите один раз списком с копированием и предупредите,
  что второй раз их не покажут. Отправлять их в заметки по умолчанию — плохая идея: обычно это и
  есть место, где их ищет злоумышленник.
- Перед запросом на экране восстановления после сворачивания проверяйте `GET /api/admin/me`: сессия
  закрывается после 30 минут бездействия, и лучше показать вход, чем ловить 401 посреди действия.
- Клавиатуру на коде TOTP ставьте цифровую (`keyboardType="number-pad"`), а автозаполнение
  выключайте (`autoComplete="off"`, `textContentType="oneTimeCode"` — для кода из SMS/аутентификатора).

### 6.2. Electron

- HTTP-запросы делайте **в main-процессе** (`net.fetch` или обычный `fetch` Node 20+), а рендерер
  общайтесь с ним через `contextBridge`/IPC. Тогда CORS не участвует вовсе, и токен не попадает в
  память страницы — а значит, не достаётся ни XSS, ни расширениям Chromium, ни devtools.
- Токен храните через `safeStorage.encryptString` (Keychain/DPAPI/libsecret) на диске и держите
  расшифрованную копию только в main-процессе; `localStorage` для него не годится.
- Если рендерер всё же ходит в API сам (браузерная `fetch`), его источник обязан быть в
  `WEBNESTDEV_ADMIN_ORIGINS`: например `app://admin` для страницы, отданной по зарегистрированной
  `standard`-схеме. Страница `file://` даёт `Origin: null` — он намеренно не разрешён, поэтому такой
  вариант работать не будет; это же правило закрывает путь «страница на чужом сайте дернула API».
- При блокировке экрана и при выходе из приложения вызывайте `POST /api/admin/logout`, чистите
  `safeStorage` и экран входа; не оставляйте токен жить в фоне.
- Автообновление подписи не нужно: сервер проверяет только `Authorization`. Сертификат должен быть
  публичным (Caddy/Let's Encrypt) — самоподписанный не пройдёт ни на Android, ни в Electron без
  отключения проверки TLS, что для админки недопустимо.

### 6.3. Общее для обоих клиентов

| Ситуация | Что делать |
|---|---|
| `401` на `2fa/verify` с `attemptsLeft` | показать остаток попыток; при `0` — вернуться к паролю |
| `401` на запросе с токеном | сессия истекла или отозвана: очистить токен и показать вход |
| `429` | показать `Retry-After` в секундах, не повторять запрос в цикле |
| `500` при live-настройке | скорее всего `WEBNESTDEV_ENCRYPTION_KEY` не тот: TOTP-секрет не расшифровывается, нужен `admin:reset-2fa` |
| телефон потерян | `reset-2fa` на сервере, затем вход с новым подключением фактора |

Значения по умолчанию (8 часов всего, 30 минут бездействия) выбраны для админки на общем
компьютере. Для личного телефона их разумно увеличить через `ADMIN_SESSION_TTL_MS` и
`ADMIN_SESSION_IDLE_TTL_MS`, но не до бесконечности: токен живёт столько же, сколько доступ к
платформе.

## 7. Статистика

Код: `server/src/routes/admin-analytics.ts` (нагрузка и пользователи) и
`server/src/routes/admin-economics.ts` (деньги). Тесты: `server/src/routes/admin-analytics.test.ts`,
`server/src/routes/admin-economics.test.ts`, `server/src/account/model-pricing.test.ts`.

Все восемь маршрутов — только чтение, с тем же `Authorization: Bearer`, что и остальная админка, и
с `cache-control: no-store`. Данные берутся из существующих таблиц; источник расхода —
`model_usage`: в ней лежат модель, токены, проект и пользователь, поэтому «сколько потратил клиент»
и «какая модель» не расходятся между собой. Новых таблиц нет, добавлены только индексы
`model_usage (usage_date)`, `model_usage (project_id, usage_date)` и `billing_payments (paid_at)` —
иначе обзор, список проектов и денежная статистика перебирали бы таблицу целиком.

### 7.1. Нагрузка

| Маршрут | Параметры | Что отдаёт |
|---|---|---|
| `GET /api/admin/stats/overview` | `days` = 1…90 (7) | всего/новые пользователи и проекты, активные за период, токены (`prompt`, `completion`, `previousTotal`), запуски, среднее на запуск, число моделей |
| `GET /api/admin/stats/series` | `days` = 1…90 (7) | ровно `days` точек, последняя — сегодня; пустые дни с нулями |
| `GET /api/admin/stats/models` | `days` = 1…90 (7) | `runs`, `promptTokens`, `completionTokens`, `totalTokens`, `users`, `share` (0…1), по убыванию расхода |
| `GET /api/admin/users` | `query`, `sort` (tokens/projects/created), `limit` 1…200, `offset`, `days` 0…365 (0 = всё время) | `total` — сколько подходит под фильтр, и страница пользователей с расходом, проектами, диалогами, `lastActiveAt` |
| `GET /api/admin/users/:id` | — | карточка: проекты (до 100), `topModels` (share внутри расхода человека), ряд за 30 дней, `profile` с именем, почтой, согласиями и полем `source` («откуда узнали»), тариф `plan` и срок `planUntil` (в корне и в `user`); `404`, если пользователя нет |
| `GET /api/admin/projects` | `query` по названию/id/почте владельца, `limit`, `offset`, `days` | проекты с расходом, числом диалогов и временем последнего запуска |

`previousTotal` равен `null`, когда в предыдущем окне такой же длины расхода не было: это не ноль,
а отсутствие базы для сравнения. Числа приходят обычными `number` — `BIGINT` и `numeric` из
Postgres приводятся на сервере, потому что node-postgres отдаёт их строками. Даты — ISO-строки.

### 7.2. Деньги: расходы и экономика подписки

Токены показывают нагрузку, но не отвечают на вопрос «какую цену ставить». Для этого нужны деньги:
сколько платформа потратила на модели и инфраструктуру, сколько получила и сколько остаётся с
каждого тарифа. Источники те же, что у биллинга: `model_usage`, `billing_payments` (только
`status = 'paid'`), `billing_subscriptions` (действующие подписки).

| Маршрут | Параметры | Что отдаёт |
|---|---|---|
| `GET /api/admin/stats/costs` | `days` = 1…90 (30) | расход по моделям, дням, пользователям, проектам и тарифам; `complete` и `warnings` говорят, всё ли посчитано |
| `GET /api/admin/stats/economics` | `days` = 1…90 (30), `margin` = 0…0.9 (0.7) | выручка, MRR, расход, маржа, экономика каждого тарифа, цена «по себестоимости» и цена под целевую маржу |

`days` по умолчанию 30, а не 7: для решения о цене неделя слишком коротка и легко искажается
одним большим запуском. `margin` — доля выручки, которую хотим оставить после расходов: `0.7`
значит «70 % себе, 30 % на себестоимость».

#### `/api/admin/stats/costs`

| Поле | Смысл |
|---|---|
| `pricing` | какие цены действуют: `configured`, `source` (`model-prices` / `single-price` / `none`), `models`, `catchAll`, `freeModels` |
| `infra` | постоянные расходы: `monthly`, `perDay`, `period`, `configured` |
| `totals` | запуски, токены, проекты и активные люди, `modelCost`, `infraCost`, `totalCost`, стоимость на запуск/проект/человека, `complete` |
| `daily` | дни периода без пропусков: токены, запуски, расход модели, инфраструктуры и всего |
| `models` | по каждой модели: токены, запуски, люди, `cost`, `tokenShare`, `costShare`, `priced`, `priceSource` |
| `plans` | `free` / `pro` / `team`: активные люди, токены, запуски, модельный расход, доли |
| `topUsers`, `topProjects` | до 10 крупнейших потребителей; `cost` и `costComplete` |
| `warnings` | человеческие объяснения: нет цен, нет инфраструктуры, неизвестная модель, резерв free-model |

`complete: false` — не ошибка запроса, а честная граница: у какой-то модели нет цены, и её токены
не вошли в деньги. Такие модели перечислены в `unpriced` (в `totals` — через `warnings`), а не
превращены в ноль: ноль означал бы «бесплатно», а не «неизвестно».

`topUsers` и `topProjects` отбираются по токенам (до 25 кандидатов, в ответе — 10), а деньги
считаются для них: при неизвестной цене модели сортировка по деньгам спрятала бы крупного
потребителя вниз. Поэтому у строки есть `costComplete` — если `false`, `cost` неполная.

#### `/api/admin/stats/economics`

| Поле | Смысл |
|---|---|
| `currencies` | `cost`, `revenue` (`RUB`) и `comparable`: можно ли сравнивать суммы |
| `revenue` | `paidInPeriod` — фактически оплаченные счёта за период, `payments`, `mrr` по действующим подпискам, число подписчиков по тарифам |
| `users` | всего, активные за период, платные, бесплатные, конверсия |
| `costs` | расход за период и в месяц: модели, инфраструктура, всего, `complete`, `unpriced` |
| `margin` | `period` (оплаты минус расход), `monthly` (MRR минус месячный расход), `monthlyRate` |
| `plans` | по тарифу: подписчики, активные люди, расход модели, доля инфраструктуры, оплаты за период, MRR, маржа |
| `unit` | расход на активного человека, инфраструктура и дотация free-тарифа на платящего, выручка и маржа на платящего |
| `priceGuidance` | по платным тарифам: текущая цена, себестоимость, рекомендуемая цена, маржа при текущей цене |
| `warnings` | те же предупреждения плюс несовпадение валют и отсутствие платящих |

Месячные числа — оценка темпа, а не бухгалтерский месяц: `period × 30 / days`. Инфраструктура
разложена по 30 дням, поэтому период в 7 дней получает 7/30 месячной суммы, а не всю.

Себестоимость подписчика считается так:

```
модель на подписчика = расход модели тарифа × 30/days / подписчиков тарифа
инфраструктура       = infraMonthly / всех платящих
дотация free         = расход модели free × 30/days / всех платящих
себестоимость        = модель + инфраструктура + дотация
рекомендуемая цена   = ceil(себестоимость / (1 − margin) / 10) × 10
```

Дотация бесплатного тарифа здесь не мелочь: если бесплатные пользователи тратят платную модель,
кто-то должен её оплатить. Цена округляется вверх до 10 ₽: 1 073 ₽ выглядит как ошибка, 1 080 ₽ —
как цена. В расчёт попадают только тарифы, где есть подписчики; `free` показан как расход, а не
как цена. Текущая цена берётся из действующей настройки магазина (`ROBOKASSA_PRICE_PRO` /
`ROBOKASSA_PRICE_TEAM`), а не из каталога, поэтому MRR не разойдётся с реальной выручкой.

Если валюта расходов не `RUB`, `currencies.comparable` равно `false`: `margin` приходит `null`, а
`priceGuidance` пустой. Складывать доллары с рублями нельзя, и лучше показать «не сравнимо», чем
красивую неверную маржу.

### 7.3. Цены моделей и инфраструктуры

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `PLATFORM_AI_MODEL_PRICES` | пусто | JSON-таблица цен за 1M токенов по моделям |
| `PLATFORM_AI_PRICE_INPUT_PER_MILLION` | пусто | общая ставка на вход, если таблицы нет или модель не найдена |
| `PLATFORM_AI_PRICE_OUTPUT_PER_MILLION` | пусто | общая ставка на выход |
| `PLATFORM_AI_PRICE_CURRENCY` | `USD` | валюта расходов; для сравнения с выручкой — `RUB` |
| `PLATFORM_INFRA_COST_PER_MONTH` | пусто | постоянные расходы в месяц: ВМ, диск, бакет, SMS, домен |

Пример для текущей модели платформы в Yandex Cloud AI Studio (цены за 1M токенов, вкл. НДС —
сверяйте в консоли). JSON — **одной строкой**: выкатка пишет переменные в `.env` построчно:

```json
{"qwen3-235b-a22b-fp8":{"input":500,"output":500},"gpt-oss-120b":{"input":300,"output":300},"gpt-oss-20b":{"input":100,"output":100},"free-model":{"input":0,"output":0}}
```

`PLATFORM_AI_PRICE_CURRENCY=RUB` вместе с этим примером. В GitHub значения удобнее держать в
**Variables**, а не в Secrets: это не ключи, и выкатка прокидывает их в `.env` на ВМ, а
`docker-compose.yml` — в контейнер. Если цена
модели выглядит как `gpt://<folder>/qwen3-235b-a22b-fp8/latest`, отдельный ключ на полный URI не
нужен: ключ таблицы ищется как часть имени. Если ключей несколько и один входит в другой, побеждает
более длинный (`gpt-oss-120b` важнее `gpt-oss`). Число вместо объекта задаёт одну ставку на вход и
выход.

Запуски бесплатной модели записываются как `free-model` и стоят ноль, пока для них явно не задана
цена. Это осознанная оценка снизу: если бесплатные ключи Agnes недоступны, шаг уходит на платную
модель платформы, но в журнале остаётся `free-model`. Админка предупреждает об этом, когда резерв
настроен; точная стоимость таких запусков потребовала бы записи фактического адреса модели в
`model_usage` — это отдельная задача, а не догадка в отчёте.

Оценка стоимости в карточке аккаунта по-прежнему использует общую ставку `PLATFORM_AI_PRICE_*`.
Админская статистика точнее, когда задана таблица по моделям; если нужны одинаковые числа в обоих
местах, задайте обе настройки либо только общую ставку.

### 7.4. Проверка после выкатки

Статистика читает SQL, поэтому нужен `WEBNESTDEV_STORAGE=postgres` (production); на JSON-хранилище
в разработке эти маршруты отвечают `500`.

```bash
TOKEN=…  # токен из /api/admin/2fa/verify
curl -s -H "Authorization: Bearer $TOKEN" 'https://panel.example.com/api/admin/stats/overview?days=7'
curl -s -H "Authorization: Bearer $TOKEN" 'https://panel.example.com/api/admin/stats/costs?days=30'
curl -s -H "Authorization: Bearer $TOKEN" 'https://panel.example.com/api/admin/stats/economics?days=30&margin=0.7'
curl -s -H "Authorization: Bearer $TOKEN" 'https://panel.example.com/api/admin/users?limit=5'
```

Что должно быть в ответе `costs`: `pricing.configured: true`, `totals.complete: true`, пустой
`warnings`, ненулевой `totals.modelCost`. В `economics`: `currencies.comparable: true`, заполненный
`revenue.mrr` при наличии подписок и `priceGuidance` с `breakEvenPrice`. Если `priceGuidance` пуст
при платных подписчиках — скорее всего не совпала валюта или не посчитана хотя бы одна модель.

### 7.5. Инфраструктура: диск, Docker, песочницы, бакеты, база

Код: `server/src/routes/admin-infra.ts`. Тесты: `server/src/routes/admin-infra.test.ts`,
`server/src/storage/object-store.test.ts`. Оба маршрута — только чтение, `Bearer`-токен и
`cache-control: no-store`; тяжёлые пробы кэшируются на 15–30 секунд.

| Маршрут | Параметры | Что отдаёт |
|---|---|---|
| `GET /api/admin/infra` | — | снимок: `host`, `disk`, `docker`, `sandboxes`, `buckets`, `database`, `alerts`, `unavailable` |
| `GET /api/admin/sandboxes` | `state` = `cold` (по умолчанию), `running`, `never`, `all`; `limit` 1…200 (50) | `total` — число подходящих до `limit`, `sandboxes` — страница, отсортированная по `lastActiveAt` |

**Любая секция необязательна.** Если сервер не может что-то измерить, поле приходит `null` (или
секция отсутствует), а в `unavailable` появляется `{section, reason}`. Ноль вместо «не знаю» здесь
запрещён: админка должна отличать «на диске правда пусто» от «statfs не ответил».

- `disk.pressure` — `ok` / `warn` (≥80%) / `danger` (≥90%) по худшему разделу, а не по среднему.
  В `mounts` попадают `/`, `/var/lib/docker` и каталоги песочниц/данных, если они лежат на отдельных
  файловых системах; одинаковые устройства не дублируются. `filesystem` берётся из `/proc/mounts`.
- `docker.available: false` — Docker не установлен или недоступен; `containers`, `images` и
  `reclaimableBytes` тогда не выдумываются. `dockerBytes`/`reclaimableBytes` считаются по
  `docker system df`; если хоть одна строка не разобрана, сумма приходит `null`.
- `sandboxes.running` — живой предпросмотр (контейнер или статическая раздача), `cold` — проект
  известен, но не работает: рабочая папка на диске, архив в бакете или остановленный контейнер.
  `neverStarted` — проекта нет ни на диске, ни в бакете. В этой платформе контейнер предпросмотра
  удаляется при остановке, поэтому «холодный» не может означать только остановленный контейнер.
  Если не прочитан хотя бы один из источников состояния (отметки архива, контейнеры, каталог
  песочниц), раздел `sandboxes` не присылается вовсе, а `GET /api/admin/sandboxes` отвечает `503`:
  частичные счётчики выглядели бы точными, хотя часть проектов попала бы не в ту категорию.
- `sandboxes.coldStarts24h`, `averageStartMs`, `slowestStartMs` и `startMs` в списке пока `null`:
  журнала холодных стартов нет. Когда он появится, менять контракт не придётся — поля уже есть.
- `diskBytes` в списке — измеренный размер проекта (для архивного — размер архива, он же входит в
  квоту аккаунта). Если замера ещё нет, приходит `null`, а `sandboxes.diskBytes` тоже становится
  `null`: частичная сумма выдавала бы себя за полную. У проекта без файлов это честный `0`.
- `buckets` — один настроенный бакет `PLATFORM_S3_*`. Объекты и байты считаются `ListObjectsV2` под
  префиксом; на пределе страниц `truncated: true`, и цифры не выдаются за полные. `updatedAt` пока
  `null`.
- `database` — только для `WEBNESTDEV_STORAGE=postgres`: имя базы, размер, соединения и таблицы
  (`rows` — оценка `pg_stat_user_tables.n_live_tup`, размеры точные). `lastBackupAt` — `null`, пока
  нет журнала резервных копий. На JSON-хранилище секции нет, в `unavailable` — причина.
- `alerts` — до пяти коротких фраз для баннера: диск, Docker, память, бакет, база.

Что проверить после выкатки:

```bash
TOKEN=…
curl -s -H "Authorization: Bearer $TOKEN" 'https://panel.example.com/api/admin/infra'
curl -s -H "Authorization: Bearer $TOKEN" 'https://panel.example.com/api/admin/sandboxes?state=cold&limit=10'
```

В снимке должны быть `generatedAt`, `host.build` (та же сборка, что в `/api/version`), заполненный
`disk` и `docker.available`; в `unavailable` не должно быть `sandboxes` и `docker`, если Docker
работает. Если `buckets` пуст, а `PLATFORM_S3_*` заданы — смотреть причину в `unavailable`.

### 7.6. Безопасная очистка Docker

Код: `server/src/routes/admin-prune.ts`. Тесты: `server/src/routes/admin-prune.test.ts`.

Кнопка «Безопасная очистка» удаляет ровно две категории: кэш сборки (`docker builder prune -a -f`)
и висячие образы без тегов (`docker image prune -f`). Остановленные контейнеры — это песочницы
проектов в холодном старте, а в томах может лежать состояние проекта, поэтому `container prune`,
`volume prune` и `system prune -a` маршрут не выполняет и не принимает: тело разбирается строгой
схемой и `{"scope":"volumes"}` отвечает `400`, а не «молча ничего не делает». По той же причине
команды идут в Docker массивом аргументов (`execFile`, без шелла) — подставить свои аргументы через
тело запроса нечем.

| Маршрут | Параметры | Что отдаёт |
|---|---|---|
| `GET /api/admin/infra/prune` | — | `scope` (`builderCacheBytes`, `danglingImages`, `safeTotalBytes`), `keep` (`stoppedContainers`, `volumes`), `commands`, `canRun`; при отказе пробы ещё и `reason` |
| `POST /api/admin/infra/prune` | тело `{confirm: true}` | `ok`, `freedBytes`, `beforeBytes`, `afterBytes`, `ranAt`, `details` — по строке на команду |

`reclaimableBytes` из `GET /api/admin/infra` — это сумма **всех** строк `docker system df`, вместе с
холодными песочницами и томами: показывать её как «мусор к удалению» нельзя. Поэтому безопасная
часть считается отдельно — `builderCacheBytes` (то, что Docker вернёт из `Build Cache`) плюс
`danglingImages.bytes`, итог в `safeTotalBytes`. `keep` — не цель очистки, а цена нажатия: сколько
холодных песочниц и томов останется.

Если не ответил `docker system df`, `docker image ls` или `docker ps`, приходит `canRun: false` и
причина в `reason`, а приложение кнопку блокирует: неполная оценка не должна выглядеть кнопкой
«удалить». Числа в этом ответе — нули, и выдают их за измерение именно `canRun: false` рядом, а не
молчание.

Ограничения: не чаще одного раза в 30 секунд (`429` с `Retry-After`), каждая команда под таймаутом
60 секунд, набор команд не зависит от запроса. `freedBytes` — разница итогов `docker system df` до
и после; если итог не разобран, берётся сумма «Total reclaimed space» из вывода команд, чтобы
освобождённое место не показывалось нулём. Событие уходит в журнал безопасности действием
`infra.docker.pruned` с `freedBytes`, `beforeBytes`, `afterBytes` и списком команд.

Что проверить после выкатки:

```bash
TOKEN=…
curl -s -H "Authorization: Bearer $TOKEN" 'https://panel.example.com/api/admin/infra/prune'
# ожидаем scope.safeTotalBytes, keep.stoppedContainers и canRun: true

docker ps -aq --filter status=exited | wc -l      # до
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"confirm":true}' 'https://panel.example.com/api/admin/infra/prune'
docker ps -aq --filter status=exited | wc -l      # после — то же число

curl -s -o /dev/null -w '%{http_code}\n' -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' -d '{"scope":"volumes"}' \
  'https://panel.example.com/api/admin/infra/prune'   # ожидаем 400
```

Главная проверка — число остановленных контейнеров до и после совпадает, а `GET /api/admin/infra`
после очистки показывает те же холодные проекты.

### 7.7. Действия над аккаунтом

До этих маршрутов админка только читала: проблему было видно, а сделать с ней ничего нельзя.
Каждое действие отвечает на один вопрос и не делает заодно второе.

| Метод и путь | Тело | Что меняется |
|---|---|---|
| `GET /api/admin/users/:id/restriction` | — | только чтение: `blocked` и `restriction` |
| `POST /api/admin/users/:id/sessions/revoke` | `{confirm: true}` | все сессии аккаунта удалены, `blocked` не меняется |
| `POST /api/admin/users/:id/block` | `{confirm: true, reason?}` | запись блокировки **и** отзыв всех сессий |
| `POST /api/admin/users/:id/unblock` | `{confirm: true}` | блокировка снята, сессии не восстанавливаются |
| `POST /api/admin/users/:id/plan` | `{confirm: true, plan, months?, days?, notify?}` | подписка без оплаты; `plan: "free"` — снять |
| `POST /api/admin/users/:id/tokens` | `{confirm: true, tokens, notify?}` | надбавка к пулу текущего месяца |

Общие правила:

- схема тела **строгая**: `confirm: true` обязателен, лишнее поле — `400` (запрос с `scope` или
  чем-то похожим не «игнорируется», а отвергается);
- цель обязана существовать — `404`, иначе админка правила бы записи несуществующих аккаунтов;
- свой аккаунт заблокировать нельзя (`400`). Администраторы живут в отдельной таблице
  (`admin_users`), поэтому проверка — страховка, а не единственная защита;
- каждое действие пишет событие в журнал безопасности (`user.blocked`, `user.unblocked`,
  `user.sessions.revoked.admin`, `user.plan.granted`, `user.tokens.granted`) вместе с id админа.

**Блокировка** действует на всех четырёх входах (пароль, регистрация, телефон, Яндекс ID):
`attachSession` не выдаёт сессию заблокированному, а `getCurrentUser` не пускает по уже выданной
cookie. При входе по паролю и телефону человек видит `403` и причину, которую администратор указал
в `reason`, а не «ошибку сети»; у Яндекс ID остаётся общее сообщение о блокировке. Данные и тариф
при блокировке не меняются — действие обратимо.

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"confirm":true,"reason":"спам в поддержку"}' \
  'https://nestdev.ru/api/admin/users/<id>/block'
```

```json
{
  "ok": true,
  "blocked": {
    "userId": "…",
    "blockedAt": "2026-10-27T09:00:00.000Z",
    "blockedBy": "…",
    "blockedByLabel": "admin@example.test",
    "reason": "спам в поддержку"
  },
  "revoked": 3
}
```

**Тариф без оплаты** (`plan`) собирает запись по тем же правилам, что и настоящий платёж:
если подписка ещё действует, срок считается от текущего `planUntil`, а если её нет — от сегодня.
Это верно и при продлении того же тарифа, и при переходе на другой: выдача не отнимает уже
оплаченные дни. `months` от 1 до 12 (по умолчанию 1) или `days` от 1 до 366 — для короткой
компенсации; передавать оба сразу нельзя (`400`).

Отличия от платежа, которые важно сохранить: `autoRenew: false` — свипер не выставит счёт живому
человеку, и `noticeAt: null` — письмо о списании не уходит. `plan: "free"` — истечение срока
сейчас; если подписки нет, ответ `409`, а не «ок». В ответе всегда есть `planUntil` — по нему
админка подтверждает, что срок действительно сдвинулся.

```json
{ "ok": true, "plan": "pro", "planName": "Плюс", "planUntil": "2026-11-28T09:00:00.000Z", "message": "Вам активировали «Плюс» на 1 месяц", "subscription": { "plan": "pro", "status": "active", "renewsAt": "2026-11-28T09:00:00.000Z", "autoRenew": false }, "notified": false }
```

**Токены** — надбавка к пулу, а не правка расхода: `model_usage` остаётся единственным источником
правды, поэтому «выдали 5 млн» не искажает статистику. Сумма складывается с уже начисленным
(`bonus` в ответе — итог месяца), на следующий месяц не переносится, на бесплатном тарифе
(`agentTokensPerMonth: 0`) не расширяет ничего — это видно по `appliesToPool: false`. `tokens` в
ответе — новый доступный остаток на месяц (`budget.remaining`), а `granted` — сумма этой выдачи;
по ним админка показывает, что баланс действительно вырос.

```json
{ "ok": true, "tokens": 53800000, "message": "Начислено 5 000 000 токенов", "month": "2026-10", "granted": 5000000, "bonus": 5000000, "appliesToPool": true, "budget": { "used": 1200000, "limit": 55000000, "bonus": 5000000, "remaining": 53800000 } }
```

**Уведомления человека.** Оба маршрута принимают `notify: true`; тогда вместе с действием
создаётся уведомление только этому аккаунту. Так баланс не меняется молча: в шапке сайта и в
колонке главной появляется колокольчик со счётчиком. Человек читает их под своей сессией:

| Метод и путь | Что возвращает |
|---|---|
| `GET /api/me/notifications` | `{notifications: [{id, kind, message, tokens, plan, planUntil, createdAt, readAt}], unread}`; `kind`: `gift` — токены, `plan` — тариф |
| `POST /api/me/notifications/:id/read` | `{ok: true}`; чужое или неизвестное уведомление — `404` |
| `POST /api/me/notifications/read-all` | `{ok: true, read: <сколько отмечено>}` |

Пример уведомления о тарифе: `{"kind":"plan","message":"Вам активировали «Плюс» на 1 день","tokens":null,"plan":"pro","planUntil":"2026-10-29T09:00:00.000Z"}`.
О подарке токенов: `{"kind":"gift","message":"Начислено 500 000 токенов","tokens":500000,"plan":null,"planUntil":null}`.
Если `notify` не передан или равен `false`, действие проходит без уведомления, а `notified` в
ответе равно `false`.

Сброса второго фактора (`2fa/reset`) здесь нет намеренно: у пользователей панели TOTP нет
вовсе — второй фактор есть только у администраторов, и перевыпуск их кодов уже описан в 2.3.

### 7.8. Реестр платежей и подписок

Данные магазина (`billing_payments`, `billing_subscriptions`) лежали в хранилище, но ни один
маршрут их не отдавал: «кто истекает на этой неделе», «у кого автопродление упало дважды» и
«сколько денег реально пришло» нельзя было узнать вообще.

```bash
curl -s -H "Authorization: Bearer $TOKEN" 'https://nestdev.ru/api/admin/billing?days=30&limit=100'
```

```json
{
  "generatedAt": "2026-10-27T09:00:00.000Z",
  "window": { "days": 30, "from": "…", "to": "…" },
  "money": { "paidRub": 1980, "paidCount": 2, "initialPaid": 2, "renewalsPaid": 0,

      "planName": "Плюс", "amount": 990, "status": "paid", "kind": "initial",
      "autoRenew": false, "attempts": 0, "createdAt": "…", "paidAt": "…" }
  ],
  "subscriptions": {
    "total": 3, "live": 2, "canceled": 0,
    "expiringSoon": [
      { "userId": "…", "email": "…", "plan": "pro", "planName": "Плюс",
        "renewsAt": "2026-10-28T09:00:00.000Z", "autoRenew": true, "status": "active", "daysLeft": 1 }
    ],
    "renewalFailures": [ { "userId": "…", "attempts": 1, "autoRenew": true, "status": "active" } ]
  },
  "pool": {
    "month": "2026-10", "subscribers": 2, "medianTokens": 7500000, "p90Tokens": 15000000,
    "averageTokens": 7500000, "fullPoolShare": 0, "nearPoolShare": 0,
    "fullPoolCount": 0, "nearPoolCount": 0

```

Правила чтения:

- `money` считается по тому же окну, что и `payments`: «пришло 1 980 ₽» и список под ним
  сходятся, иначе цифра и таблица рассказывают разное;
- `pending` — счёт выставлен, уведомление не пришло; `failed` — отказ банка или три неудачи
  автопродления, после третьей подписка истекает;
- `expiringSoon` — действующие подписки со сроком в ближайшие 7 дней;
- `renewalFailures` — у кого `renewalAttempts > 0`: один-два отказа ещё лечатся, третий закрывает
  доступ;
- **`pool` — калибровка тарифа.** `medianTokens` и `p90Tokens` считаются по действующим
  подписчикам за календарный месяц из `model_usage`. `p90Tokens` — масштаб, а не решение:
  столько токенов покрывает 90% подписчиков. `fullPoolShare` — доля тех, кто выбирает пул целиком
  (`used >= agentTokensPerMonth`), `nearPoolShare` — от 90% пула. Высокая доля при низкой медиане
  значит «тариф тесен», низкая доля при высокой медиане — «в пуле есть запас». Общий расход для
  этого вопроса слишком грубый: он смешивает кабинет с тяжёлым пользователем.

Ответ не кэшируется (`cache-control: no-store`): это живые деньги.

### 7.10. Тарифы и скидки

Администратор меняет название, описание, базовую цену и скидку обоих платных тарифов. Скидка

## 8. Обращения поддержки

Создание обращения по ключу невозможно: его пишет только вошедший пользователь из кнопки
«Поддержка». Админка читает обращения и получает подробную карточку автора.

| Метод и путь | Что отдаёт |
|---|---|
| `GET /api/support/tickets?limit=50` | список обращений без картинок, с профилем автора |
| `GET /api/support/tickets/<id>` | одно обращение, живая карточка автора и его прошлые обращения |
| `GET /api/support/tickets/<id>/screenshot` | скриншот обращения |
| `POST /api/support/tickets/<id>/reply` | ответ человеку письмом от имени платформы (раздел 8.3) |
| `PATCH /api/support/tickets/<id>/status` | статус обращения: `open` / `in_progress` / `closed` (раздел 8.4) |

### 8.1. Что уже есть в каждом обращении

- `reporter` — снимок аккаунта **на момент отправки**: `name`, `contactEmail`, `phone`,
  `signIn` (`password` / `phone` / `yandex`), `plan`, `planName`, `accountCreatedAt`,
  `projects` (число проектов) и `lastActiveAt`. Снимок не меняется задним числом: по нему видно,
  кем человек был тогда, даже если тариф или профиль уже другие.
- `ip` — адрес, с которого отправлено обращение; `userAgent`, `page`, `projectId`, `context` —
  как и раньше, помогают воспроизвести проблему.
- `email` — адрес обращения, `emailKind` — `real` (логин и есть почта) или `internal`
  (служебный идентификатор платформы, например `yandex-2260862792@yandex-id.webnestdev.local`),
  `contactEmail` — адрес, который человек указал в самой форме обращения. У новых обращений это
  поле самого тикета, у старых его может не быть — тогда рядом стоит `reporter.contactEmail`.
  Поля стоят рядом с `email` и в списке, и в карточке: по `emailKind` админка решает, активна ли
  кнопка «Написать автору», а письмо при необходимости отправляется на `contactEmail`. Если в
  профиле почты не было, адрес из формы сохраняется в профиль — следующее обращение подставит
  его само; ошибка этой записи не отменяет уже сохранённое обращение.
- `messages` — переписка обращения: `author` (`admin` / `user`), `authorName` (почта того, кто
  ответил), `subject`, `body`, `to` (куда ушло письмо), `status` (`sent` / `failed`), `error`,
  `messageId`, `createdAt`. Пустой массив означает «ответов не было», а не «поле не пришло»: поле
  есть и в списке, и в карточке. Неудачная отправка остаётся в переписке с причиной отказа.
- У обращений, созданных до появления снимка, `reporter` дополняется при чтении списка. Если
  аккаунт уже удалён, остаются поля самого тикета.

```json
  "ticket": { "id": "…", "category": "bug", "severity": 8, "reporter": { "…": "…" } },

    "id": "…",

    "name": "Иван Петров",
    "contactEmail": "ivan@example.com",
    "phone": "+7 999 123-45-67",

```

`user` — состояние на момент чтения, а не на момент отправки. `null` означает, что аккаунт
удалён или карточка не собралась; само обращение при этом отдаётся полностью. `history` — до 20
последних обращений того же аккаунта (включая текущее): повторные жалобы видно сразу, без
отдельного запроса. Пароля, хешей, секретов и API-ключей в карточке нет; `tokens` — только
расход модели за месяц.

Две двери:

1. **Сессия админ-приложения** (рекомендуется): `Authorization: Bearer <token из
   /api/admin/2fa/verify>`. Отдельный ключ не нужен; срок, бездействие и отзыв сессии работают
   так же, как в остальной админке.
2. **Ключ чтения**: `X-Support-Key: <ключ>` или `Authorization: Bearer <ключ>`. Ключ задаётся в
   панели «Ключи сервера» → «Поддержка» → `SUPPORT_API_KEY` либо в `.env`/GitHub Secret
   `SUPPORT_API_KEY`; значение из панели важнее. Пробелы и невидимые символы убираются при
   сохранении и сравнении — скопированный из документа ключ не превращается в «сохранён, но 401».

```bash
TOKEN=…  # токен администратора
curl -s -H "Authorization: Bearer $TOKEN" 'https://nestdev.ru/api/support/tickets?limit=3'
curl -s -H "Authorization: Bearer $TOKEN" 'https://nestdev.ru/api/support/tickets/<id>'
curl -s -H "X-Support-Key: $SUPPORT_API_KEY" 'https://nestdev.ru/api/support/tickets?limit=3'
```

Диагностика без раскрытия значения:

- `/api/health` → `support: { keySource, keyConfigured, keyUsable }`: откуда взят ключ (`panel`,
  `environment`, `none`), задан ли он и годится ли по длине.
- На отказ чтения сервер пишет в лог `support read refused` с источником ключа и ставит заголовок
  `X-Support-Auth: key-mismatch | key-not-configured | session-required`. Одинаковый 401 больше не
  скрывает, «ключ не сохранён» это или «сохранён в другом процессе».
- Если ключ сохранён в панели на одной реплике, а запрос попал на другую, сервер перечитывает
  `platform/env.json` по изменению файла — перезапуск не нужен.

### 8.3. Ответ человеку письмом

Ответ отправляется письмом от имени платформы через тот же транспорт, что у рассылки (REST v2
Postbox): те же `POSTBOX_SENDER`, `POSTBOX_KEY_ID` / `POSTBOX_SECRET` (или ключ сервисного
аккаунта) и тот же `PLATFORM_URL`. Второй раз настраивать нечего.

**Дверь другая.** Ответить можно только сессией админ-приложения
(`Authorization: Bearer <токен /api/admin/2fa/verify>`); ключ поддержки `SUPPORT_API_KEY`
обращения читает, но писем людям не отправляет — это разные полномочия, и совмещать их в одном
ключе значило бы отдать отправку писем любому, у кого есть ключ чтения.

```bash
TOKEN=…  # токен администратора
curl -s -X POST https://nestdev.ru/api/support/tickets/<id>/reply \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"body":"Здравствуйте! Проверка ответа из админки."}'
# → {"ok":true,"to":"chelovek@example.ru","messageId":"…","sentAt":"…"}
```

Тело: `body` (10–8 000 символов, обязательный) и необязательный `subject`; без `subject` тема —
`Обращение <id>: ошибка|идея`.

| Отказ | Код | Когда |
|---:|---|---|
| `400` | `body_too_short` | текст короче 10 символов |
| `400` | `body_too_long` | текст длиннее 8 000 символов |
| `400` | `contact_email_missing` | у аккаунта нет пригодной почты (только служебный логин) |
| `401` | — | нет сессии админ-приложения |
| `404` | `ticket_not_found` | обращения нет |
| `429` | `quota_exceeded` | выбран суточный предел писем Postbox |
| `502` | `send_failed` | Postbox отказал; причина — в тексте ошибки и в переписке |

Куда уходит письмо: сначала `contactEmail` самого обращения (почта, которую человек ввёл в форме),
потом `reporter.contactEmail` из профиля (у старых обращений — живой профиль), потом `email` логина.
Письмо о новом обращении в поддержку тоже ставит `Reply-To` на почту из формы: ответ на него
уходит автору, а не на служебный логин. Адрес проверяется на сервере теми же
правилами, что и получатели рассылки: служебные зоны (`.local`, `.internal`, `.invalid`, `.test`,
`.example`, `.localhost`, `.lan`, `.home`) и домены без точки отсекаются до отправки — письмо на них
вернулось бы отскоком и съело квоту. Если пригодного адреса нет, маршрут честно отвечает
`contact_email_missing` вместе с логином аккаунта, а не отправляет письмо в никуда.

Две вещи, которых в письме нет: ссылки отписки (ответ на обращение — не рассылка, его ждут) и
любых служебных заголовков. Есть `Reply-To` — адрес из ключа `SUPPORT_REPLY_TO` (по умолчанию
`support@nestdev.ru`): если человек нажмёт «Ответить», письмо придёт в поддержку, а не на адрес
отправителя без ответа.

**Квота общая с рассылкой.** Ответы считаются в тот же суточный предел Postbox (по умолчанию
200 писем за 24 часа), что и рассылка: это квота аккаунта, а не кампании. Иначе рассылка на 200
адресов выбирала бы предел целиком, и следующие ответы людям падали бы с `429` уже на стороне
сервиса. Когда предел выбран, маршрут отвечает `429 quota_exceeded` и говорит, сколько из суток
занято рассылкой; ответ можно отправить, когда окно освободится.

Отправленное (и неудачное) письмо дописывается в переписку обращения — файл
`<id>.messages.jsonl` рядом с самим обращением — и отдаётся полем `messages` в списке и в карточке
(раздел 8.1). События «отправлен ответ» и «ответ не ушёл» идут в журнал безопасности действиями
`support.reply` / `support.reply.failed`: письмо живому человеку от имени платформы должно быть
видно постфактум.

### 8.4. Статус обращения

```bash
curl -s -X PATCH https://nestdev.ru/api/support/tickets/<id>/status \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"status":"closed"}'
# → {"ok":true,"id":"…","status":"closed"}
```

`status` — `open`, `in_progress` или `closed`. Дверь та же, что у ответа: только сессия
админ-приложения (ключ чтения обращения читает, но состояние не меняет). Тело строгое: лишнее поле
— `400`. Статус живёт в файле обращения, поэтому его видит и список, и карточка.

У обращений, созданных до появления поля, статуса в файле нет: при чтении он читается как `open`,
и старые тикеты не приходится переписывать. Статус — отдельное поле, а не вывод из факта ответа:
человек может ответить сам («спасибо, помогло»), а закрывает тему поддержка. Смена статуса пишется
в журнал действием `support.status`.

```bash
curl -s -H "Authorization: Bearer $TOKEN" https://nestdev.ru/api/admin/support/stats
```

```json
{
  "generatedAt": "2026-10-27T09:00:00.000Z",
  "total": 42,
  "byStatus": { "open": 12, "inProgress": 5, "closed": 25 },
  "byCategory": { "bug": 31, "idea": 11 },
  "awaitingReply": 15,
```

## 9. Рассылка по сегментам

Письма платформы (оплата, предупреждение о списании, тикет) уходят по SMTP, рассылка — по REST API
Postbox v2: у очереди свои требования — один получатель на письмо, идентификатор отправки в ответе,
остановка на середине. Настройка ключей — `docs/MAIL.md`, раздел 4.

| Метод и путь | Что отдаёт |
|---|---|
| `GET /api/admin/mail/overview` | сегменты с числами, последние десять кампаний, квота, состояние домена, текущая очередь |
| `POST /api/admin/mail/preview` | получатели, отброшенные адреса, три примера письма, цена — ничего не отправляет |
| `POST /api/admin/mail/test` | тестовое письмо администратору |
| `POST /api/admin/mail/send` | ставит кампанию в очередь |
| `POST /api/admin/mail/campaigns/<id>/stop` | останавливает очередь |

### 9.2. Предпросмотр

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"segmentId":"active30","subject":"Новое в NestDev","body":"Здравствуйте, {{name}}!\n\nВаш тариф: {{plan}}."}' \
  'https://nestdev.ru/api/admin/mail/preview'
```

Ответ: `recipients`, `excluded` (с разбором по причинам; `noConsent` — адреса без согласия на
рекламные письма), `skipped` (первые адреса с причиной), `sample` (до трёх настоящих писем с
раскрытыми тегами), `cost: { amount, currency, per1000, freeLeft, billable }`, `quota`, `footer`
и `warnings`. Согласие берётся из профиля (`productUpdates`): включить его можно в знакомстве или
в настройках аккаунта, отозвать — там же.

### 9.3. Отправка и остановка

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"segmentId":"active30","subject":"Новое в NestDev","body":"…","confirm":1127}' \
  'https://nestdev.ru/api/admin/mail/send'

curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  'https://nestdev.ru/api/admin/mail/campaigns/<id>/stop'
```

`confirm` — число получателей из предпросмотра. Сервер пересчитывает сегмент сам и при расхождении
отвечает `409 { "error": "Число получателей изменилось: 1131" }`: между предпросмотром и отправкой
кто-то мог зарегистрироваться или отписаться, и это уже другой список людей. Кампания создаётся со
статусом `queued`; очередь берёт её в течение секунды и пишет состояние каждого письма в
`mail_recipients` — поэтому перезапуск сервера посреди рассылки ничего не теряет.

`stop` не отзывает уже отправленные письма: остаток очереди помечается пропущенным, кампания
получает статус `stopped` и время завершения.

### 9.4. Что в письме

Теги: `{{name}}`, `{{email}}`, `{{project}}`, `{{plan}}`, `{{unsubscribe}}`. Неизвестный тег
остаётся как есть, а предпросмотр предупреждает о нём. Ссылка отписки дописывается автоматически,
если автор письма не поставил тег сам; страница `/unsubscribe?t=<подпись>` пишет адрес в
`mail_suppressions` — после этого его пропускают и следующие рассылки, включая текущую.

Сегменты считаются по росписи аккаунтов: почта для письма — из знакомства, логин используется только
как запасной вариант и отбрасывается, если он служебный.

### 9.5. Проверка после выкатки

```bash
curl -s -H "Authorization: Bearer $TOKEN" https://nestdev.ru/api/admin/mail/overview | jq '.configured, .domain.verified'
```

`true` в обоих полях означает, что ключ читается и домен подписан. `false` в первом — смотрите
`reason` (чаще всего не задан `POSTBOX_SENDER` или нет роли `postbox.sender` у сервисного
аккаунта); `false` во втором — `domain.hint` перечисляет, какой записи не хватает.

## 10. Журнал безопасности

Экран «Безопасность» в админке: что происходило со входом и платформой. Последние события сверху,
только чтение и только по админ-токену (`server/src/security/audit-journal.ts`,
`server/src/routes/admin-audit.ts`).

### 10.1. Запрос

```bash
curl -s -H "Authorization: Bearer $TOKEN" \
  'https://nestdev.ru/api/admin/audit?limit=50&action=admin.login.failed&days=7'
```

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `limit` | 100 | сколько событий вернуть, 1…500 |
| `action` | — | фильтр по имени действия; неизвестное имя даёт `400` со списком известных, а не пустой ответ |
| `actorId` | — | события одного администратора или пользователя |
| `days` | 0 | окно в сутках назад; `0` — без ограничения по времени |

### 10.2. Ответ

```json
{
  "entries": [
    {
      "id": "…",
      "at": "2026-10-26T17:40:12.345Z",
      "action": "admin.login.failed",
      "actorType": "system",
      "actorId": "",
      "actorLabel": "pimashin2015@gmail.com",
      "target": "",
      "targetLabel": "",
      "ipHash": "…",
      "details": { "reason": "bad_password" }
    }
  ],
  "total": 1,
  "range": { "days": 7, "limit": 50 },
  "actions": [{ "action": "admin.login.failed", "label": "Неудачный вход администратора" }]
}
```

- `entries` — события, `actions` — каталог для фильтра экрана (имя и подпись), его можно не
  хардкодить в приложении.
- `actorType`: `admin`, `user` или `system` (системные — отказы по лимиту попыток).
- `ipHash` — хеш адреса, не адрес: сравнить два события можно, восстановить адрес — нет.
- `details` — только строки, числа и булевы значения, не больше 12 ключей и 300 символов на
  значение. Значений ключей, паролей, TOTP-секретов и кодов восстановления в журнале нет по
  построению — вызывающие передают имена, счётчики и причины.

### 10.4. Хранение

Локальный режим — `security-audit.jsonl` в `DATA_DIR` (0600); Postgres — таблица `security_audit`
с индексами по `at` и `action, at`. Запись не отменяет само действие: сбой журнала не мешает входу
или сохранению ключей, но уходит в лог сервера строкой `[audit] не удалось записать событие…`.
