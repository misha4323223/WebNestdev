# Карта репозитория: этап 1

Дата: **15.11.2026**  
Статус: **код за флагом `AGENT_REPO_MAP`; baseline и canary ещё не пройдены**  
Связанные документы: [`AI_AGENT_CAPABILITY_PLAN.md`](AI_AGENT_CAPABILITY_PLAN.md), [`AI_EVAL.md`](AI_EVAL.md).

## 1. Задача

Старый контекст проекта — дерево до 500 записей и 9 000 символов, а автоподбор файлов —
лексический top-8. На большом проекте этого мало: модель видит имена, но не видит, кто кого
импортирует, где точка входа пакета и какие файлы образуют одну функцию.

Карта репозитория отвечает на три вопроса:

1. **Где я?** — языки, пакеты, entrypoints, тесты, верхние каталоги.
2. **Что связано с задачей?** — файлы по пути, символам, импортам и обратным зависимостям.
3. **Что прочитать дальше?** — точные пути для `fs.read`/`fs.outline`, а не весь репозиторий.

Она не заменяет чтение кода. В индексе **нет содержимого файлов**, поэтому он дешёвый,
кэшируемый и не раздувает контекст.

## 2. Модули

| Модуль | Ответственность |

| `server/src/agent/repo-index/types.ts` | Схема индекса, лимиты, результат поиска |
| `repo-index/scan.ts` | Обход проекта: игноры, секреты, symlink, лимиты, fingerprint |
| `repo-index/parse.ts` | Импорты, re-export, `require`, Python, CSS/HTML, символы |
| `repo-index/build.ts` | Разрешение импортов, alias, workspace-пакеты, entrypoints, кэш |
| `repo-index/query.ts` | Ранжирование, обратный граф, `repo.map`/`repo.find` |
| `tools/repo-tools.ts` | Два read-only инструмента |
| `agent/context-retrieval.ts` | Использует индекс при флаге, иначе старый лексический путь |
| `agent/context-builder.ts` | Добавляет сжатую карту в PROJECT CONTEXT при флаге |

## 3. Почему не TypeScript Compiler API

План этапа 1 предполагал `typescript` для парсинга. В production-образе стоит
`npm ci --omit=dev` (`server/Dockerfile`), а `typescript` — devDependency. Импорт компилятора в
рантайм либо упал бы на production, либо потребовал бы тащить десятки мегабайт в каждый API-контейнер.

Поэтому `parse.ts` — **консервативный regex-парсер**: он ищет импорты и экспортируемые имена, но
не строит типы. Точная карта символов по-прежнему у `fs.outline`; если regex пропустит ребро,
модель всё равно сможет прочитать файл. Ложное ребро опаснее пропущенного, поэтому шаблоны узкие.

Ограничения парсера перечислены в §9.

## 4. Сканирование и безопасность

Сканируются только текстовые кандидаты: исходники, конфиги, README, CSS/HTML, SQL, скрипты.

Не попадают в индекс:

- `node_modules`, `.git`, `dist`, `build`, `.next`, `.webnestdev`, `coverage`, `vendor` и
  остальные каталоги из `project-ignore.ts`;
- `.env`, `.env.local` и другие секретные файлы (`secret-paths.ts`), включая вложенные;
- символические ссылки — они не раскрываются и не читаются;
- двоичные файлы;
- lock-файлы и файлы больше лимита.

Лимиты по умолчанию:

| Лимит | Значение | Зачем |
|---|---:|---|
| файлов | 4 000 | ограничить обход и размер карты |
| один файл | 512 КБ | не читать бандлы и гигантские JSON |
| всего байт | 64 МБ | один запуск не должен читать гигабайты |
| кэш на диске | 8 МБ | повреждённый/раздутый кэш не читается целиком |

При достижении лимита индекс честно помечает `stats.truncated`, а не делает вид, что файлов
больше нет.

## 5. Разрешение импортов

Поддерживается:

- относительные пути `./service`, `../lib/db`;
- корневые пути `/src/app.js`;
- расширения `.ts/.tsx/.js/.jsx/.mjs/.cjs/.mts/.cts/.vue/.svelte/.astro/.py/.json/.css/.html`;
- `index.*` и `__init__.py` для каталогов;
- TypeScript `compilerOptions.baseUrl` и `paths` (например `@/* -> src/*`);
- workspace-пакеты по `package.json` (например `@shop/ui`);
- Python-относительные импорты (`from .helper import`, `from ..pkg import`);
- CSS `@import`, HTML `src`/`href`;
- `fs.grep scope`: имя workspace-пакета или каталог проекта (`@shop/ui`, `packages/ui`).

Не поддерживается пока: `tsconfig.extends`, `exports`-map пакета, generated-код, алиасы из
`vite.config`, path mapping вне корневого `tsconfig.json`. Для больших монорепо это следующий шаг.

## 6. Кэш

Два уровня:

1. **В памяти процесса** — 15 секунд; `repo.map`/`repo.find` в одном запуске не пересканируют проект.
2. **На диске** — `.webnestdev/repo-index.json`, атомарная запись через временный файл и `rename`.

Ключ актуальности — `fingerprint` из пути, размера и mtime каждого файла плюс лимиты. Сначала
сканер собирает метаданные, потом сравнивает fingerprint: неизменённый проект не перечитывает
содержимое файлов.

Инвалидация:

- `fs.write`, `fs.edit`, `fs.rename`, `fs.delete` вызывают `invalidateRepoIndex`;
- `terminal.exec` может менять файлы, но не инвалидирует индекс; поэтому у инструментов есть
  `refresh:true`, а TTL памяти — 15 секунд;
- `AGENT_REPO_MAP` выключен → индекс не строится вообще.

Планировщик получает `useDiskCache:false`: он обещал не менять проект, и служебный кэш ему тоже
писать нельзя.

## 7. Инструменты

### `repo.map`

Возвращает:

- `stats` (файлы, исходники, truncated, skipped);
- `languages`;
- `packages` (имя, каталог, entry);
- `entryPoints`;
- `testFiles`;
- `topDirectories`;
- `anchors` — с чего начать чтение.

Без содержимого файлов, обычно несколько килобайт.

### `repo.find`

Вход: `{query, limit?, includeTests?, refresh?}`.

Скоринг:

- точное имя файла/символа — сильнее всего;
- вхождение в путь/символ — средне;
- импорт — слабее;
- entrypoint и конфиг получают бонус только при уже найденном совпадении.

Затем один шаг по графу:

- вызывающие файлы (reverse import) — «кто использует этот модуль»;
- импортируемые файлы — «что нужно этому модулю».

Расширение начинается только от сильных совпадений (не менее 4 и не менее 40% от лучшего
score), иначе запрос про одну функцию вытягивал бы целую несвязанную ветку workspace.

## 8. Подключение и откат

Флаг: `AGENT_REPO_MAP=1`.

При выключенном флаге:

- `context-retrieval.ts` идёт старым лексическим путём;
- `repo.map`/`repo.find` не попадают в каталог инструментов запуска;
- `executeTool` откажет в вызове инструмента вне каталога;
- индекс не сканируется и не пишется.

При включённом:

- `buildProjectContext(..., {repoMap:true})` добавляет сжатую карту, сохраняя дерево как fallback;
- `retrieveRelevantFiles(..., {repoMap:true})` пробует индекс; любая ошибка индекса логируется и
  откатывается на старый путь;
- `selectToolNames({repoMap:true})` добавляет два инструмента;
- `repo.map`/`repo.find` работают только с проектом из sandbox и не принимают произвольный путь.

Откат — выключить флаг, без миграции данных: кэш можно удалить, он пересоберётся.

## 9. Известные ограничения

- Regex-парсер не понимает вычисляемые импорты, `tsconfig.extends`, `exports`-map и некоторые
  синтаксисы; это осознанный компромисс ради production-зависимостей.
- `.vue`/`.svelte`/`.astro` индексируются как файлы, но их внутренние импорты пока не parsed.
- Нет LSP/типов: `repo.find` не говорит, совпадает ли сигнатура функции.
- Нет git-aware инкремента: fingerprint по mtime/size, а не diff; переименование пересобирает
  затронутую часть.
- После `terminal.exec` индекс может быть свежим только через 15 секунд или `refresh:true`.
- Сжатая карта добавляется к дереву, а не заменяет его: дерево остаётся страховкой для ассетов
  и файлов вне индекса.
- `fs.grep scope` строит индекс, если его ещё нет; это чтение проекта, а не изменение кода.
- Нет замера на 100k LOC и eval top-10; без baseline нельзя считать этап закрытым.
