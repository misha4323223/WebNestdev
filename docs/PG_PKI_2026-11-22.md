# PostgreSQL PKI и ротация сертификатов

**Статус:** внедрено и проверено на production 22.11.2026, 07:33 UTC.
**Следующий этап:** подготовлен переход на Yandex KMS (без `ca.key` на `node-1`); код и
workflow готовы, но production ещё не мигрирован. Порядок и ограничения — в
[`PG_PKI_YANDEX_KMS.md`](PG_PKI_YANDEX_KMS.md).
**Область:** PostgreSQL 17 на `node-1`/`node-2`, HAProxy ↔ PostgreSQL и standby.

## Что изменилось

До 22.11.2026 обе ноды использовали один общий самоподписанный `server.crt`, который был
одновременно CA. Теперь есть отдельный корневой CA и уникальные листья нод:

- корневой CA: `CN=WebNestDev PostgreSQL Root CA`, срок 10 лет;
- листья: `CN=webnestdev-postgres-node-1` и `CN=webnestdev-postgres-node-2`, срок 90 дней;
- у каждой ноды свой приватный ключ; ключи и CA лежат только на `node-1` в
  `/etc/webnestdev-ha/pg-pki` (`700 root`, ключи `600`);
- на `node-2` есть только публичный CA и лист/ключ `node-2`;
- HBA остаётся только `hostssl`, HAProxy — `ssl verify required ca-file /etc/haproxy/pg-ca.crt
  alpn postgresql`, standby — `sslmode=verify-full`.

Публичные проверки на обеих нодах после ротации:

```bash
sudo openssl verify -CAfile /etc/haproxy/pg-ca.crt \
  /etc/postgresql/17/main/tls/server.crt
sudo -u postgres psql -p 5433 -Atc 'show ssl'   # on
grep -c 'BEGIN CERTIFICATE' /etc/haproxy/pg-ca.crt  # 1
```

`node-1` и `node-2` имеют разные fingerprint; старый самоподписанный сертификат больше не
проходит проверку новым CA. Для сравнения сохранялись публичные fingerprint в отчёте
выкатки, приватные ключи не выводились.

## Миграция без простоя

Порядок, который выполняет `pg_pki.sh migrate`:

1. Создать CA и оба листа; ничего в production не менять.
2. Собрать `/etc/webnestdev-ha/pg-pki/trust-bundle.crt` из **старого и нового** CA и
   положить его в `/etc/haproxy/pg-ca.crt`, `/etc/postgresql/17/main/tls/ca.crt` и
   `pg-tls/ca.crt` на обеих нодах; reload PostgreSQL и HAProxy.
3. Заменить лист `node-1`, reload PostgreSQL/HAProxy, проверить `pg_stat_replication`/
   `pg_stat_wal_receiver`.
4. Заменить лист `node-2`, reload, проверить streaming.
5. Убрать старый CA из bundle, оставить только новый; reload; проверить цепочку,
   TLS 1.3, API и plaintext-отказ.
6. Установить `webnestdev-pg-tls-rotate.timer` на `node-1`.

Проверено вживую 22.11.2026: на каждом шаге публичный `/api/ready` и health обеих нод
отдавали `200`, репликация оставалась `streaming`, после финального шага plaintext к
`5433` отклоняется (`no pg_hba.conf entry ... no encryption`), direct TLS показывает
`TLSv1.3` и `Verification: OK` для листа соответствующей ноды.

## Ротация

```bash
sudo /opt/webnestdev-ha/pg_pki.sh rotate       # принудительно новые листья
sudo /opt/webnestdev-ha/pg_pki.sh auto-rotate  # только если осталось < 30 дней
sudo /opt/webnestdev-ha/pg_pki.sh verify       # обе ноды
```

Ручная ротация проверена 22.11.2026: fingerprint `node-1` и `node-2` изменились, CA остался
тем же, HBA/HAProxy/ALPN сохранились, API — `200`, standby — `streaming`. Таймер
`webnestdev-pg-tls-rotate.timer` включён (`enabled`, `active`), первый запуск `auto-rotate`
корректно определил «осталось 89 дн. — ротация не нужна».

## Остаточные риски и границы

- Приватный ключ CA и оба листовых ключа хранятся на `node-1`; это осознанный компромисс
  текущего production. Подготовлен переход на Yandex KMS: после миграции `ca.key` на ноде
  нет, подпись выполняет отдельный signer. Пока миграция не выполнена, компрометация
  `node-1` означает компрометацию PKI. Подробности — в
  [`PG_PKI_YANDEX_KMS.md`](PG_PKI_YANDEX_KMS.md).
- CA-ключ имеет **проверенный** off-site backup: 22.11.2026 создан age-архив и выполнен
  restore drill (`RESTORE-DRILL-OK`). Настройки, объект и порядок восстановления — в
  [`PG_PKI_BACKUP.md`](PG_PKI_BACKUP.md). Остаточная граница — отсутствие HSM: после
  перехода на KMS компрометация `node-1` больше не даёт ключ CA, но KMS-ключ
  асимметричной подписи не является HSM. До миграции компрометация `node-1` по-прежнему
  означает компрометацию PKI.
- Ежедневный таймер запускается только на `node-1`. Если она выключена, ротация не
  происходит; действующий лист живёт 90 дней, запас 30 дней. При возврате `node-1`
  `auto-rotate` догонит срок.
- `node2-sync.sh` передаёт лист `node-2` из `pg-pki/nodes/node-2`; общий `server.crt`
  `node-1` на `node-2` больше не копируется.

## Файлы

- `deploy/ha/pg_pki.sh` — CA, выпуск, миграция, ротация, проверка, systemd timer.
- `deploy/ha/pg_tls.sh` — раскладка файлов и HBA; `setup` блокируется при активном PKI,
  `apply` берёт `ca.crt`, а не лист.
- `deploy/scripts/node2-sync.sh` — передаёт на `node-2` её уникальный лист и CA.
- `deploy/ha/install-node1.sh` — вызывает `pg_pki.sh setup`.
- `deploy/ha/runtime-files.txt` — `pg_pki.sh` и `pg_ca_backup.sh` входят в runtime-набор.
- `deploy/ha/pg_ca_backup.sh` — age-архив CA и загрузка в Yandex Object Storage.
- `.github/workflows/pki-backup-setup.yml`, `.github/workflows/pki-backup.yml` — настройка
  без терминала на ВМ и backup по расписанию.
