# Security hardening: 21.11.2026

**21.11.2026, 19:38 UTC.** Разбор пяти находок и безопасные правки без изменения
пользовательских сценариев. Код не выкатывался: изменения лежат в рабочем дереве и вступят в
силу только после обычной выкатки образа. Единственное изменение на нодах — права
`.env.production` (`600`); содержимое не читалось.

## Что изменено

### 1. Ссылки подтверждения почты и сброса пароля больше не доверяют Host

**Было.** `verificationBaseUrl()` в `server/src/routes/auth.ts` брал `PLATFORM_URL`, затем
разрешённый `Origin`, а при их отсутствии — `request.protocol + Host`. Последний fallback
позволял построить ссылку из поддельного `Host`, если `PLATFORM_URL` не задан.

**Стало.** Логика вынесена в `server/src/auth/public-base-url.ts`:

1. `PLATFORM_URL` — как и раньше, главный источник;
2. если его нет — разрешённый `Origin` из `WEBNESTDEV_ALLOWED_ORIGINS`;
3. если нет и его — первый разрешённый origin (`fallbackOrigin`), а не `Host`;
4. только в полностью пустой конфигурации — локальный адрес для разработки.

`fallbackOrigin` экспортирован из `server/src/oauth/oauth-flow.ts`; для OAuth поведение не
изменилось. Тесты: `server/src/auth/public-base-url.test.ts`.

**Важно:** в текущем production `PLATFORM_URL` задан на обеих нодах, поэтому активного
изменения ссылок нет. Правка закрывает будущий сценарий «переменную забыли на новой ноде».

### 2. Дверь preview не ходит на link-local и metadata адреса

**Было.** `previewOwnerTarget()` принимал любой host и порт, включая
`169.254.169.254`, link-local IPv6 и metadata-имена. Пока `owner_address` пишет только
сервер, это было defense-in-depth, но при подмене строки registry или адреса ноды
открывался путь к metadata.

**Стало.**

- в `server/src/security/address-policy.ts` добавлена
  `isLinkLocalOrMetadataAddress()`: link-local IPv4/IPv6, metadata-адреса, unspecified и
  multicast;
- `previewOwnerTarget()` отклоняет такие адреса и имена `metadata`,
  `metadata.google.internal`, `instance-data`;
- private, loopback и публичные адреса **по-прежнему разрешены**: это сделано намеренно,
  чтобы не ограничить работу нод и будущих конфигураций. Запрещены только адреса, которые
  не могут быть легитимной дверью preview.

Тесты: `server/src/security/address-policy.test.ts`,
`server/src/preview/peer-door.test.ts`.

**Остаток.** Если `owner_address` — DNS-имя, которое резолвится в link-local/metadata,
проверка по строке его не поймает. Сейчас адрес формирует сервер из записи ноды, а не
пользователь; для полной защиты нужен резолв и проверка всех полученных адресов перед
соединением. Это отдельная задача, потому что добавляет DNS-запрос в путь двери.

### 3. `/api/tls-ask` больше не отдаёт внутренние идентификаторы

**Было.** Ответы содержали `projectId`, `siteId` и `slug`. Caddy использует только статус
`200/404`, поэтому эти поля были лишней информацией для внешнего наблюдателя.

**Стало.** В `server/src/routes/hosting.ts` ответы содержат только `allowed`, `host` и
`kind` (`api-host`, `site`, `custom-domain`, `preview`). Проверка статусов не менялась.
Тест `server/src/routes/custom-domains.test.ts` дополнительно проверяет отсутствие `siteId`.

## Что сознательно не менялось

### Ограничение `/api/tls-ask` по сети и rate limit

Маршрут остаётся публичным и без rate limit. Закрыть его «на всякий случай» нельзя без
риска сломать выпуск сертификатов: Caddy обращается к нему из контейнера, а прямые запросы
приходят через тот же Caddy. Нужен отдельный внутренний listener/секрет и согласованное
изменение Caddyfile; это операционная задача, а не локальная правка кода.

Старый `GET /api/preview/tls-ask` оставлен для совместимости. Текущий Caddyfile его не
использует; удалять его можно только после проверки, что старые конфиги Caddy нигде не
остались.

### `PLATFORM_URL` как обязательная переменная

Мы не стали ронять старт production без `PLATFORM_URL`: это могло бы остановить ноду при
ошибке выкатки. Вместо этого fallback теперь не использует `Host`. Рекомендация на будущее:
сделать переменную обязательной и проверять HTTPS на старте, когда операционный порядок
выкатки будет это гарантировать.

### HTTP-origin в `WEBNESTDEV_ALLOWED_ORIGINS`

В production-настройках обеих нод среди разрешённых источников есть
`http://178.236.27.102:8787`. Это не секрет, но лишний HTTP-origin. `.env` не менялся:
правка требует изменения production-конфигурации и проверки, что этот origin нигде не
используется. Рекомендация: оставить только HTTPS-origin панели.

### `PUBLIC CONNECT` в клиентской и платформенной БД

`REVOKE CONNECT ... FROM PUBLIC` не выполнялся. Это изменение на уровне кластера может
отрезать роли, которые сегодня подключаются неявно; сначала нужен аудит всех ролей и
PgBouncer. Текущие базы находятся в разных кластерах (`17/main` и `17/client`), поэтому
tenant-роли клиентской БД не получают доступ к платформенной базе. Разделение кластеров
нужно сохранить; `REVOKE` — отдельная hardening-задача.

### Публичные production-документы

Точные IP, SSH-детали и внутренние пути остаются в публичном репозитории: их удаление
затрагивает операционные runbook'и и должно сопровождаться переносом в приватное хранилище.
Это не сделано «наполовину», чтобы не сломать инструкции. Рекомендация: вынести
эксплуатационные детали в приватный репозиторий, а публичные docs оставить без адресов
доступа.

## PostgreSQL TLS включён

**21.11.2026, 22:08 UTC.** Включён на живой паре `node-1`/`node-2`: общий самоподписанный
сертификат с SAN для `host.docker.internal`, `localhost`, `127.0.0.1`, `10.0.0.4` и
`10.0.0.5`; `ssl=on` на обеих нодах; HBA содержит только `hostssl`; HAProxy ходит в
PostgreSQL по TLS с проверкой CA; `node-2` — с `sslmode=verify-full`.

При включении найдена критичная деталь: PostgreSQL 17 принимает direct TLS **только с ALPN
`postgresql`**. HAProxy 2.8 открывает TLS сразу, без `SSLRequest`, поэтому без
`alpn postgresql` сервер рвёт новые соединения, хотя старые пулы API ещё работают. Это
ложное ощущение исправности; `db_proxy.py` и тесты обновлены, runtime установлен на обе ноды.

Проверено на реальных ВМ: новые пулы API обеих нод — `200`; все соединения приложения — TLS
1.3; `sslmode=disable` к `5433` отклоняется; `sslmode=require` доходит до authentication;
`sslmode=verify-full` проверяет цепочку; `pg_stat_replication` — `streaming`, лаг близок к
нулю; `pg_stat_ssl` для walsender — `true`. Остаточная граница: сертификат самоподписанный,
общий для двух нод; ротация и KMS/HSM — отдельный проект.

## Остаточные риски

- `/api/tls-ask` остаётся публичным endpoint без отдельного rate limit; для закрытия нужен
  внутренний доступ Caddy и согласованная конфигурация.
- `owner_address` с DNS-именем, ведущим в link-local, не проверяется по разрешённому IP.
- `PUBLIC CONNECT` на обеих БД не отозван; текущая изоляция держится на разных кластерах.
- Публичные docs продолжают раскрывать production-топологию.
- `PLATFORM_URL` пока не обязателен на старте; защита — только безопасный fallback.
