# DNS Setup — reg.ru (для WebNestDev, nestdev.ru)

**Актуально на 09.11.2026.** Панель: `https://nestdev.ru`. Публичный IP: `178.236.27.102`.

## 1. Текущие записи

В REG.RU (`Домены` → `nestdev.ru` → `DNS-серверы и управление зоной` → `Записи`) сейчас должны
быть такие A-записи:

| Тип | Имя | Значение |
| --- | --- | --- |
| A | `@` | `178.236.27.102` |
| A | `www` | `178.236.27.102` |
| A | `host` | `178.236.27.102` |
| A | `*.host` | `178.236.27.102` |
| A | `*.preview` | `178.236.27.102` |
| A | `ha-test` | `178.236.27.102` |

Остальные записи (DKIM CNAME, SPF/DMARC TXT, `_acme-challenge.preview`) не относятся к A-записи
панели и при обычном переключении IP не меняются.

TTL положительных ответов — `1h`. Это текущий минимум в интерфейсе REG.RU для зоны; не путать с
полем `Minimum` (оно отвечает за кэш негативных ответов).

## 2. Где находится статический IP

`178.236.27.102` — статический внешний адрес MWS `ea-webnestdev`, теперь привязанный к
NLB `webnestdev-nlb-main`. NLB распределяет трафик на Caddy `node-1` и `node-2`; адрес не
меняется при падении или возврате любой ВМ. DNS менять при failover не нужно.

У `node-1` management-адрес `2.59.83.250` (`ea-webnestdev-admin`). У `node-2` постоянного
внешнего адреса нет: NAT MWS меняется, штатный SSH — `10.0.0.5` через ProxyCommand на
`node-1`; при выключенной `node-1` текущий NAT берётся из MWS API. В DNS management-адреса
не добавлять.

**Важно:** старый `2.59.82.143` был адресом `node-2`, MWS освободил его после перезагрузки.
Возвращать его в DNS или делать на него переадресацию нельзя — адрес больше не принадлежит
нашим ВМ.

## 3. Проверка

```bash
dig +short nestdev.ru A
dig +short www.nestdev.ru A
dig +short test.preview.nestdev.ru A
```

Все три команды должны вернуть `178.236.27.102`.

Проверка через публичные резолверы:

```bash
nslookup nestdev.ru 1.1.1.1
nslookup nestdev.ru 8.8.8.8
```

С самого сервера сайт проверяется без DNS:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' --resolve nestdev.ru:443:178.236.27.102 https://nestdev.ru/
```

Ожидается `200`.

## 4. Если старый IP остался в кэше

«Не заслуживающий доверия ответ» в `nslookup` — это нормальный ответ из кэша, а не ошибка
безопасности. Если домашний роутер или провайдер отдаёт `2.59.82.143`, а `1.1.1.1` уже отдаёт
`178.236.27.102`:

1. На роутере поставить DNS `1.1.1.1` и `8.8.8.8`, затем перезагрузить роутер.
2. Либо на компьютере прописать эти DNS вручную.
3. Очистить кэш: Windows — `ipconfig /flushdns`; macOS — `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder`.
4. В Chrome при необходимости очистить `chrome://net-internals/#dns` и `#sockets`.

Смена TTL в REG.RU не сокращает уже закэшированную старую запись. Нужно дождаться TTL, сменить
DNS-резолвер или очистить локальный кэш. VPN и мобильный интернет работают потому, что
используют другой DNS.

## 5. Failover и статический адрес

Сейчас `178.236.27.102` закреплён за NLB `webnestdev-nlb-main`; обе ВМ — его бэкенды,
трафик. Автоматического переключения DNS на `node-2` нет.

Для полноценного failover нужно одно из двух:

- зарезервировать отдельный статический внешний адрес для `node-2` и при аварии менять A-запись
  на него (TTL 1h означает до часа на обновление у части клиентов);
- получить в MWS плавающий IP или NLB, который переключает трафик между узлами без смены DNS.

Пока ни один из этих вариантов не настроен, при падении `node-1` сайт будет недоступен, даже
если `node-2` работает как runner. Не направлять DNS на автоматический IP `node-2`.

## 6. Панель REG.RU

- A-записи меняются в карточке домена: `DNS-серверы и управление зоной` → `Записи`.
- Wildcard `*.preview` — одна запись на все адреса `<uuid>.preview.nestdev.ru`.
- `_acme-challenge.preview` нужен для DNS-01 wildcard-сертификата; не удалять, пока используется
  `deploy/scripts/wildcard-cert.sh`.
- DKIM CNAME и SPF/DMARC TXT относятся к почте и не должны меняться при правке A-записей.
