# Хостинг: S3 как источник правды, диск как кэш

Статус: **этап 1 реализован и проверен тестами**, 17.11.2026, 16:33 UTC; выкатка на ВМ
ожидается.

Документ описывает, что нужно перенять у объектного хостинга, чтобы 50 сайтов не упирались
в локальный Gluster, и почему выбран именно этот порядок. Это продолжение
[`STATIC_HOSTING_PLAN.md`](STATIC_HOSTING_PLAN.md); факты внедрения — в
[`STATIC_HOSTING_PROGRESS.md`](STATIC_HOSTING_PROGRESS.md).

## 1. Где сейчас узкое место

Сайт уже хранится в S3-совместимом бакете (`PLATFORM_S3_*`), но Caddy отдаёт файлы из
локального каталога `SITES_DIR/<slug>/current`. Бакет — архив на случай потери диска, а не
рабочий источник.

Проблема не в количестве сайтов как таковом, а в том, что на диске лежат **все готовые
релизы**:

- `HOSTING_KEEP_RELEASES=3` — до трёх релизов на сайт;
- 50 сайтов × 35 МБ × 3 = ~5,25 ГБ логически;
- Gluster replica 2 — ~10,5 ГБ raw;
- свободно на `/sites` около 7 ГБ по `df` на 17.11.2026.

Отдельное ограничение: `HOSTING_MIN_FREE_BYTES=5G`. Даже с активным кэшем 50 сайтов
займут ~3,5 ГБ raw, после чего свободно останется ~3,5 ГБ — меньше резерва 5 ГБ. То есть
этот этап убирает старые версии с диска, но для 50 активных сайтов всё равно нужно либо
добавить диск, либо отдельно снизить резерв. Менять резерв молча нельзя: он защищает
Gluster от заполнения.

Плюс `reconcile` намеренно не трогает каталоги всех `ready`-релизов, потому что они нужны
для отката. Поэтому простого уменьшения `HOSTING_KEEP_RELEASES` недостаточно: вместе с
локальными файлами `pruneOldReleases` удаляет и объекты из бакета, то есть откат станет
невозможен.

## 2. Что именно перенимаем

Не «Яндекс целиком», а три свойства:

1. **S3 — источник правды.** Готовый релиз живёт в бакете, пока он есть в истории.
2. **Локальный диск — кэш.** На узле лежит только то, что нужно для быстрой отдачи.
3. **История и кэш — разные политики.** Удаление локальной копии не означает удаление
   релиза; удаление из истории — отдельное решение.

Caddy пока остаётся на локальном `current`: это самый дешёвый путь. Полноценный
S3-origin с LRU-кэшем — следующий этап, только если активных релизов перестанет хватать
локального диска.

**Вывод:** откат и восстановление уже умеют работать без локальной копии. Не хватает
разделения политик хранения.

### Этап 1. Разделить историю S3 и локальный кэш

Цель: на диске остаётся только активный релиз (по умолчанию), история — в бакете.

- [x] Добавить `HOSTING_LOCAL_RELEASES` (по умолчанию `1`).
- [x] Оставить `HOSTING_KEEP_RELEASES` политикой истории в бакете.
- [x] Удалять локальный каталог только у релиза, который уже имеет `storageKey`.
- [x] Не удалять из S3 и не помечать `deleted` при локальном вытеснении.
- [x] Не вытеснять локальные релизы, если бакет не настроен.
- [x] Научить `reconcile` не сохранять все `ready`-каталоги, а только входящие в локальный
  кэш.
- [x] Добавить тесты на выбор релизов и на запрет вытеснения без S3.

Критерии готовности:

- публикация не удаляет старый релиз из бакета только потому, что он вытеснен с диска;
- откат на вытесненный релиз восстанавливает его из бакета;
- при `HOSTING_S3_ENABLED=0` локальная история не сокращается;
- история 50 сайтов больше не занимает диск (на диске только активные релизы);
- `reconcile` не удаляет активный релиз и `building`;
- для 50 активных сайтов отдельно решается диск/резерв: текущие 7 ГБ и резерв 5 ГБ дают
  запас примерно на 28 активных сайтов.

### Этап 2. Наблюдаемость кэша

- [ ] Показывать в health: локальные релизы, размер кэша, число восстановлений из S3.
- [ ] Добавить счётчик неудачных восстановлений.

### Этап 3. S3-origin и LRU, если понадобится

- [ ] Отдельный `hosting-origin` перед Caddy.
- [ ] Промах кэша: восстановить релиз из S3, затем отдать файл.
- [ ] LRU по размеру, а не по числу версий.
- [ ] Защита от cache stampede и таймауты.

Этот этап не нужен для 50 сайтов, если этап 1 даёт достаточный запас. Он нужен, когда
локальный диск перестаёт вмещать активные релизы или когда отказ узла должен быть
незаметен без прогрева.

### Этап 4. Функции и база — отдельно

- [ ] Лимиты API Gateway: время, размер, конкурентность.
- [ ] Тёплый пул функций, если холодные старты станут заметны.

Это не смешивается с кэшем статики: у функций и базы свои точки отказа.

## 4. Риски этапа 1

- **Восстановление из S3 медленнее локального диска.** При откате на вытесненный релиз
  сначала скачивается `tar.gz` и проверяется `sha256`. Для 35 МБ это приемлемо, для
  больших релизов — измерять отдельно.
- **S3 становится обязательным для истории.** Если бакет недоступен, активный сайт
  продолжает работать с диска, но откат на вытесненный релиз временно недоступен.
- **Два узла и общий `SITES_DIR`.** Локальный кэш общий, поэтому вытеснение видят оба узла.
  Активный релиз не удаляется, а `reconcile` умеет вернуть его из бакета.
- **Legacy-релизы без `storageKey`.** Они не вытесняются: иначе откат стал бы невозможен.

## 5. Что не входит

- перенос Caddy на S3 website endpoint;
- собственный CDN;
- MinIO вместо текущего бакета;
- изменение формата релиза (один `tar.gz` + манифест);
- автоматический failover базы;
- переход на Яндекс Облако.
