# Резервная копия PostgreSQL

Статус: **этап 0.1 плана роста** (`docs/SCALING_3000_PLAN.md`). Бэкап снимается ежедневно,
проверяется отдельно и раз в месяц восстанавливается в учебную базу.

Главное правило: **бэкап, который ни разу не восстанавливали, бэкапом не считается.** Поэтому
здесь не только загрузка, но и автоматическая проверка свежести и учебное восстановление.

---

## 1. Что происходит и когда

| Когда (МСК) | Что | Режим |
| --- | --- | --- |
| 05:30 каждый день | дамп → проверка архива → загрузка в S3 → `latest.json` | `backup` |
| 13:00 каждый день | последнему бэкапу не больше 30 часов, размер совпадает с манифестом | `check` |
| 1-е число, 07:00 | скачать последний бэкап, восстановить в `restore_check_<время>`, проверить таблицы, удалить | `restore-drill` |

Расписание и запуск — GitHub Actions (`.github/workflows/pg-backup.yml`). Скрипт выполняется на
ВМ по SSH (или на self-hosted runner), поэтому заходить на сервер руками не нужно. Журнал
каждого запуска и ошибки видны в Actions.

Почему не cron на ВМ: у владельца нет терминала на сервере, а установка systemd-таймера
потребовала бы правки выкатки и root-доступа. Отдельный workflow не может сломать деплой, а
история запусков уже есть. Когда появятся runner-узлы (этап 3), таймер переедет на них.

## 2. Из чего состоит

| Файл | Роль |
| --- | --- |
| `deploy/scripts/pg-backup.sh` | оболочка: `pg_dump` в контейнере `postgres:17`, проверка архива, загрузка, учебное восстановление |
| `server/src/storage/postgres-backup.ts` | ключи, манифест, контрольная сумма, проверка свежести, чтение для восстановления |
| `server/src/scripts/postgres-backup.ts` | CLI внутри образа сервера (`put`, `manifest`, `check`, `get`) |
| `.github/workflows/pg-backup.yml` | расписание, SSH, режимы, журнал |
| `deploy/scripts/pg-backup.test.sh` | проверка оболочки без Docker и базы (заглушка `docker`) |

Дамп снимает **контейнер `postgres:17`**, а не сервер: `pg_dump` отказывается работать с сервером
новее себя, и версия клиента в образе сервера не должна решать судьбу бэкапа. Загрузку делает
**контейнер сервера**, потому что там уже есть S3-клиент и ключи `PLATFORM_S3_*`.

## 3. Где лежит бэкап

```
<PLATFORM_S3_PREFIX>/backups/postgres/<база>/<ГГГГ>/<ММ>/<ДД>/<база>-<время>.dump
<PLATFORM_S3_PREFIX>/backups/postgres/<база>/latest.json
```

Пример: `webnestdev/backups/postgres/webnestdev/2026/10/29/webnestdev-20261029T023000Z.dump`.

- `<PLATFORM_S3_PREFIX>` — тот же префикс, что у холодного яруса проектов (по умолчанию
  `webnestdev`), но каталог `backups/postgres/` отдельный: уборка архивов проектов не заденет
  бэкапы и наоборот.
- `latest.json` — единственный источник для проверки и восстановления; перечислять бакет не
  нужно. Манифест публикуется **после** дампа и только после подтверждения размера `HEAD`.
- В манифесте: `version`, `database`, `key`, `bytes`, `sha256`, `createdAt`. Контрольная сумма
  проверяется до восстановления, поэтому обрезанный или подменённый объект не попадёт в базу.

## 4. Что нужно на ВМ

Ничего нового: используются те же `PLATFORM_S3_ENDPOINT`, `PLATFORM_S3_BUCKET`, `PLATFORM_S3_REGION`,
`PLATFORM_S3_ACCESS_KEY_ID`, `PLATFORM_S3_SECRET_ACCESS_KEY`, что уже переданы серверу в
`docker-compose.yml`. Если холодный ярус настроен, бэкап заработает без правки `.env`.Проверить, что ключи есть (значения не печатаются):

```bash
cd ~/webnestdev/src
docker compose exec -T webnestdev-server node server/dist/scripts/postgres-backup.js config
```

Ожидаемо: JSON с `endpoint`, `bucket`, `prefix` и `region`. Если команда отвечает «объектное
хранилище не настроено», бэкап работать не будет — сначала проверьте `PLATFORM_S3_*`.

Переменные GitHub (не секреты): `DEPLOY_APP_DIR`, при необходимости `BACKUP_MAX_AGE_HOURS`
(по умолчанию 30). Секреты `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`, `DEPLOY_HOST`, `DEPLOY_USER`,
`DEPLOY_PORT` уже используются выкаткой.

## 5. Первый запуск после выкатки

1. Выкатить версию с этим кодом (в образе должен появиться
   `server/dist/scripts/postgres-backup.js`).
2. GitHub → Actions → **PostgreSQL backup** → **Run workflow** → `mode = backup`.
3. Убедиться, что в журнале есть строка `[pg-backup] бэкап готов`, а в выводе — `"ok":true`,
   ключ и размер.
4. Повторить с `mode = check` — проверка должна пройти.
5. Запустить `mode = restore-drill` — это и есть проверка «бэкап действительно восстанавливается».
   Ожидаемо: `[pg-backup] восстановление проверено: N таблиц; учебная база удалена`.

Если шаг 2 отвечает, что скрипта нет в образе, — на ВМ ещё старая версия; сначала выкатка.

## 6. Учебное восстановление

`restore-drill`:

1. читает `latest.json`;
2. проверяет свободное место (дамп распаковывается примерно в 5 раз больше сжатого размера);
3. создаёт `restore_check_<ГГГГММДД_ЧЧММСС>` — **никогда** не рабочую базу;
4. скачивает дамп, проверяет `sha256` и восстанавливает `pg_restore --exit-on-error`;
5. считает таблицы в `public`; ноль таблиц — отказ;
6. удаляет учебную базу (даже при ошибке восстановления — через `trap`).

Рабочая база в этом режиме не упоминается ни в `CREATE`, ни в `DROP`; имя учебной базы
проверяется отдельно и не может совпасть с `POSTGRES_DB`.

Чтобы оставить учебную базу для разбора, запустите скрипт с `KEEP_RESTORE_DB=1` (например, по
SSH вручную); по умолчанию она удаляется. В workflow отдельного переключателя нет намеренно:
учебная база не должна копиться на диске.

## 7. Хранение и срок жизни

Бэкапы **не удаляются скриптом** — это осознанно: автоматическое удаление по ошибке опаснее
лишнего гигабайта. Срок жизни задаётся lifecycle-правилом бакета:

- префикс: `<PLATFORM_S3_PREFIX>/backups/postgres/`;
- действие: удалить объекты старше **30 дней**;
- правило включить в консоли провайдера (Yandex Object Storage, Cloud.ru, Timeweb и т. п. —
  раздел «Lifecycle» / «Жизненный цикл»).

Если у бакета уже есть lifecycle-правила (например, для архивов проектов), **добавьте новое
правило, не заменяя существующие**: у архивов другой срок, и общее правило может удалить нужное.

Если провайдер не умеет правило по префиксу, поставьте его на весь бакет **после** проверки, что
архивы проектов живут дольше: у них другой срок, и общее правило может удалить нужное.

Оценка объёма: дамп сжатый. При базе 100–300 МБ это десятки мегабайт в день; 30 дней — единицы
гигабайт. Диск ВМ при этом не растёт: временный дамп удаляется сразу после загрузки.

## 8. Безопасность

- Бакет **приватный**, доступ только по ключу `PLATFORM_S3_*`; публичный бакет с бэкапами — это
  утечка паролей, сессий и персональных данных.
- Трафик до хранилища — HTTPS; ключи не печатаются ни в одном режиме.
- В дампе есть хеши паролей, сессии, зашифрованные секреты и данные пользователей. Не скачивайте
  его на рабочий ноутбук без необходимости и не пересылайте в мессенджерах.
- Ключ хранилища должен быть отдельным для платформы (не личным ключом владельца) и с правом
  только на этот бакет; при утечке — ротация.
- Шифрование на стороне провайдера включите в настройках бакета. Клиентское шифрование с ключом
  из `.env` намеренно не делается: при потере ВМ ключ потеряется вместе с ней, и бэкап станет
  бесполезным. Если понадобится, ключ должен храниться вне ВМ — это отдельная задача.

## 9. Если что-то пошло не так

| Симптом | Причина | Что делать |
| --- | --- | --- |
| `объектное хранилище не настроено` | нет `PLATFORM_S3_*` в контейнере сервера | проверить `.env` на ВМ и блок `PLATFORM_S3_*` в compose |
| `нет ни одного бэкапа` | первый запуск ещё не прошёл | запустить `mode=backup` вручную |
| `Последний бэкап … старше 30 ч` | бэкап не сработал | посмотреть предыдущий запуск в Actions, затем ручной `mode=backup` |
| `pg_dump завершился с ошибкой` | блокировка, нет места, база недоступна | `docker compose logs postgres`, свободное место, повторить |
| `мало места` | диск ВМ заполнен | освободить место (архивация проектов, `docker system prune`), повторить |
| `восстановление … не прошло` | повреждён дамп или нет расширения | проверить `sha256`, журнал `pg_restore`, запустить ещё раз; не удалять старые бэкапы до разбора |
| `загрузка … не удалась` | ключи, сеть, права бакета | проверить `PLATFORM_S3_*` и доступ к бакету |

Проверка свежести (`check`) запускается отдельно в 13:00. Если она упала, GitHub пришлёт
уведомление о failed workflow; в этапе 0.2 добавится внешний алерт, который не зависит от
настроек уведомлений GitHub.

## 10. Ограничения и следующий шаг

- Расписание живёт в GitHub Actions. Если Actions или репозиторий недоступны, бэкап не снимется;
  следующий запуск это покажет. Для этапа 0.1 это приемлемо, для 3к — нет: на этапе 3 таймер
  переедет на runner-узел, а GitHub останется внешней проверкой.
- Скрипт не делает point-in-time recovery: это ежедневный логический дамп. Для PITR нужен
  managed PostgreSQL с архивированием WAL (этап 4).
- Восстановление в **рабочую** базу автоматически не делается: это ручная операция с остановкой
  сервера, отдельной базой и переключением `DATABASE_URL`. Учебное восстановление проверяет
  дамп, но не заменяет план аварийного восстановления.
