# Почта платформы: Yandex Cloud Postbox

Платформа отправляет покупателям и владельцу три вида писем:

| Письмо | Когда уходит | Код |
|---|---|---|
| Обращение поддержки | Сразу после сохранения тикета — на `SUPPORT_EMAIL_TO` | `server/src/support/support-mail.ts` |
| Оплата принята | После подтверждения платежа Робокассой | `server/src/billing/notify.ts` |
| Предупреждение о списании | За `BILLING_NOTICE_DAYS` дней (по умолчанию три) до автопродления | `server/src/billing/recurring.ts`, `notify.ts` |

Основной путь — **Yandex Cloud Postbox**: письма уходят от подтверждённого домена (`noreply@…`),
а вход в SMTP — API-ключом сервисного аккаунта, а не паролем живого ящика. Ключи вводятся в
**«Настройки → Ключи сервера → Почта (Yandex Cloud Postbox)»**, читаются на каждое письмо и
начинают работать без перезапуска. Старые ключи личного SMTP (`SUPPORT_SMTP_*`, smtp.yandex.ru и
т. п.) продолжают работать как запасной путь для поддержки; письма биллинга отправляются только
через почту платформы.

Отказ почты ничего не ломает по деньгам: тариф включает уведомление об оплате, а не письмо, и
тикет сохраняется, даже если письмо не ушло. Но **предупреждение о списании — условие списания**:
без отправленного письма свипер подписку не оплачивает, поэтому включить автопродление нельзя ни
без настроенной почты, ни без адреса у аккаунта (сервер отвечает отказом с причиной).

## 1. Что нужно в Yandex Cloud

1. **Платёжный аккаунт** в статусе `ACTIVE` или `TRIAL_ACTIVE`. Подходит аккаунт физического лица —
   отдельного бизнес-аккаунта Postbox не требует. Оплата — российской картой.
2. **Сервисный аккаунт** в том же каталоге, где создан адрес Postbox, с ролью `postbox.sender`.
3. **API-ключ** этого сервисного аккаунта с областью действия `yc.postbox.send`. Секрет
   показывается один раз. *Идентификатор ключа — это логин SMTP, секретная часть — пароль.*
   Пароль живого ящика и «пароль приложения» здесь не подходят.
4. **Адрес-домен** в Postbox: заведите адрес вида `noreply@ваш-домен` и подтвердите владение
   доменом. Отправлять можно только с подтверждённого домена (поддомен — отдельным адресом).

## 2. DNS-записи домена

Postbox выдаёт **две CNAME-записи DKIM** на странице адреса — добавьте их у регистратора и не
удаляйте после проверки. Дополнительно:

- **SPF.** Если записи ещё нет: `TXT` со значением `v=spf1 include:spf.postbox.yandexcloud.net ~all`.
  Если SPF уже есть — добавьте `include:spf.postbox.yandexcloud.net` в существующую запись перед
  `all`; второй SPF-записи быть не должно.
- **DMARC (рекомендуется):** `TXT` для `_dmarc.ваш-домен` со значением `v=DMARC1;p=none`.

Проверка домена может занять время из-за кеширования DNS; если за 24 часа статус не сменился —
запустите проверку повторно на странице адреса.

## 3. Ключи в панели

| Ключ | Значение |
|---|---|
| `MAIL_SMTP_HOST` | `postbox.cloud.yandex.net` |
| `MAIL_SMTP_PORT` | `465` (по умолчанию; платформа поддерживает только шифрование сразу) |
| `MAIL_SMTP_USER` | Идентификатор API-ключа сервисного аккаунта |
| `MAIL_SMTP_PASSWORD` | Секретная часть того же API-ключа |
| `MAIL_FROM` | Адрес на подтверждённом домене, например `noreply@nestdev.ru` |
| `MAIL_FROM_NAME` | Необязательно: имя отправителя, например `NestDev` |
| `BILLING_NOTICE_DAYS` | Необязательно: за сколько дней предупреждать о списании (по умолчанию 3, допустимо 1–30) |

Строка `[deploy] Почта платформы: сервер=…, отправитель=…, пароль=…` в логе выкатки показывает
только «есть/нет», без значений — по ней видно, доехали ли ключи.

**Запасной (и более короткий) набор — та же пара ключей под именами рассылки.**

| Ключ | Значение |
|---|---|
| `POSTBOX_KEY_ID` | Идентификатор API-ключа сервисного аккаунта — это **логин SMTP** |
| `POSTBOX_SECRET` | Секретная часть того же API-ключа — **пароль SMTP** |
| `POSTBOX_SENDER` | Адрес отправителя на подтверждённом домене, например `noreply@nestdev.ru` |
| `POSTBOX_FROM_NAME` | Необязательно: имя отправителя |
| `POSTBOX_SMTP_HOST` / `POSTBOX_SMTP_PORT` | Необязательно: по умолчанию `postbox.cloud.yandex.net` и `465` |

Если `MAIL_SMTP_*` не заполнены, сервер собирает SMTP-настройки из этой пары: адрес отправителя —
`POSTBOX_SENDER`, логин и пароль — `POSTBOX_KEY_ID` и `POSTBOX_SECRET`. Этого достаточно для всех
писем платформы, включая **ответ на обращение из админки** и письмо о новом тикете. Явные
`MAIL_SMTP_*` всегда важнее — две настройки в одном окружении не спорят.

**Важно:** этот же ключ **не подходит** для REST-рассылки. `POSTBOX_KEY_ID` / `POSTBOX_SECRET` —
API-ключ сервисного аккаунта, а SigV4 подписывается статическим ключом доступа (`POSTBOX_STATIC_KEY_ID`
и `POSTBOX_STATIC_SECRET`). Попытка подписать SendEmail API-ключом заканчивается `403 Forbidden` с
пустым телом — отказом шлюза авторизации, а не ошибкой письма. Подробнее — раздел 7.

## 4. Рассылка по сегментам (REST API)

Письма выше — **служебные**: оплата, предупреждение о списании, тикет. Рассылка — другое дело:
её отправляют по сегменту, она идёт часами и её останавливают на середине. Поэтому у неё
свой транспорт: **REST API Postbox v2** (`POST /v2/email/outbound-emails`), одно письмо — один
получатель. SMTP для этого не годится: в ответе нет идентификатора письма, а пакетная отправка
не даёт ни остановиться, ни понять, сколько ушло за сутки.

| Ключ | Значение |
|---|---|
| `POSTBOX_SENDER` | Подтверждённый адрес, например `mail@nestdev.ru` — им представляется рассылка |
| `POSTBOX_FROM_NAME` | Необязательно: имя отправителя рассылки |
| `PLATFORM_URL` | Адрес платформы (`https://nestdev.ru`) — из него собирается абсолютная ссылка отписки |
| `POSTBOX_IAM_TOKEN` | Готовый IAM-токен сервисного аккаунта (живёт ~12 часов: для проверки, не для постоянной работы) |
| `POSTBOX_KEY_ID` + `POSTBOX_SECRET` | **Ключ SMTP** (логин и пароль), а не ключ рассылки: им отправляются письма платформы, REST-запросы им не подписываются (см. раздел 3) |
| `POSTBOX_STATIC_KEY_ID` + `POSTBOX_STATIC_SECRET` | Статический ключ доступа: запросы рассылки подписываются SigV4, токен обновлять не нужно |
| `POSTBOX_SA_KEY` / `POSTBOX_SA_KEY_FILE` | Ключ сервисного аккаунта (можно не задавать: сервер возьмёт `YANDEX_SA_KEY`, если у роли есть `postbox.sender`) |
| `POSTBOX_DAILY_LIMIT` | Необязательно: писем за 24 часа (по умолчанию 200) |
| `POSTBOX_RATE_PER_SECOND` | Необязательно: писем в секунду (по умолчанию 1) |
| `POSTBOX_DKIM_SELECTORS` | Необязательно: селекторы DKIM через запятую — без них админка скажет «DKIM не проверен», а не «не настроен» |
| `POSTBOX_PRICE_PER_1000` | Необязательно: цена за 1 000 писем — предпросмотр покажет стоимость |
| `WEBNESTDEV_MAIL_UNSUBSCRIBE_SECRET` | Необязательно: ключ подписи ссылок отписки (от 32 символов). Без него берётся `WEBNESTDEV_ENCRYPTION_KEY`, а в разработке — встроенный ключ. **Менять после первой рассылки нельзя:** уже отправленные ссылки перестанут работать |

Ключи рассылки вводятся там же, где остальные — **«Ключи сервера → Почта»** — и начинают работать
без перезапуска. Если у сервисного аккаунта роли `postbox.sender` нет, send отвечает отказом;
роль выдаётся в каталоге, где создан адрес.

### Маршруты (админ-токен, `Authorization: Bearer`)

| Маршрут | Что делает |
|---|---|
| `GET /api/admin/mail/overview` | Сегменты с числами, последние кампании, квота, состояние домена (DKIM/SPF/DMARC), причины предупреждений |
| `POST /api/admin/mail/preview` | `{segmentId, subject, body}` → получатели, отброшенные адреса, три живых примера письма с раскрытыми тегами, цена |
| `POST /api/admin/mail/test` | `{subject, body, to?}` → письмо администратору (без `to` — на его адрес входа) |
| `POST /api/admin/mail/send` | `{segmentId, subject, body, confirm}` → ставит кампанию в очередь; при расхождении числа получателей отвечает `409` |
| `POST /api/admin/mail/campaigns/:id/stop` | Останавливает очередь: отправленные письма не отзываются |

Теги в теме и тексте: `{{name}}`, `{{email}}`, `{{project}}`, `{{plan}}`, `{{unsubscribe}}`.
Неизвестный тег остаётся в письме как есть, а предпросмотр предупреждает о нём — молча выбрасывать
часть текста нельзя. Сегменты: `active30`, `paying`, `free`, `inactive30`, `never`, `all`.

**Без согласия письмо не уходит.** Рассылка — рекламная, поэтому получатель должен явно включить
«Реклама и новости» в знакомстве или в настройках аккаунта (поле `productUpdates` профиля).
Адреса без согласия попадают в `excluded.noConsent` и в предупреждение админки: это не ошибка
сегмента, а его честный размер. Служебные письма (оплата, поддержка) идут другим путём и
согласия не требуют; отписка из письма по-прежнему закрывает рассылку сразу.

### Очередь

Одно письмо в секунду, состояние каждого письма — в таблице `mail_recipients`. Поэтому перезапуск
сервера посреди рассылки ничего не теряет: очередь продолжается с того письма, на котором
остановилась (письмо, застрявшее в состоянии `sending`, возвращается в очередь при старте). Повторов
— не больше трёх; после третьего адрес помечается `failed`, один недоставленный адрес не задерживает
остальных. Достигнув суточного предела, очередь останавливается и продолжает сама, когда предел
освобождается.

Служебные адреса (`…@phone.webnestdev.local`, `…@yandex-id.webnestdev.local` и всё без точки в
домене) в очередь не попадают: письмо на них уйдёт отскоком и съест квоту. Получатель — почта из
знакомства, а не логин аккаунта.

### Отписка

Ссылка отписки подписана (`/unsubscribe?t=<адрес>.<HMAC>`) и дописывается в конец письма, если тег
`{{unsubscribe}}` не поставлен автором. Адрес попадает в `mail_suppressions`, и следующие рассылки
его пропускают — включая ту, что идёт прямо сейчас. Страница отписки подтверждает действие кнопкой:
почтовые сервисы сами открывают ссылки из писем, и отписка по одному открытию срабатывала бы без
человека.

### Проверка

1. `GET /api/admin/mail/overview` — `configured: true`, сегменты с числами, `domain.verified: true`.
2. `POST /api/admin/mail/test` — письмо приходит во «Входящие», а не в «Спам». Если в спам — смотрите
   `domain.hint` в overview: чаще всего не хватает DKIM или `include:spf.postbox.yandexcloud.net`.
3. `POST /api/admin/mail/preview` — сверьте числа: получатели, отброшенные адреса, цена.
4. `POST /api/admin/mail/send` с `confirm` из предпросмотра — сначала на маленьком сегменте.
5. Нажмите отписку в полученном письме — число получателей в следующем предпросмотре должно
   уменьшиться на единицу.

До первой большой рассылки попросите в консоли повышение квоты: на стартовых 200 письмах в сутки
анонс по базе в 1 500 человек идёт больше недели.

## 5. Квоты и цены

Стартовые квоты Postbox (увеличиваются по запросу через Quota Manager или поддержку — сделайте это
до запуска продаж):

| Ограничение | Значение |
|---|---:|
| Отправка | 1 письмо/с |
| Письма за 24 часа | 200 |
| Получателей в письме | 200 |
| Размер письма с вложениями | 30 МБ |

Первые **2 000 писем в месяц** не тарифицируются; плата считается по письмам, принятым к отправке,
даже если доставка не состоялась, а при нескольких получателях — по числу получателей. Актуальные
ставки — на странице тарификации Postbox.

Частые ответы SMTP: `454 Maximum sending rate exceeded` — превышена скорость отправки,
`550 Daily sending quota exceeded` — выбрана дневная квота. Оба пишутся в лог сервера строкой
`[billing] письмо… не ушло` или `support mail not delivered`.

## 6. Проверка писем платформы

1. Заполните ключи в «Ключи сервера» (значения не перезапускают сервер).
2. Создайте обращение через кнопку «Поддержка»: письмо должно прийти на `SUPPORT_EMAIL_TO`, а окно
   покажет, что доставка состоялась.
3. Проведите тестовую оплату в Робокассе (см. `docs/ROBOKASSA.md`): после подтверждения платежа на
   контакт аккаунта придёт письмо «Оплата принята».
4. Для автопродления: включите `ROBOKASSA_RECURRING` и дождитесь окна `BILLING_NOTICE_DAYS` —
   письмо-предупреждение должно уйти до списания; в логе будет строка
   `[billing] предупреждение о списании отправлено`.

## 7. Если Postbox ответил 403

`403 Forbidden` без тела JSON — это отказ шлюза авторизации, а не проблема письма: у неподтверждённого
домена и у лимитов свои коды (`400 MailFromDomainNotVerifiedException`, `400 LimitExceededException`,
`400 SendingPausedException`). Причину видно без чтения `.env`:

```bash
curl -s https://nestdev.ru/api/health | jq .mail
```

```json
{
  "provider": "postbox",
  "sender": "noreply@nestdev.ru",
  "credentialKind": "smtp-key",
  "credentialSource": "POSTBOX_KEY",
  "folderId": "b1g…",
  "tokenAgeSeconds": null,
  "ready": true,
  "campaigns": { "configured": false, "credentialKind": "smtp-key", "reason": "нет ключа рассылки: …" },
  "lastError": { "at": "2026-10-27T09:00:00.000Z", "kind": "smtp", "message": "SMTP ответил 535 на шаге «password»" }
}
```

Что означает каждое поле:

- `credentialKind` / `credentialSource` — чем уходит письмо и откуда взяты имена:
  `smtp-credentials` / `MAIL_SMTP` (явные `MAIL_SMTP_*`) или `smtp-key` / `POSTBOX_KEY`
  (`POSTBOX_KEY_ID` + `POSTBOX_SECRET`). Ключ рассылки описан отдельно, в `campaigns.credentialKind`
  (`iam-token-env`, `static-key`, `service-account-key` или `metadata`);
- `ready: false` — почта не настроена вообще: ни `MAIL_SMTP_*`, ни пары `POSTBOX_KEY_ID` /
  `POSTBOX_SECRET`;
- `campaigns.configured: false` с причиной — рассылка не сможет отправить ни одного письма;
  письма платформы при этом работают;
- `tokenAgeSeconds` — возраст IAM-токена из метаданных или из ключа сервисного аккаунта. У готового
  токена из `POSTBOX_IAM_TOKEN` его не знает никто (`null`), и это первое, что надо проверить при
  «вчера работало»: статический IAM-токен живёт около 12 часов;
- `lastError` — последний отказ любого транспорта с ответом сервиса (без значений ключей).

Порядок разбора:

1. `lastError.kind: "postbox-rest"` и `403` в тексте — рассылка подписана ключом SMTP. Выдайте
   `POSTBOX_STATIC_KEY_ID` / `POSTBOX_STATIC_SECRET` (статический ключ доступа) или ключ сервисного
   аккаунта с ролью `postbox.sender`. Ответ поддержки от этого не зависит — он идёт по SMTP.
2. `lastError.kind: "smtp"` и `535` — неверная пара логин/пароль: проверьте, что `POSTBOX_KEY_ID` —
   идентификатор API-ключа сервисного аккаунта с областью `yc.postbox.send`, а `POSTBOX_SECRET` —
   его секретная часть (не пароль живого ящика и не «пароль приложения»).
3. `ready: true`, но писем нет — смотрите `lastError` и квоту (`docs/MAIL.md`, раздел 5): при
   выбранном суточном пределе ответ из админки честно отвечает `429 quota_exceeded`.
4. `ready: false` — переменные не доехали до контейнера: compose передаёт только перечисленные в
   `docker-compose.yml` имена, а workflow — только те, что перечислены в `.github/workflows/deploy.yml`.
   После правки ключей нужна повторная выкатка (или сохранение их в панели «Ключи сервера» —
   панель важнее окружения и работает без перезапуска).

### Ответы SMTP и что они значат

В тексте ошибки теперь есть шаг по-человечески, дословный ответ сервиса и подсказка: например
`SMTP ответил 550 на шаге «MAIL FROM (адрес отправителя)»: 550 5.7.1 Sender address is not
verified: noreply@nestdev.ru. Postbox не принимает адрес отправителя: …`.

| Ответ | Шаг | Причина | Что делать |
|---|---|---|---|
| `550`, `553`, `554` | `MAIL FROM` | домен не подтверждён, адрес не создан в каталоге сервисного аккаунта — **или** выбрана суточная квота (`Daily sending quota exceeded`) | подтвердить домен, создать адрес, проверить `POSTBOX_SENDER` (в health — `mail.sender`); при слове `quota` — ждать окно |
| `535`, `534` | пароль | не та пара логин/пароль | нужен идентификатор и секрет API-ключа сервисного аккаунта с областью `yc.postbox.send` и ролью `postbox.sender` |
| `550`, `553`, `551`, `450` | `RCPT TO` | получатель не существует или не принимает почту | проверить адрес человека; письмо не ушло, обращение сохранено |
| `454`, `421` | любой | превышена скорость или квота | повтор позже; скорость — `POSTBOX_RATE_PER_SECOND` |

**Отправитель берётся из `POSTBOX_SENDER` (или `MAIL_FROM`)**, а не из адреса человека и не из
админки: `550` на `MAIL FROM` — это отказ именно тому адресу, которым представляется платформа.
Одинаковых адресов «на всякий случай» не бывает: если в Postbox создан `mail@nestdev.ru`, а в
`POSTBOX_SENDER` стоит `noreply@nestdev.ru`, письмо не уйдёт — даже при верном ключе и
подтверждённом домене.

Проверка после исправления: ответ из админки должен прийти на адрес из профиля автора обращения
с темой «Обращение …: ошибка|идея» и `Reply-To` из `SUPPORT_REPLY_TO`, а в переписке обращения
появиться запись со статусом `sent`.
