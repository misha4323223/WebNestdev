# Телефонная авторизация и защита демо WebNestdev

Текущий статус: базовые API входа по SMS, привязка телефона, хранение OTP и ограничения попыток добавлены в ветку разработки. Это ещё не подтверждение production-готовности: CI, тестовая SMS-доставка, интеграционные проверки YDB и юридическая проверка остаются обязательными.

## Цель

Сделать телефон проверяемым идентификатором аккаунта и условием получения демо-тарифа, а не просто добавить поле в профиль. Email остаётся контактным адресом и не должен давать дополнительные попытки получить демо.

## Предлагаемая политика

- Номер нормализуется в E.164 для РФ: `+7XXXXXXXXXX`. Форматы `8...`, `7...` и номер с пробелами должны приводиться к одному значению.
- Подтверждённый номер уникален и привязан максимум к одному аккаунту. Нельзя автоматически отвязывать номер или переносить его на другой аккаунт через повторный SMS-код.
- Вход по телефону — одноразовый SMS-код; пароль и email не нужны для нового телефонного аккаунта. Для существующих email-аккаунтов реализован отдельный сценарий безопасной привязки телефона после авторизации.
- Демо Pro/Team выдаётся один раз на подтверждённый номер. Факт выдачи хранится отдельно от текущего статуса подписки и не очищается после истечения срока, отмены или смены тарифа.
- Проверка права на демо и запись факта выдачи выполняются в одной транзакции YDB. Постоянный реестр demo_claims использует хеш номера и не очищается после истечения срока, отмены или изменения текущей подписки. В локальном JSON-режиме данные предназначены только для разработки в одном процессе.
- Пока платежи не подключены, никакие банковские карты, реальные списания и статусы «оплачено» не имитируются.

## Безопасность OTP

- Код из 6 цифр, срок действия 5 минут.
- Не более 5 попыток ввода на один challenge; повторная отправка не чаще раза в 60 секунд.
- Ограничения по номеру, IP и общий лимит отправки SMS работают через YDB в production: по умолчанию не более 3 SMS на номер в час, 10 на IP в час и 100 SMS глобально в час. Лимиты проверки кода также хранятся в YDB и применяются между экземплярами сервера. Проверка и увеличение всех применимых счётчиков (глобального, номера и IP) выполняются в одной YDB-транзакции; резервирование OTP-challenge тоже транзакционное, чтобы параллельные экземпляры не отправляли конкурирующие коды. Если API работает за reverse proxy, настройте только доверенные IP/CIDR в WEBNESTDEV_TRUST_PROXY, иначе IP-ограничения могут видеть адрес самого прокси.
- Хранить только HMAC-хеш кода с серверным секретом, никогда не писать код в production-логи и не возвращать его через API. Факт согласия на обработку номера записывается с версией согласия, целью, временем и хешем IP; локальный режим пишет такие события в файл с ограниченными правами.
- Ответ на запрос отправки не должен раскрывать, зарегистрирован ли номер.
- В production отправка разрешена только через настроенного SMS-провайдера. Режим вывода кода в консоль допустим только для локальной разработки.
- Перед публичным production-запуском нужно добавить CAPTCHA/антибот-защиту, метрики стоимости SMS и аварийное отключение отправки. Установлен общий лимит 100 SMS в час, который снижает риск неконтролируемых расходов, но не заменяет CAPTCHA.

## Хранение и миграции

Используются отдельные таблицы для телефонных идентификаторов, OTP-challenge, лимитов отправки и постоянных демо-прав. Это позволяет не ломать существующие email-аккаунты и добавлять поля без опасной миграции основной таблицы пользователей. Телефон уникален, на аккаунт можно привязать один телефон, а право на демо хранится по хешу подтверждённого номера.

JSON-хранилище допустимо только для локальной разработки в одном процессе. Общая production-среда должна использовать YDB и транзакционную проверку права на демо.

## SMS-провайдер

Реализован адаптер SMS.RU через серверный API. Для production задаются WEBNESTDEV_SMS_MODE=smsru, SMSRU_API_ID и WEBNESTDEV_PHONE_OTP_SECRET и WEBNESTDEV_TRIAL_CLAIM_SECRET длиной не менее 32 символов. TRIAL_CLAIM_SECRET необходимо хранить неизменным между развёртываниями, так как он защищает постоянный реестр демо-прав. Глобальный лимит можно снизить или изменить через WEBNESTDEV_SMS_MAX_PER_HOUR. Для локальной разработки допустим WEBNESTDEV_SMS_MODE=console, который выводит код только при NODE_ENV не равном production. Для первого российского подключения можно рассмотреть SMS.RU через серверный API с ключом из переменной окружения. Ключ нельзя хранить в репозитории или передавать клиенту. До production нужно проверить регистрацию имени отправителя, доставку у операторов, работу CAPTCHA/антибот-защиты от SMS-бомбинга и фактическую стоимость. Цена SMS зависит от оператора, типа сообщения и настроек аккаунта.

## Восстановление аккаунта

На текущем этапе нет самостоятельной смены номера и восстановления доступа при потере SIM-карты. Перед публичным запуском нужен безопасный recovery-процесс, который не позволяет злоумышленнику отвязать номер и получить повторный демо-тариф. Не отвязывать номер автоматически по одному только SMS-коду.

## Персональные данные РФ

Телефон — персональные данные. До запуска нужно проверить применимость 152-ФЗ, наличие уведомления оператора при необходимости, согласие и политику обработки персональных данных, сроки хранения и удаления, процедуру запросов субъектов, а также требования локализации первичного сбора и хранения данных граждан РФ в базах данных на территории РФ. Это требует проверки конфигурации фактической инфраструктуры и юридического согласования; один только выбор российского SMS-провайдера не обеспечивает соответствие закону.

## Критерии готовности

1. Повторный запрос не может повторно активировать демо для одного аккаунта или подтверждённого номера, даже если запись текущей подписки изменена.
2. Один телефон не может получить демо на двух аккаунтах даже при параллельных запросах к разным экземплярам API.
3. Повторная отправка и перебор OTP ограничены и проверяются тестами.
4. Код не попадает в production-логи, клиентские ответы и аналитические события.
5. Добавлены тесты нормализации телефона и конкурентной активации демо; отдельные интеграционные тесты истечения OTP, неправильного кода, блокировки после попыток и конфликтов уникальности ещё должны быть подтверждены CI/YDB.
6. CI зелёный, а перед production выполняется интеграционный тест на реальной тестовой YDB и тестовом SMS-аккаунте.
