# Правила работы с репозиторием

Актуальное состояние ВМ, env-файлов, токенов, `NODE2_PG_PASSWORD` и production-сборки:
[`docs/PRODUCTION_STATE.md`](docs/PRODUCTION_STATE.md). При следующей сессии читать его до
начала работ с `node-2`.

## Вторая production-ВМ (`node-2`)

`node-2` — **не тестовая и не одноразовая машина**. Это вторая нода production-контура
(API/runner/PostgreSQL standby и общий storage), которая будет работать круглосуточно.

**Текущее решение пользователя (10.11.2026): `node-2` остаётся включённой (`power=ON`), пока
пользователь сам не скажет выключить.** Не выключать её после работ «по привычке»: HA-контур
теперь рассчитан на два постоянно включённых узла, и выключение peer'а меняет поведение
quorum/failover-проверок.

- Для работы, которой нужны две машины, `node-2` можно включать без дополнительного вопроса.
- Пока нет отдельного указания — оставлять `node-2` включённой и проверять по MWS, что
  `status.hardware.power=ON`.
- Если пользователь попросит выключить: после всех работ убедиться, что MWS показывает
  `power=OFF`, и только тогда считать работу законченной.
- Пока `node-2` выключена, прод нельзя переводить на базу или storage, которые живут
  только на ней: вместе с ней пропадёт сервис.
- После production-запуска она работает постоянно; это фиксируется в
  `docs/CLUSTER_HA_PLAN.md`.

Перед работой: дождаться SSH и нужных сервисов, проверить, что прод не смотрит на `node-2`
как на единственную базу/storage. После работы: вернуть прод в исходное состояние; питание
менять только по явной просьбе пользователя.

Все настройки и данные на `node-2` (PostgreSQL, `NODE2_PG_PASSWORD`, storage, runner) — это
production-конфигурация второй ноды. Их нужно доводить до рабочего состояния при включённой
машине, а не откладывать как «тестовую заготовку».

## Доступ к MWS и второй ВМ (проверено 08.11.2026)

- MWS API уже настроен в окружении: `MWS_SA_KEY_ID` + `MWS_SA_PRIVATE_KEY`. Значения не
  печатать. Проверка: `cd server && npm run mws:check --silent` → `MWS-ACCESS=ok`;
  проект `project-pimashin2015`, сервисный аккаунт `nestdev`.
- ВМ `node-2`: `compute/projects/project-pimashin2015/virtualMachines/node-2`, зона
  `ru-central1-b`, приватный IP `10.0.0.5`, Ubuntu 24.04, пользователь `ubuntu`, Docker 29.9.3.
  Внешнего IP нет, поэтому SSH идёт через прод.
- Питание — через MWS Compute API: `GET /compute/v1/projects/project-pimashin2015/virtualMachines/node-2`
  даёт `metadata.etag`; затем `POST` по тому же пути с
  `{metadata:{etag},spec:{hardware:{power:"ON"|"OFF"}}}`. После теста обязательно проверить
  `status.hardware.power=OFF`.
- SSH на `node-2`: приватный ключ `/tmp/nestdev-agent`, пользователь `ubuntu`. В cloud-init
  `node-2` прописан публичный ключ `nestdev-agent`. Прямого маршрута из workspace нет:
  `ssh -i /tmp/nestdev-agent -o 'ProxyCommand=ssh -i /tmp/nestdev-agent -W %h:%p Misha@2.59.83.250' ubuntu@10.0.0.5`.
  Если `/tmp/nestdev-agent` пропал, на проде есть `~/.ssh/node2_key` (`prod-to-node2`): через
  него можно поставить новый публичный ключ в `~/.ssh/authorized_keys` на `node-2`.
- Первая ВМ: `Misha@2.59.83.250` (management-адрес `ea-webnestdev-admin`), тот же
  `/tmp/nestdev-agent`. Публичный `178.236.27.102` теперь принадлежит NLB
  `webnestdev-nlb-main`, а не ВМ; SSH туда не идёт. Ключ из `AGENT_SSH_PUBKEY` deploy-скрипт
  ставит только на первую ВМ, не на `node-2`.
- На 10.11.2026 после полного destructive-прогона обе ВМ включены по решению
  пользователя: `node-1` — primary, `node-2` — streaming standby, общий storage и одна
  база на обеих (legacy `src-postgres-1` остановлен). Это не тестовый режим.
- Внешний NAT `node-2` динамический: читать текущий адрес из MWS API, а не из документов.
- На обеих ВМ стоят таймеры `webnestdev-storage.timer` (перемонтирование Gluster) и
  `webnestdev-sandbox-ownership.timer` (владелец каталогов проектов); ставит
  `deploy/ha/install-storage-guard.sh`. Проверка: `systemctl is-active webnestdev-storage.timer
  webnestdev-sandbox-ownership.timer`.

## Текущий фокус: вторая ВМ принимает всё после падения первой

- Сейчас делаем **отказоустойчивость ядра**: вторая ВМ должна принять API, PostgreSQL и
  состояние/данные после падения первой, а вернувшаяся первая — стать standby/рабочим узлом.
- **Preview, sandboxes, 30 одновременных preview, ёмкость под них, диск под storage и бэкапы
  сейчас не блокер.** Пользователь поднимет это позже; не отказываться из-за них от
  двухмашинного теста и не требовать увеличения `node-2` на этом этапе.
- Текущих 2 vCPU / 4 ГБ `node-2` достаточно для текущей нагрузки. Диск увеличивается отдельно
  к production; для проверки переживания падения его хватает.
- Проверять в первую очередь: вторая ВМ становится primary/принимает API, первая возвращается
  как standby/worker, данные не теряются. Ограничения preview/sandbox можно временно
  отключить или игнорировать, если они мешают этой проверке.

## Продуктовое решение: вход по номеру и SMS не поддерживаются

- **Вход по номеру телефона и SMS не поддерживаются и не будут возвращаться.** Это решение
  от 10.11.2026, а не временное отключение из-за стоимости или недонастроенного провайдера.
- Не планировать SMS-провайдеров, не переносить `phone-store` в PostgreSQL, не включать
  `PHONE_AUTH_ENABLED`, не считать `SMS-CHECK=key-unreadable` дефектом и не предлагать
  телефонный вход в интерфейсе.
- Существующий код, таблицы, ключи и тесты можно не удалять, но новую работу по ним не
  начинать. В планах, чек-листах и отчётах телефонный вход считается отсутствующим, а не
  «отложенным до следующего этапа».

## Размер файлов и модульность

- Новую логику не добавлять большими блоками в уже большие файлы. Выносить в отдельные
  небольшие модули с одной ответственностью.
- Ориентир для нового модуля — несколько сотен строк, а не тысяча. Если файл уже превышает
  ~600–700 строк, новые крупные части должны появляться отдельно, а не внутри него.
- Не делать «модуль на всё»: лучше несколько узких файлов (`temp-paths.ts`, `placement.ts`),
  чем один общий `utils.ts` или ещё один огромный файл.
- Существующие большие файлы не переписывать целиком ради рефакторинга. Если изменение
  затрагивает такой файл, выносить только ту часть, которая нужна текущей задаче.
- Тесты держать рядом с модулем и не складывать все проверки в один файл.

## Проверки и выкатка

- Для изменений в сервере: сначала точечные тесты, затем `tsc -p server/tsconfig.json --noEmit`;
  для фронтенда — `tsc -b --noEmit`.
- Не коммитить и не выкатывать без явной просьбы. Изменения остаются в рабочем дереве.
- Не читать и не печатать `.env`; секреты не попадают в чат, логи и репозиторий.
