## Песочница

- [x] **Память по классу команды:** 25.11.2026, 21:26 UTC. Заведомо дешёвые читающие команды (`ls`, `cat`, `git status`, `grep`, `find`…) получают потолок 256 МБ (`SANDBOX_MEMORY_LIGHT_MB`, минимум 64), а сборки, установки, `node` и любое неизвестное — прежние `SANDBOX_MEMORY_MB` (1024 МБ). Резервация в общем бюджете и `--memory` контейнера берут одно и то же число; на удалённом runner потолок едет в `options.memoryMb`. Выключатель `SANDBOX_COMMAND_MEMORY_CLASS=0`. Общий `SANDBOX_MEMORY` (в production `1g`) — потолок по умолчанию, но потолок конкретной команды его перекрывает; иначе настройка из `.env` молча отключала бы деление (проверено на node-1).
- [x] **Ёмкость ноды:** 25.11.2026, 22:02 UTC. `SANDBOX_MAX_CONCURRENT` 2 → 4 на обеих нодах плюс явный `SANDBOX_MEMORY_BUDGET_MB=2048` (без него бюджет выводился бы как 4 × 1024 = 4096 МБ при 3886 МБ на машине). Замер на node-1 до выкатки: 4 лёгкие команды — пик 4 контейнера, 9537 → 5309 мс при двух и четырёх слотах; 4 обычные (`node`) — пик 2, память пропускает только две сборки; 6 лёгких при шести слотах — пик 6, свободно 2490 МБ из 3886.
- [x] **Замер ёмкости после выкатки:** 25.11.2026, 22:25 UTC. На `node-1` (образ `sha-5fa6e97d8fbe`, 2 vCPU, 3886 МБ, реальный production-конфиг): 1 лёгкая команда — 3.92 с, 4 лёгкие — 4.62 с (пик 4), 4 тяжёлые (`node`) — 8.10 с (пик 2), 8 лёгких — 8.31 с (пик 4, две волны), 2 тяжёлые + 2 лёгкие — 7.85 с (выполнены все 4), OOM в `dmesg` — 0. Итог: одна нода держит 4 одновременные команды от 4 разных аккаунтов, из них тяжёлых — до двух; 8 человек — 4 работают / 4 ждут. Подробный разбор и таблица — `docs/SANDBOX_CAPACITY.md`.
- [ ] **`SANDBOX_MAX_JOBS`: 4 → 2 (не выкачено):** 25.11.2026, 22:25 UTC. Счётчик одновременных фоновых заданий (`terminal.start`) на ноду, по умолчанию 4. Каждое задание всегда берёт базовый потолок 1024 МБ (класс команды к заданиям не применяется), бюджет — 2048 МБ, поэтому третье и четвёртое задание ждут память 60 с и падают с «нет свободной памяти»: лимит обещает больше, чем даёт память. Значение 2 делает отказ мгновенным и понятным, ёмкости не добавляет; два задания по 1 ГБ всё равно занимают бюджет целиком и команды ждут. Если приоритет — обычные команды, честнее 1 задание на ноду (остаётся 1 ГБ на тяжёлую команду). Разбор и варианты — `docs/SANDBOX_CAPACITY.md`, раздел 4.
- [x] **Замер на node-1:** 25.11.2026, 21:35 UTC. Тесты: `server/src/sandbox/command-memory.test.ts`.

Очереди аккаунта у заданий намеренно нет: фоновое задание не должно заставлять обычные команды того же аккаунта ждать своего конца. Тесты: `server/src/sandbox/job-quota.test.ts`.

## Preview

- [ ] **T2. Ускорение установки зависимостей (зеркало реестра + предустановленный слой):** сделано 2026-11-25: замер (`preview/install-metrics.ts`), слой (`preview/starter-layer.ts`), зеркало (`preview/npm-registry.ts`), скрипты `cache:stats` и `layer:build`. Дальше по этапам, после цифр с прода:
  - **Шаг 0 — замер:** смотреть медиану `cached: false` в `npm run cache:stats`. Меньше 10 с — ничего не менять.
  - **Шаг 1 — зеркало:** поднять зеркало реестра на каждой ноде (локальный диск, не Gluster), задать `WEBNESTDEV_NPM_REGISTRY` и разрешить его адрес в egress как прокси. Установка получает только `npm_config_registry`; недоступное зеркало ничего не ломает — код уже откатывается на публичный реестр. Работает для любых версий и для промтов без шаблона.
  - **Шаг 2 — слой:** `WEBNESTDEV_STARTER_KIT_DIR` (набор `package.json` + lock) и `WEBNESTDEV_STARTER_LAYER_DIR`, сборка `npm run layer:build -- --kit <каталог>`. Слой получает только проект, чьи `package.json` и lock совпали байт в байт; остальные идут обычным путём. Маркер кэша заполняется хэшем проекта, поэтому `npm install` не запускается вовсе.
  - **Тарифы:** установка нужна на всех тарифах (сборка статики — «Старт», функции — «Плюс», контейнерный предпросмотр — «Премиум»), поэтому оптимизация тарифно-нейтральна и не расширяет возможности плана. Проверять, что ограничения `entitlements.ts` не обходятся, при любых будущих правках.
  - **Не делать:** общий записываемый `node_modules` или `npm_config_cache` для всех песочниц (подмена пакетов между аккаунтами), симлинк на общий каталог, слой на Gluster, кэш реестра внутри egress-прокси (CONNECT без расшифровки).
  - **Открытый риск:** файлы слоя `0444` — если пакету нужно писать в свой файл в рантайме, проект получит `EACCES`; выключатель `WEBNESTDEV_STARTER_LAYER=0`.
